# D7 — blob-mood totally broken (none of the moods work)

**Lane:** D7 · **Surface:** `/substrates/blob-mood` · **Severity:** blocker · **Verdict:** net-new-wave (augment the D·BLOB band — slot behind W16)

## Symptom (live)

On `/substrates/blob-mood`, clicking any mood pill (idle · happy · curious · sleepy · excited) highlights the button (the `activeMood` ref flips, `bg-primary` paints) but the rendered blob does NOT change — orbit speed, wobble, pulse, iridescence/SSS sheen all stay at the idle look. Every mood reads identical. The buttons are dead.

## Root cause (source-grounded)

This is NOT a demo-wiring bug and NOT a broken import — the chain `button → blobRef.setMood(m) → mood.setMood(m)` is correct and `setMood` is correctly exposed (`GooBlob.vue:160-162,178-185`). The defect is an **architectural priority inversion inside the renderer's frame loop**: explicit `setMood` is clobbered back to `idle` within a single frame by the always-on auto-mood arc.

The exact chain:

1. `setMood(m)` (demo or expose) → `useBlobMood.setMood(m)` (`useBlobMood.ts:139-147`) retargets and arms `transitioning = true`.
2. The renderer's rAF, every non-reduced frame, calls `mood.update({...})` **unconditionally** BEFORE `mood.tick()` (`useMetaballRenderer.ts:366-373`):
   ```js
   if (!reduced) {
       mood.update({
           pointerActive: pointer.active.value,   // false — cursor not over the blob
           clicked: pointer.consumeClick(),       // false
           idleMs: pointer.idleMs(),              // small (< 6000 IDLE_SLEEP_MS)
       });
   }
   mood.tick(stepMs);
   ```
3. `update` (`useBlobMood.ts:154-169`) with no pointer, no click, `idleMs < IDLE_SLEEP_MS` falls through to the `else` branch → `setMood("idle")`. So one frame (~16ms) after any explicit `setMood`, the mood is force-retargeted back to `idle`.

The user's button selection is overwritten before its transition can paint. `activeMood` stays visually highlighted (it's a separate demo ref), so the UI lies — it looks selected but renders nothing. The auto-mood loop (`curious` on hover, `excited` on click, `sleepy` on idle) is the ONLY mood path that survives, because those are the states `update` itself drives — and even hover/click only register when the cursor is physically over the GL canvas, which the mood-pill buttons are not.

`update` was authored (W11.c) as "the single internal caller of `setMood`" (`useBlobMood.ts:151` docstring) — i.e. the design intent was that auto-mood is the ONLY mood driver and the public `setMood` expose is essentially vestigial. The demo (and the README's documented `setMood` expose) assume the opposite: that an explicit `setMood` is authoritative. The two intents are architecturally incompatible at HEAD, and the auto-mood loop wins every frame.

## Why the headless gates missed it

`proof:blob-render` / `proof:substrate-paints-color` assert the blob PAINTS color — it does. No gate asserts that an explicit `setMood("excited")` actually changes the rendered params vs `setMood("idle")` (a mood-DELTA assertion). The π-lane mood fixture exercises auto-mood arcs (hover→curious, click→excited), which DO work, so it stays green. The cardinal lesson exactly: green proof over a visually-static canvas.

## Gestalt fix (idiomatic, no patch)

The clean transposition is to make **explicit mood selection a first-class override layer** over the autonomic arc — the affect model already separates "named mood point" from "auto-driving signal," so the fix is to give `setMood` an **override latch** that suppresses `update`'s auto-driving until the user re-engages live interaction. One principled surface, no flag soup:

- In `useBlobMood`, `setMood(mood, { source })` records whether the retarget came from `update` (autonomic) or from the public expose (manual). A manual `setMood` sets a `manualOverride` latch; `update` **early-returns while the latch holds** (it does not auto-drive over a user-pinned mood). The latch RELEASES on a genuine fresh interaction signal — a click or pointer-over the canvas — so hovering/clicking the live blob still hands control back to the autonomic arc (the demo's "auto-drives from interaction" blurb stays true). This is the same priority shape `update` already uses internally (click > pointer > idle); the manual latch just sits ABOVE it.
- This also fixes the quiescence gate for free: a manually-pinned non-idle mood keeps `isSettled()` honest (the latch is part of the settled predicate), so a pinned `excited` blob keeps animating instead of being silently dragged to idle-then-parked.
- Alternatively/additionally, surface an `autoMood?: boolean` prop on `<GooBlob>` (default `true`) that gates the `mood.update(...)` call in the renderer — a story that wants pure discrete control (the mood showcase) sets `:auto-mood="false"` and drives moods entirely via `setMood`. This is the more demo-honest seam (the showcase IS a discrete-mood demonstration, not an ambient creature) and is the cleaner KISS option if the override-latch interaction-release proves fiddly. Prefer the override-latch as the library-correct default (a `setMood` that silently no-ops is a worse API contract); the prop is a complementary escape hatch, not a substitute.

Either way the demo's `MOODS` pills then drive a VISIBLE param delta, and the README's `setMood` expose stops being a documented lie. No legacy/back-compat concern — `setMood` simply starts honoring its own contract.
