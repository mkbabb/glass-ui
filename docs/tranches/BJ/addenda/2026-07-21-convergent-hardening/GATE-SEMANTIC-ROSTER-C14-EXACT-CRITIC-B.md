## RED-1 — parser flow and native forwarding are not proved as one chain

C14's row at `GATE-SEMANTIC-ROSTER-C14.json:31-276` has two separate proof
halves:

1. parser/binding rules prove that a StringLiteral reaches an approved `cn`,
   optionally an approved `computed`, and a template class binding; and
2. `componentSinkLaw` mounts an approved Reka origin with a unique sentinel and
   proves that some connected native DOM element receives that sentinel.

No exact law requires the **actual overlay token class** to pass through the
approved helper and the exact carrier expression onto the connected native
owner. The sentinel mount can exercise the Reka component directly, bypassing
the carrier's `cn`/computed expression. The source-flow detector, conversely,
models `cn` as transparent solely because its import resolves to
`src/components/_shared/class-names.ts`; it does not execute or constrain the
helper result.

This admits a concrete planted mutation. Keep the exact exported `cn` symbol,
module path, imports, carrier literals, template bindings, Reka origins and
public reach, but make `cn` remove only classes beginning with
`[--overlay-pad-inline:` or `[--overlay-pad-block:`. Every C14 AST/binding case
still passes. A directly supplied ordinary sentinel still reaches connected
native DOM through every exact Reka origin. The current ordinary `cn` test pins
other arbitrary classes but does not pin either overlay writer. Yet neither
published overlay token has a live carrier class at runtime.

The same split permits a carrier-level inertness mutation such as making the
governed tag branch permanently non-rendering while separately mounting the
approved origin. “Executable positive witness” does not say whether the exact
carrier SFC, the grammar parser fixture or the imported Reka component is the
thing executed, so independent implementations can satisfy materially
different contracts.

The origin mount itself is also not reproducibly frozen. There is no per-origin
mapping for required provider/root/portal components, open/force-mount props,
attachment target, native owner selector or ownership assertion. A query for a
unique connected sentinel is insufficient unless the schema ties that element
to the mounted origin rather than an arbitrary harness/auxiliary node.

C15 must compose the proof end-to-end. One sufficient shape is a structured
`carrierExecutionWitnesses` table with, for every current carrier/branch:

- carrier export and source path;
- provider/root/portal harness identities;
- exact open/force-mount/branch props;
- `attachTo` target;
- native owner selector and ownership relation;
- the exact expected overlay writer classes; and
- a mutation that keeps the AST path and origin mount intact while the approved
  helper drops only those writer classes.

Alternatively, freeze a structured per-origin harness table plus an executable
fixture that sends the exact token literals through the approved `cn` and
computed arms before passing the result to the exact component/native sink.
The connected element, not an unrelated harness node, must own that exact
result. Retain wrong-origin, class-drop, dead-source, severed-path and sibling-
call mutations.

C14 honestly removes universal focusability and unlisted-event claims and adds
hostile `data-state`. Its remaining mismatch is at
`GATE-SEMANTIC-ROSTER-C14.json:762-790`.

no “consumer click delivery,” and the mutation says forwarding the listener

A planted static branch can satisfy every assertion while retaining the

```html

```

The root remains a Span with no role, tabindex, `aria-pressed`, `data-state` or
button descendant. A click dispatched **at the root** does not travel downward
to the child listener, so the spy remains zero. A consumer click on the child
does invoke it. This violates both the predicate and named mutation while the
specified detector stays GREEN.

C15 must either narrow the exact promise and mutation to “the static host does
not receive/forward the consumer listener,” or prove the broader boundary by
triggering every component-owned non-button descendant/activation target (or by
an equivalent listener-ownership assertion). Caller slot content must remain
explicitly out of scope; a component-created forwarding descendant must not.
The new hostile `data-state`, attribute assertions and node-reuse law otherwise
pass.
