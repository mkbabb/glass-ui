## Live-owner discovery and descriptor interposition

C17 no longer assumes that a nominal constructor prototype owns live DOM
methods. The setup creates a target-realm element and independently walks its
prototype chain for own `addEventListener` and `removeEventListener`
descriptors. Separate discovery matters: correctness does not depend on the two
methods sharing an owner object. Preserving and restoring the complete original
descriptors also retains configurability, enumerability, writability and exact
function identities instead of merely assigning remembered function values.

The required second fresh element closes the vacuous-ledger seam. Its add must
traverse the patched method and create an active entry; its matching remove must
traverse the other patched method and return that exact element/type entry to
zero before any SUT import. A wrong global/window patch cannot satisfy that
positive-then-zero observation in the current Happy DOM realm.

I reproduced the protocol in a disposable dedicated Vitest configuration. In
the governed environment:

- the live add/remove owner used by a fresh `SPAN` was distinct from both
  `globalThis.EventTarget.prototype` and `window.EventTarget.prototype`;
- the second-element add was observed exactly once and its remove returned the
  count to zero;
- duplicate same-listener/same-capture adds remained one registration;
- a different callback identity and a wrong capture remove left the entry
  active;
- boolean `false` and `{ capture: false }` matched, while `false` and `true`
  remained distinct registrations; and
- teardown restored both original property descriptors exactly.

This also validates the correct DOM key. Passive and other non-capture option
differences do not create a second registration, while target, type, callback
identity and normalized capture do.

## Setup-before-import and clean module graph

The import-order protocol is executable without a product import in setup. My
disposable setup file used the already-created Happy DOM realm, installed and
self-probed the ledger, then published the marker without importing Glass,
Chip, Vue or Vue Test Utils. The test module had no static product import. It
asserted the marker, reset Vitest's module graph, dynamically imported a
method-capturing fixture, then dynamically imported the exact
`@glass/components/chip/Chip.vue` leaf.

The fixture captured the patched live-owner add method at module evaluation;
an exact identity assertion and an actual fixture-mediated add/remove both
proved it. By contrast, invoking the original method captured before setup
installed the patch created a real listener that the ledger did not observe.
That controlled bypass proves the order is consequential rather than
ceremonial: evaluating and retaining the fixture or a mutated Chip registration
helper before the marker would fail the captured-method identity/interposition
check. The dedicated project, product-free early setup, asserted marker,
module reset and dynamic exact-leaf import jointly prevent a previously cached
SUT from receiving formation credit. Removing that isolation/reset boundary is
therefore not behaviorally equivalent to the required protocol.

fresh elements created after reset continued to resolve through the patched
owners, and the dynamically imported Chip mounted through the same
instrumented DOM realm. There is no reset-induced prototype swap or duplicate
Vue instance blocker in this topology.

Vue registers an invoker wrapper rather than the consumer callback itself.

not need to equate that wrapper with the hostile function. Vue replacement or
removal cannot hide an installed invoker: a still-registered wrapper remains an
active structural entry even when its current value returns early.
