# D-FACTOR PASS-1 RESEARCH (raw family returns, machine-extracted)

## FACTOR-C — "behavior composables": ship triggers/dismiss/anchor/press as freely-composable hooks (useHoverTrigger, usePressTrigger, useAnchorPosition, useDismiss) so components collapse to thin ARIA shells and the product space is reached by composition, not props. VERDICT (adversarial, own-family): the maximal form is OVER-ENGINEERING at glass-ui's scale by ~an order of magnitude. But it distills to ONE real, KISS-forward kernel that is exactly the seam FACTOR-A's union overlay root should be built on — a trigger AXIS that drives reka's existing open-model, not a re-forked interaction engine. Two legs of C are already SHIPPED (press-as-composable, dock-keep-open-as-composable); the anchor/dismiss/hover-timer legs must NOT be built because reka already owns them and re-forking violates the no-dual-path law.

### mechanism
The mechanism-distinctness law reframes triggers correctly: hover/click/focus/manual are NOT components and NOT even distinct mechanisms — they are alternate OPEN-STATE SOURCES feeding one floating surface. So the KISS distillation of C is: a single `trigger` axis (hover|click|focus|manual) + a `persist`/pin affordance that resolves to reka's `v-model:open` on ONE overlay shell — never N trigger-components, never a re-implemented pointer/focus timer.

Honest layer map of what "behavior above reka" actually is in this repo:
- Trigger TIMING (hover open/close delay, tooltip delay-duration): 100% reka-owned (HoverCardRoot `open-delay`/`close-delay`, TooltipProvider `delay-duration`). glass-ui NEVER re-implements it — HoverPopover.vue passes `hoverOpenDelay`/`closeDelay` straight through. A `useHoverTrigger` that re-forks pointerenter/leave timers would DUPLICATE reka's Root listeners = a no-dual-path violation.
- ANCHOR positioning: 100% reka(floating-ui)-owned (`side`/`align`/`avoidCollisions`, `--reka-popper-*`, reka's internal `useFloating`). glass-ui owns ZERO positioning code — only CSS reads of `var(--reka-popper-transform-origin)` in .glass-reveal. `useAnchorPosition` would re-fork floating-ui. Do not build.
- DISMISS (Escape + click-outside): reka Root-owned. glass-ui adds only two REAL, glass-specific dismiss concerns: the dock click-away + portal allowlist (`data-glass-dock-portal`), and `useTouchGate` (the coarse-pointer tap-to-activate + outside-tap-deactivate registry). Those are the only dismiss behaviors worth a composable, and one already is one.
- PRESS: already a composable — `useSpringPress`/`useLiquidPress` (interruptible velocity-continuous spring press + reciprocal squish), bound on Button + Card. FACTOR-C's `usePressTrigger` leg is DONE and validated; no new work.
- KEEP-OPEN sink: the genuine glass-ui behavior algebra above reka — `useOptionalDockContext().keepOpen()/release()/held` (dockContext.ts). Cross-cuts HoverPopover, Slider, Popover. This is the one true "behavior reka does not provide" and it's already shipped as context injection.

So C is NOT "expose reka's hooks better" (reka has no interaction hooks to expose) and NOT a net-new 4-hook algebra. It is: keep the props/slot surface consumers actually use, add the trigger AXIS + persist as the ONLY new seam, and treat useTouchGate + dock-keep-open as the documented "behavior floor" the union root composes.

### degrade_story
The kernel degrades cleanly because it drives reka, which already carries the degrade paths:
- No-JS / SSR: reka Roots render inert triggers; the trigger-axis prop is a pure open-state mux with no server cost. HoverPopover already ships the native `interestfor`+popover=hint progressive-enhancement opt-in (AQ.W6) that degrades straight to the reka HoverCard when unsupported — the trigger axis inherits that ladder.
- Coarse pointer (the mandated story): `hover` triggers have no hover event on touch, so the axis MUST compose useTouchGate (already a composable) to give a tap-to-open fallback — this is the concrete leg where a C composable earns its keep, because a bare props HoverPopover is invisible on touch. The union root wires it once for all hover triggers.
- Reduced motion: the surface entrance is .glass-reveal, whose PRM carve zeroes scale/translate/filter and keeps the fade — unchanged by the trigger source.
- No anchor/collision support: reka/floating-ui provides the fallback; glass-ui adds nothing to degrade.
- The dock keep-open sink is a no-op outside a <GlassDock> (inject fallbacks null), so the behavior floor composes safely on any surface.

### a11y
WCAG 1.4.13 (dismissible/hoverable/persistent) for hover-revealed content is mostly reka-provided and the trigger axis must PRESERVE it, not re-implement: reka HoverCard's close-delay bridge gives hoverable + persistent; Escape-dismiss lives on the Roots. The axis's job is to keep the ARIA pattern correct per trigger — hover→Tooltip stays aria-describedby naming machinery (the guard floor: Tooltip is NOT a content surface, it stays distinct); click→Popover (labelled dialog-ish surface); focus→ the non-pointer-gated discovery path. The one live consumer PROVES the keyboard need: atlas EasterEgg.vue hand-wires @focus/@blur + Enter/Space pin + aria-pressed on top of HoverPopover because the props API had no focus-trigger or persist. A `trigger:"focus"|"both"` + `persist` axis deletes that hand-rolled a11y wiring and makes keyboard-reachability a library guarantee instead of a per-consumer reimplementation (an accessibility WIN, not just ergonomics). Menus keep roving-focus/typeahead on their own reka roots (distinct mechanism — not folded). Coarse-pointer WCAG 2.5.5 hit-area stays each trigger child's contract (IconTooltip's as-child forwarding precedent).

### perf_model
The kernel is net-neutral-to-negative-cost avoidance: it wraps the SAME reka Roots, so it adds ~0 runtime listeners over today (a computed open-state mux + the already-present useTouchGate registry). Bundle: a few hundred bytes for the axis; useSpringPress/useTouchGate/dock-context are already in the tree. The MAXIMAL C (a Floating-UI-style useHover/useFocus/useDismiss/useInteractions algebra) is the perf LOSER — it would run a parallel pointer/focus/outside-click listener set ALONGSIDE reka's Root-baked ones (double the interaction cost) or require abandoning reka Roots entirely (re-forking floating-ui + focus-trap + scroll-lock = kilobytes and a second correctness surface). No GL/canvas/paint cost either way. The performance argument alone rules out the maximal form: you cannot beat reka's cost by duplicating it.

### prior_art
The maximal FACTOR-C is a real, named architecture: Floating-UI React's interaction hooks — useHover, useFocus, useClick, useDismiss, useRole, composed by useInteractions onto a useFloating() context — the canonical "behaviors as free-composable hooks, component is a shell" model. Radix Primitives (which reka-ui ports to Vue) DELIBERATELY rejected that model for compound-components-with-context: interactions live INSIDE HoverCardRoot/PopoverRoot/TooltipRoot, reachable only by instantiating the Root. Confirmed empirically: reka-ui@2.9.7's entire public composable surface is utility-only — useBodyScrollLock, useDateFormatter, useDirection, useFilter, useForwardProps(Emits), useForwardExpose, useId, useLocale, useStateMachine, FocusScope, and the inject*RootContext family — plus an INTERNAL useFloating; there is NO useHover/useFocus/useDismiss/useInteractions. So FACTOR-C in glass-ui is NOT "expose reka's hooks better" (they don't exist) — it is "build the interaction algebra reka chose not to." The middle-ground precedent is Headless UI / Ariakit (behavior-rich but still component-shaped). The lesson: on the Radix/reka substrate the free-composition dream requires abandoning the substrate; the pragmatic win is a trigger AXIS over reka's Root-baked behavior.

## FAMILY FACTOR-A — "one anchored-overlay root." ONE sealed primitive, public name **`Popover`** (the survivor noun; the compound `PopoverTrigger`/`PopoverContent` and the whole `HoverCard*` + `HoverPopover` families FOLD into it). Three orthogonal axes exactly as chartered: `trigger` ∈ {click | hover | context} × `role` (content-role) ∈ {dialog | card} × `surface` ∈ {glass | veil | opaque | clear} (the already-shipped `_shared/useSurfaceAxis.ts` axis, reused verbatim). Slot contract: `#trigger` (as-child) + default/`#content`. ONE `open` v-model, ONE `keepDockOpen` dock-suppression watcher, ONE surface resolver — regardless of which reka root paints underneath. **Tooltip + IconTooltip SURVIVE distinct** (proven below): they own aria-describedby naming machinery + the shared TooltipProvider delay-grouping + role="tooltip" + a VisuallyHidden SR-mirror + a text-only-content contract that no card/dialog survivor expresses — a describedby relationship, not a content surface. The union does NOT absorb them; it DELEGATES "just a text label on hover" to them (so the union drops HoverPopover's `content:string` shortcut as a de-dup of that synonym).

### mechanism
The reka substrate ships THREE genuinely-distinct roots (verified from node_modules/reka-ui/dist source, not docs):

• **PopoverRoot** (Popover/PopoverRoot.js) — props {defaultOpen, open, modal}; NO timers. Trigger (PopoverTrigger.js) defaults `as="button"`, emits `type=button` + `aria-haspopup="dialog"` + `aria-expanded` + `aria-controls`, opens on `onClick`. Content (PopoverContentImpl.js) = `role="dialog"` + `aria-labelledby`, wrapped in **FocusScope (trapFocus iff modal)** + DismissableLayer; non-modal still MOVES focus into content on open (onOpenAutoFocus not prevented) but does not trap. → CLICK, focus moves in, modal-capable.

• **HoverCardRoot** (HoverCard/HoverCardRoot.js) — props {defaultOpen, open, openDelay=700, closeDelay=300} + the full pointer-in-transit / grace-area timer machinery. Trigger (HoverCardTrigger.js) defaults `as="a"`, carries NO aria-expanded/haspopup/controls (data-state only), opens on `pointerenter`/`focus` via **`excludeTouch(onOpen)`**, closes on leave/blur, `data-grace-area-trigger` safe-polygon. Content (HoverCardContentImpl.js) = **DismissableLayer ONLY, NO FocusScope, NO role** — focus never moves in, content is supplementary/hoverable. → HOVER+FOCUS, focus stays put, no touch.

• **TooltipRoot** (Tooltip/TooltipRoot.js) — shared TooltipProvider delay-grouping (skipDelay), {disableHoverableContent, ignoreNonKeyboardFocus}. Trigger gets `aria-describedby`; content = `role="tooltip"` + VisuallyHidden SR mirror. → the naming-machinery survivor.

**The load-bearing honesty finding:** trigger and focus-model are COUPLED by the substrate. A hover-open surface CANNOT trap focus (focus is never moved into it, and hover-leave/blur closes it — trapping would strand keyboard users); a click-open dialog MAY. So `trigger` must SWITCH the reka root, and `role` must gate the focus behaviour. The union is a `v-if` root-selector — the EXACT pattern HoverPopover.vue already runs today (its native-`interestfor` vs reka-`HoverCard` two-branch, lines 187/207). Adding a PopoverRoot branch is the same mechanism, one more arm.

**Root-selection table (what the union resolves):**
 trigger=click → PopoverRoot (role=dialog default; role=card ⇒ `@open-auto-focus.prevent` so a click-reveal card doesn't yank focus)
 trigger=hover (fine pointer) → HoverCardRoot (role=card default; role=dialog is REFUSED — dev-warn + fall to card, the WCAG trap)
 trigger=hover (coarse pointer) → PopoverRoot non-modal + `@open-auto-focus.prevent`, tap-toggle open (the touch fix reka has none of — see degrade_story)
 trigger=context → PopoverRoot + PopoverAnchor virtual reference at pointer coords, open on `contextmenu` (a right-click rich PANEL, NOT a menu — a right-click MENU stays the distinct ContextMenu/menus root per the roving-focus floor)

The three per-axis prop cohorts are honestly scoped: {modal} applies only to the Popover(click/context) root; {openDelay, closeDelay} (folding HoverPopover's `hoverOpenDelay`→`openDelay`, `closeDelay`) only to the HoverCard(hover) root; {open, side, align, sideOffset, surface, keepDockOpen, class} are shared (both roots ride reka's PopperRoot for side/align, so collision-avoidance is identical). Inert props on the non-selected root are simply not forwarded.

### degrade_story
• **Touch / coarse pointer (the critical one reka has no answer for):** reka HoverCardTrigger wraps open in `excludeTouch()` — a hover surface NEVER opens on touch, so hover content is UNREACHABLE on phones (a WCAG + touch-floor violation the current HoverPopover/HoverCard silently ship). The union closes it: on `matchMedia('(pointer: coarse)')` it renders trigger=hover as a NON-modal PopoverRoot with `@open-auto-focus.prevent` and a tap-toggle (open on tap, dismiss on outside-tap/Escape) — the card content-role is preserved, only the open mechanism switches to the touch-native tap. Fine pointer keeps the HoverCardRoot hover cadence.
• **Keyboard (no pointer):** HoverCardTrigger opens on `focus`, closes on `blur` — so keyboard users reach the trigger's supplementary card. Interactive-critical content is the honest exception: it must be role=dialog + trigger=click (focus moves in, Escape+focus-return), which is why the union REFUSES trigger=hover+role=dialog.
• **JS disabled / SSR:** the trigger renders as its as-child element; no overlay. The union's `native` PE branch (interestfor+popover=hint) gives a pure-CSS hover-open on interest-invoker engines with zero JS — off-Chromium falls straight through to the reka path (HoverPopover already does this; no polyfill dragged in).
• **Reduced motion:** the `.glass-reveal` entrance carries its own PRM carve (glass/reveal.css reduced-motion block) — spring→instant, fade kept; inherited automatically by the union content.
• **prefers-reduced-transparency / -contrast:more:** the surface axis rides `--glass-level` (opaque escape) already; `surface="opaque"`/`clear`-scrim is the explicit floor.

### a11y
WCAG 1.4.13 (content on hover/focus) per trigger, verified against reka mechanism:
• **Dismissible** — Escape closes on BOTH roots (DismissableLayer onEscapeKeyDown present in Popover/HoverCard/Tooltip content impls). MET.
• **Hoverable** — reka HoverCardRoot's grace-area/pointer-in-transit machinery + `isPointerDownOnContentRef` keep the card open while the pointer skims onto content; closeDelay bridges cluster gaps. MET (hover root only; click root is not subject to it).
• **Persistent** — hover root persists until hover-away/blur/Escape (no auto-timeout dismiss); click/context persist until dismissed. MET.

Focus model per role (the honest coupling):
• role=dialog (click/context) → reka FocusScope moves focus in; modal ⇒ trap + focus-return on close; non-modal ⇒ focus in, no trap. aria-haspopup=dialog/aria-expanded/aria-controls on trigger (PopoverTrigger.js). Correct for interactive content.
• role=card (hover, or click-reveal) → NO FocusScope; focus stays on trigger/page. Trigger carries data-state only (no false aria-expanded on an `<a>`). Interactive-critical content in a card is the a11y anti-pattern the union dev-warns on (hover+dialog refused).

Touch: the coarse-pointer tap-fallback above is the a11y-load-bearing addition — without it, trigger=hover is inaccessible on touch.

Tooltip's survival is itself an a11y fact: aria-describedby (a naming relationship on the trigger) + role="tooltip" + VisuallyHidden SR mirror + text-only content is a DISTINCT accessible-name mechanism the card/dialog roles do not provide; folding tooltip into the overlay would lose the describedby wiring. Hence it stays distinct (the FLOOR's default, now proven, not assumed).

### degrade_story
Per-fold degrade posture (coarse-pointer + reduced-motion), since the two biggest folds ride TRIGGER and MOTION.

TRIGGER=hover fold (HoverCard/HoverPopover→Popover trigger=hover): the CRITICAL degrade. On coarse pointers there is no hover — the unified Popover MUST auto-promote trigger=hover to a tap/press trigger under (pointer:coarse), reusing the touch-gate the library already ships (useTouchGate/coarse-pointer thread). Every hover trigger owes: (a) a tap-to-open coarse fallback, (b) WCAG 1.4.13 dismissible (Esc + tap-away), (c) hoverable (pointer can traverse trigger→content without dismiss — HoverCardRoot gives this, PopoverRoot needs the safe-polygon/intent bridge), (d) persistent (no timeout-only dismiss). This is exactly why HoverCardRoot (intent-timed) and PopoverRoot are separate reka roots — the wrapper keeps HoverCardRoot for trigger=hover so 1.4.13 hoverable/persistent are structurally satisfied, and only the CONTENT SFC unifies. Tooltip stays distinct precisely because its content is non-interactive (no hoverable requirement) and it is aria-describedby, not a landing surface.

TRIGGER=context fold (ContextMenu→Menu trigger=context): right-click has no coarse equivalent — the fold must ship a long-press coarse trigger (reka ContextMenuRoot already handles this) OR expose an alternate affordance; keep ContextMenuRoot under trigger=context so the platform long-press stays.

MOTION fold (already landed BH): motion=off degrades every gesture enrichment to its CSS :active/discrete floor; PRM forces full→reduced at the CSS layer regardless of prop. Sheet→Dialog placement and Drawer snap both keep their CSS-transition floor; Drawer's snap seats synchronously under reduce (SpringProgress respectReducedMotion).

Sheet→Dialog placement fold: no behavior degrade — pure paint axis; the slide-in direction is a compositor transform that PRM already carves.

Substrate viz: unchanged — useGpuSubstrate already parks offscreen + one-static-frame under PRM + WCAG-2.2.2 pause; the census does not touch it.

### a11y
The distinctness law IS an a11y law here — most survivors survive on an ARIA-pattern difference, not a paint difference.

REKA-ROOT-HONESTY (what one wrapper can genuinely unify): a wrapper may unify components that share a reka root (Sheet≡Dialog≡Drawer all DialogRoot → Dialog is one root, side/snap are additive). A wrapper may NOT flatten across DISTINCT roots without switching the rendered root by axis value — so the Popover trigger axis renders PopoverRoot for click/focus and HoverCardRoot for hover (two roots, one content SFC); the Menu trigger axis renders DropdownMenuRoot vs ContextMenuRoot. This keeps each ARIA pattern native (aria-modal, aria-haspopup, role=menu vs listbox, hover-intent timing) — the fold is a FACADE, not a re-implementation.

DISTINCT-ARIA SURVIVORS (do not fold across these — the LAW): Tooltip (aria-describedby, non-interactive) ≠ Popover (interactive anchored). Switch (role=switch) ≠ Toggle (button+aria-pressed). ToggleGroup (radiogroup/group, no panel) ≠ SegmentedTabs (tablist+panel). Menu (roving-focus+typeahead, role=menu) ≠ Select/Combobox (listbox). Section (landmark) ≠ Card (plate).

FLOORS carried: WCAG 1.4.13 (dismissible/hoverable/persistent) is the acceptance gate for the trigger=hover fold — see degrade_story. WCAG 2.5.5 44px touch floor already threaded on menu rows (menuItemVariants min-block-size) + dock controls; the chip fold (ToggleChip→SelectableChip) must preserve SelectableChip's focus-ring + aria-pressed (ToggleChip is a bare CVA today). StatusDot role=img only-when-labeled + SortableHandle role=button are intrinsic-primitive contracts to preserve across any dot fold.

RISK a11y: folding ConfirmDialog onto a Dialog preset must keep its focus-return + the confirm/cancel button labeling; folding IconTooltip onto Tooltip must keep the icon trigger focusable (icon buttons need accessible names).

### risks
- REKA-ROOT SWITCHING under an axis (Popover trigger=hover→HoverCardRoot, Menu trigger=context→ContextMenuRoot) is the load-bearing assumption of the biggest folds — it must be prototyped: a single wrapper conditionally rendering two reka roots while sharing ONE content SFC + ONE surface/side axis. If reka's HoverCardRoot and PopoverRoot content-slot contracts (anchor/collision/portal props) diverge enough, the 'one content SFC' claim breaks and the fold degrades to a shared-CSS-only fold (two thin components, one recipe). CONFIDENCE-GATING.
- WCAG 1.4.13 hoverable/persistent is only free if trigger=hover keeps HoverCardRoot; if a future 'simplification' routes hover through PopoverRoot to save a root, it silently loses hover-intent + safe-traversal — a regression the gate must forbid (a born-RED proof that trigger=hover renders HoverCardRoot).
- Coarse-pointer has NO hover/right-click — trigger=hover and trigger=context MUST auto-promote to tap/long-press or the fold ships a dead affordance on mobile. Every hover/context trigger owes a coarse story (charter FLOOR).
- SYNONYM collisions are prop-NAME clean-breaks (type→tone, axis/direction→orientation, side/position→placement, register→size, ToggleChip.variant→shape). Per the no-backwards-compat law these are hard renames across every consumer call site + the demo storybook — mechanical but wide; the api/ discovery layer + MIGRATION.md must move in lockstep.
- SelectTrigger.size{sm,default,display,audacious} is a TWO-CONCEPT axis (height AND font-emphasis) — splitting it risks the value.js trigger/items font-desync the code comments already fought (BA-VJS-4). Must split into size(height) + a named emphasis axis writing --dropdown-text, not just rename.
- Button reaches --glass-level:0 from BOTH variant=solid AND surface=opaque — a genuine two-axes-one-endpoint redundancy; deciding which axis owns 'opaque' is a real design call (surface should own it; variant=solid retires) that touches the glass-cohesion allowlist gate.
- BorderProgress/IconChip/ConfirmDialog/HeaderRibbon/LabeledField-wrappers are FOLD-CANDIDATES not settled — each needs the mechanism-distinctness verdict adjudicated (is masked-conic-border a distinct paint mechanism? is glyph-ratio-floor enough to keep IconChip?). Do not auto-fold; run them through the law individually.
- Viz suite is NOT a fold despite sharing the substrate axis-set — a naive 'one <Viz field=> component' would erase the per-viz config-surface + story identity + the consumer-evidence bar; the substrate is already the correct single-source layer. Resist over-distillation there.
