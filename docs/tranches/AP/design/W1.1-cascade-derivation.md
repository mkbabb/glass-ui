# AP.W1.1 — cascade-derivation design (T1 + T2)

The design slice that binds W2. It resolves the one brittleness window AP declared — the
Tailwind v4 `@theme` alpha-composition mechanism (T1) — and fixes the tier/four-state
recipe shapes (T2) so W2 implements against a settled target. No source is touched here.

Every claim is line-anchored to HEAD. The W2 hard gate (`proof:theme` byte-clean + the
~7-12 KiB reclaim + the preserved alpha form) reads its merge scope from this doc.

---

## T1 — `@theme` is the single token source

### The investigation (the brittleness window AP declared)

**The mechanism.** In Tailwind v4 the `@theme` block is the token-declaration primitive.
A `@theme` variable does two things at once: it emits a `:root` CSS custom property (so
`var(--color-border)` resolves at runtime, overridable by a consumer at `:root`/`.dark`)
AND it registers a utility namespace (so `--color-*` generates `bg-*`/`text-*`/`border-*`,
`--radius-*` generates `rounded-*`, `--shadow-*` generates `shadow-*`, etc.). The two-layer
split in the cascade today exists because the codebase grew `tokens.css` first (the
shadcn-vue `:root` convention) and bolted `@theme` on top as a parallel namespaced alias
layer that `var()`-bridges straight back. `theme.css` carries **198 such bridge lines** of
218 total `@theme` declarations (`grep -cE ':\s*var\(--' theme.css` → 198; the other 20 are
the §4 radius literals + the §opacity literals + the §animation composites). Each bridge
is a pure indirection hop — `bg-success` resolves `--color-success` → `--success` →
`hsl(142 71% 45%)`, one hop longer than necessary, shipped in every consumer's gzip.

**The alpha-form correction — investigated, NOT assumed.** The AP brief and CLAUDE.md
describe a raw HSL-channel form (`--primary: 222.2 47.4% 11.2%` consumed as
`hsl(var(--primary) / alpha)`). **That form is not present at HEAD.** The investigation
finds:

- Every color token holds a COMPLETE `hsl(...)` color or an alias to one, not raw
  channels: `--primary: hsl(24 10% 10%)` (`tokens.css:348`), `--foreground: hsl(24 10% 10%)`
  (`tokens.css:321`), `--success: hsl(142 71% 45%)` (`tokens.css:422`),
  `--border: var(--neutral-4)` → `--neutral-4: hsl(48 7% 70%)` (`tokens.css:345`, `:308`),
  `--destructive: hsl(0 72% 50%)` (`tokens.css:350`), `--ring: hsl(24 10% 10%)`
  (`tokens.css:352`).
- ZERO sites consume any token as `hsl(var(--x) / alpha)` (verified:
  `grep -rnE 'hsl\(var\(--[a-z-]+\)\s*/' src/styles/ src/components/` → no matches; and
  `grep -rnE 'hsl\(var\(--(primary|foreground|border|...)\)'` → no matches).
- Alpha composition is done with `color-mix`, not channel-splicing: the `--glass-bg-*`
  recipes are `color-mix(in srgb, var(--card) calc(var(--glass-opacity-*) * 100%),
  transparent)` (`tokens.css:583-587`); the shadow stack is
  `color-mix(in srgb, var(--shadow-color) N%, transparent)` over
  `--shadow-color: var(--foreground)` (`tokens.css:354`, `:454-472`); `.glass-btn:hover`
  reads `color-mix(in srgb, var(--background) 85%, transparent)` (`glass.css:133`).

**Consequence for the merge.** The "preserve the raw HSL-channel alpha form" mandate
re-reads as: **preserve the complete-`hsl()` token values and the `color-mix` alpha recipes
exactly as the alpha-composition mechanism in use** — there is no channels-form to break.
The W2 hard gate's "preserved alpha form" clause is satisfied by leaving every
`color-mix(...)` recipe and every complete `hsl(...)` value byte-identical; the merge moves
only the NAMESPACE layer, never re-expresses a color value. CLAUDE.md's
`--primary: 222.2 47.4% 11.2%` line is stale prose (a W4 hygiene item, not a W2 concern).

**The load-bearing constraint that SHAPES the merge — the self-reference trap.**
`proof-theme-style.mjs` carries a `selfReferences` check (`scripts/proof-theme-style.mjs`,
the `^(--[a-z0-9-]+):\s*var\(\1\)` line-scan) that FAILS the build if any `@theme` line is
`--x: var(--x)`. This is the exact reason the §0 shadow block and the §4 radius literals
exist today: the bridge form (`--color-border: var(--border)`) needs a DIFFERENT source
name than the namespaced one, so `tokens.css` carries `--border` and the two typography
sub-families carry non-Tailwind shadow names (`--type-leading-*`, `--font-stack-*`,
`tokens.css:22-45`) that exist ONLY to feed `@theme` without self-reference. **When `@theme`
becomes primary, the source name and the namespaced name COLLAPSE into one — the value
lives directly at `--color-border` inside `@theme`, the `--border` mirror retires, and the
self-reference can no longer arise because there is no second name.** This is what makes the
merge SAFE rather than tripping the gate.

#### Thin deliberate aliases (kept where a non-namespaced consumer reads the raw name)

A handful of sites consume the UN-namespaced name directly: scoped SFC CSS reads
`var(--foreground)`, `glass.css` reads `var(--glass-bg-resting)`/`var(--muted-foreground)`/
`var(--surface-tint-*)`. Two options per name:

1. The consumer reads the `@theme`-published name (`var(--color-foreground)`), OR
2. tokens.css keeps a thin ONE-LINE alias (`--foreground: var(--color-foreground)`) — the
   inverse of today's bridge, deliberate and singular, not a 198-line mirror.

**W2 decision:** prefer (1) where the consumer is library-internal CSS we own (rewrite the
`var(--x)` reads to `var(--color-x)` in `glass.css`/`dock.css`/scoped SFCs as the merge
lands); keep (2) ONLY for the documented consumer-override names that are part of the public
contract (`--glass-opacity-*`, `--foreground` if a consumer overrides it at `:root`). The
override surface is the constraint, not the namespace — keep the consumer-facing names,
retire the internal mirror. This keeps the alias count in the single digits, not 198.

### Representative before/after — one DERIVES cluster, one STAYS-RAW cluster

**DERIVES — `--border` (+ `--success`):**

```css
/* BEFORE — two files, lockstep */
/* tokens.css:345 */   --border:  var(--neutral-4);
/* tokens.css:422 */   --success: hsl(142 71% 45%);
/* theme.css:57  */    --color-border:  var(--border);
/* theme.css:165 */    --color-success: var(--success);

/* AFTER — one source in @theme; the tokens.css raw name + the bridge both retire */
/* theme.css @theme */ --color-border:  var(--neutral-4);   /* palette primitive stays */
/* theme.css @theme */ --color-success: hsl(142 71% 45%);   /* value moves here verbatim */
/* .dark override re-points --color-border / --color-success directly */
```

The value is byte-identical (`hsl(142 71% 45%)` unchanged — the alpha-form-preservation
clause is satisfied trivially). `bg-success` still resolves `--color-success`; `proof:theme`
asserts `bg-gold → background-color: var(--color-gold)` (`scripts/proof-theme-style.mjs`
cssAssertions), so the `--color-*` name MUST survive — and it does, now as the SINGLE source.

**STAYS RAW — `--glass-bg-resting`:**

```css
/* tokens.css:585 — UNCHANGED by the merge */
--glass-bg-resting: color-mix(in srgb, var(--card) calc(var(--glass-opacity-resting) * 100%), transparent);
```

No utility namespace, a runtime color-mix composition over the consumer-overridable
`--glass-opacity-resting` name. It is not a bridge; it stays in tokens.css verbatim. If the
merge rewrites `var(--card)` here, it rewrites to `var(--color-card)` (option 1) — but the
recipe SHAPE and the alpha math are untouched.

### What retires, what the gate proves

- **Retires:** the 198 `theme.css` bridge `var()` lines; the `tokens.css §0` shadow block
  (`:22-45`); the `theme.css:209-216` §4 radius literal-dup; the `tokens.css:320-352` /
  `:1160-1189` raw core-color mirror (folded into `@theme` `--color-*`).
- **Stays:** the `--glass-bg-*` recipes, the `--glass-opacity-*`/`--glass-blur-*` override
  names, the spring `linear()` curves, the `@property` registrations, the `--neutral-N`
  palette, the `--shadow-color` stack, the typography runtime tokens in typography.css.
- **Gate:** `proof:theme` byte-clean — its probeClasses (`bg-gold`, `rounded-card`,
  `shadow-card`, `z-dock`, `animate-dock-in`, …) and cssAssertions (`bg-gold →
  var(--color-gold)`, `rounded-card → var(--radius-card)`, `z-dock → var(--z-index-dock)`)
  all still resolve because the `@theme` namespaced names survive as the single source. The
  `selfReferences` scan can no longer trip — collapsing the two names removes the second
  name. The `forbiddenThemeNamespaces`/`forbiddenLocalThemeEntries` guards are unaffected.
- **Reclaim:** ~3-5 KiB gzip (the 198 bridge declarations + the §4 dup + the §0 block),
  against the 74928-gzip resolved draw, plus the elimination of the two-files-must-agree
  drift class.

## T2 — the tier ladder + the dock-control four-state derive from recipes

### T2a — the five glass tiers collapse to ONE token-suffix recipe

**The duplication.** `glass.css:20-70` declares five `.glass-{wash,quiet,resting,floating,
overlay}` blocks. Each is the IDENTICAL recipe varying only the `{tier}` suffix in the
token name (`background: var(--glass-bg-{tier})`, `backdrop-filter: var(--glass-blur-{tier})`,
`border: 1px solid var(--glass-border-{tier})`, `box-shadow: …var(--glass-shadow-{tier})`).
Then the grain `::after` re-lists all five selectors (`glass.css:73-77`), the dark variant
re-lists all five (`:90-94`), and the `@supports` fallback re-lists all five
(`:258-272`) — five tiers × four selector groups, ~20 hand-maintained spellings.

**Wrinkle the recipe MUST preserve:** the `box-shadow` arm is NOT uniform. `quiet`/`resting`/
`floating` PREPEND a non-inset under-shadow rung (`--glass-under-shadow-quiet`/`-default`/
`-vivid`, `glass.css:45`/`:53`/`:61`); `wash` (`:25`) and `overlay` (`:69`) carry the bare
`--glass-shadow-{tier}` (the AL-W10 SLIM retention — wash is sub-perceptual, overlay is
modal-heavy). The `@supports` fallback backgrounds are per-tier literal percentages
(`80%/88%/94%/98%` + `var(--card)`, `glass.css:259-271`), NOT a token suffix.

**The recipe shape (the fixed W2 target).** Express the surface ladder as a Tailwind v4
functional `@utility` keyed on the tier suffix, with a per-tier shadow knob so the
under-shadow wrinkle stays data:

```css
@utility glass-* {
    position: relative;
    background: var(--glass-bg-* );
    backdrop-filter: var(--glass-blur-* );
    border: 1px solid var(--glass-border-* );
    /* per-tier box-shadow resolves through a tier-keyed knob with a bare fallback,
       so wash/overlay (no under-shadow) and quiet/resting/floating (prepended
       under-shadow) both express from one recipe */
    box-shadow: var(--glass-shadow-composed-*, var(--glass-shadow-* ));
}
```

The under-shadow composition moves to DATA in tokens.css — define
`--glass-shadow-composed-quiet: var(--glass-under-shadow-quiet), var(--glass-shadow-quiet)`
(and `-resting`/`-floating`); `wash`/`overlay` define NO `--glass-shadow-composed-*` knob, so
the `@utility` falls through to the bare `var(--glass-shadow-{tier})`. Adding a sixth tier
becomes a one-line token-cluster add, not a 4-site CSS edit.

The three re-listed selector groups attach to ONE shared group via an attribute/`:where()`
match on the `glass-` class prefix:

```css
/* grain ::after — ONE rule instead of five selectors (glass.css:73-88).
   MUST enumerate the five TIERS explicitly, NOT [class*="glass-"]: the
   prefix-match over-reaches the non-tier shorthands (.glass-card / .glass-btn /
   .glass-pill, glass.css:103-222; .glass-dock in dock.css) which carry NO grain
   today — a [class*] form would newly paint grain onto them, a visual
   regression. The shared group is the exact five-tier set. */
:where(.glass-wash, .glass-quiet, .glass-resting, .glass-floating, .glass-overlay)::after {
    content: ''; position: absolute; inset: 0; …
}
.dark :where(.glass-wash, .glass-quiet, .glass-resting, .glass-floating, .glass-overlay)::after {
    mix-blend-mode: soft-light;   /* glass.css:90-94 */
}
```

The `@supports` fallback (`glass.css:257-272`) stays per-tier (its `color-mix`
percentages are per-tier literals, not a suffix) — but it is the ONLY remaining five-spelling
and it is justified data, not a mechanical copy. Disposition: keep the `@supports` block as
five explicit lines (the percentages are genuine per-tier data); collapse the grain `::after`
+ dark arms to the shared `:where()` group.

**Caveat (the sharp edge AP flagged).** A functional `@utility glass-*` with a token-suffix
match composes correctly only if the `@supports`/dark arms stay outside it (they do, above).
If Tailwind v4's `glass-*` functional-utility matching proves brittle against the existing
`.glass-card`/`.glass-btn`/`.glass-pill` shorthands (which are NOT tier members), the
fallback recipe is a single var-driven rule over an explicit five-selector `:is()` group
with the tier read from a `--glass-tier` custom property set per class — but the `@utility`
form is the primary target. W2 proves the chosen form with `proof:theme` +
`proof:phantom-classes` + the visual π re-probe.

### T2b — the dock-control four-state collapses to ONE shared `dock-control` base

**What AO already hoisted.** `dock.css:32-46` already lifts the `:focus-visible` ring and
the `:disabled` paint to two shared comma-group rules over the four dock controls (the
`:where()` motion-var group is at `:9-23`). **T2 owns the THREE arms AO left per-selector:**
`:hover:not(:disabled)`, `:active:not(:disabled)`, and the active-state
`:is(.is-active, .active, [aria-…])` arm.

**The repetition (the three remaining arms).**

| Control | base | :hover:not(:disabled) | :active:not(:disabled) | active-state `:is(…)` |
|---|---|---|---|---|
| `.dock-icon-button` | `dock.css:628` | `:656` | `:662` | `:688` |
| `.dock-tab-button` | `:762` | `:801` | `:806` | `:817` |
| `.dock-select-trigger` / `.dock-dropdown-trigger` | `:918` | `:943` | `:953` | `:976` |
| `.dark-mode-toggle-button` | `:703` | `:725` (hover+focus) | — | — |

The hover paint differs per control (`--muted` for icon/select/dropdown at `:657`/`:945`;
`--surface-tint-8` for tab at `:802`; `--surface-tint-10` for dark-mode at `:727`) and the
active paint differs (icon reads the `--dock-active-*` cohort `:689-693`; tab/select read
`--surface-tint-10`/`--muted`). So the SELECTORS repeat verbatim while the VALUES are
per-skin — exactly the menuItemVariants archetype (one contract, per-skin tokens).

**The recipe shape — `dock-control` base + per-skin token cohort.** Following the
`_shared/menuItemVariants` precedent (`src/components/ui/_shared/menuItemVariants.ts:29-46` —
one CVA promotes the four-state contract above reka-ui's base, per-instance variants paint
the differences), define ONE shared selector group that owns the four-state SELECTOR
structure once and reads a per-control token cohort for the paint:

```css
/* ONE shared base — the four-state selector structure, owned once */
.dock-control:hover:not(:disabled)  { background: var(--dock-control-hover-bg);
                                       color: var(--dock-control-hover-color, var(--foreground));
                                       transform: scale(var(--dock-control-hover-scale, 1)); }
.dock-control:active:not(:disabled) { transform: scale(var(--dock-control-active-scale, var(--scale-press-dock))); }
.dock-control:is(.is-active, .active, [aria-expanded="true"], [aria-pressed="true"], [aria-current="page"]) {
    background: var(--dock-control-on-bg);
    color: var(--dock-control-on-color, var(--foreground));
    transform: scale(var(--dock-control-on-scale, 1));
}
```

Each control then sets ONLY its per-skin cohort in its base block + adds `dock-control` to
its selector list (or the SFC adds the `dock-control` class):

```css
.dock-icon-button   { --dock-control-hover-bg: var(--muted);
                      --dock-control-hover-scale: var(--scale-hover-dock);
                      --dock-control-on-bg: var(--dock-active-bg);
                      --dock-control-on-color: var(--dock-active-color);
                      --dock-control-on-scale: var(--dock-active-scale); /* + border/shadow stay icon-local */ }
.dock-tab-button    { --dock-control-hover-bg: var(--surface-tint-8);
                      --dock-control-on-bg: var(--surface-tint-10); }
.dock-select-trigger,
.dock-dropdown-trigger { --dock-control-hover-bg: var(--muted);
                         --dock-control-on-bg: var(--muted); }
```

**Per-rung notes (what stays control-local, not in the shared base):**

- `.dock-icon-button`'s active arm also sets `border` + `box-shadow` from the
  `--dock-active-{border,shadow}` cohort (`dock.css:692-693`) — keep these as icon-local
  extensions on the icon base; the shared `:is(…)` arm owns only bg/color/transform.
- `.dock-dropdown-trigger` has a hover `transform: scale(var(--scale-hover-dock))` that
  `.dock-select-trigger` does NOT (`dock.css:949-951`) — express via
  `--dock-control-hover-scale` set on dropdown only (select leaves it at the `1` default).
- `.dock-tab-button[data-tier="primary"]` (`dock.css:841+`) is the audacious disco extension
  composing `btn-audacious` — OUT of scope for the four-state base; it stays as the documented
  dock-local primary-tier extension.
- `.dark-mode-toggle-button` carries a combined `:hover, :focus` arm (`dock.css:725`) and no
  `:active` arm — it MAY compose `dock-control` for the hover paint, but its sizing/aspect
  block (`:703-716`) is bespoke; W2 decision: include it in the shared `dock-control` hover/
  active group (it benefits) but leave its sizing block untouched.
- `.glass-btn` (`glass.css:115-159`) composes the SAME four-state contract with DIFFERENT
  paint (`color-mix` hover bg at `:133`, `--surface-tint-10` active at `:154`). It SHOULD
  read the shared `dock-control` base too — set its per-skin cohort and add the class. But
  `.glass-btn` lives in glass.css and `dock-control` in dock.css; W2 decision: lift the
  shared `dock-control` four-state base to a location BOTH files reach — author it in
  `dock.css` (the dock-control home) and have `.glass-btn` opt in via the shared class, OR
  keep `.glass-btn` reading the same per-skin-cohort pattern locally. Prefer the former
  (one base, two composers) to mirror the menuItemVariants single-source intent; if the
  cross-file `@layer components` ordering makes the cohort cascade fragile, keep `.glass-btn`
  local with the same cohort variable NAMES so a future lift is mechanical. **W2 picks the
  shared-base form and proves cascade order with the visual π re-probe.**

**The precedent.** `menuItemVariants` (`_shared/menuItemVariants.ts`) already proves the
shape: one canonical four-state contract (`hover`/`focus`/`data-highlighted`/`data-disabled`,
`:36-45`), per-instance variants for the differences (`indicator`/`density`, `:53-63`). T2b
extends the same one-contract-many-skins discipline to the dock-control CSS family — the
CSS-class analogue (a shared selector base + per-skin token cohort) rather than a CVA,
because these are CSS-class primitives, not Vue-bound components.

**Reclaim:** ~4-7 KiB gzip — dock.css is the 43 KB-source / 10.2 KiB-gzip cascade outlier
where the four-state mass lives; collapsing three arms × five controls to one shared arm
each is the bulk. Adding a control skin becomes a one-cohort-block data edit.
