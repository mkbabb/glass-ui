## Part A — R0G-7: the `/motion` SCC-carve map

### A.0 — The overturned premise

`src/motion.ts:15-27` reasons that separating the keyframes-touching leaves from
the keyframes-adjacent leaves "would be a fictitious distinction" because "the
bundler walks the sub-tree's `export *` chain as one SCC anyway." **That reasoning
is OVERTURNED by the consumer measurement.** speedtest measured `@mkbabb/keyframes.js`
(~125 KB) on every route's eager/entry graph through a path that touches ZERO
keyframes — `App.vue → useAuroraPolicy → glass-ui/motion (only useIntersectionPause)
→ keyframes` (OMEGA §2 R0G-7; EPSILON §2.1.1-3). The "one SCC anyway" claim is
the load-bearing-wrong premise: it is true ONLY because today's `/motion` barrel
(`src/composables/motion/index.ts:6-18`) `export *`-rolls all twelve leaves as one
module, so a cheap import statically reaches the keyframes-bearing leaves' module-eval
`import { … } from "@mkbabb/keyframes.js"`. The SCC is a property of the BARREL, not
of the leaves — the leaves themselves split cleanly (§A.1). AP.W3 breaks the barrel.

The asymmetry note at `src/motion.ts:15-27` and the "fictitious distinction" sentence
RETIRE in W3 — the W3 carve makes the distinction real and measured.

### A.2 — The new keyframes-free subpath: decision = new `/motion-core` subpath

**Two options the spec named, and the decision:**

- **Option A — restructure the sub-tree barrels** so the two leaf-sets are separately
  importable *under the existing `/motion` subpath* (e.g. `/motion/core` nested, or
  two barrels under one entry). REJECTED: the SCC trap is exactly that a single
  flat-barrel entry walks both sets; any shape that keeps one `dist/motion.js` entry
  re-exporting both sets leaves the eager graph joined. Nested subpaths under one
  package entry also re-introduce the v0.9.x `composables/dark`-style nested-subpath
  shape that L.W1 RETIRED (CLAUDE.md §Subpath surface — "no nested subpaths"). The
  whole-repo convention is **flat** per-family entries (`vite.library.ts:40-99`).

- **Option B — a NEW flat keyframes-free subpath `@mkbabb/glass-ui/motion-core`,**
  a sibling entry to `/motion`, each a distinct `dist/*.js` chunk. **CHOSEN.**

**Justification against the L.W1 Lane C precedent.** L.W1 Lane C closed the vueuse
SCC trap by carving the vueuse-bearing surface into its OWN flat sibling subpaths
(`/dark`, `/keyboard`, `/carousel`) — each a separate `src/<flat>.ts` entry in
`vite.library.ts:48-50`, a separate `dist/*.js` chunk, a separate `exports` +
`typesVersions` pair. The keyframes carve is the exact same family (`src/motion.ts:8-13`
already says so). The Lane C move was: heavy-peer-FREE stays reachable on the root
barrel; heavy-peer-BEARING moves to a flat sibling subpath. AP.W3 applies the
mirror-image of the SAME shape one level down: within the already-carved `/motion`
family, the keyframes-BEARING leaves stay on `/motion` (the heavy path, already a
subpath off the root) and the keyframes-FREE leaves carve out to a new flat sibling
`/motion-core`. Flat-sibling-per-heavy-peer-boundary is the canonical L.W1 shape; a
nested barrel would be a novel shape the repo nowhere else uses.

**Name: `/motion-core`.** Reads as "the engine-free core of the motion family" and
pairs naturally with `/motion` (the engine-bearing surface), in the same spirit as
the `/dock` vs `/dock-group` and `/glass-carousel` vs `/carousel` name-pairs canon
(CLAUDE.md §Subpath naming pairs). `/motion-core` is the cheap leaf-set; `/motion`
is the keyframes engine.

**New file `src/motion-core.ts`** — a thin flat re-export, mirroring `src/motion.ts:42`:

```ts
// @mkbabb/glass-ui/motion-core — keyframes.js-FREE + vueuse-FREE motion leaves.
export * from "./composables/motion/core";
```

**New internal barrel `src/composables/motion/core/index.ts`** (or a re-pointed
`src/composables/motion/index.ts` split) re-exports ONLY the free set:

```ts

export * from "../useScrollProgress";
export * from "../useRAFLoop";

```

W3 picks the exact directory shape (a `core/` subdir vs two barrels in one dir) — the
binding constraint is only that `dist/motion-core.js` statically reaches NEITHER
`@mkbabb/keyframes.js` NOR `@vueuse/core`, and `dist/motion.js` reaches keyframes but
NOT the free leaves' duplicate. The leaf `.ts` files do not move (except
`installDarkModeSync.ts` → `/dark`); only the barrels re-point.

**The keyframes-bearing `/motion` barrel** (`src/composables/motion/index.ts` →
re-exported by `src/motion.ts:42`) drops the six free-set `export *` lines
(`index.ts:11,12,15,16,17,18` — staggerReveal, scrollProgress, installDarkModeSync,

(`index.ts:7,8,9,10,13,14` — useSpring, useSpringMount, useSpringPress,

## Part B — R0G-6: the 40×40 confirmation + the coarse-floor shape

### B.0 — The measured-vs-CSS contradiction, resolved

OMEGA §2 (R0G-6 row) and OMEGA §the-trap state the contradiction: `dock.css:1036`
ALREADY carries a `@media (pointer: coarse)` block lifting `--dock-control-size` /
`--size-icon-btn` to `2.75rem` (44px) on `.glass-dock` since v1.4.0 — yet speedtest
measured `DockIconButton` at **40×40** on a real coarse edge (390×844, `hasTouch`).
The W1 spec demands we PROVE whether the var-level floor reaches the rendered button
box or the size chain bypasses it. **It bypasses it. Proven by specificity below.**

### B.1 — The rendered size chain (read from source)

`DockIconButton.vue:32` renders `<button :class="classes">` where `classes`
(`:22-28`) is `cn("dock-icon-button", …)`. So the rendered box is styled by the
`.dock-icon-button` rule. That rule sets its box at `dock.css:633-634`:

```css
.dock-icon-button {
    width:  var(--dock-control-size, var(--size-icon-btn));
    height: var(--dock-control-size, var(--size-icon-btn));
}
```

So the rendered box = whatever `--dock-control-size` resolves to in the button's
cascade context. The button is a descendant of `.glass-dock`, and `--dock-control-size`
is set on `.glass-dock` (it inherits down). The question is purely: **which
`.glass-dock`-scoped declaration of `--dock-control-size` WINS at the button.**

### B.2 — The bypass: density attribute-selector specificity beats the bare-class media block

`GlassDock.vue:80` defaults `density: "comfortable"` and renders it as
`:data-density="density"` (`GlassDock.vue:282`). So the dock root **always** carries
`data-density="comfortable"` (unless a consumer overrides the prop). That activates:

```css
/* dock.css:99-102 — specificity (0,2,0): one class + one attribute */
.glass-dock[data-density="comfortable"] {
    --dock-control-size: var(--dock-density-comfortable-control-size, 2.5rem); /* 40px */
}
```

The coarse floor is:

```css
/* dock.css:1036-1041 — specificity (0,1,0): one class. @media adds NO specificity. */
@media (pointer: coarse) {
    .glass-dock {
        --dock-control-size: var(--dock-touch-target, 2.75rem); /* 44px */
    }
}
```

**Both declarations are in `@layer components`** (`dock.css:8` opens the layer; the
density blocks at `:84-135` and the coarse block at `:1036-1041` are both inside it,
layer closes at `:1042`). So `@layer` ordering is identical for both — the cascade
falls through to **specificity**. `.glass-dock[data-density="comfortable"]` is
**(0,2,0)**; `.glass-dock` (even inside `@media`) is **(0,1,0)** — a media query does
NOT add specificity. **(0,2,0) > (0,1,0), so the density declaration wins**, the custom
property resolves to `2.5rem` (40px), and the coarse floor never reaches the rendered
button. The button renders 40×40 on coarse pointers — EXACTLY speedtest's 40×40
measurement. The contradiction is resolved: the v1.4.0 floor is real CSS but is
shadowed by the always-present density attribute selector. This is the "close-by-
construction failure" OMEGA flagged — the floor was written against bare `.glass-dock`,
but the button's effective `--dock-control-size` is always set by the higher-specificity
density selector.

(`--size-icon-btn` is only the FALLBACK in `var(--dock-control-size, var(--size-icon-btn))`
— it is never reached because `--dock-control-size` is always defined by the density
block. So lifting `--size-icon-btn` in the coarse block (`dock.css:1039`) is doubly
dead for the dock-button path. It still serves bare-icon-button surfaces outside the
dock, per the comment at `dock.css:1027-1030`.)

### B.3 — The coarse-floor shape: `min-block-size`/`min-inline-size: 44px` ON the button, via a `::before` hit-area expansion that keeps the painted glyph compact

The W1 spec gives two candidate shapes; the decision, with rationale:

- **Shape 1 — `min-height`/`min-width: 44px` on `.dock-icon-button` at
  `@media (pointer: coarse)`.** This floors the BOX (a min on the element itself, not
  a custom property, so specificity-on-`--dock-control-size` is irrelevant — the min
  applies to `.dock-icon-button` directly). At comfortable density (40px) it grows the
  visible button to 44px on touch — a +4px visible bump. Simple, correct for the tap
  target, but it changes the painted glyph footprint and can disturb dense dock layouts
  (the dock width math reads `--dock-control-size`/`--dock-h`, tokens.css:843, which the
  min does not feed, so the wrapper may not reserve the extra 4px → overflow risk in a
  tight horizontal dock).

- **Shape 2 — a `::before` hit-area expansion that grows the TAP TARGET to 44px while
  the painted button stays at `--dock-control-size`.** A pseudo-element absolutely
  positioned to inflate the hittable area to ≥44px (`min-height`/`min-width: 44px`,
  centered, `content: ""`), so the WCAG 2.5.5 / target-size floor is met without
  growing the visible glyph and without disturbing dock layout math. **CHOSEN.**

**Why Shape 2.** The dock's whole value is a compact glass pill; growing every icon
to 44px visible on touch (Shape 1) bloats the chrome and risks the horizontal-overflow
class the DockLayerGroup investigation is ALSO chasing in W3. The `::before` expansion
is the idiomatic touch-target pattern (the painted control stays compact; the hit area
grows under the finger), keeps the dock visual byte-identical at coarse pointer except
for the (invisible) pseudo-element, and is layout-neutral because the `::before` is
`position: absolute` (out of flow, no contribution to the button's box or the dock's
width math). It is also the shape EPSILON §2.2 flagged as "may be preferable for dense
docks."

**The rule W3 lands** (design-fixed shape; W3 owns exact values/tokens against the
W2-settled four-state recipe and the existing focus/disabled `:where()` group at
`dock.css:8-18`):

```css
/* AP.W3 R0G-6 — WCAG 2.5.5 coarse-pointer 44px tap-target floor on the rendered
   DockIconButton box, via a hit-area ::before that keeps the painted glyph compact.
   The v1.4.0 `--dock-control-size` coarse lift (dock.css:1036) is shadowed by the
   always-present `.glass-dock[data-density]` (0,2,0) selector, so it never reached
   this box (proof: W1.2 §B.2). This floors the ELEMENT/hit-area directly, so the
   density custom-property specificity is irrelevant. Fine-pointer rendering is
   byte-identical (the block is inside @media (pointer: coarse) only). */
@media (pointer: coarse) {
    .dock-icon-button {
        position: relative; /* establishes the ::before containing box; the button is
                               already inline-flex with no position set (dock.css:629) */
    }
    .dock-icon-button::before {
        content: "";
        position: absolute;
        inset: 50% auto auto 50%;
        translate: -50% -50%;
        min-block-size: var(--dock-touch-target, 2.75rem);  /* 44px */
        min-inline-size: var(--dock-touch-target, 2.75rem); /* 44px */
        block-size: 100%;
        inline-size: 100%;
        /* transparent — hit area only; no paint */
    }
}
```

Notes for W3:
- The `::before` reads the EXISTING `--dock-touch-target` token (`tokens.css:875` =
  `2.75rem`/44px) — no new token; the coarse `@media` block's intent token is reused.
- `position: relative` is additive and safe: `.dock-icon-button` (`dock.css:628-647`)
  sets no `position`, so adding `relative` under coarse only does not perturb the
  fine-pointer box (which never enters the `@media` block).
- The `.dock-icon-button--compact` variant (`dock.css:649-654`) is auto-sized; W3
  decides whether compact buttons also floor (recommendation: YES — a tap target is a
  tap target regardless of visual density; the `::before` floor is visual-neutral, so
  flooring compact too costs nothing visible). The `::before` applies to both since it
  selects `.dock-icon-button`.
- Other dock controls (`.dock-tab-button`, `.dock-select-trigger`,
  `.dock-dropdown-trigger`) are OUT of R0G-6's scope — speedtest measured the icon
  button specifically. W3 may extend the same `::before` floor to them if cheap, but
  the binding gate is the `.dock-icon-button` box only.

### B.4 — Fine-pointer rendering unchanged (W3 hard-gate item 3)

The floor lives entirely inside `@media (pointer: coarse)`, so a fine-pointer
(desktop mouse) render NEVER enters the block — the `.dock-icon-button` box, paint,
and the four-state arms (`dock.css:628-693`) are byte-identical to pre-W3. The W3
audit records before/after: fine-pointer box `var(--dock-control-size)` unchanged
(40px comfortable); coarse-pointer hit area now ≥44px while the painted glyph stays
at `--dock-control-size`. The "measured 40×40" is disproven for the tap target (now
≥44 under coarse) while the visual stays compact.

### B.5 — Disposition of the v1.4.0 coarse block (`dock.css:1036-1041`)

W3 decision: **LEAVE the `--dock-control-size`/`--size-icon-btn` coarse lift in place.**
It is not wrong — it correctly serves (a) any dock running at a density whose selector
the consumer has NOT pinned higher, and (b) bare-icon-button surfaces outside the dock
that read `--size-icon-btn` (the comment at `dock.css:1026-1030` documents this second
