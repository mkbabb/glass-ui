## §1 — THE DESIGN DIRECTION (this wave's slice)

The headline iOS-27 move this wave delivers: **you can grab the live chrome and pull it.** The SegmentedTabs pill indicator stops being a click-target that glides on selection and becomes a PHYSICAL lozenge — the indicator follows the finger ~1:1, STRETCHES along the travel axis by drag VELOCITY (a volume-preserving gel-squish, capped LOW so it swells, never taffy-pulls), and on release FLINGS velocity-continuously to the nearest slot and settles with a small `ζ<1` overshoot. It reads as a drop of mercury you can drag and let snap home. The same gesture reaches the dock: a `DockLayerGroup` you can pull-to-switch between layers. The motion is grab → follow → squish → fling-snap; the warm-cream glass identity is untouched (the lozenge is the same `--glass-bg-floating` "selected reads as glass" plate, it just deforms under the pull).

## The defect / charge

The pull/drag-to-morph tab does NOT exist — there is only a click-to-travel indicator (the R1/R2 audit's `[med]` finding, named verbatim: "The draggable PULL/morph/squish tab does not exist — only a click-to-travel indicator"). And the SegmentedTabs strip has NO keyboard contract at all — a draggable tab that is keyboard-broken is worse than no draggable tab. Three live gaps:

**(a) no pointer-drag pipe on the indicator — only click-travel (R1 finding 4 / R2 finding 3 [med]).** `useTabIndicator.squishOnTravel` (`useTabIndicator.ts:200-255`) squishes on SELECTION travel — a CLICK target — reading `useLiquidFlex` under the `"linear"` law (the geometry-relative travel-FRACTION register, `useTabIndicator.ts:172-178`, `liquidSquish.squish(frac)`). There is no live finger-following with velocity, no interruptible mid-drag re-target, no release-to-nearest-slot spring. The user wants a tab you can PHYSICALLY DRAG so it morphs + squishes to the new slot (iOS-27's draggable control). The pieces exist scattered: `useSpringMount` has the drag-dismiss state machine (`useSpringMount.ts:159-193` — `setPointerCapture`, mid-flight re-target continuity, threshold release), `useLiquidFlex` has the velocity-driven `"tanh"` squish (`useLiquidFlex.ts:169-176`, `1 + tanh(|ṫ|·k)·(max−1)`, the DEFAULT law — UNUSED by the tabs today, which feed `"linear"`), and kf `SpringProgress` re-seats the closed-form solution from `(x,v)` for an interruptible fling (`spring.ts:473` `reset(value?, velocity?)`). Nothing composes them.

**(b) kf `Draggable` is the UNCONSUMED substrate — zero binary consumer at HEAD (the load-bearing REUSE).** `keyframes.js/src/animation/drag.ts` ships a complete `Draggable` class: pointer-capture follow (`drag.ts:214-231` `handleDown` → `setPointerCapture`), a live `SpringProgress.target` write per `pointermove` (`drag.ts:233-240`), a velocity-windowed sample buffer (`drag.ts:275-306`, average over the last `velocityWindow` ms — robust to a jittery last frame), and on release `this.spring.reset(value, releaseVelocity)` so the fling is C¹-continuous with the gesture (`drag.ts:242-257`). glass-ui peer-depends on `@mkbabb/keyframes.js` and reaches it through `composables/motion/*` (`useSpring.ts:15` imports `SpringProgress`, `curves.ts:27` imports `springTimingFunction`) — but NO glass-ui composable imports `Draggable`/`drag`. The SOTA direction here is WIRING the rich substrate glass-ui already depends on, not a net-new drag engine.

**(c) SegmentedTabs has NO keyboard contract — a draggable tab MUST add the roving-tabindex (the load-bearing prerequisite).** `SegmentedTabs.vue:313-356` renders `<button class="segmented-tab">` with `role="tab"`/`aria-selected` (underline) or `aria-pressed` (pill) and a `@click` handler — but NO `tabindex`, NO `@keydown`, NO arrow-key navigation, NO roving focus. A `role="tablist"` with N natively-focusable `<button role="tab">` and no roving tabindex puts EVERY tab in the focus order (the WAI-ARIA tablist pattern requires exactly ONE tabstop, arrow keys moving focus). Adding `:draggable` makes the keyboard gap acute: a pointer gesture that morphs the indicator while keyboard users cannot even arrow between tabs is a half-built control. So this wave OWES the roving-tabindex keyboard contract — `tabindex="0"` on the active tab / `-1` on the rest, ArrowRight/ArrowLeft (horizontal) or ArrowDown/ArrowUp (vertical) moving focus + activation, Home/End jumps — as a structural prerequisite, not a nice-to-have. The drag is pointer-only; the keyboard path is the equal-and-additive contract.
