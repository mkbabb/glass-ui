## The defect / charge

speedtest C8 (the user verbatim, the ask-brief §8): *"hovering this speedtest button is not smooth — this sort of liquid glass that's more realistic is good, and should be suffused at the root within glass-ui."* The F2 retirement ledger names the two component defects precisely: **"the dead-centre static gleam + disco-grain pop (T8-F5/F6)."** The primitive is HALF-shipped at 3.13.0 — `useSpecularTracking` exists + is wired into `DockIconButton` + `Card`, but the tier-root auto-arm is incomplete, so every glass control that does NOT hand-wire the composable hovers DEAD: the catch-light lifts in intensity but freezes at the centred 50% fallback. Two root causes, both grounded at HEAD (`f3c4170e`):

**1. The dead-centre static gleam — the position write is a per-consumer opt-in, not a tier-root auto-arm.** The unified `.glass-material::before` recipe (`src/styles/glass/material.css:65-135`) already (a) maps `--mouse-x/--mouse-y → --specular-x/--specular-y` (`:89-90`) and (b) lifts `--specular-intensity` on `:hover`/`:active` for EVERY glass rung incl. the dock controls (`:155-244`). So the gleam is fully wired to PAINT — it just sits frozen at `var(--mouse-x, 50%)` (the centred fallback, `:89`) for any surface where nobody WRITES `--mouse-x/y`. The position write lives ONLY in `useSpecularTracking` (`src/composables/glass/useSpecularTracking.ts`), hand-composed at exactly TWO call sites: `DockIconButton.vue:53,69-70` (`:style="specularStyle" @pointermove="onPointerMove"`) and `Card.vue:110,135,155` (gated behind `specularArmed`). A bare glass **Button** is the smoking gun — `button/index.ts:69-73` documents it outright: the glass variant inherits the moving-specular `::before` "but the position is the consumer's (a pointermove handler writing `--mouse-x/--mouse-y`)." Since `<Button>` ships no such handler, `<Button variant="glass">` (the speedtest dock CTA) lifts intensity on hover but the gleam never moves — the exact "dead-centre static gleam." The charge's "suffuse at the root with ZERO per-consumer wiring" means the position write must auto-arm on the interactive-glass tier itself, not on N hand-wired call sites.

**2. The disco-grain pop — a discrete `none→image` engage, not an opacity cross-fade.** The glass grain `::after` overlay (`src/styles/glass/ladder.css:336-352`) paints `background-image: var(--paper-clean-texture)` at a static `opacity: var(--glass-grain-opacity)`. The library's audacious disco-grain hover (`--glass-grain-opacity-disco` + the `--paper-clean-texture`/`--phase-color` radial) was already RETIRED at BA.W-GLASS-CAL (`tokens/glass.css:190-193`, `btn.css:83-96`, `tab-button.css:96-110`), so the residual the speedtest sees is the COMPOSITION CLASS, not a surviving disco rule: any state-driven grain ENGAGE that toggles `background-image: none → var(--paper-clean-texture)` is a discrete swap (the image decodes + appears in one frame — the "pop"), whereas the smooth path keeps the image always present and cross-fades its `opacity` (a compositor-cheap interpolation). The charge: the grain ENGAGE must ride an `opacity` cross-fade — direct-write, no easing, ~120ms — never a `background-image` `none→image` swap. (The ledger names this T8-F6 alongside the gleam T8-F5; both are ONE liquid-hover smoothness defect.)

## Scope (the gestalt — not a workaround; no legacy, idiomatic transposition)

1. **Mint the tier-root auto-arm seam ONCE — the position write becomes a property of the interactive-glass tier, not a per-consumer opt-in.** The position-write LOGIC stays the `useSpecularTracking` single-source (its rAF-coalesce + the cached-PRM listener + the cleanup discipline are correct and KEPT — this is a re-home, not a rewrite). The new artefact is the AUTO-ARM that attaches that write to every interactive glass surface with zero call site. The idiomatic mechanism is a **dependency-free Vue directive** `vSpecular` (`src/composables/glass/vSpecular.ts`, the `vReveal` `ObjectDirective<HTMLElement>` playbook — `mounted` attaches the rAF-coalesced `pointermove` listener + writes `--mouse-x/y` on the host, `unmounted` removes it + cancels the pending rAF), so an interactive surface auto-arms by being a directive target, NOT by hand-composing the composable + the `:style`/`@pointermove` pair. The directive WRAPS `useSpecularTracking`'s write (one logic source, the directive is the zero-wiring delivery). It is PRM-aware (skips the write under reduce, the CSS bracket already pins static) by reusing the composable's cached-PRM gate. The auto-arm reaches the interactive-glass surfaces at their COMPONENT root: the directive is applied internally on Button (the glass/glass-wash/primary-audacious/gold-audacious variants), the dock control family (DockIconButton/DockTabButton/DockSelectTrigger/DockDropdownTrigger), and the glass-btn primitive — so a CONSUMER writes `<Button variant="glass">` and the gleam follows the pointer with zero added wiring (the acceptance bar). The directive is published on the `/glass` subpath barrel (`composables/glass/index.ts`) so a consumer with a NET-NEW interactive glass surface auto-arms it with `v-specular` (the ≥2-consumer generality bar met by the in-library Button + dock + glass-btn consumers at birth).

2. **Retire the two per-consumer hand-wires onto the auto-arm (the DRY single-source restored — no two copies).** `DockIconButton.vue`'s `useSpecularTracking` + `:style="specularStyle"` + `@pointermove="onPointerMove"` triplet RETIRES onto the `vSpecular` directive (the dock control auto-arms by being a directive target). `Card.vue`'s `specularArmed`-gated wiring is the ONE case that stays a CONDITIONAL opt-in (a Card is NOT inherently interactive — the gleam is an explicit `specular` prop affordance, not an always-on control register), so Card keeps its prop-gated arm but routes it through the SAME seam (the directive applied conditionally, OR the composable retained for the gated case — the investigation picks the cleaner of the two; the rule is ONE position-write source, never a re-paste). The net: the position-write logic has exactly ONE home (`useSpecularTracking`), the auto-arm has ONE delivery (`vSpecular`), and the interactive controls auto-arm while the Card stays an explicit opt-in — no hand-copied `@pointermove` survives on an always-on control.

3. **Kill the disco-grain pop — the grain ENGAGE rides an `opacity` cross-fade, never a `background-image` swap.** The grain `::after` overlay (`ladder.css:336-352`) keeps its `background-image: var(--paper-clean-texture)` ALWAYS PRESENT (the image is decoded once at rest, never toggled), and any STATE-driven grain engagement (a hover/active grain lift, wherever a glass surface raises grain on interaction) animates `opacity` ONLY — a `transition: opacity ~120ms` direct-write (the §6 doctrine: surface-opacity → `--ease-standard`, but per the ask "no easing" the cross-fade is a plain ~120ms linear direct-write so the engage reads instant-but-smooth, NOT a spring). The grain `background-image` is NEVER `none` at rest on a surface that engages grain (the `none → var(--paper-clean-texture)` swap is the forbidden pop). The ~120ms grain cross-fade tokenizes (`--glass-grain-engage-duration`, a thin token so the timing is tunable, default `120ms`). This is the structural pop-kill: the gate's negative predicate (scope-gate W3) reds any `background-image: none` → image transition on a grain layer. (The BA.W-GLASS-CAL disco retirement already removed the audacious disco-grain RULES; this wave closes the COMPOSITION CLASS so a future grain engage cannot re-introduce the pop.)

4. **The a11y/PRM brackets hold by construction.** The reduced-motion bracket (`glass-specular-track.css:34-48`) pins `--specular-x/y` static at 50% and the directive skips the position write under reduce (the cached-PRM gate); the reduced-transparency bracket (`:55-67`) drops the `::before` entirely — both UNTOUCHED.
