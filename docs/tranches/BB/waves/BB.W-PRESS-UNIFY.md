## The defect / charge

`useSpringPress` is a published HALF-primitive: it ships on `@mkbabb/glass-ui/motion` + the root barrel with a beautiful `(response 0.25, ζ 0.7, ~5% overshoot)` iOS tap-press preset, the `press()`/`release()`/`handlers` ergonomics, and a worked `<button>` example in its own docstring — and it has ZERO internal binary consumers (re-grepped at HEAD: `useSpringPress` appears ONLY in the export lines + doc comments, never bound on an SFC). This is the J-invariant-10 substrate-without-consumer state, live: a primitive shipped that nothing presses.

Meanwhile the actual press across the library is a CSS `:active` transition — `.tap-squish:active { scale: var(--scale-press) }` (`utilities/base.css:270-272`) on `scale … var(--spring-smooth)`, mirrored on `.btn-pill` (`glass/surfaces.css:155`), `.btn-interactive` (`utilities/btn.css:198`), `.glass-btn` (`surfaces.css:96-97`), and the dock control press (`dock-controls.css:44`, the no-overshoot `--scale-press-dock` squish). A CSS `:active` transition has TWO defects this wave fixes:

1. **It cannot absorb a rapid re-press mid-flight.** A CSS transition is a fixed `from→to` interpolation re-armed from the CURRENT computed value on every state flip. Tap-tap fast (a double-tap, an excited rapid-fire on a CTA) and the second `:active` RESTARTS the scale transition from wherever the release transition happened to be — a visible micro-stutter, never the iOS velocity-continuous re-seat where the second press inherits the first's momentum. The shipped `useSpringPress` wraps `useSpring` → kf `SpringProgress`, whose `reset(value, velocity)` (kf `spring.ts:473`) re-seats the closed-form trajectory from the live `(position, velocity)` — the EXACT interruptible contract, sitting unused.

2. **It is scale-ONLY — no coupled liquid beat.** The button press is a uniform shrink (`button/index.ts:27` `active:scale-(--scale-press-btn)` = 0.97); the glass-wash default/primary-audacious only swaps `active:bg-(--glass-bg-floating)` on the bezier surface leg. So a press reads as a bg-snap-THEN-scale-spring desync, not the unified squishy-glass press the user named (R3 W-PRESS-COUPLE; A2 "Press feel is a single scale leg … no coupled fade/brightness"). The §6 / W-MOTION-CANON P3 doctrine says the enter/press couples opacity WITH transform on the SAME clock — the press is the most-touched surface and is the one register where that coupling is absent.

The charge is precise: **wire `useSpringPress` as the ONE interruptible, coupled spring-press across buttons + cards + dock controls — reaching the ≥2-consumer bar by construction (Button + Card + dock = three binaries) — OR demote it honestly** (retire the export + book the CSS `.tap-squish` path as the canonical press). The user-directed answer is the WIRE (the press SHOULD read liquid on the surfaces named); the demote is the §Triumvirate fall if the wire cannot meet the bar without overfitting. PRM: the press is INSTANT (the gesture confirms, the physics off — W-MOTION-CANON P6).

- **The wire cannot reach the ≥2-consumer bar without overfitting** — if binding `useSpringPress` on Button + Card + dock produces a press that reads WORSE than the CSS floor on any surface (a JS-spring press that lags the pointer-up because the rAF spin-up costs a frame, a Card press that fights its hover-lift, a dock press whose JS curve desyncs from the surface CSS), OR the only honest binaries are < 2 (the Card `:pressable` has no real demo home, the dock press is genuinely better as CSS) AND three iterations have not isolated the cause, that is the WIRE-OR-DEMOTE reveal: triumvirate (research whether the press is genuinely better as the interruptible JS spring on these surfaces, OR whether `useSpringPress` should be honestly RETIRED + the CSS path booked canonical). The demote is a LEGITIMATE outcome (the charge names it) — do NOT force a third overfit consumer to manufacture the bar; the honest demote (retire + book) is the correct close if the wire does not earn its keep.
- **The interruptible re-seat races a Vue flush / the rAF spin-up** — if the mid-flight re-press cannot inherit velocity because the `reset(value, velocity)` reads a stale pre-flush value, or the rAF loop has parked between press and re-press so the second press spins up from rest (no momentum), that is an interruptibility-ordering reveal: triumvirate (research the `SpringProgress.reset` timing vs the Vue reactivity flush + the rAF auto-resume gate `useSpring.ts:129-136`), do NOT fall back to the CSS transition (the non-interruptible restart is the defect) and do NOT re-tune the spring preset to mask a timing race.
- **The coupling fights W-BUTTON-GLASS's specular seam** — if driving the brightness/specular beat off `--press-t` collides with W-BUTTON-GLASS's `useSpecularPointer` write (both writing `--glass-specular-intensity`, a double-write that flickers), that is a seam-coordination reveal: triumvirate with W-BUTTON-GLASS (research the ONE drive both read — `--press-t` for the press intensity, `--mouse-x/y` for the pointer position — they are orthogonal channels of the same specular cohort), do NOT fork a second specular intensity token (the band has ONE specular family — the W-LENSING/W-LIQUIDHOVER reconcile).
- **The compositor-only ban catches the squish** — if the reciprocal-squish register (the `useLiquidFlex` X/Y scale pairing) needs a `transform-origin` or a `filter` that `proof:no-layout-animation` flags, that is a property-tier reveal: triumvirate (the squish must be `transform: scale()` + `filter: brightness()` ONLY — both compositor; a layout-property leak is the A'-3 defect), do NOT animate any layout/paint property to get the deform.
- **Diagnostic loop halt** — if the press still stutters on a rapid re-press after the interruptible wire, OR the PRM press still animates a transform frame, and three iterations have not isolated whether the cause is a CSS `:active` floor STILL winning over the JS write (the cascade-precedence class), a stale spring re-seat, or a PRM policy not threading, halt and triumvirate.
