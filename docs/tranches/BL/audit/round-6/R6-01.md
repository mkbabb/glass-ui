## 2. Findings

### R6-01-01 (HIGH, EXTENDS F-22): the overlay layer has no host; every plate portals to `document.body`

- **Mechanism**: every content part mounts through a reka Portal with its default target, `body`, and no content part passes a target: `TooltipContent.vue:68`, `SelectContent.vue:65`, `menu/DropdownMenuContent.vue:50` through `menu/context.ts:78`, `DialogContent.vue:190`, `SheetContent.vue:292`, `toast/Toaster.vue:144`, `slider/Slider.vue:284,302`, `ExpandableContainer.vue:2`. `PopoverContent.vue:22,42,81-87` offers `portal: boolean` and nothing else. The z rungs (`tokens/scheme-motion.css:210-213`, 120-150) cannot rank against the top layer, so an overlay opened from any host that is not the document body lands outside it. F-22's content seam (`_shared/overlay/content.ts:48`, `overlayContentAttrs`) carries a z, an edge and a dismissal leg (round 4); the host a layer lives in is the missing fourth leg, and the library advertises two such hosts itself: the native top-layer grammar `.glass-top-layer` (`styles/animations.css:195-313`) and its own fullscreen, ExpandableContainer (R6-01-08).
- **Evidence**:
  - Fullscreen (`#stage` via `requestFullscreen()`): Select, Popover, DropdownMenu, Tooltip, Dialog and Sheet plates are outside the fullscreen element and not hit-testable (`elementFromPoint` at each centre returns `html` or the stage), 2 of 2 (`fullscreen.json`, `fullscreen-r0-DialogContent.png`: nothing painted). Focus does not enter the Select (ArrowDown then Enter picks nothing) or the Dialog (focus stays on the trigger). The Dialog leaves `body { pointer-events: none }`, so the next click on the stage's own Button lands 0 times and closes the invisible Dialog, 2 of 2 (`fullscreen-dead-stage.json`). Popover repeated in Playwright WebKit and Playwright Firefox, 2 of 2 each (`engines.json`).
  - Native modal `<dialog class="glass-top-layer">`: Select, Popover, DropdownMenu, Tooltip and Dialog plates outside the dialog, hit test on the dialog's `::backdrop` or the page, 2 of 2 (`toplayer.json`, `toplayer-r0-native-*.png`); Select keyboard pick null; a click on the menu item's position gives 0 activations and dismisses the menu as an outside press; a toast fired while the modal is open lands under the backdrop, outside the modal, so it is inert. Select repeated in Playwright Firefox (2 of 2); Playwright WebKit could not click the trigger inside the dialog (not measured).
  - Shadow root with the stylesheet in the shadow root only: all five plates in `document.body` with no rule applied (`position: static`, transparent) (`shadow.json`, `shadow-shadow-only-*.png`).
- **Disposition**: BUILD, in F-22's content-seam wave.
- **Wave shape**: the seam resolves a target from the trigger (the nearest open `dialog:modal` containing it, `document.fullscreenElement` when it contains the trigger, else the trigger's root node: the shadow root, or `body`) and passes `to` to every Portal, the Toaster's included; z stays host-relative inside that target. Born-RED: from inside a fullscreen element and a `showModal()` dialog, each of Select, Popover, DropdownMenu, Tooltip and Dialog is a descendant of that host and hit-testable at its centre (HEAD: 0 of 5 in each host).

### R6-01-02 (HIGH, NEW): the shortcut registry reads a retargeted `event.target`, so typing into a shadow-root input fires app shortcuts

- **Mechanism**: the registry listens on `window` (`composables/keyboard/useKeyboardShortcuts.ts:351-357`) and filters editable targets with `isEditableTarget(e.target)` (`:176-183`, called at `:326-329`). At `window` a keystroke from inside a shadow root is retargeted to the shadow host, a custom element, which is not `INPUT`, `TEXTAREA`, `SELECT` or contenteditable. So every registered key fires while the reader types into any input that lives in a shadow root: a third-party web component (Material Web, Shoelace, Ionic, MathLive) beside a glass app, or glass mounted inside a shadow root. The global Escape fires too, which the same filter otherwise keeps from a text field.
- **Evidence**: `<r6-field>` (an open shadow root holding one `<input>`) beside the top-level battery: typing `kkk` then Escape gives `k` 3 and Escape 1; the glass Input on the same page then adds 0 and 0. Chromium, Playwright WebKit and Playwright Firefox, 2 of 2 each (`engines.json`, `shadow2.json`). Glass Input inside a shadow root: `k` 3 of 3 and the global Escape +1, against 0 and +0 at top level, in each of the three css modes (`shadow.json`). The demo registers `]`, `[`, `}`, `{` and `?` (`demo/shell/AppShell.vue:189-211`), so a `?` typed in such a field would open the help overlay (inferred from the registration, not driven).
- **Disposition**: BUILD, W-ROOT-RELATIVE (the NEW family's wave, §3).
- **Wave shape**: the registry reads `e.composedPath()[0]` for the editable test. Born-RED: `kkk` + Escape typed into `<r6-field>` gives 0 and 0 (HEAD 3 and 1), in three engines.

### R6-01-03 (MED, NEW): the modal focus trap enumerates tabbables in the light DOM only

- **Mechanism**: the Dialog and Sheet trap through reka's FocusScope, whose Tab wrap reads `getTabbableEdges`, a `document.createTreeWalker` over the container that does not descend into shadow roots (reka 2.10.1 and 2.10.5 `FocusScope/utils.js:40-42`, `FocusScope.js:141-152`). ExpandableContainer uses the same scope (`ExpandableContainer.vue:3-9`). A focusable inside a web component at either edge of the content is outside the computed edges, so the wrap jumps over it.
- **Evidence**: `<r6-field>` placed after the Dialog's footer: seven Tabs cycle Close → Dialog field → Inner select → Done → Close and never reach the web component's input; three Shift+Tabs do not either. Chromium and Playwright Firefox, 2 of 2 each (`trap-wc.json`). Playwright WebKit differs for a separate reason: its default Tab order skips buttons, so even without the web component Tab escapes the content to BODY every second press (`trap-wc-control-webkit.json`; noted in §4, not filed here).
- **Disposition**: BUILD, W-ROOT-RELATIVE; upstream the walker fix to reka and carry a library tabbable walker until it lands.
- **Wave shape**: the trap's edges come from a walker that descends open shadow roots. Born-RED: the Tab trail inside the Dialog reaches the web component's input within 5 presses (HEAD: never in 8).

### R6-01-04 (MED, NEW): focus guards compare against `document.activeElement`

- **Mechanism**: nine library sites decide "is focus inside me" with `document.activeElement`, which is the shadow host whenever focus is inside a shadow root: `data-table/DataTable.vue:101`, `tabs/composables/useTabRovingFocus.ts:97-101`, `pager-dots/PagerDots.vue:210-211`, `dialog/DialogContent.vue:137`, `sheet/SheetContent.vue:259`, `expandable-container/ExpandableContainer.vue:211`, `dock/DockCrossfade.vue:158`, `dock/composables/useDockRun.ts:219`. When the component itself is inside a shadow root, each guard misses.
- **Evidence**: DataTable's retention guard (`:99-107`: remember the focused row before update, re-focus after). Focus each of the four rows in turn and reorder the rows: at top level 4 of 4 keep focus; inside a shadow root (stylesheet in both) rows 2-4 drop to BODY, 3 of 4. Chromium, Playwright WebKit and Playwright Firefox, 2 of 2 each (`shadow2.json`, `engines.json`). The other eight sites are cited from source and not driven.
- **Disposition**: BUILD, W-ROOT-RELATIVE.
- **Wave shape**: one helper returns the focused element of a node's own root (`node.getRootNode().activeElement`, descending nested roots), used at all nine sites. Born-RED: the shadow-root reorder keeps focus on 4 of 4 rows (HEAD 1 of 4).

### R6-01-05 (LOW, NEW): tokens are declared on `:root` only

- **Mechanism**: the package's 124 CSS files hold 66 `:root` or `html` selectors and 0 `:host` selectors (for example `styles/tokens/color-radius.css:5`, `tokens/glass-fx.css:6`, `tokens/glass-deep.css:47`). Inside a shadow tree `:root` matches nothing, so a stylesheet adopted only by the shadow root carries no glass tokens. Tailwind's own theme in the same compile is declared on `:root, :host` and does arrive.
- **Evidence**: stylesheet in the shadow root only: `--background`, `--primary` and `--space-body` compute to "" on the Button while Tailwind's `--radius` is `.625rem`; the Button renders 20 px unstyled, the Input and Select lose their plates, and the console reports `Invalid keyframe value for property transform: scale()` (`shadow.json`, `shadow-shadow-only-rest.png`). Loading the stylesheet in the document as well restores the tokens by inheritance, so a consumer has a workaround; a fully encapsulated embed does not.
- **Disposition**: BUILD (small), W-ROOT-RELATIVE; or an owner ruling that shadow mounts are unsupported, which moves this row to F-63 as a documented limit.
- **Wave shape**: token blocks declare on `:root, :host`. Born-RED: in the shadow-only mount the Button's `--primary` is non-empty (HEAD "").

### R6-01-06 (MED, EXTENDS F-65): the dark arm keyed to an ancestor class does not reach a shadow tree

- **Mechanism**: glass-ui keys its dark arm on an ancestor class: `@variant dark (&:where(.dark, .dark *))` (`styles/theme/dark.css:7`) and 30 `.dark …` selector lists in the package (75 after the consumer's compile), for example `.dark .control-bit` (`styles/glass/control-bit.css:192`) and `.dark .glass-deep` (`styles/tokens/dark-arm-glass.css:25`). A descendant selector cannot cross a shadow boundary, while the inherited arm (`color-scheme` driving `light-dark()`, and custom properties set on `html.dark`) does. So a shadow-mounted subtree paints half a scheme. This is F-65's R2-08-12 mechanism (two dark arms, and a scope where only one reaches) in a new scope, with one addition: two of the missed arms are not colours, so `light-dark()` alone cannot carry them.
- **Evidence**: page dark (`.dark` and `color-scheme: dark` on `html`), stylesheet in both: the Checkbox's `--control-bit-fill` stays on the light arm, `color-mix(in oklab,#e9e6e2 4%,transparent)` against `oklch(0% 0 0/.14)` at top level; the Button's backdrop stays `saturate(1.605)` against `saturate(1.8)`. Tokens flip in both (Input `rgb(63, 55, 49)` in both). 2 of 2 (`darkreach.json`, `darkreach-r2.json`, `darkreach-*-controls.png`).
- **Disposition**: FOLD into W-DARK-ONE-ARM.
- **Wave shape**: W-DARK-ONE-ARM's one arm is inherited: colours through `light-dark()`, and the non-colour dark values (saturation, fill alpha, blend, strengths) through an inherited custom property the rules read, not a `.dark` ancestor. Born-RED: in the shadow mount in dark, `--control-bit-fill` and the Button's `backdrop-filter` equal the top-level values (HEAD: light arm, 1.605).

### R6-01-07 (MED, EXTENDS F-22): a consumed Escape is not marked consumed, so each enclosing dismissal also fires

- **Mechanism**: F-22's round-4 dismissal leg names the cure: the layer calls `preventDefault` on the Escape it consumed. Two more consumers read that flag and act when it is unset. The native `<dialog>` turns an unprevented Escape into `cancel` and closes. The registry's Escape LIFO (`useKeyboardShortcuts.ts:309-319`) runs ExpandableContainer's registrant (`ExpandableContainer.vue:213`, the only in-library one, R4-01-13), which collapses the container.
- **Evidence**:
  - A glass Select, Popover, DropdownMenu, Tooltip or Dialog opened inside a `showModal()` dialog: one Escape closes the overlay and the native dialog, 5 of 5, 2 of 2 (`toplayer.json`). An unportaled Popover inside the native dialog: one Escape closes both in Chromium; in Playwright Firefox and Playwright WebKit the native dialog closes and the Popover's content stays mounted inside it; Chromium and Firefox emit `update:open(false)` twice for the one close (`toplayer-inline-expand.json`, `engines.json`).
  - Inside an expanded ExpandableContainer: one Escape closes the Select, Popover, DropdownMenu, Tooltip or Dialog and also collapses the container (`update:open` true then false), 5 of 5, 2 of 2 (`expand-fullviewport.json`).
- **Disposition**: BUILD, in F-22's dismissal leg.
- **Wave shape**: as F-22 round 4. Born-REDs added: Escape on a Popover inside a native modal dialog leaves the dialog open; Escape on a Select inside an expanded ExpandableContainer leaves it expanded (HEAD: closed and collapsed).

### R6-01-08 (MED, EXTENDS F-22): the library's own fullscreen host outranks the overlays opened inside it

- **Mechanism**: the expanded ExpandableContainer is `position: fixed; z-index: var(--z-modal)` (`expandable-container/styles.css:7-9`, 140). A Select or Popover (130), a Tooltip (120) or a DropdownMenu (no z) opened inside it portals to `body` at its own fixed rung, below its host: F-22's first mechanism, with a first-party host. `--z-fullscreen` (150, `tokens/scheme-motion.css:213`) is declared and read by nothing.
- **Evidence**: each plate's mean luminance, collapsed then expanded: Select 0.720 → 0.411, Popover 0.796 → 0.451, DropdownMenu 0.808 → 0.457, Tooltip 0.726 → 0.414, 2 of 2: all four paint under the container's scrim (`expand-paint.json`, `expandpaint-*.png`). The Popover and Tooltip are not hit-testable (the hit lands on the container), and focus sits inside the dimmed Popover. The Select and DropdownMenu are hit-testable only because their modal `body { pointer-events: none }` reaches the container too.
- **Disposition**: BUILD, in F-22's z leg.
- **Wave shape**: host-relative z: the seam places an overlay one rung above the nearest layer ancestor of its trigger, or R6-01-01's target puts it inside that host. Born-RED: in an expanded ExpandableContainer each plate's luminance equals its collapsed value within 0.02 (HEAD −0.31 to −0.35).

### R6-01-09 (MED, EXTENDS F-21): the top-layer grammar's rest state makes the dialog a containing block

- **Mechanism**: `.glass-top-layer[popover]:popover-open, dialog.glass-top-layer[open]` rest at `scale: 1; filter: blur(0)` (`styles/animations.css:255-266`). Any `scale` other than `none` and any `filter` other than `none` make the element the containing block of its fixed-position descendants, so a Floating-UI plate inside the dialog is clipped by the dialog's `overflow: auto`. The entry values outlive the entry, which is F-21's round-4 containment rule (a containment declared for one purpose applies only while that purpose holds). The library's own `focus-veil.css:60-68` documents the same trap for its veil. The only escape hatch for an overlay inside a native modal, `PopoverContent :portal="false"`, is the one this clips.
- **Evidence**: dialog centred (`margin: auto`, as the UA sheet intends; the consumer's Tailwind preflight removes it), unportaled Popover opened at the dialog's lower edge. Shipped: computed `scale: 1`, `filter: blur(0px)`; the plate is clipped to the dialog's box (a sliver shows). A/B through CSSOM with `scale: none; filter: none` at rest: the plate paints whole at the same coordinates, 2 of 2 each (`toplayer-containing-block2.json`, `tl5-pair-crop.png`). The grammar sits behind `@supports (overlay: auto)`, so this is the Chromium arm (R2-01-12, F-66).
- **Disposition**: FOLD into F-21's containment row.
- **Wave shape**: the open state rests at `scale: none; filter: none`, and `@starting-style` keeps the entry values. Born-RED: an unportaled Popover inside an open `.glass-top-layer` dialog paints whole (HEAD: clipped to the dialog box).

### R6-01-11 (LOW, EXTENDS F-22): a native top-layer element above a glass modal is dead, and a click on it dismisses the modal

- **Mechanism**: reka's modal makes the page inert by writing `pointer-events: none` on `body` and `aria-hidden` on the other body children, neither of which knows the top layer. A native modal would leave the popover inert without closing.
- **Evidence**: glass Dialog open, `#np.showPopover()`: the popover's button computes `pointer-events: none` and sits inside an `aria-hidden` ancestor; a click on it gives 0 activations and `update:open(false)` on the Dialog. Chromium, Playwright WebKit and Playwright Firefox, 2 of 2 each (`toplayer-beside.json`, `engines.json`, `tl2-r0-*.png`).
- **Disposition**: FOLD into F-22's dismissal leg.
- **Wave shape**: an outside press whose target is in the top layer and outside the modal does not dismiss it. Born-RED: the click leaves the Dialog open (HEAD: dismissed).

### R6-01-12 (LOW, EXTENDS F-22): dismissal does not cross the frame edge

- **Mechanism**: the dismissal leg listens for `pointerdown` and `focusin` on the frame's own document (reka 2.10.1 `DismissableLayer/utils.js:21-85,90-119`). A click in the embedding page reaches neither, and nothing watches the frame's window `blur`.
- **Evidence**: battery in a same-origin and a cross-origin iframe; open Popover, DropdownMenu, Select or Dialog, click a button in the parent: all four stay open, `document.hasFocus()` false in the frame, 4 of 4 runs (`iframe.json`). The Dialog staying open is correct (modal); the Popover, the menu and the listbox are not what a native `<select>` does.

- **Wave shape**: non-modal layers dismiss on the window's `blur` when focus leaves the document. Born-RED: after a parent click, the frame's Popover, menu and listbox are closed and the Dialog is open (HEAD: all open).

## 3. The NEW family

- **Proposed family**: the host is read through document-global handles that a shadow boundary retargets or hides. Proposed band E (three of its four members are keyboard and focus).
- **Mechanism**: the library asks the document, not the node's own root, where it is: `event.target` read at `window` (R6-01-02), `document.activeElement` (R6-01-04), a light-DOM tree walk for tabbables (R6-01-03), and `:root` as the only token scope (R6-01-05). A shadow tree anywhere on the path, a web component inside a glass app or glass inside a shadow root, makes each read wrong.
- **Members**: R6-01-02 (HIGH), R6-01-03 (MED), R6-01-04 (MED), R6-01-05 (LOW).
- **Placements weighed**: F-22 is the overlay's layer contract, and none of these is an overlay (R6-01-01, the portal target, is placed there instead, because its cure lands in the content seam F-22 already rebuilds; it could sit here by the same "document-global handle" reading). F-38 is focus keyed to mount and unmount, a timing mechanism, and W-FOCUS-LIFECYCLE cannot carry a walker or a root-relative read. F-42's mechanism is naming and missing keys.
