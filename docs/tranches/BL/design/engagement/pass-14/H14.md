## 2 · What H14 found and what it changed

### 2.1 · Findings against S14 as written (for the fold)

- **S-1 · b.1 step 1 / 3.5: a transform-carrying link's size change sends the whole step to paint.** An insert inside a tilted card (M1, perspective inside C) changes C's size. As written, the stage takes the paint path for that frame, and Newton started at 0 diverges under a strong card: the fixture's first read (04:47, load 30.5) painted the root 3096 px off on the act's frame (P 200 θ 60, insert 40), and **cand13 does the same today: 3334.79 px on the act's frame, 26510 px over 16.7 ms** (its log of record). This contradicts S14's own claims for Y6, b.1 step 4 and M28 (exact). H14's fixture reads b.1 step 1 as: the link's size change is a step only where its map resolves against its size (a percentage translate, or an origin that moves with the size under a `rotate`/`scale`/`transform`/`perspective`), and when the paint path does run it starts Newton at the chain's own −Δ for the part of the step below the transformed link. On that reading M1 8/8, M6 3/3 and M28 1/1 pass in Chromium. The route's S14 build must make the same choice and state it.
- **S-2 · a.2 / b.1: Q is summed in mixed units under CSS zoom.** `offsetTop` is in the element's own zoomed units, and a translate on the root paints × the root's zoom (`probes/zoom-units.mjs`, Chromium: G's `offsetTop` 30 → 78 under a 40 px insert, the root's 10 inside a `zoom: 2` box, a `translate: 0 -40px` paints −80). A chain path that sums raw offsets misplaces the root by Δ × (1 − z) on a positioned zoomed link below the change: the fixture read 8.00 px (zoom 0.8), 10.00 (1.25) and 40.00 (2) on E-10's `hostglide · chain · zoom` cells. Cure in the fixture: each level is put in the root's units, `level × currentCSSZoom(link) / currentCSSZoom(root)`; the cells then read 0.00. S14's K should name the units.
- **S-3 · b.3's 16.7 ms bound under a projective card** (above, §1). The bound takes the map's stretch along the glide's path.
- **S-4 · M2's limit corners.** N11's 42.5 px and 0.7 px are figures of N11's own library-free scene; on E-14's scene the same corners read other values (cand12 and HEAD fail them; the fixture's 4 iterations read within them). H14 reports them, it does not grade them.
- **S-5 · b.8's exit bound needs the clock alone.** The fixture's first S14 stage read the travel (clock and easing) at release to set `exitAt`; the easing read is loud, so a planted `--spring-press` raised an error on E-11's `travel loud · carry` cells while the carry travel ran, and E-11's clean self-test read BROKEN (5 cells). The bound now reads the settle alone, silently; the loud easing read belongs to a travel that runs. S14's b.8 should say the exit bound reads no easing.
- **S-6 · b.11, the library's resize observers.** Stated in §2.4.
- **W-1 · WebKit lays out a late `<link>` sheet and a decoded image after the resize observation of their frame** (M9). Read three times on the clean fixture (13:48, 13:57 ×2, load 16-20) and again at 14:17 and 16:02: the root is cut 40.00 px on the act's frame, painted back on the next frame (0.00 px from where it was) and glided home, which is b.11's cut-then-glided-back form. Chromium holds both cells exact. S14's M9 claims a step; in WebKit these two inputs are b.11's limit. E-14 grades them so in WebKit, by name (`gradeCutBack`), and the fold should state it.
- **W-2 · a re-snap with no range change is carried as a scroll** (M24, rule 6). `probes/resnap.mjs` (WebKit, library-free): the resize observation sees the re-snap and the range change on the same frame (`scrollTop` 600 → 650, `scrollHeight` 1500 → 1600 at the `center` grow), as Y4 read. E-14's first M24 scene hid the range change: G (the padded `<main>`) overflowed the snapped item, so the item's growth left the scroller's range as it was, WebKit still re-snapped 50 / 100 px, and rule 6 (a scroll is the engine's only on a frame whose range changed) carried it unglided. The scene now zeroes G's padding (the cell is Y4's); the gap stands for S14: a re-snap whose item grows inside the scroller's existing overflow has no range change to attribute it by.
