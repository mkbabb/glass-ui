## S14-0 · In brief

1. **The invariant is stated on paint (§S14-a).** The held host's painted place, read once per frame, never steps on the frame a re-render lands (≤ 0.5 px on the act's frame) and never moves more than H14's 16.7 ms bound between frames, measured against what carries it. What carries it is the composite of every transform between the host and the viewport and the scroll the user or a script asks for. Its place is where the engine lays it out, at every level of the layout tree. A carrier move is carried, at any rate. A place step is glided from where it was painted. The stage's own glide is invisible to its own read, so it lands.
2. **The decomposition, chosen (§S14-b): the engine's layout separates the two families, and the engine's paint measures the step.** Every frame a host is on the stage (engaged, or on its exit clock), the stage reads in the frame's resize step, after layout and before paint, without writing:
   - the **layout key** (the offset chain of the host to the root, its offset size, and each scroll ancestor's offsets and scroll range);
   - the host's **painted box**.

   If the layout key is unchanged, nothing the frame did is a place step. The carrier moved, or nothing did, and the stage writes no glide. If only scroll offsets changed, that is a scroll someone asked for, and it is carried. Otherwise the frame holds a place step. The stage glides what that step painted on this frame, solved on the engine's own paint through paused probes (true Newton, the map re-asked each iteration), and glides nothing else. **No observer hears anything; no record decides anything.** The MutationObserver, `own()` and the record callback are deleted (E-1).
3. **Why this and not the other two constructions (§S14-b.2).** The record-driven glide is finding 3's mechanism. Its plant `plant-child` proves it (CE13c §0.1). A painted-only frame read (painted − now on every frame) cannot tell a carrier from a step: a pure translation of the carrier equals a step in paint, and D1 is exactly that. The split S14 first had in view read the layout box by undoing every ancestor's transform with paused replace animations. **N1 shows that read is exact on every carrier kind but `!important`. N1c shows it is unusable: undoing a transform that extends a scroller's overflow clamps the scroller's offset, permanently, by 68-300 px, with a scroll event, identically in both engines.** So the layout is read from the engine's own layout values, the offset chain, which reads no paint and writes nothing (N12).
4. **A layout-property animation belongs to both families (§S14-b.6).** S14 carries its velocity and glides only its change from frame to frame. The step glided on a frame that follows a step is the difference of the two steps, and it is glided only if it exceeds the glide floor (0.5 px, `glide()`'s existing figure). So a constant-rate layout animation is carried exactly. An insert during it is glided. Its onset frame is glided like any act, and every acceleration beyond the floor is glided.
5. **The members (§S14-c)** carry a range each, with the reason the range bounds the family. Every member cand12 or cand11 passes is a row with that build as the passing reference and cand13 as the plant where cand13 fails. Eight members are **stated limits**, each with its read (or the cell owed) in each engine:
   - a sub-pixel step that changes no rounded offset;
   - a carrier move in the same frame as a step;
   - the extremal projective corner;
   - a user scroll in a step frame;
   - an `!important` transform (moot for the chosen read);
   - the probe's own clamp hazard;
   - a context-relative gutter;
   - a token changed at runtime under WebKit's `transition: all`.
6. **The token reads move into the stylesheet (§S14-e).** Each token the engagement reads becomes a registered property *declared* on the member's own class, as its consumer's own expression, read back by `getComputedStyle`. There is no inline write, so no `style=""` (class 3), no record and no `own()`. The names move outside `--engage-*` (`--stage-read-*`, class 1, CK-09). The refusal is an ident (`<time> | stage-unset`), which no math form computes to, so no sentinel collides with a value (N5). The clock is read as the consumer computes it, root-substituted (N9), and clamped as `transition-duration` clamps it, so `--motion-tempo` ≤ 0 runs the clock CSS runs: 0, instant, no error. **N9 also finds a counterexample on cand13 by the bytes:** `rowClockMs` reads `var(--spring-dock-settle) × motionTempo(host)` on the host, while the consumer's `--spring-dock-duration` is substituted at `:root`. So a nearer override of the settle or the tempo makes the script run 1 s or 0.21 s where CSS runs 0.21 s or 0.42 s.
7. **CK-04's frame (§S14-f)** is re-read on every frame the host's painted box or its layout key changes. That includes D9's card scaled about the held control.
8. **CK-22 (§S14-g)** lists every header and comment sentence P-E14 rewrites or deletes, and seven MIGRATION rows.
9. **Cost (§S14-h).** The construction removes the document-wide observer, the per-record callback and every forced read inside it. It adds, per engaged frame, a layout-key read with layout already clean. On a step frame it adds the probes (at most 3 plus 3 per Newton iteration). The plan prices the drag's forced work beside cand12 and CPU per frame held still beside cand8, cand11, cand12 and cand13, and adds two cells this construction needs: a carrier loop and a step frame.

## S14-a · The invariant, stated on paint

The row asks for continuity in paint (§P1-6 CK-20: "no one-frame discontinuity on any engagement transition"). S14 starts there.

**(a.1) What is read.** The held host's painted place, once per frame, at the frame's resize step, after layout and before paint (N2, N13), at the frame's one animation time. The place is the host's painted box (`getBoundingClientRect()`), and its centre is the point the harness grades.

**(a.2) What carries the host.** The painted map from the host's layout box to the viewport is a composition of two maps, and the engine computes them separately:

- **the carrier**: every transform-family value between the host and the viewport (`transform`, `translate`, `rotate`, `scale`, a perspective, an origin or percentage resolved against a size, CSS zoom), whatever writes it (a stylesheet, a CSS transition or animation, WAAPI, a script writing inline style every frame, a custom property such a value reads), plus every scroll offset the user or a script asks for;
- **the place**: the host's layout position at every level of the layout tree. Any box above it laying out differently moves the place: an insert, a removal, a size change, a font or sheet arriving, a shadow tree, a form control's own size, a pseudo-class restyle. So does any scroll offset the engine sets as the consequence of a layout change: an anchoring adjustment, or a clamp when the scroll range shrinks.

**(a.3) The invariant.**

- **A move of the carrier is carried and never resisted, at any amplitude and any rate.** The stage writes nothing for it.
- **A step of the place is glided from where the host was painted**, on the `dock` row, so that on the step's own frame the painted place moves ≤ 0.5 px (the act's bound) and over any 16.7 ms by no more than H14's bound for a glide of that size.
- **The stage's own glide is not a move of either kind.** The layout key does not see it (a `translate` is a carrier value and changes no offset), so nothing re-glides it, and each glide runs to its end and lands.
- **A step's paint includes what the step paints through the carrier's size-resolved values.** A percentage `translate` or a `50%` origin moves when the box it resolves against changes size. The Dialog's re-centring is this case. It is part of the step and is glided with it on the step's frame. On every other frame the carrier is carried.

**(a.4) What the invariant does not ask.** It does not ask the host to stay still in the viewport when its carrier moves. A script scrolling the page, a card the author rotates or translates every frame, or a Carousel scaling its member all move the held host with what holds it. The held control never comes apart from its card (CE13c §3: "a held object coming apart from what holds it" is the failure). It does not ask a size change of the host itself to be glided: the size step is the host's own geometry, and only a move of a point the layout keeps fixed is a place step (§S14-b.5).

## S14-b · The decomposition, chosen and defended by painted geometry

### b.1 · The construction

Per frame, in the resize step, for each host on the stage (engaged, or released and on its exit clock; §S14-b.8). Every read comes first, and every write after.

1. **The layout key K.** It is read from the engine's layout values only. Each is a read of clean layout in the resize step (N13), and none reads paint. K has three parts:
   - **the chain**: `offsetLeft`, `offsetTop`, `offsetWidth` and `offsetHeight` of the host and of each element on its `offsetParent` chain;
   - **the scroll offsets S**: `scrollLeft` and `scrollTop` of each scroll ancestor (an element whose `overflow` scrolls, and the root);
   - **the scroll ranges R**: `scrollWidth − clientWidth` and `scrollHeight − clientHeight` of the same ancestors.

   N12 reads what the chain is: it ignores every transform (the five card kinds give one sum) and every scroll (unchanged after `scrollTop = 50`), and a transformed card is an `offsetParent`. So a transformed wrapper's size is on the chain, and a centred `DialogContent` that changes size changes the chain even when the host's own offsets do not (a removal below the host). The chain and the scroll-ancestor list are walked at the hold and again on a frame whose chain changed.
2. **The painted box** of the host, and the painted offset of the stage's own running glides: Σ offsetᵢ · (1 − progressᵢ) through the host's map. N6 shows `getComputedTiming().progress` gives the painted offset to 0.0000 px under the `dock` row's `linear()` easing.
3. **Classify.**
   - **The chain and S unchanged:** no place step, whatever R did (a range change alone paints nothing). Nothing is glided. The lens is laid and the reach re-read if the painted box changed (§S14-f).
   - **The chain unchanged, S changed:** a scroll asked for, carried. The one exception is a scroller whose range shrank in this frame and whose offset now sits at the new range end. That is the engine's clamp, and it is a place step.
   - **The chain changed:** a place step on this frame. Every S change in this frame is the engine's consequence (anchoring, a clamp, a re-snap) and belongs to the step.
4. **Measure the step on paint.** The step is s = (P°₋₁ − P°₀), the painted displacement over the frame of the host's **reference point**, glide-free. On each axis, the reference point is the host's start edge, centre or end edge, whichever the chain moved least (b.5); when the host's size is unchanged, that is its centre. For a point other than the centre, P° is the painted centre plus J·u, where u is the point's offset from the centre in the host's px. Its compensation t is the `translate`, in the host's own px, that paints the host at P₀ + s on top of every running glide. t is solved on the engine's own paint by paused composite-add probes of the host's `translate` (F2: applied in the same task, equal to the inline write, both engines):
   - **affine carrier:** one solve through the probe map is exact (the map is linear);
   - **projective carrier:** true Newton, the map re-asked at each iterate (3 probes per iteration), at most 4 iterations. N11 reads the residual per iteration;
   - **seed:** when the step is in the host's own frame (the offsets changed only between the host and its nearest transformed `offsetParent`), the seed is −Δ of the chain's integer offsets. The engine paints that compensation exactly under any map (N11: "inside −Δ" 0.000 px on all 81 members, both engines).
5. **Glide** t on the `dock` row from where the host was painted: `translate` keyframes `[t, 0]`, `composite: "add"`, as cand13's `glide()`. It is written in the resize step and laid out and painted in the same rendering update (N13: a resize-step write is delivered in a second observation round before the next frame).
6. **Remember** P° (glide-free), K and the step s for the next frame.

### b.4 · Scroll, stated

The classification of scroll is the one place S14 needs a rule beyond the two maps. Both a scroll someone asks for and an engine's adjustment change scroll offsets, and the engine paints both the same way. **The rule is geometric and needs no event.** A frame whose chain is unchanged and whose offsets changed is a scroll asked for, except a clamp: the range shrank and the offset now sits at its end. A frame whose chain changed attributes all its offset changes to that layout change.

- Anchoring changes both the chain (the insert) and the offset, and paints still. So s = 0 and nothing is glided.
- A clamp (removal below) shrinks the range and leaves the offset at its new end. So it is a step, and s is its painted move.
- **Stated limits:**
  - A user scroll that lands in the same frame as a layout step is glided with it, by at most that frame's scroll delta. It is continuous and decays on the `dock` row. Its cell is owed in both engines (§S14-c M12).
  - A carrier whose transform shrinks a scroller's range while that scroller sits at its end makes the engine clamp (N1c's mechanism). That clamp is glided as a step on each frame it occurs. A D1 loop at a scroller's end is the member. Its cell is owed in both engines (§S14-c M6).

### b.5 · The host's own size change

When the host's size changes, the step on each axis is the layout displacement of the one point of the host the layout moved least: its start edge, its centre or its end edge on that axis, read from the chain (`offsetLeft`, `offsetLeft + offsetWidth/2`, `offsetLeft + offsetWidth`). If that point did not move (a left-aligned NumberField 9 → 10; a centred one; a right-aligned one), the axis glides nothing. The painted change is the host's own geometry, and the grow's share of it (centre origin, (s − 1)·Δw/2, CA13c §2.5's 2.40 px) is the host's own transform, which is carried. If every point moved (a resize together with a move), the glide is the painted displacement of the least-moved point, P° + J·u, where u is that point's offset from the centre in the host's px and J is the host's map.

### b.6 · A layout-property animation: both families, and the treatment

A script or transition writing `top`, `margin`, `width` or `height` of an ancestor every frame moves the place (K changes every frame) and is meant as a continuous motion (a carrier in intent).

**Treatment:** on a step frame that follows a step frame, the stage glides s − s₋₁, the change of the painted step from the previous frame. It glides only when |s − s₋₁| exceeds the glide floor of 0.5 px (`glide()`'s existing `Math.hypot(dx, dy) < 0.5`, not a new figure), and carries s₋₁, the continuing velocity. After a still frame, s₋₁ = 0, and the frame is an act like any other.

So:
- a constant-rate layout animation is carried exactly after its first frame, and that onset step is glided home on the `dock` row;
- an eased layout animation is carried except the part of its frame-to-frame acceleration above 0.5 px, which is glided;
- an insert during a running layout animation is glided in full (40 px over a step of 2.7 px a frame).

**Range:** rates 0-1000 px/s; eased transitions of 150-600 ms over 20-200 px (`ease`, `linear`, the `dock` row); constant script ramps; onset from rest and from a running glide. The reason it bounds the family: the glided quantity is the second difference of the place, which for a constant rate is 0 at any rate, and for an eased transition peaks at its largest acceleration, highest at the shortest duration and longest travel (150 ms over 200 px). **Stated limit, read owed in both engines:** an eased layout animation shorter than about 300 ms trails its ancestor by the glided acceleration, at most the largest |s − s₋₁| of its run.

### b.7 · The stage's own glide lands

K does not see a `translate`. So no frame of a running glide is a step, nothing re-glides it, and it reaches 0 on its clock. D2's failure (a 40 px insert that never arrives under a page loop: 43 glides in Chromium, `+358 ms` 0.0 px moved, CE13c D2) has no mechanism here: the page loop's text writes change no offset, and the insert is one step frame and one glide.

### b.8 · The released host

A released host stays on the stage until its animations finish (cand13's `leave()`), and **the frame read continues for it until then** (cand13 stopped the loop at release and read the leaving host only on scroll, resize and records, D3). Under the frame read, D3 (the released host gliding an ancestor's scale transition on the next unrelated record) has no mechanism: the ancestor's transition is a carrier, and the unrelated append changes no offset of the host's chain. The loop stops when the last host leaves the stage, so at rest nothing runs (CK-16).

### b.9 · The lens

- **The lens is laid level, at the subject's painted scale, read as the axis lengths of the subject's probe map**: √(a² + c²) and √(b² + d²), painted px per CSS px along each of the subject's own axes (cand12's reading).
- **cand13's bounding-box ratio is deleted (E-1).** N8 reads both, identically in both engines:
  - axis lengths are 1.0000 / 1.0000 under `rotate(10deg)` on every track aspect, while the box ratio reads 0.9883 / **9.6672** on 300 × 6 and 1.0791 / 1.3047 on 140 × 76;
  - under `rotate(10deg) scale(0.8)`, 0.8000 / 0.8000 against 0.7906 / 7.7338;
  - under `skewX(15deg)`, 1.0000 / 1.0353 = 1/cos 15°;
  - under `rotate(90deg)`, 1.0000 / 1.0000 against 0.0200 / 50.0000;
  - under `perspective(400px) rotateX(40deg)`, 1.0048 / 0.8187.
- **The lens's room is its CSS height × the subject's axis length along y**, so the side it turns to no longer reads the lens 4-10× tall (CA13c §2.4: "hung below").
