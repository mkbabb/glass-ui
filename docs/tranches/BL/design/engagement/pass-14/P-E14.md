## S14-0 · In brief

1. **The invariant is stated on paint (§S14-a).** The held host's painted place, read once per frame, never steps on the frame a re-render lands (≤ 0.5 px on the act's frame) and never moves more than H14's 16.7 ms bound between frames, measured against what carries it. What carries it is the composite of every transform between the host and the viewport and the scroll the user or a script asks for. Its place is where the engine lays it out, at every level of the layout tree. A carrier move is carried, at any rate. A place step is glided from where it was painted. The stage's own glide is invisible to its own read, so it lands.
2. **The decomposition, chosen (§S14-b): the engine's layout separates the two families, and the engine's paint measures the step.** Every frame a host is on the stage (engaged, or on its exit clock), the stage reads in the frame's resize step, after layout and before paint, without writing:
   - the **layout key** **[F2]**: the host's place **Q**, its border-box position in the root's layout frame (the offset chain plus each offsetParent's client edge, so that a link joining or leaving the chain moves Q by its rounding only, Y1); the offset of each level; the host's offset size; the size of each link that carries a transform-family value; each link's `currentCSSZoom`; each scroll ancestor's offsets and scroll range;
   - the host's **painted box**.

   If the layout key is unchanged, nothing the frame did is a place step. The carrier moved, or nothing did, and the stage writes no glide. If only scroll offsets changed, and no scroll range changed with them, that is a scroll someone asked for, and it is carried; so is the offset that scroll gives a sticky box. Otherwise the frame holds a place step. **[F2]** A step below the nearest transformed link, with no scroll between, is compensated by −Δ of the chain, which is exact under any carrier and any carrier motion (N11, Y6) and needs no probe. Any other step is glided as painted on this frame, solved on the engine's own paint through paused probes (true Newton, the map re-asked each iteration). **No observer hears anything; no record decides anything.** The MutationObserver, `own()` and the record callback are deleted (E-1).
3. **Why this and not the other two constructions (§S14-b.2).** The record-driven glide is finding 3's mechanism. Its plant `plant-child` proves it (CE13c §0.1). A painted-only frame read (painted − now on every frame) cannot tell a carrier from a step: a pure translation of the carrier equals a step in paint, and D1 is exactly that. The split S14 first had in view read the layout box by undoing every ancestor's transform with paused replace animations. **N1 shows that read is exact on every carrier kind but `!important`. N1c shows it is unusable: undoing a transform that extends a scroller's overflow clamps the scroller's offset, permanently, by 68-300 px, with a scroll event, identically in both engines.** So the layout is read from the engine's own layout values, the offset chain, which reads no paint and writes nothing (N12).
4. **A layout-property animation belongs to both families (§S14-b.6).** S14 carries its velocity and glides only its change from frame to frame. The step glided on a frame that follows a step is the difference of the two steps, and it is glided only if it exceeds the glide floor (0.5 px, `glide()`'s existing figure). So a constant-rate layout animation is carried exactly. An insert during it is glided. Its onset frame is glided like any act, and every acceleration beyond the floor is glided. **[F2]** A still frame resets the carried velocity only when that velocity is at least one layout px a frame, the chain's resolution, so a slow animation's integer still frames no longer restart it (Y7). A train of equal steps on consecutive frames is, in paint, a place moving at constant velocity, and it is carried after its onset by design (§S14-b.6).
5. **The members (§S14-c)** carry a range each, with the reason the range bounds the family. Every member cand12 or cand11 passes is a row with that build as the passing reference and cand13 as the plant where cand13 fails. **[F2]** The **stated limits**, each with its read (or the cell owed) in each engine:
   - a sub-pixel step that changes no rounded offset, and a link joining or leaving the chain (its rounding, at most 1 px per link, Y1);
   - a carrier move in the same frame as a step that is measured on paint (M6, now bounded at its extremal cell);
   - the extremal projective corner;
   - a user scroll in a step frame, or in a frame whose scroll range changed;
   - anchoring caused off the host's chain with the scroll range unchanged (Ch-F1);
   - another resize observer's write after the stage's read (Ch-F4);
   - an `!important` `translate` on the host, which blocks the probe and the glide and is refused loud at the hold (Ch-F5);
   - a layout animation under uneven frames, and an outside layout animation under a looping carrier (Ch-F12);
   - the probe's own clamp hazard;
   - a context-relative gutter;
   - a consumer's own `transition: all` on the host's `::before` (the read's new seat, Y5).
6. **The token reads move into the stylesheet (§S14-e).** Each token the engagement reads becomes a registered property *declared* on the member's own class, as its consumer's own expression, read back by `getComputedStyle`. **[F2]** It is declared on that class's `::before`, which the host's own transition list does not reach (Y5), so a class arriving under `transition: all … allow-discrete` (Ch-F8) and a token changed at runtime (N4) read exactly. There is no inline write, so no `style=""` (class 3), no record and no `own()`. The names move outside `--engage-*` (`--stage-read-*`, class 1, CK-09). The refusal is an ident (`<time> | stage-unset`), which no math form computes to, so no sentinel collides with a value (N5). The clock is read as the consumer computes it, root-substituted (N9), and clamped as `transition-duration` clamps it, so `--motion-tempo` ≤ 0 runs the clock CSS runs: 0, instant, no error. **N9 also finds a counterexample on cand13 by the bytes:** `rowClockMs` reads `var(--spring-dock-settle) × motionTempo(host)` on the host, while the consumer's `--spring-dock-duration` is substituted at `:root`. So a nearer override of the settle or the tempo makes the script run 1 s or 0.21 s where CSS runs 0.21 s or 0.42 s.
7. **CK-04's frame (§S14-f)** is re-read on every frame the host's painted box or its layout key changes. That includes D9's card scaled about the held control.
8. **CK-22 (§S14-g)** lists every header and comment sentence P-E14 rewrites or deletes, and seven MIGRATION rows.
9. **Cost (§S14-h).** The construction removes the document-wide observer, the per-record callback and every forced read inside it. It adds, per engaged frame, a layout-key read with layout already clean. On a step frame it adds the probes (at most 3 plus 3 per Newton iteration). The plan prices the drag's forced work beside cand12 and CPU per frame held still beside cand8, cand11, cand12 and cand13, and adds two cells this construction needs: a carrier loop and a step frame.

## S14-a · The invariant, stated on paint

The row asks for continuity in paint (§P1-6 CK-20: "no one-frame discontinuity on any engagement transition"). S14 starts there.

**(a.1) What is read.** The held host's painted place, once per frame, at the frame's resize step, after layout and before paint (N2, N13), at the frame's one animation time. The place is the host's painted box (`getBoundingClientRect()`), and its centre is the point the harness grades.

**(a.2) What carries the host.** The painted map from the host's layout box to the viewport is a composition of two maps, and the engine computes them separately:

- **the carrier**: every transform-family value between the host and the viewport (`transform`, `translate`, `rotate`, `scale`, a perspective, an origin or percentage resolved against a size), whatever writes it (a stylesheet, a CSS transition or animation, WAAPI, a script writing inline style every frame, a custom property such a value reads), plus every scroll offset the user or a script asks for, **and the offset that scroll gives a `position: sticky` box on the chain [F2]** (the stick moves the box in layout by at most the scroll's own delta, Y3). A **constant** CSS zoom is in the map the probe reads;
- **the place**: the host's layout position at every level of the layout tree. Any box above it laying out differently moves the place: an insert, a removal, a size change, a font or sheet arriving, a shadow tree, a form control's own size, a pseudo-class restyle, **and a change of CSS zoom on the host, an ancestor or a box before it [F2]**. Zoom is layout, not a transform: it lays the zoomed boxes out at a new size and moves every box after them (X8, Y2; Ch-F9). So does any scroll offset the engine sets as the consequence of a layout change: an anchoring adjustment, a clamp when the scroll range shrinks, or a re-snap.

**(a.3) The invariant.**

- **A move of the carrier is carried and never resisted, at any amplitude and any rate.** The stage writes nothing for it.
- **A step of the place is glided from where the host was painted**, on the `dock` row, so that on the step's own frame the painted place moves ≤ 0.5 px (the act's bound) and over any 16.7 ms by no more than H14's bound for a glide of that size.
- **[F2] A place moving at constant velocity is carried after its onset, whatever moves it** (a layout animation, or a train of equal steps on consecutive frames). Its onset, and every departure from its velocity, is a step and is glided (§S14-b.6). Its stop is not a step. A place that steps with still frames between its steps is glided at each step.
- **The stage's own glide is not a move of either kind.** The layout key does not see it (a `translate` is a carrier value and changes no offset), so nothing re-glides it, and each glide runs to its end and lands.
- **A step's paint includes what the step paints through the carrier's size-resolved values.** A percentage `translate` or a `50%` origin moves when the box it resolves against changes size. The Dialog's re-centring is this case. It is part of the step and is glided with it on the step's frame. On every other frame the carrier is carried.

**(a.4) What the invariant does not ask.** It does not ask the host to stay still in the viewport when its carrier moves. A script scrolling the page, a card the author rotates or translates every frame, or a Carousel scaling its member all move the held host with what holds it. The held control never comes apart from its card (CE13c §3: "a held object coming apart from what holds it" is the failure). It does not ask a size change of the host itself to be glided: the size step is the host's own geometry, and only a move of a point the layout keeps fixed is a place step (§S14-b.5).

## S14-b · The decomposition, chosen and defended by painted geometry

### b.1 · The construction

Per frame, in the resize step, for each host on the stage (engaged, or released and on its exit clock; §S14-b.8). Every read comes first, and every write after.

1. **The layout key K [F2].** It is read from the engine's layout values only. Each is a read of clean layout in the resize step (N13), and none reads paint. K has these parts:
   - **the links**: the host and each element on its `offsetParent` chain, and for each link its `offsetLeft`, `offsetTop`, `offsetWidth` and `offsetHeight`;
   - **the place Q**: Σ (`offsetLeft`, `offsetTop`) over the links, plus Σ (`clientLeft`, `clientTop`) of each link's `offsetParent` other than `<body>`. This is the host's border-box position in the root's layout frame. `offsetTop` is measured to the offsetParent's padding edge, so the raw sum moves by that parent's border when a link joins or leaves the chain; Q does not. Y1 reads it in both engines: a transform, `will-change`, `contain`, `filter`, `perspective` or `offset-path` onset on a bordered card (and a `position` control) moves the raw sum by (−3, −2) and **Q by (0, 1) on a fractional layout and (0, 0) on an integer one**;
   - **the level offsets**: each link's own offsets, so a change can be placed at the level where it happened (step 4);
   - **the host's offset size** (b.5);
   - **the size of each link that carries a transform-family value** (computed `transform`, `translate`, `rotate`, `scale` or `offset-path` other than `none`), read only on a frame where that link's offset size changed. Such a link's transform can resolve against its size (an origin, a percentage; the library's `DialogContent` is `translate: -50% -50%`, `dialog/styles.css:32`), so its size change is a place step painted through the carrier (a.3, last item). A size change of a link that carries no transform moves the host only through Q, and Q decides it. That is Ch-F11's trigger, narrowed: X1 (e)'s insert below the host in a positioned card leaves Q unchanged and is no step;
   - **each link's `currentCSSZoom`** (Y2: an ancestor's zoom change shows on the host's own link on the frame it lays out, `1 → 1.25`, both engines);
   - **the scroll offsets S**: `scrollLeft` and `scrollTop` of each scroll ancestor (an element whose `overflow` scrolls, and the root);
   - **the scroll ranges R**: `scrollWidth − clientWidth` and `scrollHeight − clientHeight` of the same ancestors;
   - **the sticky links**: each link whose computed `position` is `sticky`, with its scroll ancestor.

   N12 reads what the offsets are: they ignore every transform and every scroll (unchanged after `scrollTop = 50`), and a transformed card is an `offsetParent`. **Corrected (Ch-F14):** the raw sum is 110, 131 under the static card and 110, 132 under the other four kinds, in both engines (`S14-records/logs/facts14-*.log`, N12). The extra px is the transformed card's own link and its rounding, which is Ch-F2's mechanism, and Q is defined to absorb it. The links, the sticky links and the scroll-ancestor list are walked at the hold and again on a frame whose link set changed. `position` and the transform-family values are read only on those frames and on a frame where a link's size changed.
2. **The painted box** of the host, and the painted offset of the stage's own running glides: Σ offsetᵢ · (1 − progressᵢ) through the host's map. N6 shows `getComputedTiming().progress` gives the painted offset to 0.0000 px under the `dock` row's `linear()` easing.
3. **Classify [F2].** In this order:
   1. **Sticky.** For each sticky link whose scroll ancestor's offset changed by ΔS on an axis this frame, the link's own offset change on that axis, up to |ΔS| and in ΔS's direction, is the scroll's: it is carried and taken out of that level's change. The rest is layout. Y3 reads this in both engines on every frame of a top-sticky box (page and scroller), a bottom-sticky box and a top-sticky box pushed off by its containing block's end: the sticky link's change is 0 before the stick, 50 against a scroll of 60 on the stick frame, equal to the scroll while stuck and 30 against 60 on the release frame. An insert above an unstuck sticky box with no scroll is 40 of layout, a step (Ch-F3).
   2. **Links joined or left.** If the link set changed, a change of Q on an axis no larger than the number of links that joined or left is their rounding (Y1), and it is no place step. A larger change is a step measured on paint (step 4), less nothing for the rounding. That is M10's class.
   3. **Zoom.** If a link's `currentCSSZoom` changed, the frame is a place step measured on paint (step 4). Q's units change with the zoom (Y2: 80 → 72 while the paint moves 7.5 px), so Q cannot measure it.
   4. **Q or a level offset changed** (after 1 and 2): a place step.
   5. **A transform-carrying link changed size:** a place step measured on paint (the size-resolved share; the Dialog).
   6. **Q and the level offsets unchanged, S changed:** if that scroller's range R changed in this frame, the change of S is the engine's (a clamp, a re-snap, any adjustment the range forced), and it is a place step measured on paint. Otherwise it is a scroll asked for, and it is carried. This replaces "a clamp: the range shrank and the offset sits at its end" with the rule that covers it (Ch-F6; b.4).
   7. **Nothing changed** (whatever R did alone, which paints nothing): no place step. Nothing is glided. The lens is laid and the reach re-read if the painted box changed (§S14-f).

   A step's S changes in the same frame belong to it (anchoring, a clamp, a re-snap), as before.
4. **Measure the step [F2].** The step has up to two parts.
   - **In the host's frame, by the chain.** On a frame where no scroll ancestor's offset changed (the root's included), the part of the step at levels below the nearest link that carries a transform-family value is compensated by **t = −Δ** of those levels' integer offsets, in the host's px. The engine paints that compensation exactly under any map, and under any motion of the carrier between the two reads: N11 reads 0.000 px on all 81 perspective members, and Y6 reads 0.000 px against an identical twin card under a running translate, a running rotate, and a perspective tilt with a running translate, for inserts of 40 and 120 px, in both engines. The one exception is a WebKit translate cell at 0.427 px, which is the instrument's: H13c F4's up-to-1 ms sample drift between the twin's read and the card's. This part needs no probe, and it holds none of the carrier's motion, so Ch-F11 and Ch-F12 cannot reach it. A frame with any scroll change is excluded, because anchoring in any scroll ancestor (the page's own included) moves the scroller and keeps the paint still (N3), and −Δ would then glide a move that did not paint.
   - **On paint, for the rest.** Every other step (a level above the transformed link, any step on a frame with a scroll change, links joined with a step, a zoom change, a transform-carrying link's size change, the engine's scroll adjustment) is s = (P°₋₁ − P°₀), the painted displacement over the frame of the host's **reference point**, glide-free, less the paint of the in-frame part when both occur. On each axis, the reference point is the host's start edge, centre or end edge, whichever the chain moved least (b.5); when the host's size is unchanged, that is its centre. For a point other than the centre, P° is the painted centre plus J·u, where u is the point's offset from the centre in the host's px. Its compensation t is the `translate`, in the host's own px, that paints the host at P₀ + s on top of every running glide. t is solved on the engine's own paint by paused composite-add probes of the host's `translate` (F2: applied in the same task, equal to the inline write, both engines):
     - **affine carrier:** one solve through the probe map is exact (the map is linear);
     - **projective carrier:** true Newton, the map re-asked at each iterate (3 probes per iteration), at most 4 iterations. N11 reads the residual per iteration.

     This part holds that frame's carrier motion at the host, which is M6's stated limit (§S14-c), now with its bound at the extremal cell.

   **Considered and not adopted: Ch-F11's lead, "J · Δ in the frame where Δ occurs", for every step.** J is the host's probe map, and it holds every transform between the host and the root, the host's own included. A step above a transformed link paints through the maps above that link only. Under a card at `scale: 0.5`, a 40 px move of the card in layout paints 40 px, while J · Δ is 20 px. Reading the map at each level would need probes on ancestors, which carry N1c's and M21's clamp hazard to every level. So J · Δ is exact only below the nearest transformed link, which is exactly where −Δ already applies, and there no probe is needed at all. The lead is adopted in that form.
5. **Glide** t on the `dock` row from where the host was painted: `translate` keyframes `[t, 0]`, `composite: "add"`, as cand13's `glide()`. It is written in the resize step and laid out and painted in the same rendering update (N13: a resize-step write is delivered in a second observation round before the next frame).
6. **Remember** P° (glide-free), K and the step s for the next frame.

### b.2 · Why this decomposition, and not the other two

| construction | what separates carried from stepped | fails on | status |
|---|---|---|---|
| **record-driven** (cand13: a MutationObserver on `<html>`, painted − now at the record) | which observer heard which record | an animation made of records (D1, the Carousel's `--member-scale`), a record that starts an animation (CA13c §2.2), a page loop writing every frame (D2), moves with no record (CA13c §2.3), the released host (D3). The plant `plant-child` passes D1, D2 and D5 where cand13 fails (CE13c §0.1). This is finding 3, of record in both engines | **replaced** |
| **painted-only frame read** (painted − now on every frame; H13 §1.1 (i)) | nothing: one painted point per frame cannot tell a carrier translation from a place step of the same vector | every D1 member (a script writing the card's `translate` per frame is, in paint, a step every frame) | **not chosen**, by the geometry: it has no second quantity to separate the families |
| **carrier map × layout offset, the layout read by undoing transforms** (paused replace animations of `transform`, `translate`, `rotate`, `scale` on the host and every ancestor) | the engine's layout box (N1: exact against the transform-free control, 0.000 px, under a stylesheet rotate, an inline translate, a perspective, a mid-flight CSS transition, a running `@keyframes`, a running WAAPI add, nested rotate and scale, and the host's own scale and glide; 0 records; every running animation's time unchanged) | **N1c: undoing a transform that extends a scroller's scrollable overflow clamps its offset, and it stays clamped after the cancel** (both engines, identical: −300, −100 and −68 px for `translate: 0 300px`, `scale: 2`, `rotate: 30deg`, under both `overflow-anchor` values, one `scroll` event each). The choice is defended by the geometry the engine paints. The two families are the two halves of the painted map (a.2). The engine computes them apart: the layout tree, then the transform and scroll tree. It exposes the first through the offset chain, which no transform or scroll changes (N12). It exposes their composition through paint. The decomposition reads each half where the engine keeps it. No observer is consulted: a move with no record changes K on the frame it lays out (N2: the field-sizing, shadow, `<link>` and `insertRule` moves each show in the resize step of the frame they first lay out).

### b.4 · Scroll, stated [F2]

The classification of scroll is the one place S14 needs a rule beyond the two maps. Both a scroll someone asks for and an engine's adjustment change scroll offsets, and the engine paints both the same way. **The rule is geometric and needs no event.**
- A frame whose place Q and level offsets are unchanged, whose scroll offsets changed and whose scroll ranges did not change is a scroll asked for, and it is carried.
- A sticky link's offset change, up to the scroll's own delta and in its direction, is that scroll's (b.1 step 3.1; Y3). So the frame a box sticks, the frames it stays stuck, the frame it lets go and the frame its containing block pushes it are all carried. As written before the fold, the stick frame glided the 10 px of the asked scroll that went by before the stick (X2, Ch-F3). That has no mechanism now.
- A frame whose scroll range changed attributes every scroll change on that scroller to the engine (a clamp, a re-snap, an anchoring adjustment the range forced). It is a place step, measured on paint. This is the old clamp rule widened to every range change, so it covers the re-snap X4 read in WebKit (Ch-F6): the snapped item grows, the range grows on that frame, and WebKit's re-snap of 50 px is glided, not cut.
- A frame whose place changed attributes all its scroll changes to that layout change, as before. Anchoring of an insert on the host's chain changes both Q and the offset and paints still, so s = 0 and nothing is glided (N3).

**Stated limits, each with its read:**
- **A user scroll in a step frame, or in a frame whose range changed,** is glided with the step, by at most that frame's scroll delta (1-400 px a frame, M12's range). It is continuous and decays on the `dock` row. Its cell is owed in both engines (§S14-c M12).
- **Anchoring caused off the host's chain, with the range unchanged** (Ch-F1). An insert above the engine's anchor node in a sibling column, a sibling grid cell or a sibling flex item scrolls the scroller and leaves the host's place and the range unchanged. The rule reads that as a scroll asked for and carries it, so the host is cut by the adjustment: X3 reads **40.000 px**, page and scroller, both engines. Y4 reads that focus does not change it: the same 40.000 px with the host focused, as a `tabindex` div and as an `<input type=range>`. So a focused held control is not an anchor priority candidate in either engine. The cut is the size of the insert, 20-200 px across M13's range. **Why it is a limit and not a cure:** the engine does not expose its anchor node, and nothing on the host's chain or in the scroller's range changes. The only quantity that would separate this from an asked scroll is the layout of boxes off the chain, and reading that means reading every box in the scroller on every frame. The stage does not take that cost, and it does not write `overflow-anchor` on the consumer's scroller: that would be a write to the consumer's page that changes its own anchoring for every other box. H14's cell: X3's two scenes with inserts of 20-200 px, the anchor in a sibling column, a sibling grid cell and a sibling flex item, both engines, with the cut read as the limit.
- **A carrier whose transform shrinks a scroller's range while that scroller sits at its end** makes the engine clamp (N1c's mechanism). The range changes, so the clamp is glided as a step on each frame it occurs (rule 6). A D1 loop at a scroller's end is the member. Its cell is owed in both engines (§S14-c M6).

### b.5 · The host's own size change

When the host's size changes, the step on each axis is the layout displacement of the one point of the host the layout moved least: its start edge, its centre or its end edge on that axis, read from the chain (`offsetLeft`, `offsetLeft + offsetWidth/2`, `offsetLeft + offsetWidth`). If that point did not move (a left-aligned NumberField 9 → 10; a centred one; a right-aligned one), the axis glides nothing. The painted change is the host's own geometry, and the grow's share of it (centre origin, (s − 1)·Δw/2, CA13c §2.5's 2.40 px) is the host's own transform, which is carried. If every point moved (a resize together with a move), the glide is the painted displacement of the least-moved point, P° + J·u, where u is that point's offset from the centre in the host's px and J is the host's map.

### b.6 · A layout-property animation: both families, and the treatment [F2]

A script or transition writing `top`, `margin`, `width` or `height` of an ancestor every frame moves the place (Q changes every frame) and is meant as a continuous motion (a carrier in intent).

**Treatment.** The stage carries the place's running velocity v and glides only the step's departure from it. On a step frame the departure is d = s − v, where s is the frame's step in the measure b.1 step 4 gives it: −Δ of the chain's integer offsets in the host's frame, or the painted step otherwise. The stage glides d when |d| exceeds the measure's resolution, and then v = s. **The resolution is the measure's own, not a new figure:** 0.5 px for a painted step (`glide()`'s existing `Math.hypot(dx, dy) < 0.5`), and 1 layout px for the chain's integer step (N12: one rounding per link). **A still frame resets v to 0 only when |v| exceeds that resolution.** Below it, a still frame is the chain's rounding of a motion slower than one px a frame, not a stop (Ch-F7 (ii)).

So:
- a constant-rate layout animation is carried after its first frame, at any rate, and its onset is glided home on the `dock` row;
- a slow one (under one layout px a frame) is carried through its integer still frames. Y8 reads X10's ramps on the chain's integer step: §S14-d gives the counts, as written and folded, in both engines;
- an eased layout animation is carried except the part of its frame-to-frame acceleration above the resolution, which is glided;
- an insert during a running layout animation is glided in full: its frame's step is the animation's v plus the insert, so d is the insert;
- **a train of equal steps on consecutive frames is a place moving at constant velocity, and it is carried after its onset** (Ch-F7 (i)). This is the statement, by design, and a.3 now says so. In paint, a 16 px line inserted above the held control on every frame is the place moving at 960 px/s. Nothing on the chain, in the scroll or in paint separates it from a `margin` ramp at that rate, and the invariant does not ask the stage to. The row forbids a one-frame discontinuity (CK-20). A place moving at constant velocity has none after its onset, so the stage glides the onset and carries the motion with the page, as it carries a carrier. A train with a still frame between its steps (every second frame) has a discontinuity at each step, and each step is glided. So the treatment follows whether the place's motion is continuous in paint, which is what the invariant reads. It does not follow what made the motion, and the challenge's "sorts by mechanism" does not apply: no mechanism is read;
- the stop of a layout animation is not glided. The place's velocity drops to 0, and the place does not step.

**Stated limits, each with its read:**
- **Uneven frames.** Under frame-time jitter, a script ramp's per-frame step changes from frame to frame, and each change above the resolution is glided, by at most one frame's motion of the animation. Y7 reads a 200 px/s ramp measured on paint. In Chromium (120 frames/s, load 11-13) it is 21 glides and 15.06 px on one run and 6 glides and 4.52 px on the next. In WebKit (60 frames/s) it is 12 glides and 10.97 px. On the chain's integer step (Y8) the folded rule glides 0-1 times on ramps up to 200 px/s and 3-5 times (7-14 px) at 400 px/s, in both engines. **Considered and rejected: a per-time velocity** (the expected step v · dt, from the frame's own timestamp delta). On the same ramp it reads 36 glides and 27.75 px in Chromium and 28 glides and 27.84 px in WebKit (Y7). A script ramp lays out from the time it read, not from the frame's, so the frame's interval misattributes its step.
- **An outside layout animation under a looping carrier** (Ch-F12). When the layout change is above a transformed link, it is measured on paint. If that link's transform loops, the painted step holds the carrier's frame-to-frame change, so d holds the carrier's acceleration. For M5's sine of 80 px at 200 ms and 60 frames/s that is 80 · (2π/0.2)² / 60² = **22.0 px a frame**; at 600 ms it is 2.4 px. That is glided every frame, so the carrier is resisted by its acceleration. A layout animation inside the card (below the transformed link) is measured by −Δ and holds none of it (Y6). M28's row; the cell is owed in both engines.

**Range:** rates 0-1000 px/s; eased transitions of 150-600 ms over 20-200 px (`ease`, `linear`, the `dock` row); constant script ramps of 0.2-2 px a frame, which is the band around the chain's resolution at both engines' frame rates; step trains of 8-40 px, every frame and every second frame; onset from rest and from a running glide. The reason it bounds the family: the glided quantity is the second difference of the place. For a constant rate it is 0 at any rate. For an eased transition it peaks at its largest acceleration, which is highest at the shortest duration and longest travel (150 ms over 200 px). **Stated limit, read owed in both engines:** an eased layout animation shorter than about 300 ms trails its ancestor by the glided acceleration, at most the largest |d| of its run.

### b.7 · The stage's own glide lands

K does not see a `translate`. So no frame of a running glide is a step, nothing re-glides it, and it reaches 0 on its clock. D2's failure (a 40 px insert that never arrives under a page loop: 43 glides in Chromium, `+358 ms` 0.0 px moved, CE13c D2) has no mechanism here: the page loop's text writes change no offset, and the insert is one step frame and one glide.

### b.8 · The released host [F2]

A released host stays on the stage for its own exit clock, and **the frame read continues for it until then** (cand13 stopped the loop at release and read the leaving host only on scroll, resize and records, D3). Under the frame read, D3 (the released host gliding an ancestor's scale transition on the next unrelated record) has no mechanism: the ancestor's transition is a carrier, and the unrelated append changes no offset of the host's chain.

**The exit is bounded by clocks the stage already reads, not by the subtree's animations (Ch-F10).** cand13's `leave()` awaits every subtree animation whose `endTime` is finite (`stage.ts:420-424`). X11 reads, in both engines, that a paused finite animation and a `view()`-timeline animation (`endTime` NaN, which passes the filter) never settle in 1.5 s. Under a per-frame read for released hosts, either one would keep the loop running at rest indefinitely. The library ships both forms: `animation-play-state: paused` in `sortable-list/styles.css:256`, `StatusDot.vue:286` and `Skeleton.vue:112`, and `view()` timelines in `styles/scroll-choreography.css:114, 120`. So the released host leaves the stage at the **later** of two times:
- the end of its own running glides (the stage's animations, finite by construction on the `dock` row);
- release plus the longest of the clocks the stage reads for it: `--stage-read-clock` (the glide, carry and `--rung-grow` clock) and its class's release clocks (`--stage-read-<role>-release`, §S14-e).

A clock that reads 0 makes the exit immediate. A refused clock (`stage-unset`) is loud at the hold already, and the exit then ends with the host's glides. `leave()`'s `getAnimations({ subtree: true })` wait is deleted (E-1). A step during a longer exit animation of the consumer's own, after the bound, is the consumer's motion on a host that is no longer on the stage, like any element at rest. The loop stops when the last host leaves the stage, so at rest nothing runs (CK-16), whatever runs in a released host's subtree. H14's cell: X11's four forms in a released host's subtree, with CK-16's 0 rAF/s read after the bound.

### b.9 · The lens

- **cand13's bounding-box ratio is deleted (E-1).** N8 reads both, identically in both engines:
  - axis lengths are 1.0000 / 1.0000 under `rotate(10deg)` on every track aspect, while the box ratio reads 0.9883 / **9.6672** on 300 × 6 and 1.0791 / 1.3047 on 140 × 76;
  - under `rotate(10deg) scale(0.8)`, 0.8000 / 0.8000 against 0.7906 / 7.7338;
  - under `skewX(15deg)`, 1.0000 / 1.0353 = 1/cos 15°;
  - under `rotate(90deg)`, 1.0000 / 1.0000 against 0.0200 / 50.0000;
  - under `perspective(400px) rotateX(40deg)`, 1.0048 / 0.8187.

### b.10 · An `!important` `translate` on the host: refused loud at the hold [F2]

The probe (b.1 step 4) and the glide (b.1 step 5) are WAAPI animations of the host's `translate`, and an author `!important` declaration beats them. X5 reads this in both engines, identically: under a sheet `translate: 10px 0 !important`, an inline `!important` and `translate: none !important`, a (40, 0) probe moves the box (0.000, 0.000), and a running 40 px add glide paints 0.000 px. `transform: rotate(10deg) !important` does not block them (40.000). §S14-0 item 5 had called the `!important` case "moot for the chosen read". It is moot for K, but not for the probe or the glide (Ch-F5).

**The stage's answer.** At the hold, the stage probes the host's map anyway: §S14-f reads its axis lengths there. A probe that moves the box 0.000 px on both axes means a declaration the stage cannot animate owns the host's `translate`. The stage then writes **one `console.error` naming the host and `translate !important`**, once per host (cand13's `loud`). It engages without probes or glides on that host, so every place step during that hold is cut. The reach (`--stage-reach`, an inline custom property) and the lens still work. The same check covers the lens's subject. This is E-2: the primary does not work on that host, and it says so at the hold, by name. It never runs a fallback that hides it. The ordinary consumer form is Tailwind's important modifier (`!translate-x-*`). H14's cell: X5's three blocking forms, the `transform !important` control, and the error counted once per hold.

### b.11 · Another resize observer's write after the stage's read [F2]

The stage reads in its own ResizeObserver callback. X7 reads the case where another observer inserts 40 px above the host in its own callback in the same resize step:
- the other observer created **before** the stage's: Chromium sees the write (90.0); WebKit misses it (50.0);
- created **after** the stage's: both engines miss it;
- the write made in a **second** delivery round: both engines miss it.

A missed write is laid out and painted on that frame unglided (N13), so it is a cut. On the next frame K has changed against the remembered pre-write state, and the stage glides from the pre-write place, so the host returns by the write and glides home. **Stated limit (Ch-F4):** a write by a resize observer delivered after the stage's read is cut on its frame and then glided from the place it had before. Read in both engines (X7); in WebKit it holds for every observer order.

**Why no cure.**
- No callback runs after the last observation round and before paint.
- A re-base read after paint (a posted task) would also take in writes from tasks queued ahead of it, which have not painted. Those would then be cut instead.
- Re-creating the stage's observer each frame would put it last in round 1 in Chromium only. It would still miss round 2, and it would miss every order in WebKit.

The library's own observers that could write above a held control are `dock/composables/dockMorphMeasure.ts`, `data-table/composables/useDataTableResponsive.ts`, `fading-scroll/composables/useFadingScroll.ts`, `ToggleGroup.vue` and `morph/useSelectionIndicator.ts`. H14's cell is X7's three orders in both engines. H14 also states, for each of those five, whether it writes layout above a held control in any library scene, by reading its callback's writes.
