**The frame.** In P-E10, `paintedScale(el)` walked the transforms and `scale`s from `el` up to the first top-layer box. In P-E11 it is split into three parts:
- `ownScale(e)`: one box's own `transform` and `scale`.
- `frameOf(el)`: `el`'s ancestors' `ownScale`, stopping at the first top-layer box (none for a top-layer box itself), times `el.currentCSSZoom`. This is the painted size of one CSS px that the stage writes on `el`. The zoom is inherited in the top layer, so the popover lens carries its card's zoom: its frame is its zoom.
- `paintedScale(el) = ownScale(el) × frameOf(el)`.

Every write goes through it:

| write | P-E10 | P-E11 |
|---|---|---|
| `--lens-dx/-dy` | the painted correction, written as CSS px | painted correction ÷ `frameOf(lens)` |
| `--lens-sx/-sy` | the subject's transforms only | `paintedScale(subject) ÷ frameOf(lens)` (the subject's zoom over the lens's) |
| the side test | `t.top − lens.offsetHeight × s.y`, with `offsetHeight` unzoomed against painted `t` | `t.top − lens.offsetHeight × paintedScale(subject).y`: the lens's painted height at rest |
| the travel's span | painted px handed to `translate` | painted ÷ `frameOf(lens)`, stored in the lens's px |
| `owed` | `span × (1 − progress)` | `span × frameOf(lens).y × (1 − progress)`: back to painted px, where the correction is computed |
| `--stage-room` | painted centre against unzoomed `offsetWidth` | the host's painted width (`offsetWidth × frameOf(host)`) against its painted centre; the room ÷ `frameOf(host)` |
| the host's re-render glide (`flowBox`) | the sum of offsets, each in its own box's px | each offset × `currentCSSZoom(box) / currentCSSZoom(host)`, so the sum is in the host's px |

**Why layout reads take the zoom ratio and not the frame.** A transform maps an offset and a `translate` alike, as P-E10's glide comment said. Converting offsets through the transforms would turn an ancestor's running scale animation into a moved place, and the next unrelated mutation would glide it. Zoom is different: it changes layout px, so it is the one factor that must be carried. The new unit case, "a move outside its zoomed scroller", reads a −32 px glide for a 40 px unzoomed move under `zoom: 1.25`. No browser cell drives the host glide under zoom (§8 item 2).

**`currentCSSZoom` is read with no fallback.** It is typed in the repository's TypeScript (`lib.dom.d.ts`) and both target engines expose it (H11's `zoomfacts`). A `?? 1` would hide a dead read (E-2).

**CK-21.** `glide` reads `--spring-dock` on every travel. `const parsed = easing !== "" && CSS.supports("animation-timing-function", easing)`. If it is not parsed, `loud("--spring-dock", el)` logs once per host, and the move is not travelled. Both the lens's side change and `onMutation`'s host glide call this one function, so both paths are covered by one check. The settle clock was already loud through `rowClockMs`. Nothing throws, so the observer callback completes and lays the lens. That is why "the loop alive" reads true.

**CK-12, the band's reason, answering C-A10's remark ("the band measures scroll, not a hand").** The line moves against the lens only when the control's world moves under the hand: a scroll, a wheel or a carry. That is a relative displacement between hand and world. `HOLD_SLOP_PX` (8) is the register's one figure for how far hand and world part before the register reads intent rather than jitter: "the series rung above coarse-tap jitter (5-10 px)" (`hold.ts:19-25`). Both are viewport px, since pointer coordinates and `getBoundingClientRect` are both read in the viewport. So the band and the slop are the same quantity in the same unit, not a figure borrowed across kinds. The header now says so. No figure is minted.

**The "May" (§P10-7 item 6), declined, with the reason in the header.** A re-press during the exit keeps the side the lens is painted on and travels from it. At the re-press the lens is visible: opacity 0.85-0.89 in Chromium and 0.53-0.57 in WebKit (`repress · moved`, §2.1). A fresh side would cut that visible lens 100 px across its track in one frame, which is pass 9's swap. The REPORT cell reads 27 frames off in Chromium and 19 in WebKit for about 190 ms, the one travel, as on cand10.

**No construction without a side change** was needed. **No lighting layer, no blur token, no radius (O-87, CK-26):** the CSS change is three comment lines.
