## 1 · The derivation (`§P12-8.1` (a), (b))

This section restates H13's derivation (`H13.md` §1, the harness's) where it is the same, and adds what is the library's alone: the inputs the library stage itself writes and reads, and the token consumers in `src/`. The engine facts are H13's `facts13` (Chromium, `H13/logs/facts-chromium.log`) and C-A12's (`pass-12/C-A12/logs/facts-webkit.log`, WebKit 26.5); **H13's own WebKit facts read was never run** (H13 §7), so every WebKit statement here is C-A12's, cited as such, or is marked UNREAD.

### 1.1 · (a) What can move a held host's painted place between two frames

Let `P` be the host's painted centre (the centre of `getBoundingClientRect()`). It is the host's layout place `L`, carried through the paint map `M` of every box from the host to the root, shifted by the scroll offsets of its scrollers, at the document timeline's current time `T`. So between two reads, `P` moves when and only when one of these moves: `L`, `M`, a scroll offset, or `T`. Each is enumerated from the grammar that produces it.

**(a)(i) Layout `L`, moved by script through the DOM.** The DOM's change grammar is the `MutationObserver` record grammar: exactly three record types.
- `childList`: a node inserted or removed (`v-if`, a list re-render). This includes a `<style>` or `<link>` element inserted or removed anywhere under `<html>`, `<head>` included.
- `attributes`: any attribute. It moves layout through three channels: the inline `style` attribute (`v-show`, a `:style` binding), any selector that matches on an attribute (`class`, `[attr]`, `:is([open])`), and the UA rules on attributes (`hidden`, `open`, `popover`).
- `characterData`: a text node's data (a text interpolation reflowing a line). This includes the text of a `<style>` element.

**(a)(ii) Layout `L`, moved with no record.** The members, each named with what can hear it:
- a CSSOM edit (`insertRule`, `deleteRule`, a rule's `style`, `replaceSync` on a constructed or adopted sheet): no record and no event;
- a viewport resize, and every media or container query it flips: the `resize` event;
- a web-font swap, an image decode that sizes a box, a `:hover`, `:focus`, `:active` or `:has()` restyle: no record and no event;
- a scroll: the `scroll` event (a scroll is a move of a scroll offset, (a)(iv), not of `L`).

**(a)(iii) The paint map `M`.** A box's paint map is the CSS transform matrix: `translate`, `rotate`, `scale` and the `transform` list (every transform function: `matrix()`, `matrix3d()`, `translate*()`, `scale*()`, `rotate*()`, `skew*()`, `perspective()`), about `transform-origin`, composed with the parent's `perspective` about `perspective-origin`, with `offset-path` (a motion path) and with `zoom`. Its parts, by what each does to a translate written on the host:
- the linear part (scale, rotation, skew, and every 2D matrix): the move turns and scales (`facts13` C: under `rotate: 10deg` a host translate `0 40px` paints `(-6.946, 39.392)`; under `skewX(15deg)` `(10.718, 40)`);
- the projective part (`perspective`, any 3D function): the map depends on where the point lands (`perspective(600px) rotateX(25deg)`: `(-2.92, 37.309)` against 40);
- the size-dependent parts (a percent `translate`, a percent or default `transform-origin`, `perspective-origin`, `offset-anchor`): the paint moves when the box resizes, with no offset moving;
- `zoom`, on any box and on `<html>`.

A box's map changes only through its computed style or its size, so `M` moves only through (a)(i), (a)(ii), or (a)(v) (time).

**(a)(iv) The scroll offsets.** A scroll by the person or by script (the `scroll` event), and the engine's own adjustments after a layout move:
- **anchoring** at the default `overflow-anchor: auto`: an insert or a removal above the viewport moves the offset by the same amount, so the paint stays still;
- **the clamp**: a removal that shrinks the scrollable overflow below the offset moves the offset, so the paint moves;
- `position: sticky`, whose offset is a scroll adjustment of the same kind.

`facts13` A (Chromium) shows anchoring and the clamp already applied at a forced layout, synchronously after the mutation. They are what a `MutationObserver` callback reads: insert above, `st 540 → 580`, the target's top `100 → 100`; clamp, `st 280 → 240`, top `360 → 400`. In WebKit, C-A12 read anchoring on an insert above the viewport (scrollY 98 → 138, the root still, `C-A12 §0.2`). H13's own WebKit read of the clamp is UNREAD.

**(a)(v) Time `T`.** These move `P` with no move of `L`, `M`'s inputs or a scroll offset: every running animation and transition on the host or an ancestor (CSS transition, CSS animation, WAAPI), the host's own grow on its envelope, the stage's own glides (`composite: "add"`), and a scroll-driven animation (whose time is a scroll offset, so it moves with (a)(iv)). **This is the one input that must glide nothing.**

**(a)(vi) The stage's own writes.** Each is a mutation the stage's observer would hear, from the source:
- `--stage-reach` on the host;
- `--lens-dx`, `--lens-dy`, `--lens-sx`, `--lens-sy` on the lens;
- `data-engage-stage` and `data-engaged` on the host, and `data-engage-lens-below` on the lens;
- after this patch, the token read's one inline property on the element read, (b) below.

`Element.animate()` and `Animation.cancel()` make no record.

**(a)(vii) The order of reads.** The glide compares two reads of `P`: where it was painted, and where it is after the mutation. These must be at one `T`. The document timeline's time changes only at a frame's update-animations step, which runs before that frame's `requestAnimationFrame` callbacks. So:
- a read in a `requestAnimationFrame` callback of frame N is at `T_N`;
- a mutation in any task or microtask between that callback and frame N+1's update step is also at `T_N`;
- a mutation made by a frame-N+1 animation-frame callback that runs **before** the stage's own callback is at `T_{N+1}` against a read at `T_N`.

Animation-frame callbacks run in the order they were requested, and the stage's loop re-requests itself first in its own callback. So the third case is a callback registered before the stage's loop started that is still running when the mutation lands. **Named, not cured.** It carries (a)(v)'s motion over one frame into the glide (at most one frame of an ancestor's animation).

### 1.2 · (a), the cure by construction, and its limit

- **The place painted** is `P`, read on every engaged frame in the stage's `requestAnimationFrame` callback (`hear`), and also at the hold's start, on every `scroll` and `resize` event, and after every re-render the stage handles.
- **The place now** is `P`, read in the observer's callback, at a forced layout. Per (a)(iv) that read already holds the engine's own scroll adjustment. Per (a)(vii) it is at the same `T` as the painted read.
- **The glide** is painted − now, in viewport px. It is solved into the translate that paints it, using the map asked of the engine (`frameOf`).
  - `frameOf` makes two probe reads, a paused `composite: "add"` WAAPI `translate` of 40 px on each axis. That is no mutation, (a)(vi), and it leaves the base value and every running animation in place.
  - It inverts that 2×2, then takes one Newton step: probe at the solution, correct by the residual. The Newton step is what the projective part needs.
  - So every member of (a)(iii) is carried as the engine paints it, without being modelled. A singular map (a scale of 0) glides nothing.
- **What this covers.** Every move of (a)(i), each in all three record kinds, observed on `<html>` with `subtree`. That includes stylesheet elements, and every (a)(iii) map and (a)(iv) adjustment those moves cause. Anchoring paints still, so painted − now is 0 and nothing is glided. The clamp moves the paint, so it is glided.
- **Time.** (a)(v) moves both reads alike, so it contributes nothing to the glide. A running ancestor animation glides nothing, and neither do the host's grow or its own glides.
- **The stage's own writes** (a)(vi) are taken from its observer before delivery. `own()` runs `takeRecords()` before and after each write, and re-delivers any foreign record it took first. So the stage's own writes never re-enter its observer.
- **The limit.** These glide nothing:
  - (a)(ii)'s members with no record and no event (CSSOM edits, a font swap, an image decode, a pseudo-class restyle) are a one-frame cut, as at HEAD. The painted read is re-taken every engaged frame, so the next heard move starts from where the host was painted, never from a stale place;
  - a resize is not glided (a viewport change, E-10's `stale place` family since pass 5);
  - a scroll by the person or script is not glided;
  - (a)(vii)'s early callback is named, not cured.
- **A released host on its exit clock.** O-103f (3): the loop stops at release. Its painted place is read at the release, on every `scroll` and `resize` event, and after every re-render, never per frame. A layout move with no record during its exit, or an ancestor's animation during its exit, is read as moved. **Named, and not driven by any H13 cell.**

### 1.3 · (b) The grammar each token's consumer accepts, per engine

Each token the stage and `useEngage.ts` read (`P-E12 §1.2`'s table, re-read in the source at this seat with `grep -n -e tokenOf -e easingOf -e rowClockMs`) has a CSS consumer property and a script reader. The consumer's grammar is the CSS Values grammar of its type, `<time>`, `<number>` or `<length-percentage>`, one value each. That means a dimension in any unit case, with an exponent, a sign, comments and whitespace. It also means every math function (`calc()`, `min()`, `max()`, `clamp()`, `round()`, `mod()`, `rem()`, `abs()`, `sign()`, and the constants `e`, `pi`, `infinity`), `var()` with or without a fallback, and the CSS-wide keywords (which make the consumer fall back to its initial value).

| (b)(1) | `--spring-<row>-settle` (`dock`, the release row) | `transition-duration` (the stylesheet's travel) | `<time>` | the registered read, `<time>` |
| (b)(2) | the envelope clocks `--engage-<role>-attack`, `-release` | `transition-duration` | `<time>` | the registered read, `<time>` |

**What each engine's parser for the reader takes.**
- **Typed OM** (`CSSNumericValue.parse`, P-E12's `tokenOf`) is narrower than every consumer above, in both engines:
  - WebKit 26.5 throws on every `calc()`, `min()`, `max()` and `clamp()` (C-A12 `facts-webkit.log`);
  - Chromium 149 throws on `round()` and `abs()` (`facts13` B), and cannot convert `rem` or a percentage to px without a context;
  - Firefox 151 has no `CSSNumericValue` at all (C-A12 §5 item 5).
  **The patch removes Typed OM.**
- **A registered custom property** (`@property` with `syntax: "<time>"`, `"<number>"` or `"<length>"`) is parsed by the engine's own CSS value parser for that type. Its computed value is that type's canonical value: one number with the canonical unit (`facts13` B: `round(…)` computes to `0.21s` in Chromium).
  - So it takes every form the consumer of that type takes: math functions, `var()`, case, exponent, sign, comments, `rem` and `em` for a `<length>` (computed to px).
  - A form the type refuses (a list, a word, a bare number for a time, a CSS-wide keyword, an undefined `var()`) is invalid at computed-value time, so the property computes to its initial value.
  - **The patch's reader writes `var(<token>)` into one of three registered properties on the element read, reads the computed text, and removes it.**
  - The initial values are `-1s`, `-1` and `-1px`. No reader's `ok` takes a negative, so a refused form is refused loud by name, never a masked default.
  - The canonical computed text is parsed by one pattern per unit: `<number>(ms|s)`, `<number>`, `<number>px`. In WebKit, H13's facts read of registered computation is UNREAD. That is the WebKit cell this patch's CK-21 rests on (§9).
- **`shape-margin`**, (b)(7)'s reader since P-E12, is a `<length-percentage>` that draws nothing without `shape-outside`. Its computed value is canonical: a px length, a percentage, or `calc(<percentage> ± <length>)`.
  - The patch reads all three. A percentage resolves against the root's inline size (`document.documentElement.clientWidth`), the box the page gutter pads. That is a stated reading: each consumer resolves `%` against its own containing block.
  - `CSS.supports("shape-margin", raw)` keeps a form `shape-margin` refuses refused loud. Without that check it would compute to its initial `0px` and pass silently.
  - A negative `calc()` clamps to 0 in `shape-margin` as in `padding` (C-E12 §2: `calc(-1rem)` reads 0 and matches the padding consumer).
- **`KeyframeEffect`** is `animate()`'s own parser, so for `--spring-dock` the reader *is* the consumer. For `--spring-panel` the reader takes one easing, where `transition-timing-function` takes a list. That is a stated narrowing since P-E12 (C-9): a list on `--spring-panel` is refused by name.

**The forms the script refuses where CSS's consumer computes something.** Each is stated, none silent:
- `calc(infinity * 1s)`: a non-finite clock is refused loud. REPORT, `§P12-2`'s stated non-counterexample;
- `0s` and `-0s` on a clock, and any non-positive settle: refused loud. The consumer runs them instantly; the stage cannot travel on a zero clock;
- a `%` gutter: read against the root's inline size, above;
- a list on `--spring-panel`: the row above.

**The platform dependencies.**
- `@property`, already the library's: `--stage-reach`, `--rung-crest` and `--scrub-pitch` are registered.
- `Element.animate` with `composite: "add"`, already used by the glide.
- `CSS.supports`, already used.
- **Removed:** `CSSNumericValue`.
- **No new dependency.**

### 1.4 · (b), the cure by construction, and its limit

Every token whose consumer is a `<time>`, `<number>` or `<length>` is read by the engine's own parser for that type, in the element's own context, through a registered property. So the script takes exactly what the type takes, in each engine, math functions included, and agrees with CSS to the ms: the computed value is the same computation.
- A refused form computes to the negative initial value and is loud by name: one `console.error` per host and token, no throw.
- The one `<length-percentage>` consumer is read through a `<length-percentage>` property.
- **The limit.** A page rule that targets the read's private properties (`--engage-read-time`, `--engage-read-number`, `--engage-read-length`) by name would narrow it. This is H13 §3 item 1's trap: a probe narrowed by a page rule on its property. No consumer writes these names, and §8's grep will say so. A reduce rule on `transition-duration` does not reach them.
- **The refused reach input** (§P12-7 item 6). A refused `--scale-engage` or `--space-section` writes `--stage-reach: 1`: no inline grow. The message says exactly that. The registered `0` is never the paint of a refused input.
