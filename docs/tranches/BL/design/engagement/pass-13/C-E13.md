## 2 · The derivations attacked (`§P12-8.3`: a member a derivation omits is a counterexample to the row it breaks)

### D1 · A script-animated ancestor (CK-20). Omitted by P-E13 §1.1 and H13 §1.1 (iv). By the bytes

- **(a)(v) lists the moving inputs that must glide nothing:** "CSS transition, CSS animation, WAAPI", the host's grow, the stage's glides, and scroll-driven animation. **(a)(i) lists the records to glide:** any `style` or `class` attribute.
- **An animation made of attribute records is in both lists, and the construction treats it as (a)(i).** On every frame such an animation writes, `onMutation` reads `was` (the frame before's painted centre) against `now`. It glides the difference when it exceeds 0.5 px: at 500 px/s that is 8.3 px a frame. Each glide is a fresh 210 ms `dock` travel (`glide`, P-E13.patch 8576-8582), so the host's paint lags its card while the animation runs. The lag is the sum of the glides still running.
- **The writers in the library itself** (`static-reads.txt`):
  - `CarouselContent.vue:65-66` writes `--member-scale` on every member at every deck position;
  - `useScrollChrome.ts:165` writes `--chrome-collapse-t` on every scroll step;
  - `vSpecular.ts:59-60` writes `--mouse-x/y` on every pointer move (no move, cost only).
- **Consumer writers:** any keyframes.js spring writing an inline transform, and a scroll-linked parallax.
- **H13 does not drive it.** Its `anim` cells are a CSS transition and two WAAPI animations (H13 §1.1 (iv)).
- **cand12** observed `childList` only (`§P12-2`, `watchWorld` at P-E12.patch:8530), so it heard none of these records. This is a regression P-E13 introduced while curing the pass-12 finding that attribute re-renders were not heard.
- **The tension is in the derivation, not the code.** A record cannot tell a re-render from one step of an animation. A partition by mechanism (record, or time) does not match the row's intent, which is continuity in paint.
- **Drive:** `held-battery.txt` D1.

### D2 · The early animation-frame callback compounds (CK-20). Misstated by P-E13 (a)(vii). By the bytes

- **Why the page's loop runs first.** HTML runs animation-frame callbacks in request order, and a loop re-requests itself in its own callback. A page loop that ran before the stage started (`startFrames` requests at the hold, outside any frame) therefore runs before `hear` in every later frame.
- **What happens each frame.** If that loop writes anything (a text node, an unrelated attribute), the record's callback reads `now` at T(N+1). `h.painted` is from frame N's resize step (`heard`, P-E13.patch 8636-8648). So `was − now` holds one frame of everything running:
  - the stage's own glide (which (a)(v) says "moves both alike");
  - an ancestor's CSS transition;
  - a lens travel.
- **The result.** That progress is glided back on every frame the loop writes. A 40 px glide meant to finish in 210 ms is pushed back by its own per-frame progress for as long as the loop runs. An ancestor transition is glided against frame by frame, as in D1.
- **How P-E13 bounds it, and why the bound is wrong.** P-E13's bound, "at most one frame of an ancestor's animation", holds for a single mutation. It does not hold for a writer that runs every frame, which is what a page loop is.
- **Drive:** D2.

### D3 · The released host on its exit clock (CK-20). Named by P-E13 §1.2 and left uncured

- **What the bytes do.** `leave` stops the loop when no control is engaged (P-E13.patch 8687-8703). `onMutation` still visits every holder, released ones included, and compares against a `painted` read at the release, a scroll or the last record.
- **How it fails.** A card transition that starts at the release (a Dialog's close, a Sheet settling), followed by any record during the exit clock, glides the transition's progress so far.
- **Why it is a counterexample.** P-E13 writes "Named, and not driven by any H13 cell". `§P12-8.1`'s must-prove has no exception for a released host, so naming the case does not cure it.
- **Drive:** D3.

### D5 · The host's own content resize (CK-20). PLAUSIBLE, by the bytes

- **What the code compares.** The glide compares centres. A held host whose own content changes its width (a scrubbing NumberField whose value goes 9 → 10, in a row that is not centred) moves its centre by half the change while its leading edge stays put.
- **What it then does.** P-E13 now hears character data, so it glides the box: the leading edge jumps by half the change, then travels back. That is motion the stage made.
- **What closes it.** A non-issue if every held host has a fixed inline size. That is unread here. Drive D5.

### D6 · A transition that reaches the registered read (CK-21). PLAUSIBLE: an engine fact, unread

- **Why the read can be narrowed.** `--engage-read-*` are registered with typed syntax (P-E13.patch 9358-9374), so they can be interpolated.
- **What a `transition: all` host would do.** Assume `transition-property: all` includes registered custom properties in an engine, which the spec text ("all properties that can transition") implies. Then the read's write (`-1s` → `var(token)`), followed by the forced style read, starts a transition. The computed value at that read is the before-change `-1s`, so the token is refused and the console names it, falsely, on default tokens.
- **The limit P-E13 states, and what it misses.** P-E13 §1.4 states a limit for a rule that names the read properties. H13 §8 item 3 names `!important` rules. Neither names a transition reaching them through `all`.
- **Where it would show.** The library itself writes no `transition-all` (0 lines in `src`). The siblings carry no `transition-all` on a glass-ui control. The member is a consumer's Tailwind `transition-all` on a Button or Switch.
- **Drive:** fact F5, then D6.

### D7 · `--motion-tempo` ≤ 0 (CK-21). By the bytes

- **The three reads.**
  - `rowClockMs` returns `tokenOf(…settle…) * motionTempo(el)` (P-E13.patch 8241-8244);
  - `motionTempo` reads `--motion-tempo` by `parseFloat` and returns 1 for any value not above 0 (`motionTempo.ts:39-40`);
  - CSS registers `--motion-tempo` as a `<number>` (`property-regs.css:240-244`), so `0` and `-1` are valid and inherited, and `--spring-dock-duration: calc(var(--spring-dock-settle) * var(--motion-tempo))` computes to 0s (a negative time clamps to 0 inside `calc()`).
- **The disagreement.** At `--motion-tempo: 0`, CSS's dock clocks are 0 while the stage's travel and the release carry run 210 ms, with no `console.error`.
- **Why it is a counterexample.** The comment at `property-regs.css:232-233` says the script "mirrors the ≤0 → 1 clamp JS-side", but no CSS clamp exists to mirror. That is a masking fallback on a clock the engagement reads at runtime (E-2). `§P12-8.1` (b) asks for "every token the stage and `useEngage.ts` read" and its consumer's grammar; P-E13 §1.3's table and H13 §1.2 both omit `--motion-tempo`.
- **Not P-E13's regression.** `motionTempo` is at HEAD and `rowClockMs` has multiplied by it since P-A7. It is CK-21's instance on the candidate all the same.

### D8 · A context-relative gutter (CK-21). PLAUSIBLE, by the bytes

### D9 · A map change that moves neither the centre nor the offset chain (CK-04). PLAUSIBLE, by the bytes
