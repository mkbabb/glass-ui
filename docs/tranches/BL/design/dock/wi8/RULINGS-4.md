## The finding that changes how MEASURE-4 is read

On the measured build every horizontal dock whose seats are one size rests one seat short when open, at every width, in both engines. MEASURE-4 reports this as three separate things (a lane that hides a seat early, a controls dock that loses a seat at 360, a run that never grows), and does not report it at all where it is plainest.

- *Rows.* `rows/m4/p3-fold-pill-fine`, Chromium and WebKit, at open rest: the dock is 164 px wide, the run's region 140 px, seats at 650, 698 and 746 show and the fourth, at 794, has an empty visible box. The same cell on MEASURE-3's build (`rows/m3`): 208 px wide, four of four showing. The viewport is 1440; nothing limits the room.
- *Rows.* The same difference, exactly one pitch, is in every horizontal fold cell I compared between the two builds: the pill, the card, the rounded dock, the rim cell, the controls docks at all four corners, daraksha (212 against 260), sci-report, the code pane, the outlet into a controls dock, keyframes's transport (118 against 162), the outlet (258 against 302), fourier (156 against 204), the six-seat controls dock at 360 (264 against 312) and the seven-seat dock (332 against 374 at 390).
- *Source.* `fitWhole` (`useDockBody.ts:531-551`, added by `ab39f81b5` for RU-23) takes the seats' window as `clientWidth − 2 × reserve`. A horizontal run's client box holds one reserve, not two: its end padding is 0 (`run.css:410-412`) and the trailing reserve is a spacer box in the scrollable overflow. So a run that hugs its seats reads one reserve short of fitting. `n = floor((S − reserve + gap) / pitch)` is then the seat count less one, the run is capped to `n` pitches, and the dock shrinks round it. Fourier by this arithmetic: seats' span 148, client box 152, window 144, n = 2, cap 104; the rows read the region at 100 px, which is that cap less the run's margins.
- *Why no gate saw it.* The travel judges read only rows with `[data-morphing]`. "Visible until covered" reads a unit only while its box is inside the plate, and the lost seat lies outside the shrunken plate, except where a `#persistent-end` region sits over it: the outlet, the region cell and fourier, which are exactly the cells MEASURE-4 lists as hidden by a lane. And `read4.mjs` was changed after the pass (`ebd546e7f`) to accept a seat that is "whole or absent", so an absent seat passes at any width.

So G-2, G-4, G-8 and G-13 on `5883827f6` were read on docks that were each a seat short. The six gates MEASURE-4 calls GREEN read no seat count and I do not withdraw them, but the fifth pass reads them again with the rest.

## The rulings

**RU-25. A lane is already the plate's edge; "visible until covered" is read against the lane. Replaces RU-21.**
Evidence, *rows*: fourier's unfold, `rows/m4/p3-fold-fourier-fine`, Chromium, f38: the plate's start edge is at 927.2; the run's region paints at 876.0 with `clip-path: inset(-4px -0.05px -4px 51.24px …)`, so its lane starts at 927.2 and ends at 976.0, where the trailing region's box starts (976.0). The same holds in each of f37 to f46. Evidence, *source*: the lane is built from the plate's painted box in the same `write()` that sizes the plate (`useDockBody.ts:1027-1039`, `const lane = { ...P }`), narrowed only at a neighbour's painted facing edge (`boundary()`, `:1023-1026`).
The 40 to 307 ms is not a lane running ahead. It is the seat RU-23's cap pushed under the trailing region for the whole open state: 300 ms is the length of the unfold during which that seat's box is inside the plate, and 41 to 81 ms is the part of the fold before it fades under 0.1. With the cap gone (RU-26) the reading returns to MEASURE-3's one row.
That one row is geometry, not timing, and a tolerance in milliseconds was the wrong instrument for it. A trailing region rides the plate's end edge, so its near edge is ahead of the plate's edge by its own width plus the padding. A run seat it passes over is covered by that region. With a one-seat trailing region the gap between "under the neighbour" and "outside the plate" is the padding, 4 to 12 px, which is one row mid-travel; with a two-seat trailing region it would be 50 px and no build could meet 20 ms.
The mechanism: unchanged. Lanes stay. A single clip on the plate's shape does not do the job: without the cut at the neighbour's edge a leaving run seat prints under the trailing seat that slides over it, which is C-2's fault.
The gate reading, for G-2, G-4 and G-8, in place of RU-21's 20 ms:
- A unit above 0.1 is covered when its box no longer meets its lane by more than 0.5 px on each axis, where the judge builds the lane itself: the plate's painted box, cut at each neighbouring region's painted near edge as the sampler reads it. A unit that meets its lane has a non-empty visible box. A unit that showed and was hidden never shows again in that travel.
- So the clause cannot pass by construction: in every row the clip the carrier wrote on a region (the judge already parses it) equals the plate's painted edge within 0.5 px on each side that has no neighbour, and the neighbour's painted near edge within 0.5 px on each side that has one.
- At both rests nothing of the showing face is hidden (RU-26's clause).
- Plants: a lane inset 12 px inside the plate's edge on a side with no neighbour (RED on the second clause); the neighbour cut removed (RED on "no overlap", as today).

**RU-26. RU-23's cap as built is struck, and a gate reads the rest.**
Evidence: the finding above; MEASURE-4, G-14: "RU-23's cap (`ab39f81b5`) is a `max-inline-size` on the run, which holds the run's preferred size down, so a dock whose room grows never grows to read it again."
Two faults, one wrong test and one wrong mechanism. The test counts a reserve the client box does not hold. The mechanism writes a length on the run: a length caps the run's own preferred size, the dock shrinks to fit it, and then a host that gives the dock more room changes nothing the carrier observes, since the dock's box does not change. No trigger exists for "the room grew" once the dock is narrower than its room, so a length written by script cannot follow the room.
The mechanism: delete `fitWhole`, the lift of `data-run-whole` and of the inline `max-inline-size` / `max-block-size` in `fitRun` (`useDockBody.ts:506-511`), and the call. RU-27 says what replaces them.
The gate reading, added to G-2 and G-13: at open rest, in a run whose seats fit (the fit law, below), every seat's visible box is its whole box, and the dock's extent on its axis is the extent of its content; `read4.mjs` accepts an absent seat only in a run that does not fit. Plant: `fitWhole` restored as built; RED when the four-seat pill at 1440 shows three.

**RU-27. When the seats do not fit: whole seats, by a rule the layout applies itself. Replaces RU-23.**
Evidence: MEASURE-4: "At 360 and 390, O-358's dock rests with six whole seats and one absent, no sliver"; "the six-seat controls dock, which fits with its reserve yielded and now loses a seat"; the 13 l1 and k1 tests.
The rule has two cases and no third.
- *The seats fit.* The test is the shipped fit law and no other: the seats' span is no longer than the run's port, with the reserve free to yield (`publishFit`, `data-run-fits`, 10.1.5 e4 and k3). Every seat shows. Nothing is cut and nothing is rounded. The six-seat controls dock at 360 is this case.
- *The seats do not fit.* The run scrolls, its window is a whole number of seats, the current seat is brought in, and a seat is whole or absent at each end.
The mechanism for the second case is CSS, with one flag from the carrier.
- The carrier sets `data-run-whole` on the run when the dock is open, the run is a scrolling run (not `run="plain"`), its seats are one size within 0.5 px, and the fit law fails. It removes it otherwise. It writes no size.
- Under the flag, on a horizontal run (`run.css`, where the built rule is):
  `max-inline-size: calc(round(down, 100% - var(--dock-run-reserve-inline) + var(--dock-run-gap), var(--dock-pitch)) - var(--dock-run-gap) + var(--dock-run-reserve-inline));`
  `justify-self: center;`
  `scroll-padding-inline: var(--dock-run-reserve-inline);` (as built).
  The run is content-box, so this caps its content at `n` seats and `n − 1` gaps plus the one reserve its client box holds. The next seat starts a gap past the last whole one, and the house gap (8 px) is larger than the reserve (4 px), so it is absent, at offset 0 and at the end alike. What is left over, under one pitch, is room at the two ends of the run inside the plate.
- Why this follows the room. A percentage cap is not counted in the run's own preferred size, so the dock still takes all the room its host gives. The rounding is redone by layout whenever that room changes, with no script. The carrier's flag depends only on fit, and it reads fit from a box the flag does not change: the seats' span against the layers region's client extent plus the run's start padding (not `run.clientWidth`, which the cap narrows). When the host lifts a cap the dock's own box grows, the ResizeObserver already on the root fires, the fit is read again, and the flag goes. That is l1 and k1.
- A vertical run is not rounded in 11.2.0. A percentage cap on the block axis needs a definite height above it, which a content-sized vertical dock does not have, and O-358 is about 360 to 390 wide. A vertical run that overflows keeps the shipped rest. Whole seats on the block axis go to 12.0.0 if a consumer asks.
- Not read: whether WebKit 2287 resolves `round()` over a percentage in `max-inline-size`. The build seat reads that first, on the seven-seat cell at 390. If it does not resolve, the second form is the carrier writing the count as a number, `--dock-run-n`, when it sets the flag, and the rule reading `calc(0% + var(--dock-run-n) * var(--dock-pitch) - var(--dock-run-gap) + var(--dock-run-reserve-inline))`: the `0%` keeps the cap out of the run's preferred size, which is the whole point, and the count is refreshed by the same root observer. If neither holds in WebKit, stop and report; do not write a length.
- The compact form does not apply, because it no longer exists: RU-28. "The seats shrink to 44 px" in RU-23 needs no build either; a coarse seat is 44 px.
The gate reading: G-2's "the seven-seat dock shows every seat whole, with no sliver" becomes: at 360 and 390 the seven-seat dock at rest, at offset 0 and scrolled to its end, shows only whole seats (six), no partial visible box on any seat, the current seat among them, and the dock's extent equals its host's room within 1 px; the six-seat controls dock at 360 shows six; at 1440 every dock shows every seat; and with the host's cap lifted on an open dock (a new cell, l1's action) the run shows every seat within two rows of the change. Plants: the flag never set (a sliver at 390); a length written in place of the percentage (the lifted-cap cell stays short).

**RU-28. Names leave the run. The compact form, RU-24's build and the names on `f` are struck; the mark as a small plate moves to 12.0.0.**
Evidence: MEASURE-4: "RU-24 … not built. The open seat's name still changes two seats' widths by 96 px in one row … and the compact switch moves a seat 104 px in one row"; "The mark behind the open seat as a small plate: not built"; both unbuilt after two passes. *Source*: `run.css:533-536` gives the current seat `inline-size: var(--dock-open-seat)`, three pitches; a seat's name is whatever the consumer put in `DockControl`'s default slot (`DockControl.vue`, `<slot />`), so glass owns no element that is the name; a seat's two pseudo-elements are already taken (the catch-light and the touch target).
Why it cannot be built on the one clock as specified. The layout changes once, so at the trigger the old open seat is already one glyph wide. Its own box paints its mark and holds its name, and a box cannot be painted wider than it is laid out; a clip can only take away. So the old seat's width cannot travel unless the mark is an element of its own, and its name cannot fade "clipped by the mark's edges" unless glass can address the name, which RU-15 ruled out when it struck the `label` prop. The new seat could grow by a clip; the old one cannot shrink by one. Half a tween is a cut. The seat's material is rebuilt in 12.0.0 in any case (W-R.1: every DockControl a `.plate`, the active seat's lens).
What is left is the cause, and the cause can go. A named open seat moves every seat between the old page and the new by 96 px on every page change. That is the same thing RU-15 struck the labelled seat for ("it also tweened every seat of the run on each hover, against the second bound"), and the owner's bound for names is "keeping the dock the same size". O-358 itself asks for "icon-only seats". On a phone with six seats or more, this build already shows no name.
The rule: every seat of a run is one seat wide, the current one included, at every width. The mark says which page is current. Names show above the seat by Tooltip (R-7, OQ-6), not in the run.
The mechanism:
- Delete the two rules that read `--dock-open-seat` on the current seat (`run.css:533-536` and the vertical pair at `:560-563`), the `data-compact` rules (`:552-555`, `:566-569`), and in `fitRun` everything that decides, lifts or sets `data-compact` (`useDockBody.ts:485`, `:488-492`, `:512-519`). `fitRun` becomes: one span read, the fit flag, RU-27's flag.
- `--dock-open-pitches` and `--dock-open-seat` stay declared and unread in 11.2.0 and are deleted in 12.0.0 with a MIGRATION row; a consumer that set them gets one-seat seats like everyone.
- A change of open seat then changes no box. In a scrolling run the offset still travels as built (`2a5a198f9`, `a112ec8c8`). The mark changes by the seat's own paint transitions; the lens landing in one frame is L-34's stated fault and is not made worse.
- The seat carry (`readSeats`), the joining and leaving control and the scroll offset stay: a seat set that changes still moves seats, on the clock, as read.
What moves to 12.0.0, with W-R.1: the mark as one small plate that glides from seat to seat (RU-8's third clause). With seats of one size it is one element and two quantities, and it cures L-34 in the same stroke. RU-24 stays as law (no width changes in one row) and has nothing left to break.
What the owner is told, as a new question with this default: the current page's name no longer shows inside the dock; it shows above the seat on hover and focus in 11.2.0 where a site wraps its seats in Tooltip, and by a press and hold when Tooltip's touch path lands. If he wants the name beside the icon, it returns only with the 12.0.0 mark, because that is the only build that lets its width travel. atlas is told at booking; it is a default atlas consumes.
The gate reading: G-4's open-seat clause becomes: on a change of open seat, to a neighbour, to the far end and twice within 90 ms, at 1440, 390 and 360 and right to left, no seat's box and no plate edge changes by more than 0.25 px in any row; in a scrolling run the offset is inside the travel bounds. `read4`'s clause "the run is not compact where its seats with the name do not fit" is deleted with the form. Plant: the open-seat width rule restored (RED: 96 px in one row). G-14: the shipped tests that read a three-pitch open seat (`release-10-1-5.spec.ts` has the sites) are triaged by RU-22; a test of the open seat's reach, ring or flush rest is restated on the one-seat seat, and a test whose whole promise was the name's width is listed for the owner with this ruling.

**RU-29. G-11's trigger frame: three layouts, four on a named frame, never five; the 0.94 ms bound is restated.**
Evidence: MEASURE-4: "5 on the trigger frame in every cell (bound 3; MEASURE-3 read 4)"; "The trace carries no stack for them". `cost2.m4.json`: `w-pill@4x` `layoutMsMax` 1.173, `w-flow@4x` 1.532.
The reads on the trigger frame, from the source, in order:
1. *Needed.* The engine's own, for the input's hit test.
2. *Not needed.* `rectOf(leave)` in `exchange()` (`useDockBody.ts:264`). The pre-flush watch in `GlassDock.vue` sets `[data-morphing]` and then calls `exchange()`, so the read runs on a layout the attribute has just dirtied (the hidden face gains its box). The leaving face's rectangle does not depend on that box: the hidden face is `position: absolute; inset: 0` (`layers.css:207-210`). Call `body.exchange()` first and set the attribute after it; the read then lands on a clean layout and costs nothing. W-I.8's stated order ("set `[data-morphing]`; read the painted boxes") is reversed in those two steps for a dock at rest. For a dock in travel the attribute is already set and nothing changes.
3. *Needed.* The carrier's one read of the new layout: the first read in `sync()` after the class changes (`run.offsetParent`, `fitRun`, `:487`). Every later read shares it while nothing is written.
4. *Not needed.* The reads after the lifts in `fitRun`: `data-compact` removed and set again (`:513`, `:518`), the span after it (`:520`), and `publishFit`'s `clientWidth` after `fitWhole`'s write (`:564`). They go with RU-26 and RU-28; nothing is lifted to be read any more.
5. *Not needed.* Reads after `placeLeaves()` has written: the returned face's rectangle (`:729`) and `runScroll.resting()` (`:744`, `:751`). Order `sync()` as all reads, then all writes: the root, the seats, the regions, the resting offset and each returned face's rectangle first; then `placeLeaves`, the offset and `write()`. `placeLeaves` itself reads a containing block between writes when two faces leave at once (`:795`, `:801`); it reads them all first.
6. *Needed only on a named frame.* When the first read decides a flag that changes layout, the flags are written together and the layout is read once more. The frames are two: the fit flags flip (`data-run-fits`, `data-run-whole`; a yielded reserve or the rounded window moves the seats by a few pixels), or the curve inset changes on a dock taller than one row (C2-6's named second read). Both in one frame are still one write and one more read.
7. *Needed.* The frame's own.
The bound, restated honestly: on the trigger frame, three layouts at most where no flag changes, four where one does, and each is named. They are named without a stack: in the hold build only (`VITE_DOCK_HOLD=1`, the constant that already compiles the pose out of the library) the carrier brackets its phases with `performance.mark` (`dock:read`, `dock:flags`, `dock:reread`, `dock:write`), and the cost cell attributes each `Layout` event by the marks it falls between. G-12 scans the library build for the mark names beside `__dockPose`.
The 0.94 ms. No record gives its source, three passes have read 1.18, 1.28 and 1.53 under a load of 5 to 16, and the out-of-flow pill reads 1.17 on the same build, so the number was never a reading of block flow. Restated: at a 4x throttle no single layout in any cost cell is longer than 2 ms (*derived*: a quarter of a 120 Hz frame under the throttle, 0.5 ms unthrottled), read as the median of five runs' longest; and after the trigger frame the block-flow cell's median layout is no more than twice the out-of-flow pill's in the same run. Every other clause of G-11 stands.
Added to G-11's rest clause, for RU-30: a vertical, height-capped run that overflows, with a wide tab at its start, at rest for 2 s in WebKit: 0 frame callbacks scheduled by glass (the init script's counter is engine-free).

**RU-30. The seat that never settles in WebKit (10.1.5 k2): the curve inset does not apply to a run that overflows.** *Hypothesis.*
Evidence: `m4-g14-build-webkit-b.log`: `locator.hover` on `[data-witness="S1"]`, "element is not stable", 112 retries; the dock is at rest, open, focused, vertical, capped at `stageH=360`, its run overflowing, a wide tab at the flush start. *Source*: of everything `sync()` writes, only `fitCurve` (`useDockBody.ts:582-636`) changes a box the ResizeObserver watches: `--dock-curve-inset` is the root's padding (`morph.css:116`, `:147`), which resizes the regions, which calls `sync("ro")`, which runs `fitCurve` again.
My reading of the cause. `fitCurve` converges in one step only while a child's shortfall falls by exactly what the inset grows. In a capped run that scrolls it does not: the inset shrinks the port instead of growing the dock, a child is read "only as far as the port" (`:598-600`, `:612-615`), and the child cut by the port's far edge has its corner taken as half its cut slice (`:617`), which changes with the inset. So each pass can write a different inset, more than 0.25 px from the last; each write moves the layers region, which starts a travel, which moves S1; at the landing the observer fires again. WebKit keeps a scroll offset whole, which is enough to keep two values alternating where Chromium settles. A wide tab at the cap of a vertical pill is exactly the child the inset exists for.
Where to look first: log `reason`, `short`, `pad`, `want` and the current inset at the write (`:630-635`) on k2's page in WebKit. A repeating sequence confirms it. If the inset is still, count `sync()` calls by reason for 2 s at rest on that page; a dock at rest makes none, and the reason that repeats names the loop.
The rule, which stands whether or not the log confirms the cause: the curve inset is for a run whose content all shows. Where the run overflows its axis (the fit law fails), `fitCurve` removes the inset and returns. A flush edge of an overflowing run is the port's own clip, which is k2's law as shipped ("a vertical run that overflows clips square at a flush edge").
The gate reading: k2 passes in WebKit in G-14; RU-29's added rest cell reads 0 callbacks.

**RU-31. keyframes's transport, 4.39 px past the curve under reduced motion: a lane too narrow to carry its corner is closed.**
Evidence, *rows*: `rows/m4/p3-fold-transport-rm`, Chromium, f92: the plate lands in one row at 692 to 748; the run's region has no width and its lane is 740 to 748, 8 px, written `inset(-8px -8px -8px 0px round 0px 28px 28px 0px)`; seat#0, held where it painted at 723 to 763 and at opacity 1, shows through it at 740 to 748. The same row on MEASURE-3's build: seat#0 is at 701 to 741 and shows at 740 to 741, one pixel, which reads 0. `m4-read4-chromium.txt`: "content 4.39 px outside the plate's curve (seat#0 row 92 (travel))".
The cause is read, not guessed, in two parts. The fault itself is older than this build: a rounded `inset()` on a box narrower than its radius is scaled down by CSS on every corner, so an 8 px lane at a 28 px cap is rounded at 8 px and paints up to 4.39 px outside the plate's curve. `516f591b0` cured the case of a corner the lane does not share with the plate; this is the corner it does share. What made it show is RU-23's cap: it moved the transport's seats 22 px, so 8 px of a seat stands in that sliver where 1 px stood before. Under the spring the run has faded by the time the lane is that narrow; under reduced motion the plate lands in the first row with the run at full strength.
The mechanism: in `write()`, where the lanes are built (`useDockBody.ts:1027-1039`), a lane that shares an end with the plate and is narrower on the dock's axis than the radius it would round that end with is written closed (`inset(50%)`). Nothing whole fits in a band inside a cap. With the spring it changes no row that shows content: a run is under 0.1 before its lane is under one radius, in both directions (R-3's window). With reduced motion the leaving run fades out of sight and the folded dock shows its persistent seat, which is its rest.
Not chosen: a `path()` clip of the stadium cut by the lane's edges. It is exact, and it is forty lines and a string per region per frame to show a strip nobody reads.
The gate reading: G-2's "inside the plate" on the transport under reduced motion reads 0.02 px or less in both engines, with RU-26 landed and without it (the plant: RU-23's cap restored must not bring 4.39 back, or the lane rule is not the cure).

**RU-32. The right-to-left layer change: a seat's place is its start edge.** *Hypothesis, with the arithmetic behind it.*
Evidence: `m4-judge-chromium.txt`, `p4-swap-layers-rtl-fine`: "L 5.8px … R 5.8px … leaving face full moves 11.53 px in the first row (plate 0.00 px)"; WebKit: edges 6.1 px, the face 12.17 px. The face moves by the whole change of width, twice what either edge travels, in the row where the plate has not moved.
*Source*: `readSeats` (`useDockBody.ts:426-477`) takes a seat's place as `offsetLeft` and carries any change of it (`:461-466`). A layer group is a child of the run, so it is a seat to this function. Left to right, a group that changes width keeps its left edge and nothing is carried. Right to left it keeps its right edge, its `offsetLeft` moves by the whole change of width, and the function gives the group a translate of that size in the first row. The leaving face is inside the group and moves with it.
The mechanism: in `readSeats`, the place on the inline axis is the seat's start edge: `offsetLeft` left to right, `offsetLeft + offsetWidth` when `flip` is set (it is set at `:663`, before `readSeats` runs at `:677`). The offsets kept for a removed control (`rx`) take the same edge.
Where to look first: log the group's carried `x.d` at the trigger of the right-to-left layer change; the hypothesis says it equals the change of width (11.6 px in Chromium), where left to right it is 0.
The second segment of the same cell (9.87 and 10.78 px on a 3 px travel) does not fit twice the edge travel, so something else may ride with it; read it again after this cure before calling the cell closed.
The gate reading: G-4's leaving-face clause (0.5 px in any row) on the mounted right-to-left layer change, both segments, both engines.

**RU-33. The six O-101a mid-expand failures: cure, by removing what can be stale.**
Evidence: MEASURE-4: "one frame after the host change reserves 1019 px against a settled 976 (or 356 against 390)". The two differences are 43 px, a fine pitch within a pixel, and 34 px, which is what a whole-seat cut leaves over at 390.
The promise is real and is kept, not restated: from the frame after a host change, an expanding dock's layout box is the box it settles at. *Hypothesis* for the cause: the root's box on this build depends on states only `sync()` writes (RU-23's cap, the compact flag), and those are written a pass after the layout that needs them.
