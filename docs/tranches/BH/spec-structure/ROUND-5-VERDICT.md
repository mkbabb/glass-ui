### 2. README-mandatory-when-complex is UNENFORCEABLE / circular (aristotelian + migration + dx — THREE lenses; folded `[R5c]`)
**Verified on disk.** `proof-colocation.mjs:60-62` derives its target set by README-EXISTENCE (`readdirSync(CUSTOM).filter(existsSync(dir/README.md))`), so §2.1's "README.md mandatory when complex" is machine-unenforceable: a genuinely-complex family that OMITS its README is not a target and is NEVER checked. Proto-1 built the exact case — `custom/timeline` is a 9-file/6-sub-component/2754-line family ("complex" by §2.1's own bar) with NO README, therefore invisible to the whole proportion regime (composables/constants/depth clauses AND the missing-README flag itself). §6 G1's rationale ("cannot be gamed by adding a complex dir un-listed") is true but inverted — it CAN be gamed by OMITTING a README. The README=enrollment equivalence is elegant for EXEMPTING trivial dirs (the direction §6 spells out) but is a decidability HOLE in the mandatory-when-complex direction, and "complex" is never made decidable anywhere in the otherwise-scrupulously-decidable spec.

**FOLD (proto-1's recommendation).** Add a POSITIVE complexity trigger that ENROLLS a family into the proportion regime INDEPENDENT of README presence — **≥3 sibling SFCs OR a sub-component carrying its own multi-file dir OR a root file-line-sum over a ceiling**. A complexity-triggered family with no README born-REDs for the missing README; a trivial dir stays exempt. "Mandatory when complex" becomes machine-real; the monolith-drift end of the regime cannot be escaped by omitting a README.

### 3. The own-runtime-barrel-sibling naming does not generalize + `core` is tri-overloaded (aristotelian + dx + migration open-Qs; folded `[R5c]`)
The spec mints exactly TWO example names — `variants.ts` (CVA) and `core.ts` (color runtime fns) — but the constellation's real un-mix targets are heterogeneous: proto-3 measured speedtest's target is a Pinia `store.ts`; a general barrel could need `constants.ts`/`helpers.ts`. Three ad-hoc names for one role ("the thing un-mixed out of a pure barrel") reads as naming-grammar incoherence. Separately `core` now means THREE things: FE own-runtime sibling (`core.ts`), BE infra-ring (`core/`), BE orchestration tier (floridify `core/` → proto-4 flagged as a gate name-collision).

**FOLD.** State the RULE, not two examples: *own runtime exports move to a purpose-named sibling named by their KIND — `variants.ts` (CVA), `store.ts` (a store), `constants.ts` (magic numbers), `core.ts` (pure runtime functions with no narrower kind, the fallback); the barrel re-exports it via `export * from './<sibling>'`.* A barrel carrying BOTH a CVA AND own helpers gets BOTH siblings. De-overload `core`: BE `core/` is RESERVED for infra-ring; BE orchestration is `pipelines/` (already §5.1); FE `core.ts` is the last-resort own-runtime kind-name.
