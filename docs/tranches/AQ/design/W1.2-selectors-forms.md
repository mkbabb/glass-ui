# AQ.W1.2 — Selectors, transforms & form vocabulary (design slice)

The implementation-ready design for AQ's CSS-structure cluster (W3) and forms cluster (W4). This slice
turns the W0 wave-matrix rows into exact CSS/prop/token/composable shapes, a per-site migration map, a
per-feature fallback ladder keyed to Baseline status, and the hard gate each impl wave closes against.

Companion to W1.1 (color & theming, W2) and W1.3 (motion/anchor, W5-W6). This doc owns the seam where
glass-ui exposes the **validity visual vocabulary + the `aria-invalid` bridge** that muster J.W6/J.W7
consume — that contract is specified to the line so J can implement against it without re-deriving.

## Scope

Waves designed:

- **AQ.W3** — modern selectors & transforms. Four W0 rows: `:has()` parent-state (grep 0); multi-property
  `transform: scale()`/`translateY()` with no identity base (stacking-context hazard on `--z-dock`);
  `text-wrap` (grep 0, hero pins `white-space: nowrap`); tokenized scrollbar (`.scrollbar-thin` single
  inline-color utility). The scrollbar row is split out to W1.1 (it depends on W2's `--scrollbar-*`
  tokens + auto-dark) and is referenced here only at the seam; W3's CSS-only scope in THIS slice is
  `:has()` + individual transforms + `text-wrap`.
- **AQ.W4** — form primitive modernization. Six W0 rows: `:user-invalid`/`:user-valid` rungs + the
  `useUserInvalidAria` bridge; attr-passthrough contract + `inputmode="decimal"` NumberField default;
  `field-sizing` autosize; `required` + error slot on LabeledField/Label; `GlassNativeSelect` on
  `appearance: base-select`; `:focus-visible` consistency fix.

## Design

### W3.1 — `:has()` parent-state recipes (replaces JS class toggles / `:deep()`)

Three scoped recipes. All live in `@layer components`, scoped to the most specific container (never
`body`, never bare element). Each ships with the mandatory `@supports not selector(:has(*))` class
fallback per the child-state-based-styling guide. Variables drive the state so the `:has()` rule and the
fallback class redefine the SAME custom properties (one source of the override values).

**(a) `Card:has(:focus-within)` — keyboard-focus elevation.** Today `<Card>` has no focus-within
elevation; consumers add JS or accept a flat card when a child input/button is keyboard-focused. New rule
in `cards.css` (or `glass.css` adjacent to `.glass-card`):

```css
@layer components {
  .glass-card {
    --card-focus-shadow: var(--shadow-card);     /* identity = at-rest shadow */
    --card-focus-border: var(--glass-border-quiet);
    box-shadow: var(--card-focus-shadow);
    border-color: var(--card-focus-border);
    transition: box-shadow var(--duration-fast) var(--ease-standard),
                border-color var(--duration-fast) var(--ease-standard);
  }
  /* Elevate one rung when a descendant holds keyboard focus. Scoped to .glass-card. */
  .glass-card:has(:focus-visible) {
    --card-focus-shadow: var(--shadow-md);
    --card-focus-border: var(--glass-border-floating);
  }
}
@supports not selector(:has(*)) {
  .glass-card.is-focus-within {           /* fallback class toggled via focusin/focusout */
    --card-focus-shadow: var(--shadow-md);
    --card-focus-border: var(--glass-border-floating);
  }
}
```

Use `:has(:focus-visible)` not `:has(:focus-within)` — the elevation is a keyboard-affordance, not a
pointer one (matches the `:focus-visible` discipline below). Fallback class toggled by a ≤6-LOC inline
guard ONLY when `!CSS.supports('selector(:has(*))')` (so modern engines run zero JS):

```ts
// Card.vue onMounted — runs only on non-:has() engines
if (!CSS.supports('selector(:has(*))')) {
  el.addEventListener('focusin',  () => el.classList.toggle('is-focus-within', el.matches(':focus-within')))
  el.addEventListener('focusout', () => el.classList.toggle('is-focus-within', el.matches(':focus-within')))
}
```

**(b) `GlassDock:has([data-state="open"])` — open-descendant surface response.** When a dock-hosted
trigger (`.dock-select-trigger[data-state="open"]`, a popover trigger, a `DockLayerGroup` open layer)
is open, the dock root can hold its elevated read. Today this requires the consumer to read dock state in
JS. New rule in `dock.css`, scoped to `.glass-dock`:

```css
.glass-dock:has([data-state="open"]) {
  background: var(--glass-bg-floating, var(--glass-bg-resting));
  border-color: var(--glass-border-floating, var(--glass-border-resting));
}
```

This composes with the existing `.glass-dock[data-held]` rung (`dock.css:325`) — same elevated surface,
different trigger; both redefine the same paints so they coexist. Fallback: the dock already carries
`data-state` and open-state data attributes from `useDockState`; the `@supports not selector(:has(*))`
block keys off the existing `.glass-dock.has-open` class the SFC can set from `useDockState` (no NEW JS —
`useDockState` already tracks open descendants for `dockHeld`):

```css
@supports not selector(:has(*)) {
  .glass-dock.has-open { background: var(--glass-bg-floating); border-color: var(--glass-border-floating); }
}
```

**(c) `LabeledField:has(:user-invalid)` — group error highlight.** The forms headline. When any
descendant control is `:user-invalid`, the whole field group highlights (the label reddens, the field
edge marks). Scoped to `.labeled-field`:

```css
.labeled-field {
  --field-label-color: var(--muted-foreground);     /* identity */
}
.labeled-field:has(:user-invalid) {
  --field-label-color: var(--destructive);
}
.labeled-field:has(:user-valid) .labeled-field-error { display: none; }  /* hide error text once valid */
```

`.labeled-field-label` (utilities.css:44) changes its `color:` declaration to read `var(--field-label-color, var(--muted-foreground))`. Fallback uses `.has-error`/`.has-valid` classes the
`useUserInvalidAria` bridge (W4.4) already toggles when it runs in fallback mode — no separate parent
listener needed.

**Retire vs keep:** No existing JS class-toggle is being removed in glass-ui src (these are NEW
behaviors). The retirement is in the **consumer** (muster's `VoterRow.vue:47-63` `touched` ref) — see
Coupling contract. The `@supports not selector(:has(*))` classes are the SOLE fallback (no alias). The
inline `CSS.supports` guards run zero JS on supporting engines.

**Fallback ladder:** `:has()` is Baseline Widely Available (2023). Per policy this would qualify for
"adopt natively, no fallback." BUT recipes (a) and (c) are user-experience-critical (focus elevation,
error highlight), so per the child-state-based-styling guide's MANDATORY clause we ship the
`@supports not selector(:has(*))` class fallback anyway. Recipe (b) is decorative (a surface tier shift)
— it could ship fallback-free, but since `useDockState` already exposes the class hook for free, we ship
the fallback at zero marginal cost. Net: all three carry the class fallback.

### W3.2 — individual-transform migration (every hover/press `scale()`/`translateY()` site)

Every `transform: scale(...)` / `transform: translateY(...)` that fires on a state change (`:hover`,
`:active`, `:focus`, a transition) mints a new stacking context ONLY in that state — a z-index/anchor
hazard, acute on `--z-dock` surfaces that host portaled popovers. Migration: convert to the `scale:` /
`translate:` longhands AND add the identity base (`scale: 1` / `translate: 0`) on the at-rest selector so
the stacking context exists at rest and does not flicker into being on hover.

**Fixed application-order caveat (binding):** individual transforms always apply in the order
`translate → rotate → scale → transform`, regardless of source order. Every migrated site here uses ONLY
`scale` or ONLY `translate` (or both, never combined with a `transform` function on the same element), so
the fixed order is a no-op for us. The two sites that combine motion (`.shadow-cartoon-*` uses
`translateY` for lift) stay single-property. No site needs `scale-before-rotate` ordering, so no site
retains `transform: scale()`. The one exception: `.dock-select-trigger__chevron` (`dock.css:1007`) uses
`transform: rotate(180deg)` for the open-state chevron flip — rotate is fine to migrate to `rotate: 180deg` but it is NOT a stacking-context hazard (no scale/translate, fires on a child glyph, no
z-index interplay), so it MAY stay as `transform: rotate()` OR migrate to `rotate:` for consistency;
recommend migrate-for-consistency since the chevron also needs no identity base hazard.

**Migration map** (old site:line → new form). Identity base added on the at-rest rule; the
state rule swaps the function for the longhand:

| Site | Old | New base (at-rest) | New state |
|---|---|---|---|
| `glass.css:136` `.glass-btn:hover` | `transform: scale(var(--scale-hover))` | add `scale: 1` to `.glass-btn` | `scale: var(--scale-hover)` |
| `glass.css:140` `.glass-btn:active` | `transform: scale(var(--scale-press))` | (covered by base above) | `scale: var(--scale-press)` |
| `utilities.css:138-144` `.tap-squish` | `transform: scale(var(--scale-press))` | `.tap-squish { scale: 1 }` | `.tap-squish:active { scale: var(--scale-press) }`; PRM `scale: 1` (not `transform: none`) |
| `utilities.css:114-116` `.interactive-item:active` | `transform: scale(0.98)` | add `scale: 1` to `.interactive-item` | `scale: 0.98` |
| `utilities.css:307-318` `.metric-badge` hover/active | `transform: scale(...)` ×2 | `.metric-badge { scale: 1 }` | `scale: var(--metric-badge-hover-scale)` / `var(--metric-badge-press-scale)` |
| `utilities.css:471-482` `.hover-lift*` | `transform: translateY(var(--lift-*))` | `:where(.hover-lift,…) { translate: 0 }` | `translate: 0 var(--lift-sm)` etc. |
| `utilities.css:497-508` `.shadow-cartoon-*` | `transform: translateY(-1px/-2px)` | (static, not state-driven — see note) | keep as `translate: 0 -1px` for cleanliness; identity not strictly required (no state change) |
| `utilities.css:544-550` `@utility scale-on-hover` | `transform: scale(var(--scale-hover))` | add `scale: 1` to the `@utility` base block | `&:hover { scale: var(--scale-hover) }` |
| `utilities.css:804-836` `@utility btn-interactive` | `transform: scale(...)` hover+active | add `scale: 1` to base | `&:hover { scale: var(--scale-hover) }` / `&:active { scale: var(--scale-press) }` |
| `dock.css:311` `.glass-dock.collapsed:hover` | `transform: scale(var(--dock-collapsed-hover-scale))` | `.glass-dock { scale: 1 }` (covers all dock scale sites) | `scale: var(--dock-collapsed-hover-scale)` |
| `dock.css:676,680` `.dock-icon-button` hover/active | `transform: scale(...)` | `.dock-icon-button { scale: 1 }` | `scale: var(--scale-hover-dock)` / `var(--scale-press-dock)` |
| `dock.css:710` `.dock-icon-button.is-active` | `transform: scale(var(--dock-active-scale))` | (base above) | `scale: var(--dock-active-scale)` |
| `dock.css:824` `.dock-tab-button:active` | `transform: scale(var(--scale-press-dock))` | `.dock-tab-button { scale: 1 }` | `scale: var(--scale-press-dock)` |
| `dock.css:967,971-973` `.dock-*-trigger` hover/active | `transform: scale(...)` | `.dock-select-trigger, .dock-dropdown-trigger { scale: 1 }` | `scale: var(--scale-hover-dock)` / `var(--scale-press-dock)` |
| `dock.css:1007` `.dock-select-trigger__chevron[data-state=open]` | `transform: rotate(180deg)` | `.dock-select-trigger__chevron { rotate: 0deg }` | `rotate: 180deg` |
| `glass.css:307-312` (same row as collapsed:hover) | — | — | — |

`transition` property names must update in lockstep: every rule that lists `transform var(--duration-…)` in its `transition` changes to list `scale` and/or `translate` (and `rotate` where migrated). E.g. `.glass-btn` transition `transform var(--duration-normal) var(--spring-snappy)` → `scale var(--duration-normal) var(--spring-snappy)`. The dock controls' transitions (`transform var(--dock-motion-fast)`) → `scale var(--dock-motion-fast)` (+ `rotate` for the chevron). The `--scale-*`/`--lift-*` tokens are unchanged (token-first: the values stay; only the property they feed changes).

**Retire vs keep:** the `transform:` function form is RETIRED at every state-driven site (no alias — the
old declaration is replaced, not duplicated). `.shadow-cartoon-*`'s `translateY` is a static lift (not
state-driven) so its migration to `translate:` is cosmetic-only; it MAY stay as `transform: translateY`
if a reviewer prefers, but converting keeps the family uniform. The `transform` property remains in the
codebase only where a function COMBINATION in a non-default order is required — there are zero such sites
in W3 scope.

**Fallback ladder:** individual transforms are Baseline Widely Available (2022). Adopt natively, no
fallback. (If a consumer's browserslist somehow targets pre-2022, the guide's `@supports not (translate: 0px)` re-declare-the-stack form is documented but NOT shipped — we do not carry it because glass-ui's
own browserslist floor is post-Baseline-2022.) The identity base is the mandatory anti-flicker measure,
not a fallback.

### W3.3 — `text-wrap` on the type ladder (per-element, never `*`)

Place `text-wrap` deliberately on specific type utilities (the guide + css §7 forbid `*`). Three
placements:

**`balance` on display/heading utilities** — `typography.css` heading and display ladder. Add
`text-wrap: balance` to the heading-tier utilities that render multi-line headline-like content:
`.text-heading`, `.text-title`, `.text-subheading`, `.text-display-1`…`.text-display-5`,
`.text-display-mega`, `.text-display-hero`, `.text-display-audacious`. Caveat from css §7: avoid
`balance` on elements with a visible box (background/border/shadow) — these type utilities are
text-only (no box), so balance is safe. Do NOT add it to `.text-hero` (it pins nowrap, see below).

**`pretty` on prose/body** — `.text-prose` and `.text-body` (the long-form reading registers) and the
`.section-description` recipe (utilities.css:32). `pretty` fixes orphans/rivers in paragraph text. Apply
to the prose-bearing utilities only, not to every text class.

**`nowrap` (text-wrap form) on the hero** — `typography.css:180` `.text-hero` currently uses
`white-space: nowrap`. Migrate to the modern semantic form. Per the prevent-text-wrapping guide, ship
BOTH for the fallback:

```css
@utility text-hero {
  /* …existing… */
  white-space: nowrap;   /* fallback for pre-text-wrap engines */
  text-wrap: nowrap;     /* modern standard — overrides when supported */
}
```

`text-wrap: nowrap` (modern) sits after `white-space: nowrap` (legacy) so supporting browsers honor the
modern form; non-supporting browsers fall through to `white-space`. No `@supports` gate needed —
declaration order + forgiving parse handles it (an unknown `text-wrap: nowrap` is simply ignored, leaving
`white-space: nowrap` active).

**Retire vs keep:** `white-space: nowrap` on `.text-hero` is KEPT as the sole fallback (per the guide's
both-declarations recipe) — it is not a live+dead alias, it is the documented degradation path. The
`balance`/`pretty` additions are net-new (no prior declaration to retire).

**Fallback ladder:** `text-wrap: nowrap`/`balance`/`pretty` — `balance` is Baseline Newly Available
(2023+), `pretty` Newly Available (2023+ Chromium, broader 2024). Both degrade gracefully to unbalanced
wrapping with zero layout break (the text still wraps, just less prettily) — so no `@supports` gate, no
JS fallback; the guide's degrade-gracefully clause applies. The `nowrap` migration ships the
`white-space` legacy line as its inline fallback.

### W4.1 — `:user-invalid` / `:user-valid` CSS rungs

The library's validation visual vocabulary, on `.input-pill` (consumed by Input + Textarea) and as a
group highlight on `.labeled-field` (W3.1c). Uses the existing `--destructive` / `--success` semantic
tokens (tokens.css:350/422), tinted via `color-mix` per the house pattern. New block in `glass.css`
adjacent to `.input-pill`:

```css
.input-pill:user-invalid {
  border-color: var(--destructive);
  background: color-mix(in srgb, var(--destructive) 8%, var(--glass-bg-quiet));
}
.input-pill:user-valid {
  border-color: var(--success);
}
/* The :focus rule (migrated to :focus-visible in W4.6) must not be overridden by
   :user-invalid on focus — order :user-invalid AFTER :focus-visible so an invalid
   focused field shows the destructive ring, not the accent ring. */
.input-pill:user-invalid:focus-visible {
  border-color: var(--destructive);
  box-shadow: 0 0 0 var(--focus-ring-width)
              color-mix(in srgb, var(--destructive) 35%, transparent);
}
```

Non-color reinforcement (forms guide MANDATORY — never color-alone): the error TEXT (W4.5 `error` slot)
+ the asterisk (W4.5 `required`) are the non-color indicators; the border/bg shift is the supplementary
cue. The `:user-valid` rung is intentionally subtle (border-color only, no bg) so a long valid form
isn't a wall of green.

**Retire vs keep:** net-new (grep 0 today). No `:invalid`/`:valid` rungs exist to retire — and we
deliberately do NOT add `:invalid`/`:valid` (they'd flag required-empty fields red on mount, the hostile
default css §5 warns against).

**Fallback ladder:** `:user-invalid`/`:user-valid` are Baseline Newly Available (2023, "user-pseudos").
Feature-detected fallback via the `useUserInvalidAria` composable (W4.4) which, when
`!CSS.supports('selector(:user-invalid)')`, toggles `.user-invalid-fallback`/`.user-valid-fallback`
classes. The CSS uses `:is()`/`:where()` forgiving-grouping per css §3.2 to avoid rule duplication:

```css
/* GOOD — one rule covers native + fallback (forgiving group; NOT a pseudo-element) */
.input-pill:where(:user-invalid, .user-invalid-fallback) {
  border-color: var(--destructive);
  background: color-mix(in srgb, var(--destructive) 8%, var(--glass-bg-quiet));
}
.input-pill:where(:user-valid, .user-valid-fallback) { border-color: var(--success); }
```

### W4.4 — `useUserInvalidAria` — the ≤8-LOC `aria-invalid` bridge (the J.W6/J.W7 contract)

The contract muster J consumes. Native `:user-invalid` is a VISUAL state and does NOT sync ARIA
(user-pseudos feature doc + the forms guides all flag this as MANDATORY). This composable is the single
canonical bridge: it (1) keeps `aria-invalid` in sync with `:user-invalid`, and (2) in fallback mode (no
`:user-invalid` support) ALSO toggles the `.user-invalid-fallback`/`.user-valid-fallback` classes the
W4.1 CSS keys off. It lives at `src/composables/dom/useUserInvalidAria.ts`, exported from the dom
sub-tree barrel and reachable on the root barrel (vueuse-free — uses only native listeners).

**Public API (exact signature):**

```ts
export interface UseUserInvalidAriaOptions {
  /** Also toggle .user-invalid-fallback / .user-valid-fallback classes.
   *  Default: auto — true only when CSS.supports('selector(:user-invalid)') is false. */
  fallbackClasses?: boolean
}
export interface UseUserInvalidAriaReturn {
  /** Attach to a scope root (form/fieldset/field wrapper). Idempotent; returns a stop fn. */
  bind: (root: HTMLElement) => () => void
}
export function useUserInvalidAria(opts?: UseUserInvalidAriaOptions): UseUserInvalidAriaReturn
```

**The ≤8-LOC core** (the load-bearing sync — this is the byte the gate measures):

```ts
const sync = (el: EventTarget | null) => {
  const c = el as HTMLInputElement | null
  if (!c?.checkValidity) return
  const ok = c.checkValidity()
  c.setAttribute('aria-invalid', ok ? 'false' : 'true')
  if (fallback) { c.classList.toggle('user-invalid-fallback', !ok); c.classList.toggle('user-valid-fallback', ok) }
}
```

Wired on `blur` (capture phase — show error on field-exit) and `input` (clear error on correction), per
the forms guide's Validation Event Timing Matrix. `aria-invalid` is only written after the user has
interacted with a field (the bridge tracks first-blur per control via a `WeakSet`, mirroring the native
`:user-invalid` "after interaction" timing — it must NOT set `aria-invalid="true"` on a pristine
required-empty field on mount). On `submit`, sync all controls (submission counts as interaction; the
browser focuses the first invalid field). `bind` returns a cleanup fn (`useEventListener`-style; native
`addEventListener`/`removeEventListener`, no vueuse).

**Consumer shape (what J writes):**

```ts
const { bind } = useUserInvalidAria()
onMounted(() => { const stop = bind(formEl.value!); onUnmounted(stop) })
```

**Retire vs keep:** this composable REPLACES the consumer-side hand-rolled `touched` ref pattern
(muster `VoterRow.vue:47-63`). In glass-ui it is net-new. The fallback class-toggle path is the SOLE
fallback for non-`:user-invalid` engines (no alias). The composable is the binary-consumer proof carrier:
it ships because muster J.W6/J.W7 adopt it (≥2 consumers) — if J does not adopt, it ships only with the
demo story (`demo/stories/forms/validation.vue`).

**Coupling to J (specified to the line):** J.W6/J.W7 import `useUserInvalidAria` from
`@mkbabb/glass-ui` (root barrel) and call `bind(formRoot)` once per form. The CSS rungs (W4.1) ship in
`@mkbabb/glass-ui/styles`. J's 106-spec regression suite asserts: aria-invalid is absent on mount, set
to `"true"` after blur on an invalid field, set to `"false"`/cleared on correction, and synced for all
fields on submit. The honest-gate principle binds: the spec checks the REAL `aria-invalid` attribute on
the rendered DOM, not a wrapper boolean.

### W4.2 — attr-passthrough contract + `inputmode="decimal"` NumberField default

**`Input.vue` attr-passthrough.** `<input v-model>` with Vue's default attr fall-through already lands
`autocomplete`/`inputmode`/`enterkeyhint`/`type`/`name`/`pattern`/`aria-*` on the rendered `<input>`
(single-root SFC, no `inheritAttrs:false`). The gap is DOCUMENTATION + a type-level guarantee, not a code
change. Add to `Input.vue`'s prop type an explicit (optional) pass-through doc block and confirm the SFC
stays single-root so fall-through holds. The contract (documented in the SFC header + CLAUDE.md forms
section):

> `<Input>` forwards every native `<input>` attribute to the rendered element. Consumers MUST set
> `autocomplete` (e.g. `email`, `current-password`, `new-password`, `postal-code`), `inputmode` (e.g.
> `numeric`, `decimal`, `email`, `tel`), `enterkeyhint` (e.g. `next`, `done`, `search`), and `type`
> (`text`/`email`/`tel`/`search`/`url`/`password`) per the forms-guide §3 matrix. Do NOT use
> `type="number"` for ZIP/credit-card (forms-guide §3 DON'T) — use `type="text" inputmode="numeric"`.

No new props (the attrs pass through natively); the contract is the deliverable. The one functional
change is the NumberField default below.

**`NumberFieldInput.vue` `inputmode="decimal"` default.** Currently (`NumberFieldInput.vue:16-21`) uses
`inheritAttrs:false` + `v-bind="$attrs"`, so a consumer-supplied `inputmode` already lands. The change:
provide `inputmode="decimal"` as the DEFAULT, overridable by `$attrs`. Order matters — the default must
come BEFORE `v-bind="$attrs"` so a consumer override wins:

```vue
<NumberFieldInput
  inputmode="decimal"
  v-bind="$attrs"
  data-slot="input"
  :class="cn('focus-ring flex h-10 w-full rounded-input border border-input bg-background py-2 text-sm text-center placeholder:text-muted-foreground disabled:cursor-not-allowed disabled:opacity-disabled')"
/>
```

`decimal` (not `numeric`) is correct for NumberField because reka-ui NumberField supports fractional/
negative values — `decimal` surfaces the decimal point on mobile keyboards. A consumer needing
integer-only passes `inputmode="numeric"` (wins via `$attrs`).

**Retire vs keep:** net-new default + doc; no prior contract to retire. The fall-through behavior is the
existing native mechanism (kept).

**Fallback ladder:** `autocomplete`/`inputmode`/`enterkeyhint` are HTML attributes, universally supported
(Baseline Widely Available, decade+); unknown values are ignored. No fallback needed.

### W4.3 — `field-sizing` autosize prop API

`<Textarea>` gains an `autosize?: boolean` prop (default `false` — fixed-size is the unchanged default,
which is also the no-op fallback). When `true`, the textarea gets `field-sizing: content` with vertical
auto-grow bounded by `min/max-block-size`. New rule + class binding:

```css
/* glass.css or a textarea rung */
.input-pill[data-autosize] {
  field-sizing: content;
  width: 100%;                 /* stable horizontal width (guide: prevents jarring shrink) */
  min-block-size: 3lh;         /* ~3 lines floor */
  max-block-size: var(--textarea-autosize-max, 12lh);   /* token-driven ceiling, then scrollbar */
  resize: vertical;            /* keep the manual handle */
}
```

```vue
<!-- Textarea.vue -->
<textarea
  v-model="modelValue"
  :data-autosize="autosize ? '' : undefined"
  :class="cn('input-pill py-2 text-sm', autosize ? '' : 'min-h-20', props.class)"
/>
```

Prop added to `defineProps`: `autosize?: boolean`. Note the existing fixed `min-h-20` (Textarea.vue:23)
is dropped ONLY when `autosize` is on (the `min-block-size: 3lh` floor replaces it); fixed mode keeps
`min-h-20` exactly as today.

**Retire vs keep:** the fixed `min-h-20` is KEPT for the default (non-autosize) path — that IS the no-op
fallback. The autosize path is additive.

**Fallback ladder:** `field-sizing` is Baseline Newly Available (Chromium 2024; Firefox/Safari trailing).
Per the form-fields-automatically-fit-contents guide, treat as progressive enhancement: on
non-supporting engines the textarea degrades to fixed `min-block-size: 3lh` with standard scroll — no
JS, no `@supports`, the unsupported `field-sizing` declaration is simply ignored and the `min/max-block-size` bounds still apply. We do NOT ship the complex grid-mirror JS fallback (the guide explicitly
recommends relying on default fixed behavior unless dynamic sizing is critical — it is not, for a glass
textarea).

### W4.5 — `required` prop + `error` slot on LabeledField / Label

**`Label.vue`** gains `required?: boolean`. When true, renders an asterisk after the label text (forms
guide + required-field-feedback: indicate required fields visually, BEFORE interaction). The asterisk is
decorative-to-AT (the `required` attr on the input is the semantic carrier) — mark it `aria-hidden`:

```vue
<Label v-bind="delegatedProps" :class="cn('text-small font-medium leading-none …', props.class)">
  <slot />
  <span v-if="required" class="text-destructive" aria-hidden="true"> *</span>
</Label>
```

Prop: `required?: boolean` added to the props type.

**`LabeledField.vue`** gains `required?: boolean` + an `error` slot. `required` threads the asterisk to
its label. The `error` slot renders an error message region that is hidden by default and revealed by the
W3.1c `:has(:user-invalid)` group rule. The region is wired to the control via `aria-errormessage` (the
consumer binds the control's `aria-errormessage` to the region's `id`; LabeledField generates the id):

```vue
<template>
  <div class="labeled-field">
    <IconTooltip v-if="tooltip" :text="tooltip">
      <label :class="cn('labeled-field-label', labelClass)">{{ label }}<span v-if="required" class="text-destructive" aria-hidden="true"> *</span></label>
    </IconTooltip>
    <label v-else :class="cn('labeled-field-label', labelClass)">{{ label }}<span v-if="required" class="text-destructive" aria-hidden="true"> *</span></label>
    <slot />
    <div v-if="$slots.error" :id="errorId" class="labeled-field-error" aria-live="polite">
      <slot name="error" />
    </div>
  </div>
</template>
```

New `.labeled-field-error` recipe in utilities.css (hidden by default; W3.1c reveals it on `:has(:user-invalid)`):

```css
.labeled-field-error {
  display: none;
  font-size: var(--type-small);
  color: var(--destructive);
  margin-block-start: 0.25rem;
}
.labeled-field:has(:user-invalid) .labeled-field-error { display: block; }
```

Props added to `LabeledField.vue`: `required?: boolean`. The `errorId` is a `useId()`-derived stable id
(Vue 3.5 `useId`). `aria-live="polite"` announces the error when revealed (forms guide §2: use aria-live
for dynamic errors). The consumer wires `aria-errormessage="<errorId>"` on the control via the existing
slot — OR LabeledField exposes `errorId` via slot props (`<slot :error-id="errorId" />`) so the slotted
control binds it.

**Retire vs keep:** net-new props + slot; no prior required/error affordance to retire. The four wrapper
SFCs (LabeledInput/Select/Slider/Switch) thread `required` through to `<LabeledField>` (one-line prop
forward each).

**Fallback ladder:** the asterisk + error text are plain DOM (no platform feature). The
`:has(:user-invalid)` reveal carries the W3.1 fallback (the `.has-error` class). On a
non-`:user-invalid`/non-`:has()` engine the error region is revealed by the `useUserInvalidAria` fallback
class-toggle + the `@supports not selector(:has(*))` `.labeled-field.has-error .labeled-field-error { display: block }` rule.

### W4.6 — `:focus-visible` consistency fix

`glass.css:213` `.input-pill:focus` uses bare `:focus` — inconsistent with `.focus-ring:focus-visible`
(utilities.css:81), `.glass-btn:focus-visible` (glass.css:143), and every dock control. A mouse click
currently shows the accent ring on `.input-pill`; it should show only on keyboard focus. Change:

```css
.input-pill:focus-visible {           /* was :focus */
  outline: none;
  border-color: var(--color-accent-opaque, var(--ring));
  box-shadow: 0 0 0 2px var(--color-accent, color-mix(in srgb, var(--ring) 30%, transparent));
}
```

Order this BEFORE the `:user-invalid` rungs (W4.1) so an invalid focused field shows destructive, not
accent (the `:user-invalid:focus-visible` rule in W4.1 wins by specificity + order).

**Retire vs keep:** the bare `:focus` selector is RETIRED (replaced, not aliased). No fallback needed —
`:focus-visible` is Baseline Widely Available (2022). For forced-colors a separate `@media (forced-colors: active) { outline }` rung is added in W1.1 (W2 scope) — referenced here only at the seam.

**Fallback ladder:** Baseline Widely Available. Adopt natively, no fallback. (Pre-2022 engines fall back
to UA `:focus` behavior, acceptable.)

### W4.7 — `GlassNativeSelect` primitive (gated on ≥2-consumer / muster adoption)

A NEW primitive on the customizable native `<select>` (`appearance: base-select` + `::picker(select)`),
for the LOW-OPTION, form-integrated case. The reka-ui `Select` (the 10-file JS rebuild) STAYS as the
rich/async/virtualized default — `GlassNativeSelect` is the simpler, more-accessible, form-native sibling,
NOT a replacement. Per the subpath naming-pairs convention this is a substrate-boundary pair.

**Why a new primitive, not a refit of reka-ui Select:** native `<select>` keeps the browser's focus
management, top-layer rendering, keyboard handling, IME, AT integration, and native form submission for
free (branded-select-styling guide) — the things the JS rebuild re-implements. For a fixed small option
set in a form, native is strictly better. The JS Select earns its weight only for async/searchable/
custom-rendered-option cases.

**API (exact shape):**

```ts
// src/components/custom/glass-native-select/GlassNativeSelect.vue
interface GlassNativeSelectOption { value: string; label: string; disabled?: boolean }
defineProps<{
  modelValue?: string
  options: readonly GlassNativeSelectOption[]
  name?: string                 // native form submission
  id?: string                   // <label for>
  required?: boolean
  placeholder?: string          // rendered as a disabled, value="" first option
  class?: HTMLAttributes['class']
}>()
defineEmits<{ 'update:modelValue': [value: string] }>()
```

Renders a real `<select>` with `appearance: base-select`, a `<button><selectedcontent></button>` custom
trigger, and `<option>` children. Subpath `@mkbabb/glass-ui/glass-native-select` (isolated chunk). CSS in
a new `glass-native-select.css` rung:

```css
@layer components {
  /* Only opt into base-select where supported; otherwise this is a normal styled <select> */
  @supports (appearance: base-select) {
    .glass-native-select,
    .glass-native-select::picker(select) { appearance: base-select; }
    .glass-native-select::picker(select) {
      /* float-tier glass picker — reuse .glass-floating tokens */
      background: var(--glass-bg-floating);
      backdrop-filter: var(--glass-blur-floating);
      border: 1px solid var(--glass-border-floating);
      border-radius: var(--radius-panel);
      box-shadow: var(--glass-shadow-floating);
    }
    .glass-native-select::picker-icon { color: var(--muted-foreground); }
    .glass-native-select option { padding: 0.375rem 0.75rem; border-radius: var(--radius-sm); }
    .glass-native-select option:hover { background: color-mix(in srgb, var(--accent) 40%, transparent); }
    .glass-native-select option::checkmark { color: var(--primary); }
  }
  /* Fallback (and base): a glass-pill <select> with a custom arrow via appearance:none */
  .glass-native-select {
    appearance: none;
    /* …composes .input-pill geometry + a background-image chevron… */
    max-inline-size: var(--glass-native-select-max, 24ch);   /* base-select drops auto-sizing */
  }
}
```

**Retire vs keep:** the reka-ui `Select` family is KEPT (the rich default) — NOT retired. This is a
sibling primitive, not an alias or replacement, so the no-backwards-compat rule is satisfied (no two
implementations of the SAME contract; they have different contracts — `options` array vs compound
slots). `GlassNativeSelect` SHIPS ONLY IF muster J.W6/J.W7 adopts it for ≥1 real form (giving it ≥2
consumers with the demo) — otherwise it ships behind the demo story only or is deferred to a later wave.
This is the binary-consumer gate stated explicitly per the AQ invariant.

**Fallback ladder:** `appearance: base-select` + `::picker(select)` is Baseline LIMITED (Chromium-only at
HEAD, 2025). Per policy: progressive-enhancement-only behind `@supports (appearance: base-select)`. The
DEFAULT path is the `appearance: none` styled `<select>` with a CSS background-image chevron (works
everywhere, Baseline Widely Available) — the `base-select` block is the enhancement layered on top. So
even where `base-select` is unsupported, `GlassNativeSelect` renders a fully-functional, branded native
select (just with the OS picker instead of the glass picker). NO JS polyfill. The reka-ui `Select` remains
the path for consumers who need the glass picker on ALL engines today.

## Hard gate (per-wave, measurable)

**W3 gate (selectors & transforms):**

- `:has()` — Playwright: `.glass-card` `box-shadow` computed value changes when a child input receives
  KEYBOARD focus (Tab), and does NOT change on mouse click; `.glass-dock` background shifts to
  `--glass-bg-floating` when a `[data-state="open"]` descendant exists. VR snapshot of focus-within
  elevation. Assert the JS class-toggle is absent on a `:has()`-supporting engine (the inline guard's
  listener count is 0).
- Individual transforms — grep gate: `rg "transform:\s*(scale|translate)" src/styles/` returns 0 hits at
  state-driven sites (only `transform:` remnants allowed are non-default-order combinations, of which
  there are 0). Every migrated at-rest selector carries `scale: 1` / `translate: 0` / `rotate: 0deg`. VR:
  dock + button hover/press identical to pre-migration; a popover opened over the dock still stacks ABOVE
  it during a dock hover (the stacking-context regression test — the load-bearing assertion).
- `text-wrap` — VR: a wrapping headline at narrow width is balanced (`.text-heading`); a long prose
  paragraph has no orphan last-word (`.text-prose`); `.text-hero` stays single-line. grep:
  `text-wrap: balance` present on heading/display utilities, `pretty` on prose/body, and `.text-hero`
  carries BOTH `white-space: nowrap` and `text-wrap: nowrap`.

**W4 gate (form vocabulary):**

- `:user-invalid`/bridge — Playwright: type an invalid email into an `.input-pill`, blur → border becomes
  `--destructive` AND `aria-invalid="true"` lands (NOT before blur, NOT on mount); correct it → border
  clears AND `aria-invalid` becomes `"false"`/removed; submit an empty required field → all required
  fields gain the invalid paint + `aria-invalid`. axe: aria-invalid synced, no `aria-prohibited`/`aria-allowed` violations. Fallback path: with `:user-invalid` support stubbed off (force
  `CSS.supports → false`), the `.user-invalid-fallback` class toggles on the same timeline.
- attr-passthrough — Playwright: `<Input autocomplete="email" inputmode="email" enterkeyhint="next">`
  renders an `<input>` carrying all three attrs. NumberField default: `<NumberFieldInput>` with no attr
  renders `inputmode="decimal"`; with `inputmode="numeric"` override renders `numeric` (override wins).
- `field-sizing` — Playwright on a `<Textarea autosize>`: typing 5 lines grows the element with NO
  scrollbar; typing past `max-block-size` (12lh) stops growing and shows a vertical scrollbar. Non-autosize
  `<Textarea>` keeps its fixed `min-h-20` height. `@supports not (field-sizing: content)` path: the
  element keeps `min-block-size: 3lh` and scrolls (no JS error).
- `required` + error slot — axe: the asterisk renders (`aria-hidden`), `aria-invalid` appears only
  post-blur, the `error` region carries `aria-live="polite"` and is hidden until `:user-invalid`. Visual:
  asterisk present in the label.
- `GlassNativeSelect` (only if adopted) — Playwright: keyboard navigation (ArrowDown/Enter) updates the
  value AND a wrapping `<form>` submits the selected value; axe clean; VR gated on
  `CSS.supports('appearance', 'base-select')` (snapshot the glass picker where supported, the OS picker
  where not). If NOT adopted by J: the overfitting audit flags it → it ships demo-only or is deferred.
- `:focus-visible` — Playwright: mouse-click an `.input-pill` → NO accent ring; Tab to it → accent ring
  appears. Invalid + keyboard-focused → destructive ring (not accent).

**Standing gates (every wave):** `npm run typecheck` green; `npm run build` green; `npm run profile:budget` no regression (the new `useUserInvalidAria` is tiny, `GlassNativeSelect` is an isolated
subpath chunk — neither inflates an existing leaf); the overfitting audit at AQ.W8 confirms every new
artefact (`useUserInvalidAria`, `.labeled-field-error`, `GlassNativeSelect`, the `required`/`error`/`autosize` props) has ≥2 consumers OR a demo OR is not shipped.

## Risks + open questions

- **`:user-invalid` on a `v-model` input.** Vue's `v-model` writes the value programmatically; native
  validity recomputes on the actual `input`/`change` events `v-model` dispatches, so `:user-invalid`
  fires correctly on real user interaction. Risk: a programmatic model write (not user-driven) could be
  treated as interaction by the bridge's `input` listener. Mitigation: the bridge's `input` handler only
  CLEARS errors (never sets them) — setting is blur/submit-gated — so a programmatic write can at worst
  clear a stale error, never mint a false one. Verify in the W4 Playwright suite.
- **`GlassNativeSelect` adoption is the live gate.** It ships ONLY if muster J adopts it. Open question
  for the impl phase: does J's form set have a low-option select that wants native semantics? If yes →
  ship. If no → demo-only or defer to a successor wave. This is recorded, not pre-decided.
- **`field-sizing` + flex/grid stretch.** The guide warns grid/flex parents stretch children, defeating
  `field-sizing`. `<Textarea autosize>` inside a flex column may need `align-self: start`. The autosize
  rung does NOT set it (it's layout-context-dependent); document the caveat in the prop's JSDoc and the
  demo so consumers add `align-self: start` when needed.
- **`balance`/`pretty` performance on long lists.** css §7: `balance` has a cost; do not over-apply. The
  design scopes it to heading/display utilities (short text) and `pretty` to prose — both bounded. Risk
  only if a consumer slaps `.text-heading` on a 500-item list; out of scope (consumer choice), but note
  it in the typography doc.
- **`:has()` recipe (b) double-elevation.** `.glass-dock:has([data-state="open"])` and
  `.glass-dock[data-held]` both elevate to `--glass-bg-floating`. They coexist (same target paint) so
  there's no conflict, but if a future tier wants them to STACK (open + held = even higher), the design
  would need a third rung. Currently they're idempotent (both → floating); flagged for the impl reviewer.
- **`error` slot id wiring.** The consumer must bind `aria-errormessage="<errorId>"` on the control.
  LabeledField exposes `errorId` via the default slot's slot-props so the slotted control can bind it.
  Open: whether to auto-wire it for the four LabeledInput/Select/Slider/Switch wrappers (they own their
  control, so they CAN auto-bind) — recommend auto-wiring in the four wrappers, manual for the raw
  `<LabeledField>` slot. Confirm in impl.
