# AQ.W1.1 — Color & theming (design slice)

The design slice that binds **AQ.W2 (Color & theming modernization)** plus the scrollbar-token
row carried forward from **AQ.W3**. It resolves every shape AQ.W2 declared — where
`color-scheme` lands, how the 142-line `.dark` mirror collapses onto `light-dark()` without
the inheritance gotcha, the exact `hsl(var(--token)/α)` → `color-mix()` rewrite that fixes the
**live muster bug**, `accent-color`, and the forced-colors focus fallback — so W2 implements
against a settled target. No `src/`, `src/styles/`, or consumer file is touched in this slice;
every claim is line-anchored to HEAD.

The W2 hard gate (token-proof: computed-value-identical before/after, plus the light+dark VR
grid and the consumer-hairline-paints VR) reads its merge scope from this doc.

---

## Scope

Waves designed: **AQ.W2** (all five rows of the W0 matrix §AQ.W2) + the **scrollbar-token row
of AQ.W3** (the `--scrollbar-thumb`/`-track` tokens auto-dark via W2; the `scrollbar-width` +
`@supports not` webkit fallback structure ships in W3, but the tokens are minted here so the
dark mirror is correct on day one).

W0 findings addressed (W0-modern-web-baseline.md §AQ.W2, file:line grounded):
1. Zero `color-scheme` in `src/styles/` — native UI (scrollbars, spinbuttons, focus) stays
   OS-light in dark theme.
2. The 142-line `.dark` mirror re-declares ~40 paired color tokens (`tokens.css:1144-1286`).
3. **Live consumer bug**: glass-ui tokens are full `hsl()` colors, NOT channels, so a consumer's
   `hsl(var(--border) / α)` is malformed and never paints (muster `styles.css:211`, **64
   bug-class sites** across 16 files).
4. Zero `accent-color` — native controls render OS-default, ignore the brand.
5. Focus rings are `box-shadow` + `outline: none` with no forced-colors fallback
   (`utilities.css:81`, `glass.css:143`, `glass.css:213`); zero `forced-colors` brackets.

**One correction the W0 matrix inherits and this slice resolves.** The W0 row 3 framing ("tokens
are full `hsl()` not channels, so consumer `hsl(var(--border)/α)` is malformed") is exactly right
at HEAD, but the AP.W1.1 investigation already proved the corollary the *library* relies on:
glass-ui ITSELF never consumes a token as `hsl(var(--x)/α)` — its alpha composition is already
`color-mix(...)` (`tokens.css:583-587`, `:454-472`; `glass.css:133`). So the W2 migration is a
**consumer-side fix + a doc reconcile**, not a library-internal rewrite. The library's job in W2
is to (a) keep every token a complete `hsl()` so the channel-form mistake is impossible to make,
(b) ship the `--border-soft` rung consumers reach for instead of hand-mixing, and (c) fix the
two stale CLAUDE.md convention lines that *taught* the channel form. The cross-repo handoff (§Design 3)
rewrites muster's 64 sites.

## Design

### 1. `color-scheme` placement

**Lever (W0):** `color-scheme: light dark` on `:root` (`tokens.css`) + `color-scheme: dark` in `.dark`.

**Baseline status:** `color-scheme` is **Baseline Widely Available** → adopt natively, no fallback.
The property is itself progressive-enhancement (older engines ignore it and keep default light UI),
so no `@supports` guard is warranted (per `color-scheme.md` §Fallbacks: "Browsers that do not
support it will ignore this property").

**Exact placement.**

```css
/* tokens.css — at the TOP of the :root block (new, immediately under the `:root {` open,
   before the §0 theme-bridge fallbacks at line 14) */
:root {
    color-scheme: light dark;
    /* … existing §0 …§19 tokens unchanged … */
}

/* tokens.css — FIRST declaration inside the existing `.dark` block (line 1144) */
.dark {
    color-scheme: dark;
    /* … existing ~40 dark token overrides unchanged in W2 row 1 … */
}
```

Rationale for `light dark` (not `only light`) on `:root`: the library must let the consumer's
`prefers-color-scheme` drive native UI when the consumer has NOT pinned a class. glass-ui's dark
mode is class-driven (`.dark`, `@variant dark (&:where(.dark, .dark *))` at `theme.css:361`), so
`.dark` forces `color-scheme: dark` regardless of OS — but absent `.dark`, native form controls /
scrollbars / focus rings should still honor the OS preference. `light dark` on `:root` delivers that;
`.dark` overrides to a hard `dark`.

**No `only` keyword.** `color-scheme: dark` (not `only dark`) in `.dark` — we WANT browsers free to
adapt a forced-light embed (e.g. a media element a consumer scopes to `color-scheme: light`); `only`
is the wrong default for a design-system substrate (per component-specific-light-dark-theme guide §48).

**Consumer handoff note (muster):** muster currently declares `color-scheme: light` at
`styles.css:61` (a consumer-local pin from before glass-ui shipped dark tokens). Once glass-ui ships
`color-scheme: light dark` at `:root`, muster's `:61` declaration SHADOWS it back to light-only and
must be deleted (or upgraded to `light dark`) for native dark UI to engage — listed in the J handoff
(§Coupling contract). muster `styles.css:424` already sets `color-scheme: light dark` on the
score-fairness SVG; that stays (it is a component-local cross-mode pin and is correct).

**Retire vs keep:** nothing retired. The `.dark` class mechanism stays as the canonical dark trigger
(no-backwards-compat-alias: there is no second mechanism to remove). `color-scheme` is purely additive.

### 2. The `light-dark()` token architecture (collapsing the 142-line `.dark` mirror)

**Lever (W0):** rewrite color tokens as `light-dark(…)` (kept UNregistered per the inheritance
gotcha); `@supports` + retained `.dark` hook as the fallback; non-color tokens stay in `.dark`.

**Baseline status:** `light-dark()` is **Baseline Newly Available** → adopt with a feature-detected
fallback ≤ 20 LOC, no new deps. The fallback here is the **retained `.dark` block** (it already
exists), so the net new LOC for the fallback is **zero** — we keep the class-based mirror as the
sole non-`light-dark()` path and layer `light-dark()` on top under `@supports`.

#### 2a. Which tokens convert

Only **paired color tokens** convert — a token that has BOTH a `:root` value and a different `.dark`
value, where both values are `<color>`. The conversion folds the pair into one `:root` declaration:

```css
--token: light-dark(<light-value>, <dark-value>);
```

The **convertible pair set** (light site → dark site, both confirmed at HEAD):

| Token | light (`:root`) | dark (`.dark`) |
|---|---|---|
| `--foreground` | `hsl(24 10% 10%)` `:321` | `hsl(48 10% 90%)` `:1161` |
| `--card` | `var(--neutral-0)` `:322` | `hsl(24 8% 10%)` `:1162` |
| `--popover` | `var(--neutral-0)` `:324` | `hsl(24 8% 10%)` `:1164` |
| `--surface-public-data-panel` | `hsl(44 16% 96%)` `:332` | `hsl(36 9% 12%)` `:1170` |
| `--primary` | `hsl(24 10% 10%)` `:348` | `hsl(48 10% 90%)` `:1185` |
| `--primary-foreground` | `var(--neutral-0)` `:349` | `hsl(24 10% 10%)` `:1186` |
| `--destructive` | `hsl(0 72% 50%)` `:350` | `hsl(0 62.8% 30.6%)` `:1187` |
| `--destructive-foreground` | `var(--neutral-0)` `:351` | `hsl(48 10% 90%)` `:1188` |
| `--ring` | `hsl(24 10% 10%)` `:352` | `hsl(48 10% 70%)` `:1189` |
| `--shadow` | `hsl(24 10% 10%)` `:353` | `hsl(0 0% 5%)` `:1190` |

| `--gold`/`-light`/`-dark` | `:946-948` | `:1283-1285` |

**The semantic-alias subtlety.** Tokens like `--muted: var(--neutral-1)`, `--border: var(--neutral-4)`,
`--secondary: var(--neutral-2)`, `--accent: var(--neutral-3)`, `--muted-foreground: var(--neutral-5)`,
`--muted-foreground-strong: var(--neutral-6)`, `--card-foreground: var(--foreground)` are
`var()`-aliases that point at the SAME source name in both modes — only the **source** (`--neutral-*`,
`--foreground`) differs by mode. These DO NOT convert directly; they auto-track once the
`--neutral-*` ladder and `--foreground` convert to `light-dark()`. Leaving the aliases as
`var(--neutral-N)` is correct AND is the dynamic-resolution win: because the alias is an unregistered
custom property holding a `var()` (not a resolved color), it re-resolves under a descendant
`color-scheme` override. Folding `--border`'s value inline would freeze it.

The `.dark` block's `--muted: var(--neutral-1)` … re-declarations (`:1172-1183`) become **redundant**
once `--neutral-*` are `light-dark()` and DELETE from `.dark` — that is the bulk of the 142-line
collapse. The `var()`-alias level needs no per-mode statement at all.

#### 2b. The inheritance-safe UNREGISTERED-custom-property discipline (the resolve-late gotcha)

This is the load-bearing constraint, per css guide §5 (line 246) and the
component-specific-light-dark-theme guide §61-76.

**The gotcha.** `light-dark()` resolves at **computed-value time**, keyed off the element's
`color-scheme`. If a token holding a `light-dark()` value is a **registered** `<color>` custom
property (`@property … syntax: "<color>"; inherits: true`) OR is an inherited built-in `<color>`
property, it resolves ONCE at the declaring element and inherits the RESOLVED color — it will NOT
re-resolve under a descendant `color-scheme` override (e.g. a `.dark` code-block embedded in a light
page, or vice-versa).

**The discipline (BINDING for W2):**
- **DO NOT** register any color *design token* with `@property … syntax: "<color>"`. glass-ui's design
  tokens (`--foreground`, `--card`, `--neutral-*`, the `--section-color-*`, etc.) MUST stay
  **unregistered** so they keep the `light-dark()` expression live and descendants re-resolve under
  their own `color-scheme`. At HEAD glass-ui registers only THREE typed properties (§18,
  `tokens.css:1288+`) and **none are colors** (they are percentage/length cross-fade targets) — so the
  discipline is already satisfied; W2 must NOT add color `@property` registrations.
- **DO** re-specify any inherited built-in `<color>` property on every element that overrides
  `color-scheme`. The two such properties this slice introduces are `accent-color` (§Design 4) and the
  `color`/`background` pairing. The `.dark` rule already sets the surface; the `accent-color: var(--accent-color)`
  line must be REPEATED inside `.dark` (and inside any consumer `color-scheme`-override element) even
  though it reads the same token — otherwise the accent freezes to the light shade. This is encoded as
  the §Design 4 `.dark { accent-color: … }` line.
- **DO NOT** use `inherit` on a `<color>` property at a `color-scheme` boundary. glass-ui has no such
  site today; W2 must not introduce one.

#### 2c. The `@supports` + retained-`.dark` fallback ladder

```css
/* tokens.css :root — the light-dark() layer, GATED so non-supporting engines ignore it */
@supports (color: light-dark(white, black)) {
    :root {
        --foreground: light-dark(hsl(24 10% 10%), hsl(48 10% 90%));
        --card:       light-dark(var(--neutral-0), hsl(24 8% 10%));
        /* … every convertible pair from §2a … */
        --neutral-0:  light-dark(hsl(48 12% 98%), hsl(24 8% 6%));
        /* … --neutral-1 … --neutral-6 … */
        /* … --section-color-0 … -12, viz, chart-label, semantic, gold … */
    }
}
```

The **fallback** is the EXISTING `.dark { … }` class block (`tokens.css:1144-1286`), kept verbatim
for every convertible token. Resolution order:
- **Engine WITHOUT `light-dark()`** (older): `:root` carries the light value (the
  `@supports`-gated `light-dark()` block is skipped); `.dark` class still overrides to dark. **Identical
  behavior to HEAD.**
- **Engine WITH `light-dark()`, no `.dark` class:** `:root color-scheme: light dark` + the
  `light-dark()` tokens resolve to light or dark by OS preference. **NEW capability** (OS-driven dark
  without a consumer class — but only when the consumer has not pinned `.dark`/`color-scheme`).
- **Engine WITH `light-dark()`, `.dark` present:** `.dark { color-scheme: dark }` makes every
  `light-dark()` token resolve to its dark arm; the retained `.dark` class block's explicit dark
  values are now mostly redundant for the convertible tokens BUT are kept as the fallback ladder's
  floor (they cost nothing and guarantee the class works on non-`light-dark()` engines).

**Important: this is NOT a both-paths-live violation of no-backwards-compat-alias.** The `.dark` class
is the SOLE fallback path, not a parallel alias — `light-dark()` is the enhancement *over* it, and on a
supporting engine with `.dark` present the two agree on the same dark value. The class block stays
because retiring it would break the class-driven dark trigger on non-`light-dark()` engines (the
fallback floor). We do NOT keep two *different* mechanisms producing the same effect; we keep one
mechanism (class) with an enhancement layered on.

**Net LOC.** The `.dark` block shrinks: the ~30 `var()`-alias re-declarations (`:1172-1183` muted/
secondary/accent/border/input cluster, plus any pure-alias line) DELETE; the explicit-color dark
values STAY as the fallback floor. The `@supports`+`light-dark()` block ADDS ~40 lines. Net is roughly
flat in line count — the WIN is correctness (native UI dark, §1) + dynamism (descendant `color-scheme`
re-resolution), not byte reduction. (The W0 "142-line mirror collapses" framing is about the
*architecture* collapsing to a single source of truth, not a raw line-count delta.)

#### 2d. Which NON-color tokens stay in `.dark`

`light-dark()` works for `<color>` ONLY (component-specific-light-dark-theme guide §52). Every
non-color dark override STAYS as a `.dark` declaration. The confirmed stay-set:

| Stays in `.dark` | Site | Why |
|---|---|---|
| `--glass-opacity-{wash,quiet,resting,floating,overlay,chassis}` | `:1260-1265` | unitless number, not a color |
| `--glass-grain-opacity` | `:1266` | number |
| `--glass-highlight` / `--glass-specular` | `:1267`, `:1275` | `inset … <shadow>` (not a plain color) |
| `--hairline-catch-light` / `--hairline-under-shadow` | `:1270-1271` | shadow values |
| `--glass-curvature-overlay` | `:1276` | gradient |
| `--shadow-cartoon{,-hover}` / `--shadow-soft` / `--shadow-elevated` / `--shadow-modal` | `:1246-1252` | composite shadow strings (the `rgba(0,0,0,.3)` darks differ from light's `color-mix` — these are full shadow expressions, not `<color>`) |
| `--shadow-cartoon-color{,-soft}` | `:1254-1255` | `rgb(255…)` vs light `rgb(0…)` — a plain color, BUT see note |
| `--meter-track-stroke` | `:1228` | `var()` alias — auto-tracks, can DELETE if its source converts |

**Note on `--shadow-cartoon-color`/`-soft`:** these ARE plain colors (`rgb(255 255 255 / 0.07)` dark
vs `rgb(0 0 0 / 0.12)` light) and COULD convert to `light-dark()`. Convert them — they meet the
"both values are `<color>`" bar. They move into the §2c `@supports` block; their `.dark` lines stay as
the fallback floor.

### 3. The `color-mix()` alpha migration map (fixes the live muster bug)

**Lever (W0):** migrate alpha derivatives to
`color-mix(in srgb, var(--token) Nα%, transparent)`; add a `--border-soft` rung; reconcile the
CLAUDE.md channel-convention doc.

**Baseline status:** `color-mix()` is **Baseline Widely Available** → adopt natively. (`@supports`
not needed; if a browser supports `color-mix()` it supports the `in <color-space>` arg — css guide
§387.) The house already uses this exact pattern at 50+ internal sites (`--surface-tint-*`,
`--glass-bg-*`, the shadow stack), so this is the canonical form, not a new invention.

#### 3a. The exact rewrite rule

For any consumer site of the malformed form:

```css
/* BEFORE (malformed — --TOKEN is a full hsl() color, so this double-wraps → invalid → never paints) */
hsl(var(--TOKEN) / α)          /* e.g. hsl(var(--border) / 0.45) */
hsl(var(--TOKEN))              /* bare double-wrap, also invalid */

/* AFTER (canonical — N = α × 100) */
color-mix(in srgb, var(--TOKEN) Nα%, transparent)   /* e.g. color-mix(in srgb, var(--border) 45%, transparent) */
var(--TOKEN)                                         /* bare case: the token IS already a color — drop the hsl() wrapper */
```

Worked from the muster sites:
- `hsl(var(--border) / 0.45)` → `color-mix(in srgb, var(--border) 45%, transparent)` (muster `styles.css:211`)
- `hsl(var(--card) / 0.4)` → `color-mix(in srgb, var(--card) 40%, transparent)` (`PresetRail.vue:72`)
- `hsl(var(--background))` → `var(--background)` (drop wrapper; `App.vue:415`)
- `hsl(var(--foreground))` → `var(--foreground)` (`App.vue:416`)
- `hsl(var(--border, 0 0% 80%) / 0.6)` → `color-mix(in srgb, var(--border) 60%, transparent)` — the
  channel-form FALLBACK arg (`0 0% 80%`) is ALSO obsolete (a bare `var(--border)` is now always a full
  color); drop it. (`RankedVerdict.vue:331`)
- `hsl(var(--success, 142 70% 35%))` → `var(--success)` — same; drop the channel fallback
  (`SettingsDialog.vue:317`). glass-ui ships `--success` (`tokens.css:422`), so the fallback never
  fires anyway.

#### 3b. What must NOT migrate (the legitimate channel composites)

muster authors its OWN channel tokens for the hue-signal system (`styles.css:322-331`:
`--signal-rating-h: 38; --signal-rating-s: 75%; --signal-rating-l: 60%`, and the `--origin-hue-N-{h,s,l}`
family). Sites that compose THESE are correct and STAY:

```css
hsl(var(--origin-hue-${i}-h) var(--origin-hue-${i}-s) var(--origin-hue-${i}-l))   /* CORRECT — keep */
hsl(var(--signal-${safe}-h, var(--primary)) var(--signal-${safe}-s, 65%) var(--signal-${safe}-l, 55%))
```

These are NOT double-wraps — each `var()` supplies one channel of a freshly-composed `hsl()`. The
migration map excludes them. **6 such sites** (`TravelMatrix.vue:57`, `RankedVerdict.vue:136`,
`WhyThisWonSheet.vue:123`, `WinnerHero.vue:129`/`:335`, plus the signal composite).

#### 3c. The consumer-side count + cross-repo handoff

Census (`grep -rnE 'hsl\(var\(--' frontend/src`, classified):

| Class | Count | Action | Owner |

1. **Keep every token a complete `hsl()`** (no regression to channels) — the token-proof gate (§Hard

The J-side rewrite is a mechanical sweep gated by `grep -rnE 'hsl\(var\(--(border|card|foreground|background|muted|muted-foreground|primary|secondary|accent|destructive|success|warning|info|popover|input|ring)' frontend/src → 0 matches`, run against the J VR suite (the 106-spec bar) so the
hairlines that NOW PAINT are snapshotted before/after — the W0 gate ("VR shows muster hairlines paint").
This is an additive, honest-gate change on the consumer side: no server change, no spec-count change,
the suite stays green throughout.

#### 3d. The new `--border-soft` rung

The most common bug-class shape is a low-alpha border hairline (`hsl(var(--border) / {0.45, 0.6})`).
Ship a named token so consumers compose a rung instead of hand-mixing (token-first invariant), and so
the dark mirror is correct automatically:

```css
/* tokens.css :root — adjacent to the --surface-tint-* / --muted-soft cluster (~line 384) */
/* Border hairline at whisper alpha — the canonical rung for section-spine / panel-edge
   hairlines a consumer wants to read as an iOS-26 whisper rather than a hard rule.
   Auto-dark via --border (which is var(--neutral-4), light-dark()-resolved). */
--border-soft: color-mix(in srgb, var(--border) 45%, transparent);
```

And its `@theme` bridge (so `border-border-soft` / `bg-border-soft` utilities exist):

```css
/* theme.css — adjacent to --color-border (line 57) */
--color-border-soft: var(--border-soft);
```

**45% is the canonical rung** (matches muster's settled `styles.css:211` value after its W7 §2(b)
tune from 0.6→0.45). The 0.6 sites (`RankedVerdict.vue:331`) migrate to a literal
`color-mix(... 60% ...)` (one-off, not a rung — ≥2-consumer bar not met for a `--border-soft-60`).
**≥2-consumer check:** `--border-soft` has the section-spine (`styles.css:211`) + the panel-edge
hairlines (`PresetRail.vue`, `ScoreFairnessField.vue:260`, `CommandPalette.vue:680`) → ≥2 consumers,
ships. If muster J does NOT adopt it (uses raw `color-mix` instead), the rung does NOT ship — gated on
real adoption.

#### 3e. The CLAUDE.md channel-convention doc reconcile

Two CLAUDE.md lines TEACH the obsolete channel form and are the root cause consumers cargo-culted:

- **Line 167:** `- Color palette as HSL channels: \`--primary: 222.2 47.4% 11.2%\`, consumed as \`hsl(var(--primary))\` in \`@theme\``
  → **REWRITE** to: `- Color tokens are complete \`hsl()\` colors: \`--primary: hsl(24 10% 10%)\`, consumed directly as \`var(--primary)\`. NEVER \`hsl(var(--token))\` (the token is already a color — double-wrapping is invalid and never paints). For an alpha derivative use \`color-mix(in srgb, var(--token) N%, transparent)\` (the \`--surface-tint-*\` / \`--border-soft\` house pattern).`
- **Line 166:** `- All shadows use \`hsl(var(--shadow-color) / alpha)\` format`
  → **REWRITE** to: `- All shadows compose via \`color-mix(in srgb, var(--shadow-color) N%, transparent)\` over \`--shadow-color: var(--foreground)\` (tokens.css §7).`

Both are stale prose (the actual code uses the new form already, per AP.W1.1's audit). This reconcile
is a W2 deliverable (it is what makes the consumer fix STICK — a consumer reading the old line
re-introduces the bug). The token-proof gate does not cover prose; a `grep` assertion does (§Hard gate).

### 4. `accent-color` on `:root` + the dark-contrast shade

**Lever (W0):** `accent-color: var(--primary)` on `:root` (+ a dark-contrast shade).

**Baseline status:** `accent-color` is **Baseline Widely Available** → adopt natively, no fallback
(it is progressive-enhancement; unsupporting browsers use default control colors — accent-color.md
§Fallbacks).

**The placement + the inheritance discipline (ties to §2b).** `accent-color` is an inherited built-in
`<color>` property. If we set it to a `light-dark()`-bearing token it resolves at `:root` and inherits
the RESOLVED color — so per the §2b discipline we set it from a dedicated **unregistered** token and
RE-SPECIFY it inside `.dark`.

```css
/* tokens.css :root — in the color block, after --primary (line 348) */
--accent-color: var(--primary);   /* light: muted-black checkmarks/sliders on warm cream */

:root {
    /* … */
    accent-color: var(--accent-color);   /* inherited; native checkbox/radio/range/progress brand */
}

/* tokens.css .dark — re-specify (the §2b mandate): without this, accent freezes to the light primary */
.dark {
    color-scheme: dark;                  /* §1 */
    accent-color: var(--accent-color);   /* re-resolves --primary's dark arm (hsl(48 10% 90%)) */
    /* … */
}
```

**The dark-contrast shade.** In dark mode `--primary` is `hsl(48 10% 90%)` (near-white). A near-white
`accent-color` makes a checkbox's white checkmark invisible (the contrast issue accent-color.md §5
warns about: Chrome/Safari auto-pick a contrasting checkmark, but a near-white accent leaves nothing to
contrast against). So the dark accent must NOT be near-white. Define a dedicated dark accent that has
headroom for a contrasting glyph:

```css
/* tokens.css .dark — the dark accent is the RING shade, not the near-white primary */
--accent-color: var(--ring);   /* dark: hsl(48 10% 70%) — mid-tone, leaves room for a dark checkmark glyph */
```

So `--accent-color` is `var(--primary)` in light and `var(--ring)` in dark — implemented as the §2c
`light-dark()` pair (it is itself a color token, so it joins the `@supports` block) OR, simpler and
explicit, set per-mode (light value at `:root`, dark value re-specified in `.dark`). **Use the
explicit per-mode form** for `--accent-color` (not `light-dark()`): because `accent-color` must be
re-specified at the `.dark` element ANYWAY (the §2b inheritance rule), the per-mode token form costs
nothing extra and is clearer than a `light-dark()` that then needs re-specifying.

**Contrast assertion (gate):** the dark `--accent-color` (`hsl(48 10% 70%)`, L≈70) against a white
checkmark glyph yields ≥ 3:1 — the W0 "contrast assertion" row. Light `--primary` (L≈10) against its
white glyph is trivially high-contrast.

**Retire vs keep:** purely additive. No prior `accent-color` exists to retire.

### 5. The forced-colors focus fallback block

**Lever (W0):** `@media (forced-colors: active)` → `outline: 2px solid Highlight` on `:focus-visible`;
companion `border`/`outline` for structural `box-shadow` hairlines.

**Baseline status:** `forced-colors` media query + system color keywords (`Highlight`, `CanvasText`,
`ButtonText`) are **Baseline Widely Available** → adopt natively. This is itself the FALLBACK mechanism
(it only activates under Windows High Contrast / forced-colors), so no nested guard.

**The problem at HEAD.** Focus is drawn with `box-shadow` + `outline: none` at three sites:
- `.focus-ring:focus-visible` — `outline: none; box-shadow: var(--focus-ring-shadow)` (`utilities.css:81-85`)
- `.glass-btn:focus-visible` — `outline: none; box-shadow: var(--focus-ring-shadow)` (`glass.css:143-146`)
- `.input-pill:focus` — `outline: none; box-shadow: 0 0 0 2px …` (`glass.css:213-217`) — note this is
  also the AQ.W4 `:focus` → `:focus-visible` row; the forced-colors block applies to whichever selector
  W4 settles on.
- `.interactive-item:focus-visible` — same `box-shadow` pattern (`utilities.css:110-113`).

In forced-colors mode the browser STRIPS `box-shadow` (css guide §252) — so EVERY focus ring vanishes,
leaving keyboard users with no visible focus (a WCAG 2.4.7 failure that forced-colors mode exposes).

**The fix — a single forced-colors block in `utilities.css`** (cascade home for focus utilities),
restoring an `outline` for every focus surface:

```css
/* utilities.css — new block, OUTSIDE the @layer (or in the utilities layer), after the focus-ring rule */
@media (forced-colors: active) {
    /* box-shadow focus rings are stripped in forced-colors — restore a real outline.
       Highlight is the system focus color; outline survives forced-colors, box-shadow does not. */
    .focus-ring:focus-visible,
    .glass-btn:focus-visible,
    .interactive-item:focus-visible,
    .input-pill:focus-visible {
        outline: 2px solid Highlight;
        outline-offset: 2px;
    }
}
```

**Companion for structural box-shadow hairlines.** Several glass surfaces convey their EDGE via
`box-shadow` (`--glass-highlight`, `--hairline-accent`/`--border-hairline`, `--glass-specular`). These
also vanish in forced-colors. Where a `box-shadow` is the ONLY edge affordance, add a forced-colors
`border`/`outline` companion. The W2-scoped set (focus + the dock/chassis hairlines the W0 row names):

```css
@media (forced-colors: active) {
    .hairline-accent,
    .glass-dock,            /* dock pill edge is box-shadow-borne */
    .glass-card {
        border: 1px solid CanvasText;   /* structural edge restored; CanvasText = the text/border system color */
    }
}
```

(The exact surface list is finalized against the AQ.W3 `:has()`/transform VR — any surface whose only
edge is a shadow gets the companion. W2 ships the focus block + the named hairline companions; W3's
forced-colors VR catches stragglers.)

**`forced-color-adjust: none` is NOT used** for aesthetics (css guide §256 forbids it) — glass-ui's
glassmorphic look is decorative and should yield to the user's forced palette. The ONLY place
`forced-color-adjust: none` would be legitimate is a color-swatch / syntax-token where the color IS the
information; glass-ui has no such surface in W2 scope.

**Baseline status of `:focus-visible`:** Widely Available → the `.input-pill:focus` → `:focus-visible`
swap (AQ.W4 row, referenced here because the forced-colors block targets `:focus-visible`) is native.

**Retire vs keep:** the `box-shadow` focus ring is KEPT as the primary (it carries the glass aesthetic
in normal mode); the `outline` is the forced-colors-only restoration. Not an alias — they are mutually
exclusive by media query (`box-shadow` ring in normal mode, `outline` in forced-colors). No duplication.

## Risks + open questions

1. **`light-dark()` Newly-Available reach.** On the (shrinking) set of engines that support
   `color-scheme` but NOT `light-dark()`, the `@supports`-gated block is skipped and behavior is
   IDENTICAL to HEAD (class-driven dark, OS-light native UI). This is the intended graceful
   degradation, not a regression — but it means the "OS-driven dark without a class" capability is
   Newly-Available-only. Documented, acceptable (the class path is the floor).

2. **The `.dark` fallback floor is line-count-flat, not a reduction.** The W0 "142-line mirror
   collapses" headline is about architecture (single source of truth, native-UI dark, dynamic
   re-resolution), not raw LOC. If a reviewer expects a large line-count drop, the `@supports` block
   ADDS roughly what the deleted `var()`-aliases REMOVE. Flagged so the gate is judged on correctness,
   not byte-count. **Open question:** is the fallback floor worth keeping verbatim, or can the explicit
   dark color values be DROPPED on the assumption all targets support `light-dark()`? **Resolution:**
   KEEP the floor — dropping it breaks the class-driven trigger on non-`light-dark()` engines, a
   no-backwards-compat-on-the-wrong-axis trap. Revisit only when `light-dark()` reaches Baseline Widely
   Available.

3. **`accent-color` dark shade is a judgment call.** `var(--ring)` (`hsl(48 10% 70%)`) is chosen for
   checkmark-glyph contrast headroom; a designer may prefer a saturated brand accent in dark instead of
   the neutral ring. **Open question for the user:** keep the neutral `--ring` dark accent, or mint a
   dedicated `--accent-brand-dark`? Default to `--ring` (no new token; ≥2-consumer bar unmet for a
   bespoke dark-accent token) unless a consumer needs the brand hue on native controls.

4. **The forced-colors hairline companion surface list is provisional.** W2 ships the focus block + the
   named hairline companions (`.hairline-accent`, `.glass-dock`, `.glass-card`); the FULL set of
   shadow-only-edge surfaces is finalized against the AQ.W3 forced-colors VR sweep. Risk: a surface
   whose only edge is a shadow is missed in W2 and only caught in W3. Mitigated by G6 + the W3 sweep;
   no correctness loss (a missed hairline degrades to no-edge in forced-colors, same as HEAD).

5. **Cross-repo sequencing.** glass-ui W2 must PUBLISH (the `--border-soft` rung + the complete-`hsl()`
   guarantee + `color-scheme`) BEFORE muster J runs its §3a sweep, else J's `color-mix(... var(--border-soft) ...)`
   references resolve to nothing. Per the cross-repo-dev-resolution contract-v2 (CLAUDE.md §Subpath
   surface), glass-ui `build:watch` keeps `dist/` fresh; the handoff is: glass-ui W2 lands + builds →
   muster J consumes the fresh `dist/` token cascade → J runs the sweep. The `--border-soft` ships only
   AFTER J confirms adoption (the ≥2-consumer gate), so the first J pass may use raw `color-mix` and the
   rung folds in on the second pass — acceptable, the bug is fixed either way.
