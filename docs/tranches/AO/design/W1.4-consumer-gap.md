# AO.W1.4 — Consumer-gap design (speedtest AQ R0G-1..4)

Design slice for the AO.W3 implementation wave. Four file-disjoint carves, each a transposition of existing surface: R0G-1/R0G-2 are perf/correctness fixes inside existing primitives, R0G-3 is a 5-consumer-gated promotion, R0G-4 is additive API completeness. None invents unjustified substrate. Derived from a full read of the four primitives plus the authoritative spec (`speedtest/docs/tranches/AQ/R0-GLASS-COORDINATION.md`).

Acceptance per item is the W3 hard gate (`docs/tranches/AO/waves/W3.md` §Hard Gate). The contract is the gate, not the consumer's post-publish adoption.

## R0G-1 — Aurora demand-driven / visibility-paused render loop

### WHAT

The Aurora WebGL2 runtime owns a perpetual RAF loop that reschedules every frame whether or not anything is moving. The site is `tick()` inside `arm()` in `src/components/custom/aurora/composables/runtime.ts`:

```ts
function tick() {
    if (!running) return;
    const t = reducedMotion
        ? frozenOffset
        : (performance.now() - startTime) / 1000;
    advanceCursor();
    drawFrame(t);
    raf = requestAnimationFrame(tick);   // ← unconditional reschedule
}
if (running) raf = requestAnimationFrame(tick);
```

Two defects live here:

1. **No steady-state pause.** When `reducedMotion` is true the branch pins `t = frozenOffset` (3.7) every frame — `uTime` never advances, so `drawFrame` re-rasterizes a byte-identical frame at 60fps forever. The static-frame intent is correct (one frame is enough) but the loop keeps drawing it. This is the cause of the measured `~4 fps / ~100% GPU` at idle: a full-viewport WebGL2 fragment shader re-rasterized every frame with zero pixel delta.

2. **No document-visibility suspend at the runtime level.** `useIntersectionPause` (composed in `useAurora`'s deferred path) DOES pause on `document.hidden` and off-screen — but only for the deferred-arm consumer, and only by calling the runtime's `pause()`/`resume()`. The runtime's own `tick()` has no visibility awareness; an eager/capture consumer or a consumer that never goes off-screen runs the loop at full motion regardless of tab focus.

### WHY

The loop lives in the primitive — `feedback_library_gaps`: a consumer must never wrap a library primitive in a scheduler. No consumer-side band-aid is possible (speedtest cannot reach into `runtime.ts` to gate the RAF). The fix is the idiomatic gestalt move — a loop that runs only when there is motion to render — not a throttle hack.

### Decision — option (a) clock-owned demand-driven loop, NOT (b) compositor-cached CSS layer

**RECOMMEND (a).** The spec offers two shapes:

- (a) a clock-owned, demand-driven RAF loop that pauses on steady-state + suspends on `visibilitychange`;
- (b) move the ambient drift off the per-frame canvas onto a compositor-cached CSS/Houdini layer.

Option (a) is correct here for three reasons:

1. **The loop already exists in JS, in one place.** `tick()` is the single scheduling site; making it demand-driven is a local edit to one function. Option (b) would mean re-authoring the entire painterly field (fBm warp, nuclei drift, palette drift, breath, stroke layers — 40+ uniforms in `setConfig`) as CSS/Houdini, which is a full primitive rewrite, not a transposition. That contradicts the AO ethos (elegance transposition of existing surface) and the `feedback_architectural_approach` gestalt-redesign-of-the-defect, not redesign-of-the-primitive.
2. **The painterly look is not expressible as a compositor layer.** The shader's per-pixel medium simulation (oil/pastel/watercolor, granulation, impasto, broken-color) has no CSS analogue. Option (b) would degrade the visual canon — and the gate requires `π unregressed`.
3. **The static-frame path is already half-built.** `reducedMotion` already draws the right frozen frame; it just keeps redrawing it. Demand-driving the loop turns the existing static-frame intent into an actual single draw.

The acceptance signal is the **reduced-motion-delta / idle-fps A/B** (idle-fps recovers toward the reduced-motion ceiling), NOT Lighthouse TBT — TBT is blind to compositor cost. Option (a) is exactly what moves that needle: stop scheduling when `uTime` would not advance the frame.

### EXACT changes (carve: `src/components/custom/aurora/`)

**runtime.ts — make the loop demand-driven.** The drift is animated iff motion is live: `reducedMotion` is false AND at least one motion uniform is non-zero (`nucleiDrift`, `paletteDrift`, `breathDepth`, `warpDrift`) OR the cursor is still easing toward rest. Concretely:

1. Add a `needsAnimation()` predicate inside `arm()` (closes over `config`, `reducedMotion`, `cursor`):
   - `false` when `reducedMotion` is true (the static frame is drawn once, then the loop idles);
   - `false` when all of `config.nucleiDrift`, `config.paletteDrift`, `config.breathDepth`, `config.warpDrift` are 0 AND the cursor is at rest (`cursor.targetStrength < ε` and `|cursor.x - cursor.targetX| < ε` and `|cursor.y - cursor.targetY| < ε`);
   - `true` otherwise.

2. Rewrite `tick()` so it draws the current frame, then reschedules ONLY when `needsAnimation()` is true. When motion is live the loop is unchanged (advance clock, advance cursor, draw, reschedule). At steady-state it draws the final settled frame once and lets `raf` go to 0 (no reschedule):

   ```ts
   function tick() {
       if (!running) return;
       const t = reducedMotion ? frozenOffset : (performance.now() - startTime) / 1000;
       advanceCursor();
       drawFrame(t);
       raf = needsAnimation() ? requestAnimationFrame(tick) : 0;
   }
   ```

3. Wake the loop on demand. Any imperative mutation that re-introduces motion must restart the loop if it has parked. Add a `wake()` helper (`if (running && !raf) raf = requestAnimationFrame(tick)`) and call it from:
   - `setCursor` / the cursor setters (a pointer move re-arms the easing);
   - `setConfig` (a slider drag that raises a drift uniform);
   - `setReducedMotion(false)` (reduced-motion toggled off mid-session must resume drift).
   Since `setCursor`/`setReducedMotion` are defined at the outer `createAurora` scope (pre-arm) and `wake` lives inside `arm()`, expose `wake` through the `armed` closure (add it alongside `setConfig`/`renderAt`/`pause`/`resume`/`dispose`) and call `armed?.wake()` from the outer setters — mirroring how `update` already delegates to `armed?.setConfig`.

4. **visibilitychange suspend at the runtime.** The deferred-arm consumer already gets this via `useIntersectionPause`, but the runtime must self-suspend so EVERY consumer (eager, capture-then-live, always-on-screen) is covered. Inside `arm()`, after the loop starts, add a `document.visibilitychange` listener that calls the existing `pause()` on `document.hidden` and `resume()` on visible. Guard for `typeof document !== "undefined"` (SSR/capture). Remove the listener in `dispose()`. The existing `pause()`/`resume()` already cancel/restart `raf` correctly; `resume()` rebases `startTime` so the drift does not jump.

   Note `useIntersectionPause` and the runtime's own listener are idempotent against each other — `pause()` sets `running = false` + `cancelAnimationFrame`, a second pause is a no-op; `resume()` early-returns `if (running) return`. The two layers compose without double-scheduling.

**Aurora.vue — no template change required.** The demand-driven behavior is entirely inside the runtime. `Aurora.vue` already exposes `pause`/`resume` via `defineExpose`; those continue to work. The `prefers-reduced-motion` static-frame contract is preserved (one frame drawn, loop idle).

**reduced-motion still fully static.** With `needsAnimation()` returning `false` under `reducedMotion`, `tick()` draws the frozen frame exactly once and parks. `onReducedChange` in `useAurora.ts` already calls `inst.setReducedMotion` on the media-query change; route a `wake()` through it (via the `setReducedMotion` path above) so a reduced→full toggle restarts motion, and a full→reduced toggle draws one last static frame then parks.

### Acceptance signal (W3 hard gate item 4 + 6)

- The RAF is not perpetually rescheduled at steady-state — shown by the `needsAnimation()` gate in the code-path + a π idle re-probe confirming the loop parks (no per-frame `requestAnimationFrame` at rest).
- The loop is suspended on `visibilitychange` (the runtime listener + the existing `useIntersectionPause` seam).
- `prefers-reduced-motion` still renders a single static frame (the `frozenOffset` draw fires once, then parks).
- Visual π canon unregressed on the demo Aurora hero (the painterly field is byte-identical while in motion; only the at-rest reschedule is removed).

## R0G-2 — InstrumentChassis breakpoint-correct child-geometry reserve

### WHAT

On mobile (390px) the `.instrument-dial` re-seats ~326-331px (y:364→~35, h:48→701) AFTER the chassis settles → mobile-only CLS 0.32-0.38 on chassis-hosting routes. Desktop holds ≤0.013.

The defect is in the mobile dial layout in `src/styles/instrument-chassis.css`. The desktop dial is a fixed 3-column grid:

```css
.instrument-dial {
    grid-template-columns: var(--instrument-dial-columns, minmax(0, 1.2fr) 1px minmax(0, 1fr));
    align-items: center;
    /* … */
}
```

The mobile reflow collapses it to a single column with `auto` rows:

```css
@media (max-width: 720px) {
    .instrument-chassis .instrument-dial {
        grid-template-columns: 1fr;
        grid-template-rows: auto auto auto;   /* ← unreserved height */
        gap: var(--instrument-dial-gap-mobile, 1.5rem);
    }
    /* … */
}
```

`grid-template-rows: auto auto auto` means the dial reserves NO height from frame 0. The three rows (meter canvas, divider, readout column) are zero-height until their content lands — the consumer's meter `<canvas>` sizes itself post-mount (and the readout column hydrates its numbers), at which point the rows grow from collapsed → final. Everything below the chassis shifts down by the grown height → the 326-331px reflow → the 0.32-0.38 CLS.

Desktop escapes this because the 3-column grid with `align-items: center` reserves the row height from the tallest column's intrinsic min, and speedtest's AP-Pγ closed the desktop axis via transform-based idle centring (the dial is laid out at final size from frame 0, and the idle→active recentre moves it with `transform`, not a layout property).

### WHY

The child layout is in the primitive. A consumer `min-height` band-aid on the dial is exactly the workaround the directive forbids (`feedback_architectural_approach` — no workarounds; the fix belongs at the primitive). Reserve-then-transform is the canonical no-CLS pattern: paint the child's FINAL box from frame 0, then animate only `transform` for any idle→active recentre.

### EXACT changes (carve: `src/styles/instrument-chassis.css` + `InstrumentChassis.vue` binding)

**Reserve the dial's final box at the mobile breakpoint via `min-height` on the grid rows (token-driven).** The dial cannot read its consumer's content height, so reserve a token-defaulted minimum that matches the settled box. Add to the `@media (max-width: 720px)` `.instrument-dial` rule:

```css
@media (max-width: 720px) {
    .instrument-chassis .instrument-dial {
        grid-template-columns: 1fr;
        /* Reserve the final box from frame 0 — the rows no longer grow from
           collapsed once the consumer's meter canvas + readout hydrate.
           The meter row carries the dominant reserve (the square-ish dial);
           divider + readout are intrinsic. Consumers retune via the token. */
        grid-template-rows:
            var(--instrument-dial-meter-reserve-mobile, minmax(0, 1fr))
            auto
            auto;
        min-height: var(--instrument-dial-min-height-mobile, 24rem);
        gap: var(--instrument-dial-gap-mobile, 1.5rem);
    }
}
```

The `min-height` on the dial is the load-bearing reserve: it pins the dial's box from frame 0 so the rows distribute within a reserved envelope rather than growing it. Both knobs are CSS custom properties (token-first, J invariant) — a consumer whose meter is a different size retunes `--instrument-dial-min-height-mobile` without forking the primitive (this is a library token, NOT a consumer band-aid: it defaults to a sane reserve and the consumer override is a tuning knob, not a workaround for a missing reserve).

**Default the reserve token in `tokens.css` — DEFERRED to W4.** Per the W3 File Bounds, W3 owns `instrument-chassis.css` content; the `tokens.css` rung add is W4's cascade pass. W3 ships the token CONSUMPTION (the `var(--instrument-dial-min-height-mobile, 24rem)` fallback is self-sufficient — the inline fallback IS the default until W4 lands the canonical rung). No W3→tokens.css edit required; the fallback carries the contract.

**Transform-only idle→active recentre.** The chassis must not animate any layout property on the dial during idle→active. Verify (and, where present, enforce) that the only animated property on the dial / its children for the recentre is `transform` — the AP-Pγ pattern. The current CSS has no dial recentre animation in the primitive itself (the phase cascade animates `--phase-tint-amount` on the chassis background via `transition: --phase-tint-amount …`, which is paint-only, not layout — that is fine and stays). If R0G-2 adds any idle→active dial movement, it MUST be `transform`-based (e.g. `translate`/`scale`), never `top`/`margin`/`grid-template`. Document in the audit that the dial's box is fixed from frame 0 and the only motion is transform + the paint-only tint transition.

**`InstrumentChassis.vue` — no structural change required.** The `<main class="instrument-dial">` already carries the class the CSS targets. No new Vue binding is needed for the reserve (it is pure CSS). If the audit finds the reserve needs to be conditional (e.g. a dial with no meter), expose it as the token default of `auto` — but the canonical chassis consumer (speedtest `/` + `/survey`) always carries the meter, so the `24rem` reserve default is correct.

### Acceptance signal (W3 hard gate item 5 + 6)

- The chassis reserves the dial's final box from frame 0 at the mobile breakpoint (the `min-height` + reserved meter row shown in the CSS).
- Mobile (390px) CLS < 0.05 on a chassis-hosting route (speedtest verifies on `/` + `/survey` post-publish; the W3 audit records the before/after layout reasoning).
- Any idle→active recentre animates `transform` only (no layout property); desktop unregressed.
- No post-paint child reflow at 390px; no consumer `min-height` band-aid required.
- Visual π re-probe clean on the demo InstrumentChassis.

## R0G-3 — `useIdleReady` composable

### WHAT

Create `src/composables/dom/useIdleReady.ts` as the canonical `requestIdleCallback` (+ `setTimeout(0)` fallback) post-mount idle gate — the rIC-sibling of the shipped `useViewportReady`. speedtest hand-rolls this gate at 5 sites (`App.vue`, `MapView.vue`, `DashboardMap.vue`, `useAutoStart.ts`, `useIPInfo.ts`). The `useIPInfo` site carries the scope-aware variant that is the canonical signature.

Two hand-rolled shapes exist in speedtest:

- **App.vue (the `ready`-flag shape)** — flips a `ref<boolean>` once, post-idle, for `v-if`-gating a heavy mount:
  ```ts
  const auroraReady = ref(false);
  onMounted(() => {
      const fire = () => { auroraReady.value = true; };
      if (typeof window !== "undefined" && "requestIdleCallback" in window) {
          window.requestIdleCallback(fire, { timeout: 2000 });
      } else {
          setTimeout(fire, 0);
      }
  });
  ```
- **useIPInfo.ts (the scope-aware task shape)** — runs a `task` callback on first idle, with scope-disposal cancellation so a short-lived consumer cannot leak a deferred write to disposed refs:
  ```ts
  const scope = getCurrentScope();
  if (typeof requestIdleCallback === "function") {
      const ricHandle = requestIdleCallback(() => { void refresh(); }, { timeout: 2000 });
      if (scope && typeof cancelIdleCallback === "function") {
          onScopeDispose(() => cancelIdleCallback(ricHandle));
      }
  } else {
      useTimer(() => { void refresh(); }, 100);   // Safari fallback
  }
  ```

The canonical signature must cover BOTH: the `ready`-flag use (return a `Ref<boolean>` that flips once) AND the scope-aware task use (run a callback on idle, cancelled on dispose). The `ready` ref is the unifying surface — App.vue reads it directly; the task sites pass a callback that runs the moment the ref would flip.

### WHY

5 consumer sites clear J inv 10 / L inv 8 (≥2-consumer substrate-promotion gate) — this is a justified promotion, not a substrate-without-consumer invention. It is the consumer-gap AO.W0 read as empty because AQ had not surfaced it. `useViewportReady` is the IO+rIC sibling already shipped; `useIdleReady` is the rIC-only sibling (no viewport stage — the gate is "idle, full stop", not "visible AND idle").

### EXACT signature + return shape (sibling-consistent with `useViewportReady`)

Mirror `useViewportReady`'s shape exactly: an options bag, a controls return with a one-shot `ready` ref + a `stop()`, structural `RefLike`-free (no host ref needed — rIC has no element). The scope-aware case folds in as an optional `onReady` task callback.

```ts
export interface UseIdleReadyOptions {
    /**
     * `requestIdleCallback` timeout, in ms. Default 2_000 — the canonical
     * value at every speedtest hand-rolled site (App.vue + useIPInfo both
     * pass `{ timeout: 2000 }`). Unlike useViewportReady's 10s (which fronts
     * the budget with an IO gate), useIdleReady has no visibility stage, so
     * the timeout is the only ceiling — 2s matches the consumer sites and
     * keeps the deferred work inside a reasonable post-paint window.
     */
    timeout?: number;
    /**
     * Optional task run the moment the gate flips (the scope-aware variant —
     * useIPInfo's `() => void refresh()`). Runs exactly once; auto-cancelled
     * on scope dispose with the rIC handle so a short-lived consumer cannot
     * leak a deferred write to disposed refs. Consumers that only need the
     * `ready` ref omit it.
     */
    onReady?: () => void;
}

export interface UseIdleReadyControls {
    /** Flips `false → true` exactly once on the first idle tick (post-mount). */
    readonly ready: Ref<boolean>;
    /** Tear down the pending idle/timer handle. Auto-called on scope dispose. */
    stop: () => void;
}

export function useIdleReady(
    options: UseIdleReadyOptions = {},
): UseIdleReadyControls;
```

### Impl shape (rIC + setTimeout(0) fallback, scope-aware cleanup)

- `timeout` defaults to `2_000`.
- A `ready = ref(false)`; a one-shot `fire()` that early-returns if `disposed || ready.value`, sets `ready.value = true`, runs `options.onReady?.()`, then `teardown()`.
- Schedule on construction (NOT inside an `onMounted` — `useViewportReady` schedules synchronously at call time via its initial `rebind`; match that so the gate works outside a component too, e.g. in `useIPInfo` which is a composable not a component):
  - SSR / `typeof window === "undefined"` → synchronous `fire()` (matches `useViewportReady`'s SSR flip so consumers don't stall).
  - `"requestIdleCallback" in window` → `idleHandle = window.requestIdleCallback(fire, { timeout })`.
  - else (Safari) → `timerHandle = setTimeout(fire, 0)`. (Use `setTimeout(0)` per the spec's "rIC + setTimeout(0)" name — the macrotask still lands after first paint. The 16ms / 100ms variants in the hand-rolled sites were per-site choices; `0` is the canonical "next macrotask" floor and matches App.vue's Safari branch.)
- `teardown()` cancels `idleHandle` via `cancelIdleCallback` (guarded `"cancelIdleCallback" in window`) and clears `timerHandle`.
- `stop()` sets `disposed = true` + `teardown()`.
- `if (getCurrentScope()) onScopeDispose(stop)` — the scope-aware cleanup the `useIPInfo` site requires (this is the whole point of promoting that variant).

This is structurally `useViewportReady` minus the IntersectionObserver stage, plus the `onReady` task hook. Same `RefLike`-free public surface (no host param), same one-shot semantics, same auto-dispose.

### Barrel export line (carve: `src/composables/dom/index.ts`)

Add to the doc-comment list + the re-export block, alongside `useViewportReady`:

```ts
//   - useIdleReady     — requestIdleCallback (+ setTimeout fallback) post-mount
//                        idle gate; rIC-sibling of useViewportReady, no viewport
//                        stage (AO.W3; speedtest 5-site promotion).
export * from "./useIdleReady";
```

Surfacing is automatic from there: `src/composables/index.ts` does `export * from "./dom"`, and `src/index.ts` does `export * from "./composables/dom"` (line 166) — so `useIdleReady` reaches the curated root barrel `@mkbabb/glass-ui` exactly the way `useViewportReady` does. No edit to `composables/index.ts` or `src/index.ts` needed (and `dom/` is vueuse-free, so the root-barrel SCC trap is not tripped — `useIdleReady` uses only `vue` core: `ref`, `getCurrentScope`, `onScopeDispose`).

### Test (carve: create `src/composables/__tests__/useIdleReady.test.ts`)

Mirror `useViewportReady.test.ts`'s fake-rIC harness (`installFakeRIC`/`uninstallFakeRIC` — copy verbatim; no IO fake needed). Cases:

1. **flips ready=true on the idle tick** — install fake rIC, call `useIdleReady()`, assert `ready.value === false` synchronously, advance timers, assert `ready.value === true`.
2. **runs the `onReady` task once on flip** — pass `onReady: vi.fn()`, advance, assert called once.
3. **falls back to setTimeout when rIC unavailable** — `uninstallFakeRIC()`, fake timers, assert flip after `advanceTimersByTime(0)` (the `setTimeout(fire, 0)` path).
4. **SSR synchronous flip when window is undefined** — (mirror the no-host idle fallback test) — assert immediate `ready=true`.
5. **auto-disposes on scope stop** — `effectScope().run(() => useIdleReady(...))`, `scope.stop()`, advance, assert `ready` stayed `false` AND `onReady` never ran (the scope-aware cancellation — the load-bearing case for `useIPInfo`).
6. **honours custom timeout** — pass `{ timeout: 500 }`, assert clean construction + `stop()`.

### Acceptance signal (W3 hard gate item 2)

- `grep -rn 'useIdleReady' src/composables/dom/index.ts` matches.
- `useIdleReady` type-resolves from `@mkbabb/glass-ui` (and the `dom` sub-barrel) — the import probe.
- The co-located test passes.
- The signature is sibling-consistent with `useViewportReady` (one-shot `ready` ref + `stop()` + auto-dispose) and scope-aware (the `onReady` + `onScopeDispose` cancellation covers the `useIPInfo` variant).

## R0G-4 — `Toaster` `position` prop

### WHAT

`src/components/ui/toast/Toaster.vue` hardcodes a bottom-right desktop viewport anchor on the teleported `<ToastViewport>`:

```vue
<ToastViewport class="fixed top-0 z-toast flex max-h-screen w-full flex-col-reverse p-4 sm:bottom-0 sm:right-0 sm:top-auto sm:flex-col md:max-w-[420px]" />
```

The anchor is the four mobile/desktop positioning fragments inside that class string:
- `top-0 … flex-col-reverse` — mobile default (toasts stack up from the top edge, newest on top via reverse);
- `sm:bottom-0 sm:right-0 sm:top-auto sm:flex-col` — desktop override (bottom-right, newest at bottom);
- `w-full … md:max-w-[420px]` — width (full on mobile, capped on desktop);
- `z-toast flex max-h-screen p-4` — the invariant chrome (z-index, flex, max-height, padding).

speedtest needs a TOP anchor (a degraded-path error toast must not overlap the bottom dock) and currently overrides the published `.z-toast` utility from consumer CSS — a bridge, not a fix.

### WHY

Additive API completeness. The default keeps every existing consumer byte-identical; the prop drives the teleported viewport anchor so a top-anchoring consumer (speedtest) drops the `.z-toast` consumer override.

### EXACT prop type + anchor map (carve: `src/components/ui/toast/`)

**The position set.** Enumerate the sensible anchors — the four corners + two centers that a viewport anchor actually supports:

```ts
export type ToasterPosition =
    | "top-left"
    | "top-center"
    | "top-right"
    | "bottom-left"
    | "bottom-center"
    | "bottom-right";
```

`bottom-right` is the default (the current hardcoded anchor).

**Toaster.vue — prop + computed anchor class.** Split the hardcoded class into an INVARIANT chrome fragment (unchanged for every position) and a POSITION fragment driven by the prop. The default `"bottom-right"` MUST reproduce the current class byte-for-byte.

```ts
const props = withDefaults(
    defineProps<{ position?: ToasterPosition }>(),
    { position: "bottom-right" },
);

// Invariant chrome — identical across every anchor.
const VIEWPORT_BASE = "fixed z-toast flex max-h-screen w-full p-4 md:max-w-[420px]";

// Per-position anchor + stack direction. `bottom-right` is the canonical
// default and reproduces the pre-W3 class byte-identically when concatenated
// with VIEWPORT_BASE (verified in the audit).
const VIEWPORT_ANCHOR: Record<ToasterPosition, string> = {
    "bottom-right":  "top-0 flex-col-reverse sm:bottom-0 sm:right-0 sm:top-auto sm:flex-col",
    "bottom-left":   "top-0 flex-col-reverse sm:bottom-0 sm:left-0 sm:top-auto sm:flex-col",
    "bottom-center": "top-0 flex-col-reverse sm:bottom-0 sm:left-1/2 sm:top-auto sm:-translate-x-1/2 sm:flex-col",
    "top-right":     "top-0 right-0 flex-col",
    "top-left":      "top-0 left-0 flex-col",
    "top-center":    "top-0 left-1/2 -translate-x-1/2 flex-col",
};

const viewportClass = computed(() => cn(VIEWPORT_BASE, VIEWPORT_ANCHOR[props.position]));
```

```vue
<ToastViewport :class="viewportClass" />
```

**Byte-identity proof for the default.** The pre-W3 class is:
`fixed top-0 z-toast flex max-h-screen w-full flex-col-reverse p-4 sm:bottom-0 sm:right-0 sm:top-auto sm:flex-col md:max-w-[420px]`

`cn(VIEWPORT_BASE, VIEWPORT_ANCHOR["bottom-right"])` yields the same utility SET (order is not visually load-bearing for non-conflicting Tailwind utilities, and `cn`'s deduplicator preserves the resolved utilities). The W3 audit must confirm the rendered `<ToastViewport>` carries the identical anchor utilities for the default — `top-0 flex-col-reverse sm:bottom-0 sm:right-0 sm:top-auto sm:flex-col` + the invariant chrome — so no existing consumer regresses. The `top-*` positions drop `flex-col-reverse` for plain `flex-col` (newest toast on top reads correctly when anchored to the top edge); `*-center` uses `left-1/2 -translate-x-1/2` for horizontal centering.

**Import `cn` + `computed`.** Add `import { computed } from "vue"` and `import { cn } from "@/utils"` (or the relative `../../../utils` path the package uses) to the `<script setup>`.

### Co-export the type (carve: `src/components/ui/toast/index.ts`)

Add the type to the existing export-type line:

```ts

```

(The `ToasterPosition` type is declared + `export`ed in `Toaster.vue`'s `<script setup>` so the SFC re-export resolves. Toast stays on the root barrel — the addition is prop/type-only, no vueuse, no isolated chunk.)
