## Scope

1. **Establish where the SFC scoped CSS lands today.** At HEAD the `./styles` export resolves to `./dist/styles/index.css` (the @import cascade); the `./styles.css` export resolves to `./dist/glass-ui.css` (Vite's component-CSS bundle including SFC `<style scoped>` blocks). The consumer needs both lines today because the two exports point at two distinct artefacts. The W0 intake names the current emission path verbatim. WHY — the root fix is the build-pipeline carve, not a CSS authoring change; the SFC scoped CSS already exists in the dist, it just lives at a separate export.
2. **Fold the SFC scoped CSS into `./styles` so a single import carries everything.** Three viable shapes — pick one in W1 dispatch:
   - **Shape A (extend the @import chain)** — emit a build step that appends `@import "../glass-ui.css"` (or the per-SFC compiled CSS) to `dist/styles/index.css`. Lowest pipeline change; the consumer pattern is unchanged.
   - **Shape B (re-point `./styles` at the unified bundle)** — change the `package.json` `exports` `./styles` target to `./dist/glass-ui.css`; retire `./styles.css` per L invariant 4 (no backwards-compat aliases — the dual-export was the bridge AN closes).
   - **Shape C (fold the token cascade into the SFC bundle)** — invert: emit `dist/glass-ui.css` containing both cascade + SFC scoped, and re-point `./styles` at it.
   The W1 dispatch picks Shape A (default — least invasive; keeps `./styles.css` reachable as a transparent re-export, NOT an alias, for the cascade-only consumer) unless the W0 intake surfaces a payload-size reason to pick B or C. WHY — the F-side ask is "one clean @import"; the implementation shape is glass-ui's choice within the additive-only constraint.
3. **Verify `proof:theme` passes against the unified bundle.** The proof gate reads the CSS for every cascade rung; AN must not regress it. WHY — `proof:theme` is the binding completeness gate at the release script.
