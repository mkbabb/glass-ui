## Scope

### W4.A — StatusDot role contract

1. **Add `role="img"` when the consumer binds `aria-label`.** `src/components/custom/status-dot/StatusDot.vue` root is a `<span>` (per the W0 intake). When the parent passes `aria-label`, the `<span>` must carry a role that allows the attribute (`img` is the canonical safe choice — same as the RankedVerdict hue-dots fix F.W8.6 fix C2 applied consumer-side). Two implementation shapes:
   - **Shape A1 — emit `role="img"` always**. Cleanest; every StatusDot becomes a labelled image-like presentation element. Additive (no break) since consumers binding aria-label want the labelled shape.
   - **Shape A2 — emit `role="img"` only when `aria-label` is bound**. Conditional `:role="$attrs['aria-label'] ? 'img' : undefined"`. Preserves the pure-decorative case (no aria-label → no role; the `<span>` stays presentational).
   Default — Shape A2 (preserves the pure-decorative escape hatch).
2. **OR expose a `role` prop pass-through.** If the W0 intake records consumer cases needing `role="status"` (live region) or `role="presentation"`, add a `role?: string` prop that overrides the default. Optional; pick only if the intake names ≥ 2 use cases.

### W4.B — SortableHandle role contract

3. **Add an interactive role to the drag-grip span.** `src/components/custom/sortable-list/SortableHandle.vue` is a `<span>` drag affordance. The canonical role for an interactive drag-grip is `role="button"` (matches Web Content Accessibility Guidelines for drag affordances + lets axe's `aria-prohibited-attr` rule accept the consumer-bound `aria-label`). Additionally — surface a `tabindex="0"` so keyboard users can reach the handle (current shape is mouse-drag-only; the keyboard a11y is a separate consumer concern but the role contract makes the handle eligible for that wiring).
4. **Explicit `aria-label` channel.** Document that the consumer binds `:aria-label="'Reorder ' + itemName"` on `<SortableHandle>` and the primitive carries it through. If the current attr-forwarding doesn't reach the `<span>` root (the W0 intake confirms or denies), add the explicit forward (mirror Slider's `:aria-label="$attrs['aria-label']"` pattern AM used).

### W4.C — NumberField label binding re-confirm

5. **Re-derive against the F.W8.6 SignalsLayer site.** F.W8.6 reports 5 nodes/perm of `label` violations on `<input role="spinbutton">` (the NumberField inner input). AM.W0.2 already added `inheritAttrs:false` + `v-bind="$attrs"` to `<NumberFieldInput>` (per `docs/tranches/AM/audit/W0-forms-a11y.md`). Two possibilities:
   - **Possibility C1 — the AM fix is incomplete**. The `<NumberFieldInput>` wrapper forwards `$attrs` correctly but the reka-ui `NumberFieldInput` chain doesn't carry them to the `<input>` after a recent reka-ui update. AN re-derives the chain (read reka-ui's source as AM did at W0.2) and adjusts.
   - **Possibility C2 — the F.W8.6 site doesn't bind a label on the field**. muster's SignalsLayer wraps the field in a `<div role="group" aria-label="Rating weight value">` instead of binding `aria-labelledby` on the field itself. axe's `label` rule fires on the input regardless of the wrapper's `aria-label`. The fix is a consumer-side binding change (or a glass-ui doc clarifying the label-binding contract), not a glass-ui code fix.
   Default — investigate first; pick C1 (code fix) only if the AM chain is genuinely broken; else close as C2 (DOCUMENTED with the binding shape muster should use). The W0 intake is the primary evidence source.
6. **If C2 — document the label-binding contract.** CLAUDE.md §Component architecture (or §Forms a11y if a new section is warranted) carries: "A `<NumberField>` accepts an accessible name via `:aria-label`, `:aria-labelledby`, or a sibling `<label for>` binding. A `role="group"` wrapper with an `aria-label` does NOT propagate the name to the inner `<input>` — bind the name on the field itself for axe `label` compliance."
