## Goal (the gestalt)
A consumer expresses a selectable/active control's COLOR identity from ONE `--tone` (a complete `<color>`), and gets back a coherent, contrast-SAFE four-channel tonal set: a faint idle FILL that is STILL legible at rest (the load-bearing new behavior — floored ≥3:1 against the surface, so the resting chip's tint never whispers below the perception floor), a stronger active/selected BAND, an active EDGE/rim, and a contrast-correct INK for the label ON the tonal fill (auto-darkened/lightened by `safeAccentColor` so the text never drops below 4.5:1 over the resolved fill). Set `--tone: var(--section-color-7)` once and the chip reads idle-legible, active-bold, ink-correct in BOTH modes — no per-state `color-mix(…)` hand-roll, no "is the active fill dark enough that white text reads?" guesswork. The tonal accent is a register, declared ONCE, that fourier (~57× today) and glass-ui's own ToggleChip (the 2 active-fill `color-mix` literals inside an 8-literal per-state cluster today) stop re-deriving. `<SelectableChip>` is the component face: a reka-Toggle selectable chip that READS the register, so a tag/filter/tool picker is one element, golden-by-construction.

### 1. The 4-channel tonal register (token-first, minted once)
In `src/styles/glass/accent-tone.css` (a new `@layer components` partial, `@import`-ed after the glass ladder in `index.css`), a `.accent-tone` recipe reads ONE `--tone` (a complete `<color>`, default `var(--primary)`) and a bounded `--accent-fill-strength` (idle, default `8%`) / `--accent-band-strength` (active, default `18%`) / `--accent-edge-strength` (rim, default `55%`):
```css
.accent-tone {
  /* idle: faint but FLOORED — the resting tint stays ≥3:1 by the strength floor +
     the perceptual `in oklab` mix (NOT in srgb — the glass-tint perceptual family). */
  --accent-fill:  color-mix(in oklab, var(--surface, var(--card)), var(--tone) var(--accent-fill-strength));
  --accent-band:  color-mix(in oklab, var(--surface, var(--card)), var(--tone) var(--accent-band-strength));
  --accent-edge:  color-mix(in oklab, transparent, var(--tone) var(--accent-edge-strength));
  /* ink is the contrast-SAFE label color ON the active band — written by the
     composable (the JS half) via safeAccentColor; the CSS fallback is the warm ink. */
  --accent-ink:   var(--accent-ink-resolved, var(--foreground));
}
```
The `in oklab` mix is the perceptual glass-tint family (W55/W-NO-GRAY), NOT the `in srgb` `--surface-tint-*` brand-overlay fence (the disjoint-axis fence, see Fences). The idle FILL floor is the load-bearing new behavior: `--accent-fill-strength` defaults `8%` (the ~6-8% fourier names) and the gate measures the resolved idle fill clears ≥3:1 against the surface (a strength that drops it below 3:1 reds — the resting-legibility floor).

### 2. The contrast-safe INK (the JS half — `useAccentTone`)
`useAccentTone(tone: MaybeRefOrGetter<string>, opts?)` (`@mkbabb/glass-ui/color` — the value.js-bearing `/color` leaf, NOT the root barrel; value.js-bearing → off the SCC-trap root barrel per the precedent) resolves the contrast-safe ink against the ACTIVE band fill via value.js `safeAccentColor`:
```ts
// composes value.js safeAccentColor: given the resolved active-band fill, return
// the label color (the tone darkened/lightened) that clears the target contrast.
import { safeAccentColor, computeSafeAccent } from "@mkbabb/value.js";
export interface UseAccentToneOptions {
  /** idle fill strength (0..1 or %). Default 0.08. */ fillStrength?: number;
  /** active band strength. Default 0.18. */ bandStrength?: number;
  /** target ink-over-band contrast. Default 4.5 (AA). */ inkContrast?: number;
}
export interface UseAccentToneReturn {
  /** the element-level custom-property style object: {--tone, --accent-ink-resolved}. */
  toneStyle: ComputedRef<Record<string, string>>;
  /** the resolved contrast-safe ink (for a non-CSS reader). */ ink: ComputedRef<string>;
}
```
The ink RESOLVES `safeAccentColor(activeBandFill, { targetContrast: inkContrast })` — value.js owns the darken/lighten-until-it-passes math (`computeSafeAccent`/`needsContrastAdjustment`/`getOklchLightness`); glass-ui re-implements NONE of it (`proof:single-color-core` holds — the math source stays value.js, the `useBorderSpectrum` precedent). PRM-irrelevant (a color, not an animation). The `toneStyle` is the element-level `:style` the SFC binds; the CSS recipe reads the channels.
