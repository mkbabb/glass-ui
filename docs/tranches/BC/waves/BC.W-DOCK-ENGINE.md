## Goal (the gestalt)
Grab the `/dock/overview` dock and toggle it open and closed: it GLIDES — the box grows and the chrome materializes in one continuous, springy, liquid-glass motion that fills the whole gesture, settling with a tiny lively overshoot and then resting crisp. No stutter, no snap-then-wait, no mid-flight jank. The morph reads exactly like an iOS-27 control-center surface materializing: quick but never abrupt, the size and the chrome moving on ONE clock so nothing desyncs. Every transition on the dock — the morph, the hover lift, the held-state, the layer crossfade — runs on a compositor-promoted transform/opacity/filter channel, so even on a mid-range machine it is 60fps-smooth. The user's "they STUTTER / not buttery smooth" is gone because the spring curve that powered the snap now powers a glide that paints its travel across the full clock.

## Starting state (measured, file:line)
**The DEFECT-LEDGER D3 root is a PHANTOM** — `grep -rn 'transition:\s*all\|transition-property:\s*all\|transition: all' src/ demo/` → **EMPTY (exit 0, zero matches)** (glass-dock-codebase.md §2.1). There is NO `transition: all` anywhere. The morph is already a single-scalar compositor transform. The real "stutter / not buttery smooth" has TWO roots, both quantified:

1. **The front-loaded spring curve (the stutter root, glass-dock-codebase.md §2.1 + §3.3).** The morph paints its travel against `--spring-snappy` (the same curve the tabs §3.3 abrupts on). The `linear()` curve in `src/styles/scheme-motion.css` (the `--spring-snappy` token) **hits 1.0 by 12.245% and PEAKS at 1.068 (16.327%)**, then runs DEAD-FLAT `1.00000` from ~49% to ~98% (verified — the curve string is literally `1.00000` across that span). The dock morph clock is the `DOCK_SPRING` register: `src/components/custom/dock/constants.ts:69` `DOCK_SPRING = { response: 0.32, dampingFraction: 0.7 }` (the `--spring-dock`-class clock, settle ~0.28s). So the dock box reaches its target geometry in roughly the first ~16% of the clock, then the spring sits dead-flat for the rest — the eye reads an **abrupt arrival** (the "snap") followed by a wasted tail, and on a frame-budget-tight machine the front-loaded burst (almost the entire displacement in ~3 frames) is exactly where the renderer drops frames = the perceived **stutter**.
2. **The chrome/box ARE already on one clock, but the per-property compositor-promotion is incomplete + uneven.** `src/styles/dock/layers.css:60-74` reserves `inline-size: var(--dock-morph-to)` and composites `transform: scaleX(var(--dock-morph-scale))` over it with `will-change: transform` (the CDP-Layout-flat floor — correct). But the chrome legs in `src/styles/dock/morph.css` animate `--dock-expand-t`-driven bg/border/padding interps that, where they touch a `padding-*` longhand on the morph, are NOT all compositor-safe (`proof:no-layout-animation` allows a narrow named layout-reclaim allowlist; the dock chrome must be on the transform/opacity/filter set). The scoped `transition` legs at `morph.css:382-386` (held-state bg/border/box-shadow on `--duration-fast`) and `shell.css:308-311` (the vertical rail box-shadow/transform/scale) are correct + scoped — KEEP — but they are NOT compositor-promoted (`will-change` is on the morph box only).

The morph mechanism itself is SOUND and must be KEPT (glass-dock-codebase.md §2.7): the single-scalar `--dock-morph-t` clock, the reserved-footprint-`scale()` compositor transform, the `overflow: clip` aperture (`shell.css:178-199`), the V↔H topology-occlusion via VT crossfade. This wave does NOT rebuild the morph — it UNIFIES every dock morph CSS leg onto the JS-driven scalar (the buttery envelope the `DOCK_SPRING` `SpringProgress` already glides) so the travel fills the clock, and completes the compositor promotion so every dock transition is buttery. It does NOT touch the `--spring-dock` curve (owned + frozen by `BC.W-SPRING-EASE`).

The morph chrome is driven by `dockMorphContext.ts` (`src/components/custom/dock/composables/dockMorphContext.ts:234-235` reads `DOCK_SPRING.response`/`.dampingFraction` into a `SpringProgress`) — the ONE clock; `useLayerTransition.ts:260-261` reads the SAME `DOCK_SPRING`. **`DOCK_SPRING` is byte-fenced by the value.js letter** (dockMorphContext.ts:375 "DOCK_SPRING in ../constants is byte-untouched; the letter's fence") — so this wave does NOT change `DOCK_SPRING`. The fix is the SHAPE of the curve the spring SAMPLES against the clock, not the `(response, ζ)` pair.
