## Goal (the gestalt)
There is ONE motion brain in glass-ui and it is keyframes.js. Every spring you see — a dock morphing V↔H, a dialog blooming open, a tab pill flinging to its slot, a button squishing under a press, a number tweening up, a drawer snapping to a detent — is the SAME `SpringProgress` physics core running off the SAME `(response, ζ)` register table, ticked by the SAME frame discipline, snapped by the SAME `prefers-reduced-motion` gate. No surface hand-rolls a `requestAnimationFrame` spring integrator beside it; no surface re-times a spring against a generic wall-clock `--duration-*`; no surface re-derives an easing curve a value.js twin already encodes. When the user watches the whole demo, every motion reads as ONE coherent physical language — the iOS-27 "everything is the same liquid" feel — because there genuinely is one source and one clock under all of it. The gestalt this wave delivers is not a new animation; it is the PROVABLE completeness of the single source: a gate that reds the instant a wave smuggles in a second spring engine or a desynced clock.

**The user mandate (2026-06-18) binds the clock side of "every element smoothed": EVERY animating surface rides its OWN settle clock, never a generic `--duration-*`.** This wave owns the CLOCK axis of the universal bar (its sibling `BC.W-SPRING-EASE` owns the curve SHAPE, `BC.W-AFFORDANCE-MAP` the per-element affordance map). The binding fact: every `--spring-*` spatial leg — on tabs, dock, buttons, cards, dialogs, drawers, menus, reveals, the viz choreography, the page-build cascade — carries its matching `--spring-<name>-duration` (the analytic 2%-band settle, generated from the SAME `SPRING_PRESETS` table keyframes.js derives the curve from), with the coupled fade riding the SAME scalar. A spring paired with `--duration-normal`/`--duration-fast` re-times it to one wall clock and drags the dead sub-pixel tail (the R10-2 "abrupt"/"springs too slow" read the user named) — M3 reds it library-wide. keyframes.js is the ONE source AND the ONE clock: the `SPRING_PRESETS` `(response, ζ)` → `springTimingFunction` → the `--spring-*` `linear()` curve AND the `t_s = -ln(0.02)/(ζ·ωₙ)` per-spring duration both fall out of the SAME table, so a curve and its clock can never desync. So "every element on its own clock, coupled" is provable, not aspirational.
