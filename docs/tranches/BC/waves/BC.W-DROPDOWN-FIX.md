## Goal (the gestalt)
Open the Select on `/forms/select` and the page **does not jump** — the trigger stays exactly where it was, no horizontal twitch as the panel mounts. The dropdown panel drops directly under the trigger, **aligned to its left edge and matching its width**, so it reads as one continuous control, not a narrow box floating off-centre. Each option carries its selected-state dot in a **reserved gutter on the left**, fully visible, never crashing into or hidden behind the label text. The whole thing reads as a single iOS-27 glass picker: tap, panel blooms from the trigger edge, the chosen row shows a clear dot, pick, panel settles back — no shift, no misalignment, no occluded dot.

## Starting state (measured, file:line)
THREE distinct roots, all live-probed at `/forms/select` (2026-06-18, GPU Playwright):

**1. The trigger SHIFTS on open — the body scroll-lock removes the scrollbar with no gutter compensation.** Live: on opening the Select, `document.body` computes `overflow: hidden` (reka's scroll-lock) with `padding-right: 0px` (NO scrollbar-width compensation), and `<html>` computes `scrollbar-gutter: auto`. The route scroller `<main class="demo-main-scroller ... overflow-y-auto">` (`demo/layout/AppShell.vue:262`) reserves NO stable gutter. On a real OS with a classic (space-taking) scrollbar, locking body scroll removes the ~15px scrollbar → the centered `max-w-6xl` content reflows wider → **the trigger shifts left/right** by half the scrollbar width. (In the headless overlay-scrollbar probe the shift measured 0, confirming it is the classic-scrollbar reflow the user sees on their real Chrome — the same mechanism, surfaced only with a space-taking scrollbar.) The library ships no scroll-lock-gutter discipline, and the demo scroller declares none.

**2. The panel is misaligned + narrower than the trigger.** Live: trigger `left: 146, width: 384`; opened `select-content` `left: 220.5, width: 234.8, data-align: center`. So the panel is **`align="center"`, 234px wide vs the 384px trigger** — it floats centred and narrow under a wide trigger (the user's "not spaced/aligned").
- Source: `SelectContent.vue` `withDefaults(..., { position: 'popper', align: 'center', collisionPadding: 16 })` — `align: 'center'` is the default; the viewport sets `min-w-(--reka-select-trigger-width)` (`SelectContent.vue` `SelectViewport` class) so the panel is AT LEAST trigger-width, but `align: center` still centres a wider panel over a narrower trigger or vice-versa, and on a 384px trigger the 234px panel reads off-axis.
- DropdownMenu mirrors it: `DropdownMenuContent.vue` has `sideOffset: 4` but NO `align` default → reka's `align="center"` default applies (the same off-axis float).

**3. The selected dot has no reserved gutter — it is occluded.** Live: the checked SelectItem computes `padding-left: 0px`. The dot is `SelectItem.vue`'s `<span class="absolute left-2 flex h-3.5 w-3.5">` holding a `w-2 h-2 rounded-pill` indicator at `left-2` (8px). The `menuItemVariants({ indicator: hideIndicator ? 'none' : 'start' })` should reserve `pl-7` (28px) for the dot, but the live `padding-left: 0px` means the item rendered with `indicator: 'none'` (no gutter) — so the absolutely-positioned dot at `left-2` sits OVER the label text with no reserved space → **the dot is occluded by the text** (the user's "dropdown dot totally wrong + occluded"). Either the SelectItem is passing `hideIndicator` (collapsing the gutter while still rendering the dot) or the indicator variant is mis-resolved.

## Target spec (grounded)
THREE coordinated fixes, two in the library + one demo-scroller discipline (the library can ship the gutter discipline too — see below):

**A — kill the trigger shift (scroll-lock gutter).** The fix is `scrollbar-gutter: stable` on the route scroller so the gutter is RESERVED whether or not the scrollbar is present — locking body scroll then removes nothing and the content does not reflow.
- **Demo:** `demo/layout/AppShell.vue:262` `<main class="demo-main-scroller ...">` adds `scrollbar-gutter: stable` (a `[scrollbar-gutter:stable]` arbitrary util or a `.demo-main-scroller { scrollbar-gutter: stable }` rule in `demo/layout/dock-nav.css`). Baseline: `scrollbar-gutter` is Baseline-newly-available (Chrome 94+, Firefox 97+, Safari 18.2+ — cite web.dev/MDN; safe for the demo's modern target).
- **Library discipline (the durable fix):** glass-ui ships an opt-in `.scroll-gutter-stable` utility (or documents the `scrollbar-gutter: stable` requirement on any app-shell route scroller hosting portaled overlays) in `src/styles/utilities/` so a CONSUMER app-shell inherits the no-shift discipline, not just the demo. The body scroll-lock is reka's; the gutter is the scroller's — the library's contribution is the named utility + the canon note (the presets-in-consumers line: the consumer's app-shell opts in).

**B — align the panel to the trigger + match its width.**
- `SelectContent.vue` default `align: 'start'` (the panel's left edge tracks the trigger's left edge — the inspector-idiom alignment) instead of `'center'`. With `position: 'popper'` reka exposes `--reka-select-trigger-width`; the viewport already reads `min-w-(--reka-select-trigger-width)`, so `align: start` + the trigger-width floor makes the panel drop flush-left under the trigger at its width (the user's "spaced/aligned").
- `DropdownMenuContent.vue` adds `align: 'start'` to its `withDefaults` (mirror the Select default — one alignment grammar across the picker family).
- The `.glass-reveal` bloom origin (`origin-(--reka-select-content-transform-origin)`) already tracks reka's measured anchor edge (`SelectContent.vue` comment), so an `align: start` panel blooms from the trigger's left edge — coherent.

**C — reserve the dot gutter so it is never occluded.** `SelectItem.vue` must always reserve the `indicator: 'start'` gutter (`pl-7` = 28px) when a dot renders. The defect is the live `padding-left: 0px` — the gutter collapsed.
- Fix: `SelectItem.vue` passes `indicator: hideIndicator ? 'none' : 'start'` to `menuItemVariants` — this is ALREADY the code, so the live `pl-0` means `hideIndicator` is truthy at this call site OR the demo passes `hideIndicator`. Re-verify: the default (`hideIndicator` unset/false) MUST reserve `pl-7`. If the demo `/forms/select` passes `hideIndicator` while still wanting the dot, that is the bug — the dot and the gutter are coupled (you cannot show the dot AND collapse its gutter). The wave makes the coupling structural: the `<span class="absolute left-2 ...">` dot renders IFF `indicator !== 'none'`, so a `none`-gutter item never paints an occluded dot, and a dot-bearing item always reserves `pl-7`.
- The dot itself reads `var(--select-dot-color, currentColor)` (`SelectItem.vue`) — fine; the gutter is the fix. The dot sits at `left-2` (8px) inside a `pl-7` (28px) gutter → 8px in, fully clear of the label that starts at 28px.
