### The Safari flash root — the WebGL context-loss CHURN, not a missing lifecycle
The WebGL2 substrate ALREADY HAS a `webglcontextlost`/`webglcontextrestored` self-heal (`src/composables/glass/webgl/useWebGLCanvas.ts:177-218`): `onContextLost` calls `e.preventDefault()` (line 181, REQUIRED so restore can fire) + nulls the hooks + parks via `markContextLost`; `bindContextEvents` (line 198-207) wires the pair so `webglcontextrestored` re-runs `buildContext` (re-creates the program on the fresh context) + re-arms. So the DEFECT-LEDGER D7 "cross-engine context management absent" is **half-stale** — the lifecycle EXISTS. The Safari flash is the **CHURN LOOP**, four grounded mechanisms that make the present lifecycle re-fire in a storm on WebKit:

1. **The per-page WebGL-context cap is HIT, then the restore re-creates a context that gets evicted again — the storm.** Chromium/WebKit cap concurrent WebGL contexts (~8 Chromium, WebKit is stricter — historically ~4-16, aggressively reclaimed under memory pressure on iOS). `useWebGLCanvas.ts:44,70,167-168` force-releases probe + teardown contexts via `WEBGL_lose_context` precisely because of this cap, but a multi-viz page (the demo home aurora + a route aurora + the swraster fall + the morph re-render) plus the WebGPU picker ALSO creating contexts (`useGpuSubstrate.ts:91` commits WebGPU at construction, then on a no-adapter throw the page is left in an indeterminate context state) overruns the cap. WebKit evicts the oldest context → `webglcontextlost` fires → the self-heal re-creates it → the new context evicts another → that one's `webglcontextlost` fires → re-heal → … = the **rapidly-flashing re-arm storm** (goo-blob.md:33-34,110-114; SYNTHESIS failure-class #8 "headless-green / GPU-absent false-paint … Safari/WebKit context-loss D7/H never in the CI surface").
2. **The restore re-arms UNCONDITIONALLY — no debounce, no give-up.** `bindContextEvents` (`useWebGLCanvas.ts:198-207`) re-runs `buildContext` on EVERY `webglcontextrestored` with no rate-limit and no max-retry. Two contexts ping-ponging eviction → two restores per cycle → an unbounded re-arm loop. There is no "if we've lost-and-restored N times in T ms, stop re-arming and hold the parked/placeholder state" guard.
3. **The picker leaves a half-built WebGPU context on the no-adapter throw (the D8 cross-contaminant).** `useWebGPUCanvas.ts:243-245` throws `[useWebGPUCanvas] no GPU adapter` AFTER `useGpuSubstrate.ts:91` already committed the WebGPU backend synchronously. On a Safari config where `navigator.gpu` exists but an adapter momentarily isn't grantable (memory pressure, a backgrounded tab racing the arm), the canvas is left mid-configure — and the page-error churn compounds the WebGL eviction storm. (The picker async-probe + try-then-rebuild is `BC.W-WEBGPU-EVERYWHERE`'s scope; this wave assumes that lands and hardens the CONTEXT-LIFECYCLE that the rebuilt picker swaps between.)
4. **NO playwright WebKit project exists — the storm is invisible to CI.** `tests-visual/playwright.config.ts:64-87` declares ONLY `chromium-headless-new` (desktop) + `coarse-touch` (mobile chromium). There is **zero WebKit project** — so the entire Safari surface (D5(b)/D7/§H) has never been in the test matrix. The BB/BA reflects captured chromium-only (SYNTHESIS #8); the flash was structurally un-catchable.

### 1. The context-loss circuit-breaker — the re-arm storm BOUNDED (the §H flash kill)
At the WebGL lifecycle (`useWebGLCanvas.ts` `bindContextEvents` / the `createCanvasLifecycle` restore path):
- **Debounce the restore.** A `webglcontextrestored` does NOT re-arm synchronously inside the event; it schedules ONE re-arm on the next macrotask (or a short ~80-120ms debounce window), coalescing a burst of lost/restored cycles into a SINGLE rebuild. A second loss arriving inside the window cancels the pending re-arm (the context is gone again — don't waste the rebuild). This converts the storm into at most one rebuild per settle.
- **Bound the retries — the circuit-breaker.** Track lost-restore cycles in a sliding window. If the surface loses-and-restores more than **N=3 times within T=2000ms** (a real eviction storm, not a one-off GPU TDR), the substrate STOPS re-arming and HOLDS the parked state (the WebGL placeholder / the last painted frame frozen, or the CSS/2D fallback ground for aurora) WITHOUT throwing — a recognized "this host can't hold a live context right now" decision, the `aurora-swraster` inert-handle precedent (W-AURORA-SWRASTER: a software-raster fall returns an inert handle, no `onInitError`). The breaker RESETS after the window passes quiet (a later genuine single loss self-heals normally). The pinned numbers (N=3 / T=2000ms / debounce ~100ms) are SAFETY thresholds — a healthy single GPU-TDR loss (the common case) re-heals on the first cycle and never trips the breaker.
- **A genuine single loss STILL self-heals** (the present correct behavior is KEPT) — the breaker fires ONLY on the pathological storm. This is the difference between "GPU reset, recover" (heal) and "this page is thrashing the context cap" (hold).
- **One-context-per-route budget enforcement (the storm's UPSTREAM cause).** The demo must not hold N live GL contexts on one route (the home aurora + a route aurora + the morph + the swraster). The DockStage one-GL-per-route discipline (AZ.W-STAGE) is the rule; this wave's gate counts live contexts per route ≤ a budget (the one-GL-per-route cap) so the cap is never overrun in the first place — the breaker is the safety net, the budget is the prevention.
