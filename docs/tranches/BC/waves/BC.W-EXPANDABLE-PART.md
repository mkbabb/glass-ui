## Goal (the gestalt)
A consumer (the Atlas, or any app) wraps its panel in `<ExpandableContainer>` and gets the full house behaviour — the corner Maximize/Minimize trigger, the body-teleport-to-fullscreen, the body-overflow lock, the Escape-to-exit shortcut, the `glass-overlay` un-walled tier — AND can re-skin or fully replace the overlay's chrome (a different expand glyph, a branded toolbar across the fullscreen top, the consumer's own close affordance) through a NAMED, contracted seam: a `#expand-trigger` / `#fullscreen-chrome` named slot for replacement, and `::part(trigger)` / `::part(overlay)` / `::part(panel)` exposed shadow-part-style hooks for re-skin — never by forking the SFC. What a reader carries away: **the expand-fullscreen mechanism is the library's; the chrome over it is the consumer's choice, reached through a contracted hook, so the Atlas deletes its hand-rolled fullscreen-chrome shim and the next consumer never re-forks the SFC to change a glyph.** The overlay still reads as the surface LIFTING off the page (the frosted-over-content `glass-overlay` plate, BA.W-SURFACE-AXIS), the body-lock + Escape still fire — the seam adds a re-skin/replace HOOK, it changes ZERO behaviour at the default.

## Target spec (grounded)
A SINGLE-COMPONENT seam on `<ExpandableContainer>` — TWO hook mechanisms, ONE behaviour contract preserved. Token-first / component-over-class / additive-default-OFF (the default render is BYTE-IDENTICAL — a consumer who adds nothing gets exactly today's chrome).

### 1. The `data-part` re-skin hooks (the `::part()`-analogue, light-DOM Vue)
Each chrome element gains a STABLE `data-part="…"` attribute the consumer styles via a plain descendant selector (NOT a `:deep()` reach, NOT a scoped-hash leak — the data-attr is a CONTRACTED public surface, the `MetricRow` `--metric-row-*` consumer-token precedent applied to a structural hook):
- the trigger `<button>` (BOTH the inline-`!open` and the fullscreen-`open` corner button) → `data-part="trigger"` (+ `data-mode="expand"` / `data-mode="collapse"` so a consumer can target the two states distinctly);
- the fullscreen overlay frame `<div>` → `data-part="overlay"`;
- the fullscreen content wrapper `<div class="h-full w-full">` → `data-part="panel"`.
The internal `expandable-container__trigger` BEM class is RE-POINTED onto the `data-part` contract (clean break, no dual — the BEM class is retired as the consumer seam; the SFC's OWN paint moves to the `data-part` selector so the consumer + the SFC read the SAME stable surface). A consumer `<style>` `[data-part="trigger"][data-mode="expand"] { … }` re-skins the expand button library-wide on that instance — the de-shadcn reskin (`BC.W-DESHADCN`) and the Atlas both reach the chrome through this ONE contracted hook.

### 2. The named-slot REPLACEMENT hooks (the full chrome swap)
For a consumer that wants to REPLACE (not just re-skin) the chrome, TWO named slots, each with a default that renders today's chrome EXACTLY (so an unfilled slot is byte-identical):
- **`#expand-trigger`** (default: the `<Maximize2>` corner button) — replaces the inline expand affordance. Slot props: `{ expand: () => void, label: string }` (the consumer's own button calls `expand()`; the model wiring stays the SFC's). A consumer rendering its OWN expand toolbar fills this slot; the body-teleport + lock + Escape are untouched.
- **`#fullscreen-chrome`** (default: the `<Minimize2>` corner button) — replaces the fullscreen-overlay's chrome (a branded top toolbar, a custom close). Slot props: `{ collapse: () => void, label: string, fullscreen: true }`. The default slot (the CONTENT) is UNCHANGED — `#fullscreen-chrome` is the FRAME chrome beside it, not the content.
The slots are ADDITIVE: an unfilled `#expand-trigger`/`#fullscreen-chrome` renders the today-default button verbatim (the no-op floor — the default-render byte-identity is the gate's first clause). The `expand`/`collapse` callbacks are the ONLY behaviour seam exposed (they flip the SAME `v-model:open` — no parallel state path, the one-registry discipline).

### 3. The behaviour contract is INVIOLATE (the seam adds a hook, never a fork-able copy)
The body-overflow ref-counted lock, the `<Teleport :disabled="!open">` body-teleport, the `v-model:open`, the `syncBodyOverflowLock` watcher, the `registerShortcut("Escape")` exit, the `glass-overlay` un-walled tier (+ the `surface`/`buttonPosition`/`expandLabel`/`collapseLabel` props) are BYTE-UNTOUCHED. The seam exposes ONLY the re-skin `data-part` attributes + the two replacement slots + the `expand`/`collapse` callbacks — a consumer can never reach the lock/teleport/Escape internals (they stay the SFC's), so there is NO copy a consumer would fork. This is the AR-7 anti-fork bar: the consumer changes the CHROME, the library keeps the BEHAVIOUR.
