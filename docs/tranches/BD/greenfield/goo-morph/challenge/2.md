# CHALLENGE #2 — CROSS-ENGINE / SAFARI / PERF lens (ADVERSARIAL)

Verdict: **SURVIVES, but WOUNDED.** The core idea (barbell + clip-path hourglass neck
through the static `#glass-goo`) is sound and the Chrome render is genuinely a concave
metaball waist, not a slab — the headline geometry is real. But the GOLDEN as written
ships **three load-bearing falsehoods and four hardening gaps** that, left unfixed,
re-create the exact "green in the gate, broken on Metal" failure this tranche exists to
kill. None topples the central mechanism; all must land before execution.

Default was REFUTED; the spike's *visual* PNG is what pulls it back to SURVIVES.

## R1 (TOP / FATAL-to-the-gate) — the "live-verified π" is a TAUTOLOGY, not a pixel readback

§7 and §8 sell the acceptance as *"a canvas readback of the warm-cream alpha band"* yielding
`waistRatio ≈ 0.272` at p=0.5, and §8 calls the boldest mechanism *"proven."* It is not.
The spike (`golden/barbell-neck.html` line 153-159) computes:

```js
const throat = D * d.neckGirth * 0.34;   // d.neckGirth maxes at 0.80 (line 146)
const ratio  = throat / D;               // ≡ neckGirth * 0.34
```

`measure()` does **no `getImageData`, no canvas, no `drawImage`** (grepped — zero hits).
The "π readback" is `neckGirth * 0.34`, which at the bell peak is `0.80 * 0.34 = 0.272` — a
constant the code can NEVER push above 0.45 because `0.80 * 0.34 < 0.45` *by construction*.
The gate `assert waistRatio <= 0.45` (§7) is asserted against a number mathematically
incapable of failing, and it **never touches the blur→threshold filter output** — the very
thing whose cross-engine fidelity is the entire point. The render in `peak-waist.png` happens
to show a real waist, but that is eyeballed, not measured; the table in §8 is fabricated from
a formula, and "verified live" / "de-risked live" / "measured in the spike" are overclaims.
This is the **cardinal-lesson inflation** (memory: live-verify needs a captured DELTA, not a
claim) reproduced verbatim inside a de-risk spike.

Worse for the born-RED claim: §7 says the current slab "FAILS `hasLocalMinimum`." But the
spike's own π never calls `hasLocalMinimum` on a profile — it asserts a scalar. So the
born-RED proof for the *real* gate (`hasLocalMinimum(crossAxisProfile)`,
`webkit ≈ chromium ±0.05`) has **never been run on a single rendered pixel**, on either
engine. The gate is born-GREEN-by-tautology, the opposite of the §L7 contract it cites.

**Hardening:** the spike's π MUST be re-authored as a true alpha readback — rasterize the
goo-layer output (html2canvas or a `<foreignObject>`→`drawImage`, or just port the spike
into a real `*.spec.ts` that screenshots the live filter output and walks the cross-axis
alpha column at p=0.5). `waistWidth` = the min contiguous alpha run between the two body
centres on the **post-threshold** raster; `bodyWidth` = the max run. Assert
`hasLocalMinimum` on the actual profile. THEN re-run on a real Safari-26-on-Metal capture and
prove `|webkit − chromium| ≤ 0.05`. Until that paired capture exists, §8's "the boldest
cross-engine mechanism is proven" must be downgraded to "Chrome-eyeballed, Safari UNPROVEN."
No execution wave may cite §8 as the Safari de-risk.

## R2 — the GOLDEN's "current literals" (10/24/-11) DO NOT MATCH the shipped filter

§0 states the Safari floor as `feColorMatrix … 24 -11` and §2.2's table lists
`blur 10 / slope 24 / offset −11` as *current*. The actual `GlassGooFilter.vue` defaults are
**`blur: 7, thresholdSlope: 20, thresholdOffset: -9`** (verified in source). The retune table
(`10→13`, `24→15`, `−11→−7`) is therefore solved against the wrong baseline, and the §0
"Safari floor is structurally airtight, KEEP entirely" audit was written against a filter
graph that is *not the one in the repo*. The graph bytes match (good), but the literal
re-solve in §2.2/§3 is overfit to phantom numbers. The deck "≈10" and pager "8" defaults also
contradict the shipped 7/8.

**Hardening:** re-derive the slope/offset re-solve from the **real** 7/20/−9 baseline. The
"offset re-solved for slope 15" math (§2.2) must be redone — `−7` was paired to a `−11`
starting point that does not exist. Restate §0 as "verified against the shipped 7/20/−9
graph." A wrong offset directly threatens R1's waist depth on BOTH engines, so this is not
cosmetic.

## R3 — the spike's own render REFUTES the §2.4/§3 "transmissive colorful field through glass"

`peak-waist.png` (Chrome, the friendly engine) shows the two bodies as **opaque flat
warm-cream discs**. The purple/teal field is visible only in the margins AROUND the bodies —
**never THROUGH the body mass.** `opacity: 0.78` on the whole `.goo` layer dims the composite
uniformly; it does not make the body a *transmissive lens* the field reads through. §2.4's
"the vibrant slide/aurora reads THROUGH the welling neck (verified in the spike)" and §3's
"colorful field behind glass" are **contradicted by the spike's own evidence**. There is also
a hard diagonal seam on bodyA (a `radial-gradient` edge artifact) — flat-shaded, not a domed
droplet. And the spike de-risks ZERO of the §2.4 six-layer material, the §2.3 specular sweep,
the moving cast, or the catch-light arc — so "PERFECTED glass morphism" and "cartoon-punch"
are entirely unproven, on either engine.

On Safari this is *worse*: the real carousel/deck want the colorful slide/aurora to read
through a translucent glass droplet, which on WebKit means the goo layer sits over a
`backdrop-filter` glass surface. You cannot `filter: url(#glass-goo)` AND
`backdrop-filter: blur()` on the same transmissive lens and have WebKit composite the field
through the thresholded alpha — the threshold pass operates on the SourceGraphic's own alpha,
not on what is behind it. The "transmissive metaball lens" is an unsolved compositing problem
the spike sidestepped by using opaque fills.

**Hardening:** the spike must be re-run with a genuinely *transmissive* body (lowered fill
alpha + a real backing-field-through-glass composite) and the field must be shown reading
through the **body**, not just the gaps — in BOTH engines. If WebKit cannot composite the
backing field through the post-threshold alpha (likely), the GOLDEN must either (a) drop the
"field reads through the body" claim and keep the field reading only at the welling-neck/edge
(a narrower, honest §3 read), or (b) split into a transmissive backing pass + an opaque goo
fuse pass with the field pre-baked — a real mechanism §2.4 currently lacks. Either way §3/§2.4
prose is rewritten to match what actually composites.

## R4 — the `morphRef: Ref<HTMLElement>` → three-child group is a SHARED-CONTRACT break, not a "refine"

§3 calls the engine change "re-invent (broken)" for paint() but frames the ref change as
benign ("`morphRef` → a `morphRef` group hosting two body children + a neck child… the engine
writes their transforms via the group"). The shipped contract is
`morphRef: Ref<HTMLElement | null>` and paint() writes ONE `morph.style.transform` (verified,
line 178/217-219). The carousel passes `morphRef: wormEl`, the deck `morphRef: gooWormEl` —
single elements. Moving to a group whose **children** the engine addresses means either (a)
the engine must now query `morph.children[0/1/2]` (fragile, ordering-coupled, KISS-violating)
or (b) the type becomes `{bodyARef, bodyBRef, neckRef}` — which is an API break to EVERY
caller including PagerDots and forces the dock cohort (`DockGooFilter`/`useDockFission`, §3
says UNTOUCHED) into a different shape than its sibling. That is a **parallel-fork risk** the
GOLDEN claims to avoid: two goo engines with two different ref contracts. DRY is asserted but
not demonstrated.

**Hardening:** specify the exact new signature and prove PagerDots + carousel + deck all bind
it identically. If it is `{bodyARef, bodyBRef, neckRef}`, state how the dock fission path
(which §3 keeps single-neck) avoids becoming a second topology. KISS demands the engine NOT
reach into `children` by index — pass the three refs explicitly or keep one host and write
three CSS custom props the children read. Decide and write it down; "via the group" is
hand-waving over the one place DRY actually breaks.

## R5 — Safari `transform` + `filter: url()` + clip-path interaction is asserted, never tested

§2.5/§4 enumerate WebKit bugs 245510/283156/136418 as "structurally absent" — correct for the
*static-filter* class. But the GOLDEN adds, per frame, **`clip-path` animation on the neck**
(scaleX/scaleY on a clip-pathed element) feeding a `filter: url()`. WebKit's handling of a
`clip-path` polygon on a transformed element *inside* a filtered subtree is a distinct code
path from the dock's `clip-path: inset()` (fission uses `inset()`, line 462 — a far simpler
clip than a 14-point concave polygon). A concave self-intersecting-ish polygon under scale,
re-rasterized each frame inside a filter region, is exactly the kind of thing WebKit rasters
differently (sub-pixel AA on the throat, filter-region tiling). §2.5 cites the fission idiom
as precedent but fission necks with `inset()`, not a polygon — the precedent does not cover
the new geometry.

**Hardening:** the paired-Metal capture (R1) must specifically inspect the throat AA and
confirm the polygon throat width matches Chrome ±0.05 *after* the scaleX squeeze, not just at
rest. Add an `@supports` or runtime probe; if the polygon-throat differs on WebKit, fall back
to an `inset()`-based neck (the actual fission idiom) which IS proven on Metal. Do not ship a
14-point polygon as "Safari-insured" on the strength of an `inset()` precedent.

## R6 — perf claim "~2–3 transforms/frame" omits the clip-path raster + region cost

§6/G5 claims "~2–3 transforms/frame, static filter." True for the transforms, but the neck
re-rasters a concave clip-path **inside** a `-50%/200%` filter region every frame, and the
filter re-runs blur(13)+colorMatrix+composite over that enlarged region each frame because the
SourceGraphic alpha changes. `proof:no-layout-animation` will pass (no layout props), but that
gate does NOT measure filter-region raster cost — which on a big carousel plate at blur 13 over
a 200%-inflated region is the actual Safari-Metal budget risk (the very reason
`W-GOO-SPLIT-PERF` exists). §2.5 hand-waves "can TIGHTEN to the two-bead span" but does not.

**Hardening:** make the region-tighten a REQUIREMENT, not a "can." Compute the region from the
two-bead span + blur skirt and pin it, so the filter doesn't raster dead space. Add a perf
budget to G5 measured on Metal (frame time at the neck peak), not just the layout-animation
gate. Cite the actual blur-13-over-200%-region cost the spike never measured.

## R7 (minor) — PRM/a11y: `--goo-weight → 0` is claimed to zero five things from one assignment

§5 says one `--goo-weight: 0` "zeroes squash/overshoot/anticipation/arc/cast." That is only
true if EVERY one of those is authored as `f(--goo-weight)` with a clean multiplicative zero —
the anticipation pre-dip is a `linear()` keyframe (§2.3), not obviously a simple
`× --goo-weight`. A `linear()` dip does not scale to identity by a single multiplier unless
explicitly authored to. Unproven that one token collapses all five.

**Hardening:** show each of the five as `× --goo-weight` (or gate the `linear()` ease swap to
`--ease-standard` explicitly, which §5 *does* for the ease but then double-counts it under the
"one assignment" claim). Keep the explicit `display:none` on the goo layer as the real PRM
floor — that one IS airtight — and stop claiming the single-token collapse for the punch.
