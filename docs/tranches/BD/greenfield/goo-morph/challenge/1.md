## R1 (TOP — LANDS) — §8 "de-risked live" is a FAKE π. The boldest claim is unproven.

The golden's single strongest assertion is §1/§8: the clip-path hourglass waist is
"de-risked live in the spike" — the structural concavity that closes the cross-engine
class "at the GEOMETRY layer." The §8 table (`waist/body 0.272 @ p=0.5`, "✓ REAL WAIST")
is the load-bearing evidence for the entire WebKit-insurance argument.

**It is arithmetic on the input controls, not a readback of a rendered pixel.** In
`golden/barbell-neck.html`:

```js
function measure(p) {
  const d = paint(p);
  const throat = D * d.neckGirth * 0.34;   // <-- 0.34 IS the --neck-waist literal
  const ratio  = throat / D;               //  = neckGirth * 0.34, no canvas, no filter
  return { ..., waistRatio: ratio.toFixed(3) };
}
```

`waistRatio = neckGirth · 0.34`. At p=0.5, neckGirth=0.80 → `0.80·0.34 = 0.272`. The
number is the product of two CONTROLS (`bell()` output × the throat fraction). It never
samples the canvas, never reads the post-`feColorMatrix` alpha, never touches the actual
rendered silhouette. **It is structurally incapable of returning anything but
`neckGirth·0.34`** — it would print "✓ REAL WAIST" even if the SVG filter were deleted,
even if the clip-path were removed, even if the bodies overlapped into a solid disk.

The golden's OWN §7 gate is explicit that this is illegitimate: it demands a *canvas
readback* of the warm-cream alpha band + `hasLocalMinimum(crossAxisProfile)`. §8 runs
NEITHER. So the wave's headline de-risk does not exercise the gate the wave is born to
pass. The "boldest cross-engine mechanism is proven" sentence is false; what is proven is
that `0.8·0.34 = 0.272`.

The screenshot (`peak-waist.png`) DOES show a plausible concave waist in Chrome — so the
mechanism is *promising* — but a single Chrome screenshot with a self-confirming number is
precisely the single-engine-green the golden's §L7 forbids as acceptance. There is ZERO
Safari capture in the de-risk. The "perfect in Chrome AND Safari" headline rests on an
un-run engine.

**HARDENING:** Re-author the spike π to a real readback before any wave executes: draw the
filtered `.goo` layer to an offscreen canvas (`html2canvas` or `drawImage` of an
SVG-foreignObject snapshot won't capture the filter — instead render the goo layer's
computed silhouette by sampling `document.elementFromPoint` alpha along the travel axis,
or screenshot-crop + `getImageData` a cross-axis profile). Assert `hasLocalMinimum` on the
*measured* profile. Then capture the SAME spike in a real Safari-26-on-Metal and assert
`|webkit.waist − chromium.waist| ≤ 0.05`. Until both exist, §8 must be downgraded from
"de-risked" to "Chrome-plausible, Safari-UNVERIFIED" and G2 stays RED by honesty.

## R2 (LANDS) — the "reuse the `--neck-filament` hourglass clip-path idiom, NO fork" claim is FALSE. It is a parallel neck recipe.

The golden leans on deft-integration: §1 "the fission `--neck-filament` clip-path hourglass
idiom — already proves the answer at dock scale"; §3 "the `--neck-filament` hourglass +
specular + cast idioms are REUSED ... NOT forked." This is the central KISS/DRY/no-legacy
claim.

The shipped fission neck is **NOT a hourglass and NOT a polygon.** In
`src/styles/dock/fission-bridge.css`:

```css
--neck-inset: calc(var(--neck-filament) * clamp(0, ...neck-t..., 1));
clip-path: inset(var(--neck-inset) 0 var(--neck-inset) 0 round 999px);
```

`grep -n "polygon\|hourglass\|concave" fission-bridge.css` → **ZERO hits.** `--neck-filament`
is an `inset()` that grows from both block edges toward the centerline — it produces a
THINNING ROUNDED CAPSULE (a uniform-width filament that gets shorter on the cross-axis),
**never a concave-sided waist.** An `inset(... round 999px)` rectangle has convex edges; it
cannot carve the inward-pulling sides §1 requires ("the sides pull IN at the midpoint").

The spike's actual waist comes from a **brand-new hardcoded 15-point polygon** invented in
`barbell-neck.html` (`clip-path: polygon(0% 8%, 0% 92%, 18% 70%, 34% 60%, 50% 57% ...)`).
That polygon is NOT in fission-bridge.css, NOT tokenized, NOT the `--neck-filament` idiom.
So the golden's waist mechanism is a **parallel fork of the neck recipe** dressed in the
extant idiom's NAME — exactly the bolt-on the lens forbids. The `--neck-waist` "one retune"
of `--neck-filament` is fiction: you cannot retune an `inset()` into a concave polygon; they
are different clip-path functions.

**HARDENING:** Either (a) honestly mark the hourglass polygon as a NET-NEW neck primitive
(`--neck-waist` polygon recipe) and justify it as a re-invent of a broken/absent capability
— then DRY it by making the dock fission ALSO adopt it (one neck recipe, two consumers,
genuinely shared), OR (b) prove an `inset()`-only path yields the waist after the filter
weld (the blur+threshold MAY fuse two near capsules into a concavity without a polygon —
test it, since that would let you actually reuse `--neck-filament`). Pick one; the current
"reuse, no fork" text is a false integration claim and must be struck.

## R4 (LANDS, narrower) — "keeps `travel`/`snap`/`drive` verbatim, only the projection re-invented" understates the blast radius. The engine's SOLE output is replaced.

`useGooMorph.paint()` (verified, lines 171-221) writes ONE transform to ONE `morphRef`:
`translateX(center) scaleX(lenRatio) scaleY(pinch)`. The entire engine's product is a
single-element single-transform worm. `placeStatic`, the rAF loop, `--goo-len-ratio`, the
`girthFloor` pinch — ALL assume one element.

The golden turns `morphRef` into "a group hosting two body children + a neck child" and
`paint` into three independent transforms with a separation envelope + a bell + a clip-path
neck. That is not "re-author the projection" — it is **replacing the only thing the engine
emits and the shape of its single ref.** Every caller's template changes (one `wormEl` →
three spans + a group); `placeStatic` must now place three elements or hide two; the
`girthFloor` pinch logic is deleted (the golden's pinch is now `sep`/`neckGirth`, a
different model). The "same engine, refinement-in-place" framing hides that this is a
ground-up rewrite of `useGooMorph`'s core that merely keeps the PUBLIC method names. The
risk/test surface is a new engine's, not a tweak's — and the pager (which the golden calls
"the migration PROOF") today uses the SAME single-`morphRef` worm, so it ALSO rewrites, it
is not a proof-of-prior-art.

**HARDENING:** Be honest in §3/§9: this is a re-invent of `useGooMorph`'s projection AND its
ref contract (single el → group of 3). Keep the public `travel/snap/drive` names (fine), but
budget it as an engine rewrite with full three-consumer re-test, not a "values-only refine."
Verify `placeStatic`/PRM/`snap` against the 3-element model explicitly (the early-return PRM
path must hide bodyB+neck, not just stop the rAF).

## R5 (PARTIAL) — Safari risk the golden does NOT name: clip-path polygon INSIDE a filtered subtree + sub-pixel polygon AA on Metal.

The golden's §2.5 audits the filter graph (245510/283156/136418) thoroughly — good. But the
NEW mechanism puts a `clip-path: polygon()` element as INPUT to `filter: url(#glass-goo)`,
animated via `scaleX/scaleY` on a clipped node. Two un-audited WebKit facts:

1. A `clip-path` polygon scaled non-uniformly (`scaleX(neckLen) scaleY(neckGirth)` with
   neckLen often ≫1 when the gap is wide) distorts the polygon's THROAT proportions — the
   34%→66% inner points stretch, so the "waist fraction" is NOT `--neck-waist`; it drifts
   with gap. On Safari, polygon clip AA + a large scaleX can shimmer/alias the throat edge
   under the blur. The golden assumes the throat is a stable `--neck-waist`; under the live
   `scaleX(gap/D)` it is gap-dependent and engine-AA-dependent.
2. The golden never confirms WebKit applies `clip-path` BEFORE `filter` for an element that
   is itself a filter input (it does, per spec order — clip then filter — but the
   *blurred* clipped alpha is what thresholds; a hard polygon edge + 13px blur + slope-15
   threshold may re-CONVEX the throat on WebKit's sRGB clamp differently than Chrome). This
   is the exact "reads identically across engines" assumption R1 left unproven.

**HARDENING:** Add to §2.5 + the gate: (a) measure throat-fraction-vs-gap, clamp `neckLen`
or pre-distort the polygon so the throat stays `--neck-waist` across the travel; (b) the
paired-engine π MUST capture the polygon-under-filter throat at the WIDEST gap (p≈0.2/0.8),
not only p=0.5, since the AA/threshold drift is worst when scaleX is largest.

wrong: `girthFloor=0.72` (verified line 119), not 0.85, and it's the PINCH not the waist.
The born-RED arithmetic is sloppy and would confuse the gate author into measuring the wrong
quantity. Also: §7's gate runs on a `/navigation/carousel` real-click — GOOD — but §8
"proved" it on the throwaway spike, so the born-RED has never actually been observed RED on
the real build. "Born-RED" is asserted, not demonstrated.

**HARDENING:** Run the REAL §7 canvas-readback gate against the CURRENT build on
`/navigation/carousel` and capture the RED (hasLocalMinimum=false, waistRatio≈1.0) as the
born-RED artefact BEFORE the rebuild — that is the only honest born-RED proof. Fix §7's
"0.85/girthFloor" to the correct quantity (the global min cross-axis profile, ratio≈1.0 on
the convex worm; girthFloor=0.72 is unrelated).

## WHAT SURVIVES (fit — do not over-correct)
- The CORE diagnosis is RIGHT and well-argued: a single constant-cross-section worm cannot
  produce a concavity; a waist needs two masses or a clip carve. This is the correct
  root-cause, not a token tune. KEEP.
- The barbell + structural-waist DIRECTION is sound and the Chrome screenshot is genuinely
  promising. The mechanism likely works — the defect is the OVERCLAIMED de-risk + the
  FALSE reuse lineage, not the idea.
- The Safari filter-graph audit (245510/283156/136418, sRGB, static literals, regular
  filter:url, region, @supports+PRM floors) is thorough and correct for the FILTER. KEEP.
- The no-gray warm-cream floor, the PRM/a11y carve (aria-hidden decorative goo over an
  accessible scroller, WCAG-2.2.2 one-shot), and the golden-ratio proportions are clean.

## NET
The idea is fit; the EVIDENCE and the INTEGRATION CLAIMS are not. The golden fails this
lens on: a self-confirming fake π presented as a de-risk (R1), a false "reuse the hourglass
idiom, no fork" claim when the idiom is `inset()` not a polygon and the polygon is net-new
(R2), invented levers cited as extant Band-0 primitives (R3), an under-stated engine rewrite
(R4), and an un-named polygon-under-filter Safari risk (R5). Harden R1-R3 and it survives;
ship as-written and it is a bolt-on wearing a union's clothes with a gate that cannot fail.
