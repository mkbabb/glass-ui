## R1 (TOP REFUTATION — the boldest move is architecturally self-contradictory; the spike de-risks the OPPOSITE)

**Claim under attack:** §2.2 / §3 — the `envelop` goo-tear is "the dock's OWN glass skin flowing
outward, warm-cream identity continuous through the tear," reading the colourful field THROUGH a
transmissive backdrop-filter composite, with a real metaball neck bridging dock body + surface.

**The contradiction (live-verified on the GOLDEN's own spike, both screenshots captured):**
The metaball neck REQUIRES `filter: url(#goo)` on a group that contains BOTH the dock body and the
erupting surface (this is exactly what `.goo { filter: url(#golden-goo) }` does, with `.dock` and
`.surface` as descendants — confirmed `goo.contains(dock) === true`). But an ancestor `filter`
**kills `backdrop-filter` on every descendant** in BOTH Chrome AND WebKit: the ancestor's filter
forces an isolated rendering buffer, so the descendant's `backdrop-filter` samples that empty buffer
instead of the page behind it.

**Empirical proof (I drove the spike open mid-flight and screenshotted):**
- Goo filter ON: the dock body renders as a **flat opaque mud-gray slab** — the colourful field
  does NOT read through, despite the fill being `srgb(0.944 0.903 0.865 / 0.62)` warm cream. This
  is a **direct BA.W-NO-GRAY / "NEVER gray" violation** and a §3 "colourful field behind glass"
  violation, in the headline topology.
- I set `.goo { filter: none }` and re-screenshotted: the green field immediately bled THROUGH the
  dock body, backdrop blur returned. The ONLY variable was the ancestor goo filter.

So the two pillars of the boldest move — (a) the metaball goo-tear and (b) transmissive warm-cream
glass on the tearing membrane — are **mutually exclusive in the spike's own DOM**. The spike does
not de-risk the boldest move; it demonstrates that it cannot be built as drawn. "ANY payload
inherits the dock's liquid identity for free" is false: under the goo group the payload inherits a
DEAD backdrop and a gray fill.

**Hardening (R1):** the goo-tear must NOT wrap the glass bodies in an ancestor `filter`. Re-architect
so the metaball neck is a SEPARATE sibling layer (a dedicated `<svg>`/`<div>` painting ONLY the neck
membrane fill under `filter:url`, decoupled from the dock/surface backdrop layers), with the
dock+surface backdrop-filter bodies as siblings ABOVE the neck — the neck reads as the connective
gel, the bodies stay transmissive. This is exactly the pattern `fission-bridge.css` /
`DockGooFilter.vue` already ship (the neck is a bridge ELEMENT, not an ancestor of the docks). The
spike was hand-rolled and got this wrong; the GOLDEN must mandate "neck-as-sibling, NEVER neck-
filter-as-ancestor-of-glass" as a hard precept and a born-RED π arm: assert the dock body still
shows field-chroma transmission mid-eruption (sample painted pixel chroma > floor, not gray).

## R2 — "compositor-only by construction; never width/height" is FALSE for `envelop` (the spike layout-animates, and so does the shipped dock)

§4 claims `useElementMorph` "writes ONLY transform/opacity/filter ... never width/height/top/left
(the `proof:no-layout-animation` fence)." `proof-no-layout-animation.mjs` is a REAL shipped gate
(`scripts/proof-no-layout-animation.mjs`).

But:
- The de-risk spike drives the dock body via `width: calc(220px + 360px * var(--dock-portal-t))`
  and `height: calc(64px + 392px * ...)` and `border-radius: calc(...)` — I measured width animate
  220 → 382 → 580px. That is pure **layout animation** and would FAIL the cited fence. The spike's
  own comment admits it ("we animate the dock plate size here to PROVE the boundary-grows claim; in
  glass-ui this is the FLIP'd compositor morph") — i.e. the hard part (a true compositor FLIP of a
  pill→sheet boundary with correct content reflow at the destination) is hand-waved and NOT de-risked.
- The SHIPPED dock morph confirms the dock genuinely resizes via layout:
  `constants.ts` `RESIZE_MORPH_PROPS = new Set(["width","height","padding","transform"])` — the
  dock-morph window watches `transitionend` on **width/height**. The real dock grows by layout, not
  by transform-only. So "the `.glass-dock` border-box GROWS ... box-INVIOLATE, compositor-only" mixes
  two incompatible mechanisms.

**Hardening (R2):** specify HOW envelop reconciles a transform-only FLIP (compositor) with the
shipped width/height resize-morph (layout). Either (a) accept envelop rides the existing
layout-driven `--dock-morph-t` window (and then DROP the "never width/height / proof:no-layout-
animation" claim for envelop, scoping that fence to the bloom/receive surfaces only), or (b) commit
to a true FLIP where the destination sheet is laid out at rest and the dock is `transform`-scaled
into it — and then the spike must be redone to PROVE that, because the current spike proves the
layout path. As written the §4 purity claim and the §2.1 "boundary-as-surface" mechanism contradict
each other and the shipped `RESIZE_MORPH_PROPS`.

## R3 — the "FOUR engines, ONE substrate" DRY premise is partly inaccurate; H5's born-RED rationale overcounts

§0.2 + §2.1 + H5 rest on "FOUR bloom engines ALL compose the same kf `ElementMorph` +
`springTimingFunction` pair ... four bloom engines run today, each instantiate their own loop." Grep
of HEAD:
- `useLiquidReveal`, `useBloomUp`, `useDockCtaReceive`: YES — import `ElementMorph` +
  `springTimingFunction`, 4 `requestAnimationFrame` sites each. True.
- `useLiquidMorph`: **imports `SpringProgress`, NOT `ElementMorph`/`springTimingFunction`, and has
  ZERO `requestAnimationFrame` calls** (it drives a `SpringProgress` scalar, no FLIP loop at all).

So the unification is THREE FLIP engines over the kf `ElementMorph` substrate + ONE separate
`SpringProgress` scalar engine — not "four identical engines." The GOLDEN says "useLiquidMorph's
duplicate FLIP loop is DELETED," but there IS no FLIP loop in useLiquidMorph to delete. The DRY win
is real (collapse the 3 ElementMorph wrappers), but the spec mis-describes the 4th, and H5's
"countBloomRunners === 1 ... four bloom engines run today" is an overcount: there are 3 rAF FLIP
runners + 1 SpringProgress. The born-RED arm should assert against the ACTUAL topology or it can be
gamed/false-flagged.

**Hardening (R3):** correct §0.2/§2.1/§10 to "THREE kf-`ElementMorph` FLIP wrappers + the
`useLiquidMorph` `SpringProgress` scalar." Decide explicitly whether `useLiquidMorph`'s
`SpringProgress` is (a) subsumed into `useElementMorph` (then say how — it's a different kf
primitive) or (b) retained as the scalar-only path (then H5 must count "FLIP rAF runners," not
"bloom runners," to stay honest). Re-word the H5 π `countBloomRunners` to a precise definition.

## R4 — the de-overfit census (§6) is INCOMPLETE; `proof:no-hardcoded-refs` is imprecise and will false-flag legitimate structural enums

§6's excision table cites 4 `src/` sites for the `search|media|nav` enums (useDockFission:56,
useDockShellProps:198, GlassDock:408/413, useDockContextSilhouette:68). Grep of `src/components/
custom/dock/` for `"search"|"media"|"nav"` returns **20 hits across 6 files** — the table MISSES:
- `DockSection.vue:65` `s.kind === "nav"`
- `constants.ts:48,50` `DockSectionKind = "rail-core" | "section" | "nav"`

But here's the precision trap: `DockSectionKind="nav"` is a **legitimate structural layout enum**
(the trailing nav-arrows group), NOT an app-facility name. A `proof:no-hardcoded-refs` grep for
`"nav"`/`"search"` (as §7.2 describes — "greps src/ ... for app-facility names") will **false-flag
these legitimate enums**, OR, to avoid that, will be hand-tuned to skip them — at which point it's no
longer a clean grep and can be gamed. The GOLDEN conflates two different `"nav"`s: the
fission/silhouette app-DOMAIN `"nav"` (overfit, must die) vs the DockSection structural `"nav"`
(legitimate, must stay).

**Hardening (R4):** (a) complete the census — explicitly LIST `DockSection.vue`/`constants.ts`
`DockSectionKind` and CLASSIFY it as legitimate-structural (exempt), so the census is honest per the
overfitting-audit law. (b) Re-scope `proof:no-hardcoded-refs` to a CALL-EXPRESSION / type-position
scan keyed to the fission/silhouette/shell public verbs (like H3's "call-expression scan, not a
keyword grep"), NOT a bare string grep, so it catches `DockSplitContext` app-keys without
false-flagging `DockSectionKind`. As written §7.2 is a keyword grep and is both incomplete and
imprecise.

## R5 — the geometry-only IN-vs-OUT branch (H1 purity) is under-determined

§3 / §9 lens-b: the hub picks `envelop` vs `bloom` "off whether the surface ref is a dock descendant
or a portal'd sibling — ONE branch, geometry-only, NO surface-TYPE branch." But `<DockExpand>`'s
`#surface` slot content is authored by the consumer and is typically NOT mounted/positioned until
open; "is it a dock descendant?" is a DOM-topology question that depends on where the consumer (or
the portal) mounts it, which the consumer controls via `topology="envelop"` vs default. So in
practice the consumer's `topology` PROP is the real selector — which is fine and honest, but then the
"geometry-only, infer from DOM ancestry" framing is a fiction; it's a declarative prop, not an
inferred geometry. Not fatal, but the spec should not claim auto-inference it doesn't do.

**Hardening (R5):** state plainly that `topology` is a consumer-declared prop on `<DockExpand>` (the
honest contract), and that H1's "surface-TYPE-blind" means the verb has no per-CONTENT-kind branch
(card vs sheet vs viz) — NOT that it auto-infers in/out from live DOM ancestry. Keep the in/out as an
explicit topology value, drop the "infer from descendant-vs-sibling" claim or demote it to an
optional default.
