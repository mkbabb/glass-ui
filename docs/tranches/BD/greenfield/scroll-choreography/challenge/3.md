## What SURVIVES (granted, verified live — not conceded cheaply)

The **motion plumbing is real and genuinely born-RED.** I confirmed each load-bearing claim:

- **The dead pin is real.** On the live demo, sweeping `main.demo-main-scroller`
  (`scrollHeight 4164 / clientHeight 806` — matches the GOLDEN's stated numbers exactly)
  across `[0, .2, .4, .55, .7, 1.0]`: `.scroll-pin-phase-reveal` reads `transform:none`,
  `translate:none`, `scale:none`, `opacity:1` at EVERY frame, and its bound animation's
  `timeline.constructor.name === "ScrollTimeline"` with `currentTime === null`. R-PIN is
  honestly RED. Setting `--pin-t` to 0.225 / 0.45 by hand produces ZERO change — the
  current recipe does not read `--pin-t`, so the GOLDEN's `--pin-t` rewrite is real work,
  not a tweak.
- **The keyframes.js de-risk is correct and honest.** `createScrollScene` / `ScrollScene`
  ARE only `.d.ts` + lazy-chunk at 4.3.0; `SmoothProgress` / `SpringProgress` /
  `springLinearStops` ARE synchronous top-level exports with the exact API the spike uses
  (`setTarget`, `play(onFrame)`, `snap()`, `get settled`, `tickDt`). The pivot to build
  `useScrollScene` on the synchronous primitives is the right KISS call — this is the
  single best thing in the document and it catches a mistake all three lenses made.
- **The cascade swap is real work.** Live: `.scroll-cascade > *` is `linear` + `view()` +
  `gl-cascade-build` today; `--ease-scroll-spring` token is EMPTY (does not exist). The
  spring-scrub swap is genuine.
- **The spine is DRY/union, not a fork.** `scrollReader` is KEPT verbatim; `useScrollProgress`
  public `Ref<number>` unchanged; no Lenis/GSAP; one writer per axis. The survival ledger is
  disciplined. No legacy alias.

So the ENGINE survives. **The GESTALT does not.** Below is where it fails MY lens.

## TOP REFUTATION — the cartoon-punch + colorful-field + warm-glass precepts are
## demonstrated ONLY in a throwaway spike with HARDCODED palette + INVENTED DOM; the
## SHIPPING recipe writes bare opacity/translate/scale onto a NEAR-GRAY glass-card

This is the load-bearing design-fidelity failure. The GOLDEN's §1c promises the pin
"carries the CARTOON register" — anticipation dip → overshoot → settle, vol-preserving
squash, **a moving cel cast**, follow-through. The acceptance bar §6 demands "the
AUDACIOUS cartoon-slam pin loud and golden-proportioned." But:

1. **The cel-cast / cartoon punch lives ONLY in the spike, on DOM that does not exist.**
   The real demo element is `.scroll-pin-phase-reveal.glass-card` with `::after { content:
   none }`. The spike invented a `.scroll-pin-card` wrapper with a `::after` colored cast —
   **that class and that `::after` are NOT in the real DOM**, and the GOLDEN §2b recipe
   never adds them. The §2b shipping recipe writes only `opacity`, `translate`, `scale`.
   So the "moving cel cast," "anticipation dip → overshoot," and "follow-through caption"
   are PROSE + a throwaway, never wired to the real component. The headline "audacious
   cartoon-slam" is unproven against real markup.

2. **The real pin glass is NEAR-GRAY — a §BA.W-NO-GRAY violation hiding in plain sight.**
   Live readback of the real reveal card: `background: oklab(0.72 0.005 0.011 / 0.6)` —
   chroma ≈ 0.012, essentially neutral (a≈0.005, b≈0.011). That is the GRAY glass the
   binding law forbids ("transmissive warm-cream … NEVER gray, the BA.W-NO-GRAY warm
   floor"). The GOLDEN touches motion but leaves the pin's surface gray; §3's "COLORFUL
   FIELD behind glass + a defined edge" is absent — there is no field behind the card, no
   edge. The spike MASKS this by hardcoding a warm `oklch(0.99 0.03 95)` card + an
   `oklch(0.62 0.16 55)` orange edge + a colored `::after` field — a palette the real
   `glass-card` token does NOT produce. The spike's warm screenshot is a Potemkin village;
   the shipping surface is gray.

3. **`--shadow-cartoon-md` is a PHANTOM token — the exact `createScrollScene` mistake,
   repeated.** §1c and §2c both cite `--shadow-cartoon-md` as "extant (§Cartoon-shadows)".
   It does NOT exist. The real tokens are `--shadow-cartoon` / `--shadow-cartoon-hover`
   (no `-md`), and even those are `3px 3px 0 …` low-offset, not the bold `8px 10px 0` the
   spike hardcodes. The GOLDEN caught its OWN phantom (`createScrollScene`) but shipped a
   second one in the cartoon arm. The cel-cast's "1940s bold layered-offset shadow" is
   built on a token that isn't there — and the spike sidesteps it by hardcoding a literal
   value AND by not even using the token (its cast is a hand-rolled `::after background +
   translate`). The cartoon-shadow register is doubly unproven.

**Hardening:** the production wave MUST (a) add the `.scroll-pin` reveal DOM the cel-cast
needs (a `::after` carrying `--shadow-cartoon` real token + the colorful-field-behind +
defined-edge) to the REAL `scroll-choreography.vue`, not a spike; (b) re-warm the pin glass
off the warm-cream six-layer composite (drive chroma > the NO-GRAY floor, both modes) and
add the §3 colorful field + edge; (c) FIX the `--shadow-cartoon-md` reference to the real
`--shadow-cartoon` (or author `-md` in shadow.css with the bold offset and cross-link it as
a real DEPEND-ON, not "extant"); (d) re-author the born-RED gate to assert the cel-cast
`::after` TRANSLATE sweeps + a non-gray chroma readback on the real element — not on spike
DOM. Until the cartoon register + warm field paint on the REAL component, §6's "audacious
cartoon-slam loud and golden-proportioned" is an unkept promise.

## SECONDARY REFUTATIONS

### S1 — "createScrollReader resolves `main.demo-main-scroller` automatically" is FALSE; the
### real-app source-resolution is an unspecified gap
§1c line 113 claims `createScrollReader` auto-resolves the scroll port. The source
(`scrollReader.ts`) shows `createScrollReader(source, onTick)` takes an EXPLICIT source and
only disambiguates element-vs-Window-vs-document — zero auto-discovery of
`main.demo-main-scroller`. The spike papers over it by `document.getElementById("scroller")`.
So `useScrollPin` in the real app has NO specified strategy for finding the nearest scroll
ancestor (the app-shell `.demo-main-scroller` is an arbitrary ancestor, not `window`). This
is a real integration gap: the pin needs an ancestor-walk or an explicit `source` prop the
GOLDEN never defines. **Hardening:** specify `useScrollPin({ source })` resolution — either
a required explicit source or a documented `closest-scroll-container` ancestor walk — and
prove it on the real chassis, not a fixed `getElementById`.

### S2 — golden-proportion is ASSERTED, never composed into the felt motion
The binding law demands "ARISTOTELIAN golden-ratio proportion in ALL things." The GOLDEN
names `--scroll-scrub: 0.62` (1/φ) and `--scroll-scrub-pin: 0.50` — but 0.50 is NOT a
1/φ-family value (1/φ ≈ 0.618, 1/φ² ≈ 0.382); the comment "still 1/φ-family" is hand-wave
for "a round number I picked." And the pin reveal window `--scroll-pin-phase-reveal-end-frac:
0.45` and the squash `0.96 + 0.04·t` (spike: `0.92 + 0.08·t`) are arbitrary, not φ-derived.
The squash amount differs between the GOLDEN recipe (0.04) and the spike (0.08) with no
rationale — overfit knob-twiddling. **Hardening:** derive the pin scrub, reveal window, and
squash depth from the φ ladder (e.g. reveal end = 1/φ² ≈ 0.382, squash floor = 1−1/φ⁴), pick
ONE squash depth, and state the proportion explicitly rather than "1/φ-family" as a label.

### S3 — the spike's `damping = 0.06 + (1−scrub)·0.14` mapping is an UNGROUNDED magic curve
The whole liquid-weight feel hinges on translating `--scroll-scrub` (1/φ) into a
`SmoothProgress` damping. The spike does `0.06 + (1−scrub)·0.14` — four hardcoded magic
numbers with a comment "scrub 0.5 → damping ~0.13 (a perceptible glide)". This is the exact
"tight-springy by accident" risk §L4 forbids: the feel is whatever those constants happen to
land on, untied to any φ proportion or measured settle-time. There is no spec for what
damping value yields the iOS-27 felt weight. **Hardening:** define the scrub→damping map as a
named, proportion-grounded function (or a measured settle-time target in ms), not inline
magic; gate R-WEIGHT on a settle-DURATION window, not merely "keeps moving ≥3 frames" (which
a too-fast damping passes while feeling tight).

### S4 — the cascade is COMPOSITOR-spring but the pin is JS-spring: two DIFFERENT spring
### feels on the SAME page → gestalt incoherence
§1b cascade uses `springLinearStops({response:.5, dampingFraction:.85})` (a baked `linear()`
curve, ζ=0.85). §1c pin uses a `SmoothProgress` exponential damping (NOT a spring — it has no
overshoot; it is a low-pass lag). So the page mixes an OVERSHOOTING compositor spring (cascade)
with a NON-overshooting JS lag (pin reveal), then claims the pin "overshoots → settles" — but
`SmoothProgress` mathematically cannot overshoot. The spike's HUD even shows the pin
monotonically approaching (`0 → .053 → .257 → .357 → … → .429`, no overshoot past target). The
promised "anticipation dip → overshoot" is `SpringProgress` territory, but the spike's pin
uses `SmoothProgress`. **The two felt curves don't match and the headline overshoot is
absent.** **Hardening:** drive the FELT pin reveal on `SpringProgress` (which DOES overshoot)
so cascade and pin share one spring identity (ζ≈0.85), and prove the overshoot frame in
R-PIN; reserve `SmoothProgress` for the pure-lag legs (progress number, chrome collapseT).

### S5 — PRM "shows terminal phase" can DROP the user mid-narrative
§4 + §2b PRM arm: `--pin-t` becomes a hard 1:1 ratio, the pin "shows its terminal phase."
But a pinned scroll stage is a multi-PHASE narrative (reveal → settle). Under PRM a 1:1 ratio
still TRACKS scroll position (so it shows the CORRECT phase per scroll, fine) — yet the GOLDEN
prose says "the stage shows its terminal phase" (§2b) which contradicts "a scroll-progress
number still tracks" (§4). If PRM truly forces the TERMINAL phase regardless of scroll
position, the pinned content is unreadable mid-scroll. The spec is self-contradictory on
exactly the a11y path. **Hardening:** state unambiguously that under PRM `--pin-t` tracks
scroll 1:1 (correct phase per position, zero interpolation) — NOT "terminal phase" — and gate
R-PRM on a mid-scroll PRM frame showing the mid phase, not the end.

### S6 — Safari/WebKit is REASONED, never TESTED — and one real WebKit gap is unaddressed
§3 + §6 R-SAFARI assert the `--pin-t` JS path is "byte-identical" on WebKit, but no WebKit
run exists (the spike is Chrome-only via chrome-devtools-mcp; R-SAFARI is "under forced
emulation" — not a real WebKit engine). The `--pin-t` custom-prop driver is plausibly
cross-engine, BUT: the cascade leg's Safari degrade is "mount-clock cel-slam" via an
`@supports`-else — and WebKit's `view()` support has shipped buggy `animation-range`
resolution in some versions where `@supports (animation-timeline: view())` reports TRUE but
the range computes wrong, so the page takes the native path and renders BROKEN (neither the
spring scrub nor the degrade). The binary `@supports` gate cannot catch a "supported but
broken" engine. **Hardening:** run the gate on a REAL WebKit (Playwright webkit), not
emulation; for the cascade, prefer the JS floor on the FELT axis too (consistent with the
pin's "felt axes are JS on both engines" doctrine) rather than trusting WebKit's `view()`
range; capture a paired-π WebKit artefact.

### S7 — `/motion/scroll-system` + `/motion/scroll-vt` ship on `/motion-core` — the GOLDEN's
### own §2a admits threading kf physics MOVES them off `/motion-core`, an unowned break
The manifest pins `motion/scroll-vt` and `motion/scroll-system` to
`@mkbabb/glass-ui/motion-core`. §2a/§5 admit `useScrollChrome` "currently ships on engine-free
`/motion-core`; threading kf physics moves it (or a thin shim) onto `/motion`." So the spring
chrome snap either (a) breaks the `/motion-core` engine-free contract, or (b) needs a "thin
physics shim" the GOLDEN names but never specifies. The two demo pages exercising
`useScrollChrome`/`useScrollTrigger` live on `/motion-core` and would silently lose the spring
snap (degrading to the instant snap) — so the headline "liquid weight EVERYWHERE" is NOT true
on the `/motion-core` consumers. **Hardening:** specify the physics-shim seam (or decide
chrome moves to `/motion` and re-host the two demos), and state explicitly which consumers get
the spring vs the instant snap — don't claim universal liquid weight while two of three scroll
demos are on the engine-free subpath.

### S8 — overfit: the spike hardcodes `--motion-weight: 1` and an un-fallback'd cel-cast
The cel-cast translate `10px * var(--motion-weight) * (1−t) + 6px` has NO comma-fallback in
the spike, and `--motion-weight` does not exist yet (deferred to BD.W-MORPH-PUNCH-TOKENS).
The spike only "works" because it sets `--motion-weight: 1` in `:root`. In production, if the
dep wave slips, the cel-cast computes invalid and the cast VANISHES silently. §2c's recipe
uses `var(…, fallback)` but the SPIKE (the thing claimed "VERIFIED GREEN") does not — so the
green is on a hardcoded scaffold, not the real fallback path. **Hardening:** prove the spike
with the dep tokens ABSENT (fallback path live), and require comma-fallbacks on every
`--motion-weight` / `--ease-cartoon-punch` / `--shadow-cartoon*` read in the real recipe.

## VERDICT

**SURVIVES: false (as a GESTALT/design-fidelity artefact).** The motion ENGINE survives clean
— the dead-pin diagnosis, the keyframes.js synchronous-primitive pivot, the DRY union, and the
born-RED gate are real, honest, and well-grounded; I verified each live. But MY lens is the
gestalt, and on the gestalt it fails: the cartoon PUNCH, the colorful field, the defined edge,
and warm-not-gray glass are demonstrated ONLY in a throwaway spike with a HARDCODED warm
palette + INVENTED `.scroll-pin-card::after` DOM, while the SHIPPING recipe writes bare
opacity/translate/scale onto a measured NEAR-GRAY `glass-card` (`oklab .72 .005 .011`) — a
NO-GRAY violation — with a PHANTOM `--shadow-cartoon-md` token, a non-overshooting
`SmoothProgress` standing in for the promised "overshoot" (S4), and arbitrary non-φ proportions
(S2). The user feels a working-but-restrained gray pin, not the audacious 1940s-technicolor
cartoon-slam the binding law demands. Re-spec the cartoon/warm/edge layer onto the REAL
component, switch the felt pin to `SpringProgress`, fix the phantom token, and the gestalt can
match the (already-excellent) engine.
