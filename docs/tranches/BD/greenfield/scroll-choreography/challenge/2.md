## REFUTATION 1 (TOP — the one that lands) — "compositor-only" is FALSE for the headline pin; transform-on-backdrop-filter is a WebKit trap on the LOAD-BEARING surface

§3 asserts: *"every scroll-driven leg animates transform/translate/scale/opacity/... ONLY
(compositor-only, the proof:no-layout-animation floor)."* Two things are wrong:

1. **The `--pin-t` driver is NOT compositor — it is main-thread style recalc + paint every
   frame.** A JS `stage.style.setProperty("--pin-t", v)` feeds `calc()` inside the card's
   `translate`/`scale`/`opacity` AND the `::after` cel-cast's `background`/`opacity`/
   `translate`. An UNREGISTERED custom prop written from JS is string-typed and triggers a
   **style recalc on the subtree on the main thread each frame** — it is NOT the
   GPU-composited path a native `animation-timeline: scroll()` bound to a registered
   `@property --pin-t` would take. The cel-cast `::after` changing `background`+`opacity` is
   a **paint** every frame on top. Live: the pin card shows `will-change: auto`,
   `contain: content` — no layer promotion. So the golden traded a dead-but-compositor
   native timeline for a working-but-main-thread JS driver and then mislabeled the result
   "compositor-only." On a 320vh pin during a fast flick this is a per-frame recalc+paint on
   the load-bearing surface.

2. **The pin card is `glass-card` with `backdrop-filter: blur(8px) saturate(1.4)
   brightness(1.02)` — and the golden animates its transform.** VERIFIED:
   `.scroll-pin-phase-reveal` resolves `backdropFilter: "blur(8px) saturate(1.4)
   brightness(1.02)"`. The golden's headline cartoon-slam animates `translate`/`scale`/
   `opacity` on this exact element every frame. In **WebKit**, transforming a
   backdrop-filtered element forces the backdrop to RE-SAMPLE its (now transformed) backdrop
   region every frame — expensive, and a known source of the glass "swimming"/flickering
   artifact during motion. §3's "No `backdrop-filter: url()` rides a scroll axis" is true but
   a DODGE: the filter VALUE isn't animated, but the FILTERED ELEMENT'S TRANSFORM is, which
   is the actual WebKit cost. The §3 cross-engine table never addresses "transforming a glass
   surface in Safari." (The cascade entries are safer — measured `backdropFilter: none` on the
   `.scroll-cascade > *` themselves; the filter sits on inner children, not the transformed
   node. So this is specifically a PIN problem, i.e. the most important felt surface.)

**HARDENING (REQUIRED):**
- **Stop calling it "compositor-only."** Re-label the §3 carve honestly: the `--pin-t` leg
  is a *bounded main-thread recalc on a contained subtree* (one `setProperty` write +
  transform/opacity longhands on a `contain`-isolated stage), NOT a compositor animation.
  Keep the `proof:no-layout-animation` claim (translate/scale/opacity don't reflow) but drop
  "compositor."
- **Register `@property --pin-t { syntax:"<number>"; inherits:true; initial-value:0 }`** in
  the recipe so the prop is typed; it can't make a JS-written value composite, but it makes
  the calc path cheaper and lets the OPTIONAL native `scroll(nearest)` cosmetic-parallax
  sub-leg (§1c) actually animate it on the compositor where present.
- **Promote + isolate the pin stage:** the production recipe MUST set `will-change: transform`
  (added on pin-enter, removed on settle to avoid permanent layer cost) + keep `contain` on
  the stage so the per-frame recalc is bounded to the pinned subtree. The live demo's
  `will-change: auto` proves this isn't specified yet.
- **The Safari glass-swim carve:** for the pin card specifically, either (a) move the
  `backdrop-filter` to a NON-transformed wrapper and animate an inner non-filtered content
  layer (decouple the glass from the moving transform), or (b) accept the cost and gate it
  behind a `@supports` + a documented WebKit-acceptable budget. The golden must pick one; it
  currently picks neither.

## REFUTATION 2 — the `/motion-core` → `/motion` subpath migration silently DROPS liquid weight for the dock-search consumer

§2a admits threading kf physics into `useScrollChrome` *"moves it (or a thin physics shim)
onto `/motion`"* and that *"the `/motion-core` floor degrades to the existing instant snap
when the physics shim is absent."* VERIFIED the stakes: `useScrollChrome` ships on
engine-free `/motion-core` and is consumed by **`useDockSearch`**
(`src/components/custom/dock/composables/useDockSearch.ts:52,265`) — the dock-IS-the-search
component. So the consequence the golden soft-pedals:

- If `useScrollChrome` imports keyframes.js, the **dock-search bundle pulls the heavy
  animation engine** into a component-tier import deliberately kept engine-free — a real
  bundle-weight regression for every dock consumer.
- If instead the "thin physics shim degrades to instant snap on `/motion-core`," then the
  `SpringProgress` settle the golden promises for the chrome collapse (§1d, R-SNAP)
  **does NOT actually ship to the dock** — the dock keeps the instant snap. So the headline
  "liquid weight everywhere, both engines" silently EXCLUDES the dock-search collapse unless
  the consumer opts into `/motion`. That contradicts "liquid weight is the DEFAULT for every
  felt scroll axis" (§0 one-liner).

The golden names the problem but resolves it with the word "shim" and no mechanism.

**HARDENING (REQUIRED):** Specify the shim concretely. Either: (a) the `SpringProgress`
settle for chrome lives behind a `setSnapSmoother?(fn)` injection point — `/motion-core`
ships the instant-snap default, `/motion` consumers (and the demo) inject the kf spring; OR
(b) extract ONLY `springLinearStops`'s baked stop-set into `/motion-curves` (already a
subpath!) and drive the chrome snap via a CSS `transition-timing-function:
var(--scroll-snap-spring)` so NO JS engine import lands in `/motion-core` at all. Option (b)
is more KISS and keeps the dock weightless-AND-weighted. State which, and update the §3
table row "chrome collapse" to be honest that the `/motion-core` floor is instant-snap.

## REFUTATION 3 (minor) — the cascade is "cosmetic" but it is the first felt scroll surface; the Safari degrade is a real visual fork, not a non-event

§1b/§3 classify the section cascade as a native-`view()` "cosmetic, compositor, zero JS" leg
that degrades on Safari <26 to a "mount-clock cel-slam, never a flat fade." But the cascade
is the FIRST thing a user feels scrolling the page (the sections building in). The golden's
own dual-path edict says *"the JS spine is the floor for every FELT axis on both engines."*
The cascade is felt, yet it is the ONE felt-adjacent leg the golden leaves native-only with
a DIFFERENT visual on Safari <26 (scroll-scrubbed spring entrance vs a mount-clock slam). So
the edict has an asterisk the §3 table doesn't flag in the same column-language as the pin.

**HARDENING:** Either accept the cascade as genuinely cosmetic (defensible — it is an
entrance, fires once, not a continuous felt scrub) and SAY SO explicitly so the
"every felt axis has a JS floor" edict isn't self-contradicted; OR if it's felt, give it the
same `--cascade-t` JS-floor option as the pin. Recommend the former (it IS one-shot
cosmetic) — just disambiguate the language so a reader can't catch the contradiction.

## a11y / PRM — SURVIVES, one tightening

- PRM gate is real: native `scroll()`/`view()` recipes are CSS-PRM-gated already; the JS
  spine's `--scroll-scrub → 0` → `SmoothProgress.snap()` is a clean inner gate; discrete
  crossings survive (the useFadingScroll model). The vestibular floor is sound.
- **One gap:** under PRM the spike STILL attaches the scroll listener and writes raw `--pin-t`
  each tick (no smoother frames — fine). But the PRM `--pin-t` is a "hard 1:1 ratio" mapped
  straight to `opacity`/`translate`/`scale` — i.e. the pin's lift+squash still MOVES with
  scroll under PRM, just without inertia. §4 says "the pin shows its terminal phase" but the
  recipe (`translate: 0 calc((1 - t) * lift)`) tracks scroll position 1:1 → a scroll-coupled
  translate IS a vestibular trigger even without smoothing. **HARDEN:** under PRM the pin
  should SNAP to terminal at a threshold (e.g. `--t ≥ 0.5 → 1`), not track lift continuously
  with scroll. Confirm R-PRM asserts "no continuous scroll-coupled translate under reduce,"
  not merely "no smoother."
