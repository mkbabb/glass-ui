## R1 (TOP) — The keystone curve CANNOT be a `MOTION_CURVES` entry without an undisclosed engine change; the GOLDEN's "KISS / no new engine" claim is false here

The GOLDEN's single boldest move is `--ease-cartoon-punch`, and §0/§2c/§2d insist it is
"a shaped `MOTION_CURVES` entry, opt-in" — explicitly NOT a `SPRING_PRESETS` row — and §0
sells the whole amendment as "ships no new engine, KISS/DRY, no fork."

Grep-verified at HEAD (`src/composables/motion/curves.ts`):

- `MotionCurveKind = "spring" | "bezier"` (line 35) — a CLOSED two-member union.
- Every row's `js` twin is `Easing | TimingFunction`: springs are solved via
  `springLinearStops`/`springTimingFunction`; beziers via `CSSCubicBezier(...)`.
- There is NO third kind, NO hand-authored-`linear()` family, NO mechanism for a
  multi-extremum curve with a negative leg.

A cartoon-punch curve `linear(0, -0.012, -0.038 33%, … 1.22 66%, … 1)` is **neither a
spring** (it has no `(response, ζ)` derivation — its negative anticipation leg and 22%
overshoot are by construction *outside* the analytic damped-spring family; the GOLDEN
itself says so) **nor a bezier** (a `cubic-bezier()` y-output can exceed 1 but a *single*
cubic cannot express anticipate-dip → cross-1.0 → overshoot → settle; it is a 4-stop
shape, not a 16-stop polyline). To add it to `MOTION_CURVES` you MUST:

1. extend `MotionCurveKind` to a third member (`"shaped"` / `"keyframe"`),
2. add a JS-twin family that can sample a literal `linear()` polyline (there is none —
   the twins are `springTimingFunction` and `CSSCubicBezier`, both analytic),
3. teach `twinOf` / the alias resolver about it.

That is a real engine change to the canonical curve table — the exact "new engine / fork"
the GOLDEN claims it avoids. The amendment cannot simultaneously be "a MOTION_CURVES entry"
AND "ships no new engine." **This is the strongest refutation: the keystone's integration
story is internally contradictory.**

HARDENING: pick ONE and state it honestly. Either (a) `--ease-cartoon-punch` is a
**raw CSS `linear()` token in `tokens.css` with NO `MOTION_CURVES` row** (it has no JS
twin and does not need one — it is never sampled in JS, only used as a CSS animation
timing-function), and §2c/§2d/§4 drop the "MOTION_CURVES entry" framing; OR (b) the
amendment explicitly adds the third `MotionCurveKind` + a `linear()`-polyline sampler and
OWNS it as a small, scoped engine extension (still defensible, but it must be NAMED, with
its own born-RED gate row, not hidden behind "KISS"). Option (a) is the truer KISS.

## R2 — §1's own audit-correction is WRONG: the cartoon shadow tokens are NOT uniformly warm; the "no token change needed" claim is false, and a USER still sees a black-floored cartoon cast

The GOLDEN's §1 makes its entire credibility from "I cite only live grep-verified
primitives; a precept that cites a phantom is a lie." Its row 4 asserts: *"The token source
`shadow.css:92` is ALREADY `color-mix(in srgb, var(--shadow-color) 10%, transparent)`
(warm-floor compliant). Only DESIGN.md prose is stale. §2f corrects the doc, no token
change."*

Grep-verified (`src/styles/tokens/shadow.css`):

- Lines 9-10, the **PRIMARY** tokens `--shadow-cartoon` / `--shadow-cartoon-hover` (the
  ones `<Card surface="cartoon">` actually consumes — confirmed by the line-47 comment
  "`.cartoon-surface` … reads `--shadow-cartoon` directly"): these use
  `color-mix(in srgb, var(--foreground) 8%, transparent)` — **`--foreground`, not
  `--shadow-color`**. In light mode `--foreground` is a near-black ink; this is the
  classic gray/black-floor cast the BA.W-NO-GRAY edict forbids on the most-used carrier.
- Lines 88-89, raw-black primitives `--shadow-cartoon-color: rgb(0 0 0 / 0.12)` and
  `…-color-soft: rgb(0 0 0 / 0.06)` — live, raw black, still kept "for tiered cartoon
  utilities."
- Only the *tiered* `--shadow-cartoon-{sm,md,lg}` (lines 92-99) use `--shadow-color`.

So §1's "the token is already uniformly warm, only the doc lies" is itself a partial
phantom: TWO of the cartoon token families (the primary one and the color primitives) are
NOT warm-floor compliant. The GOLDEN's §2f doc-only fix leaves a user looking at a
`--foreground`-based (black-in-light-mode) cartoon cast on the canonical `<CartoonCard>`.
This is precisely the gray-glass / black-floor failure the lens hunts for, and the GOLDEN
mis-audited it as already-solved.

HARDENING: §2f must include a REAL token change (not doc-only): re-base
`--shadow-cartoon` / `--shadow-cartoon-hover` onto `--shadow-color` (the warm floor), and
either retire `--shadow-cartoon-color{,-soft}` (raw black, no warm floor) or re-mix them
through `--shadow-color`. The §1 table row 4 must be corrected to admit the primary token
is NOT compliant. Add a born-RED gate line:
`grep -q "shadow-cartoon:.*var(--foreground)" src/styles/tokens/shadow.css && echo RED`.

## R4 — The cartoon-punch curve's SETTLE TAIL re-introduces the very "tight/springy" multi-crossing the liquid-weight edict forbids

The edict: motion must carry weight/inertia/bounce — but "NEVER tight/springy," and the
live spring fence kills overshoot >10% as "the too-springy defect." The cartoon curve is
*allowed* its loud 22% punch (it is a register, opt-in) — fine. But inspect the TAIL:
`… 1.22, 1.18, 1.09, 1.02, 0.985, 0.98, 0.99, 0.997, 1`. After the peak it crosses 1.0,
**undershoots to 0.98** (a 2% reversal *past* rest the other way), then climbs back. That
is a SECOND zero-crossing — a settle wobble. On the spike's 90px travel that is the card
springing ~1.8px past rest and back. A reviewer reading the gestalt sees a faint
double-bounce — the "pointed/springy settle" texture the house explicitly retired from the
bouncy/dock presets (springPresets.ts: "the OLD pointed bouncy 12.6% / dock 10.7% are
RETIRED"). The GOLDEN green-lights a curve whose tail has the exact micro-texture the
precept body forbids, with no acknowledgement.

HARDENING: either justify the 0.98 undershoot as deliberate cartoon "rubber" (and SAY so,
distinguishing register-rubber from defect-springiness with a stated criterion), or flatten
the tail to a monotone settle (`… 1.09, 1.03, 1.008, 1.001, 1` — overshoot-then-approach,
no reversal). The born-RED live-π should assert tail monotonicity-after-peak unless the
register explicitly opts into rubber.

## R5 — `--motion-weight` co-scaling cartoon-shadow TRAVEL collides with §L7's paint-cost fence; the integration is under-specified and risks a bolt-on

§2e says `--motion-weight` "co-scales the squash depth, the overshoot share, the
anticipation pull-back, AND the cartoon-shadow travel together." §2f says the cartoon cast
travels via "a `transform` on a `::after` shadow-caster layer — never an animated
`box-shadow`." Good intent. BUT: the live cartoon shadow is a **multi-offset `box-shadow`**
(`--shadow-cartoon-md` = three layered `box-shadow` offsets). To make it "travel" on
`transform` you need a NEW `::after` caster element painting those three offsets, then
transforming it — a structural addition to every surface entering the register. The GOLDEN
asserts the mechanism in one sentence but ships NO substrate for it (no `.glass-cartoon`
caster layer exists; `grep` shows only `box-shadow: var(--shadow-cartoon-md)` static uses).
So the "moving cast" is the one genuinely-new mechanism in the amendment, it is NOT a reuse
of an extant primitive, and it is hand-waved. That is the bolt-on risk the lens exists to
catch: a precept that *names* a mechanism with no live substrate is the same phantom §1
condemns (cf. the deleted §L4 "weak tier" which at least pointed at real composables).

HARDENING: either (a) cite a REAL extant caster (does `useLiquidPress`/`useLiquidFlex`
already provide a transformable shadow layer? — it does not, per grep), or (b) admit the
moving-cast caster is a SMALL new primitive the encoding wave must build, name it, and give
it a born-RED gate + a §L7 arm — do not present it as already-integrable. Until then the
"moving cast" is aspiration, not substrate, and §2f over-claims exactly as the old §L4 did.

## R6 — §L6 proportion is asserted as law but the live radius ladder is NOT on √φ; the "values mostly already on it" claim is generous to the point of misleading

"non-golden proportion dressed as golden" failure.

HARDENING: be honest about the tension — either (a) ACTUALLY move the radii onto the √φ
ladder (a real, justified visual break; "NO LEGACY" the GOLDEN preaches), accepting the
