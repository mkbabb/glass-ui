# CHALLENGER #1 — CORRECTNESS / DEFT-INTEGRATION / KISS

**Verdict: SURVIVES (wounded).** The *visual outcome* of the golden holds — the warm-cel
field paints vivid+warm on real pixels — but the golden's **evidence apparatus is fraudulent**
and two **structural integration claims are false on the live tree**. The idea is fit; the
GOLDEN's stated numbers and its "ADOPT verbatim" foundation are not. Hardenings below convert
it from a survives-on-luck to a survives-on-truth.

---

## What I live-tested (Chrome, dev server up, both the spike and the real route)

### A. The spike's own readout, RE-RUN right now in Chrome — CONTRADICTS the GOLDEN

`golden/spike.html`, `--field-h:62` (the substrates/foundations hue), light, vivid rung. The
spike's **own panel prints**:

```
field meanC: 0.1164  (floor 0.045)  PASS ✓
field maxC:  0.1482
field meanH: 265.3  ⚠ TEAL
VERDICT:     RED — pale or cool
```

Three falsifications in one screen (artefact: `challenge/spike-reran-teal-RED.png`):

1. **`meanC 0.116`** — the GOLDEN §2d "binding numbers" say forms 0.066 / substrates 0.073 /
   data 0.081. The spike reports **0.116**. The two do not agree. §0 cites yet a THIRD value
   (the flat-page C 0.0029). **None of the three number-sets are mutually reproducible.**
2. **`meanH 265.3 ⚠ TEAL`** — the GOLDEN's #1 selling point is "zero teal, warm by type
   invariant." Its own spike computes the MEAN HUE as **265° (blue/navy)** and flags TEAL.
3. **`VERDICT: RED`** — the spike's own pass/fail line says **RED**, because its teal guard
   fires. The GOLDEN's headline ("De-risked LIVE in Chrome … clears the floor on every route
   both modes … zero teal") is refuted by re-running the exact artefact it cites.

**Root cause** (introspected live): the spike's `sampleField()` resolves each oklch stop through
a `probe.style.color` → `getComputedStyle(probe).color` round-trip and feeds the result to its
own `rgbToOklab`. That path mis-resolves: an authored `oklch(0.87 0.155 62)` (amber) comes back
through the probe and computes to **OKLab H 265°** in the spike's math. So the spike is NOT
measuring painted pixels at all — it is averaging **stop-core chroma of a corrupted resolution**,
inflating C (stop-core, not area-weighted) AND inventing a teal mean hue. **The "canvas-raster
readout" / "measured on real painted pixels" claim in the GOLDEN header is FALSE — there is no
raster in the spike; `sampleField` is a regex over `backgroundImage` string + a broken probe.**

## REFUTATION 1 (deft-integration / FORK) — "ADOPT `.paper-field` verbatim" adopts a primitive that DOES NOT EXIST in `src/`

The GOLDEN's spine (§1, §3, §7) is: *"It is the existing `@utility paper-field` — adopted
verbatim, then hardened."* Live grep of the whole repo:

- `grep paper-field src/ demo/` → **ZERO**. `src/styles/paper.css` defines `paper-underpaint`
  and `paper-grain-overlay` only. **`paper-field` is nowhere in the shipped tree.**
- `--glass-key` → **unset live, defined in no `src/` CSS.**
- `--ease-cartoon-punch` → **unset live.**

`paper-field` and `--glass-key` exist ONLY as proposals in the **sibling, also-unbuilt**
`glass-material/GOLDEN.md`. So this golden is **not a union onto a robust extant ecosystem** — it
is a **co-dependency on a second unbuilt golden**. "ADOPT + harden chroma" presumes a thing to
harden. If glass-material does not land first (or lands with different stop values), this golden's
"AUGMENT" is actually a **net-new primitive** wearing union language — exactly the bolt-on the
brief forbids, mislabeled. The "net-new artefacts are exactly THREE" accounting is false: it omits
`paper-field` itself, `--glass-key`, and the dark-arm — because it charges them to a sibling that
hasn't shipped.

**Hardening:** state the **hard ordering dependency explicitly** — `W-PAGE-FIELD` is BLOCKED on
glass-material `BD.W-GLASS-FIELD` minting `@utility paper-field` + `--glass-key` in `src/`. EITHER
(a) sequence the waves and say so in §7's gate table, OR (b) absorb the base `paper-field` +
`--glass-key` mint INTO this golden's W-PAGE-FIELD and drop the "adopt verbatim / byte-untouched"
framing (it's a co-mint, not an adopt). Re-count net-new artefacts honestly: 6, not 3.

## REFUTATION 3 (precept / cel-coherence) — G7 cannot pass; `--glass-key` is unset, so "ONE shared light" is a fallback constant, not a union

G7 ("cel-coherence: the over-glaze lit corner exceeds the opposite by ΔL keyed off `--glass-key`;

shared light** — it's a coincidence waiting to drift. The cel-coherence precept is asserted, not

**Hardening:** make G7 a **blocked gate** explicitly gated on glass-material landing `--glass-key`
as a real `src/` token that BOTH the field over-glaze AND the glass rim/cast read. Forbid the
`-58deg` literal fallback in the shipped CSS (a missing shared token must FAIL the cel-coherence
gate, not silently paper over it with a magic number that can diverge).

## REFUTATION 4 (KISS/DRY + Safari) — sRGB-interp of oklch stops will mud the warm field WebKit-side; the @supports fallback is a second muddier path (a fork by another name)

§4 authors stops in oklch but interpolates in **default sRGB** ("no `in oklab` hint WebKit handles
differently"). Interpolating high-chroma warm oklch stops THROUGH sRGB toward `transparent` is
exactly the path that produces the gray-mud midtones the no-gray precept forbids — and it gamut-maps
differently per engine, so the "byte-comparable Chrome↔Safari" claim is unproven (the spike was
NEVER run in Safari; §4 admits this is still TODO). Plus the `@supports not (oklch)` arm is a
**second hand-authored hsl triad** — a parallel color path = a fork, however small, that must be
kept in lockstep with the oklch primary. That violates the one-color-script DRY claim.

**Hardening:** (a) test `in oklab` vs default-sRGB interp on the real raster in BOTH engines and
pick the one with no gray midtone — do not assert; measure. (b) The fade-to-`transparent` stops
should fade to a warm low-chroma color at the same hue (not `transparent`/`rgba(0,0,0,0)`), so the
midtone interpolant never crosses gray. (c) Drop the bespoke hsl `@supports` triad in favor of a
single low-chroma warm solid floor when oklch is absent (oklch is Safari 15.4+/Chrome 111+, the
floor is universal) — kill the second color path.

## REFUTATION 5 (mount correctness) — the `palette` prop composes `paper-field` on the element that already carries `bg-background`; the solid bg will sit OVER the field, or the grain blend will fight it

`AppShell.vue:251` is `<PaperBackdrop class="fixed inset-0 -z-10 bg-background" />`. The golden
"composes `.paper-field` on the SAME fixed element" and "the grain rides on top." But that element
ALSO carries `bg-background` (= `--neutral-0`, opaque) AND PaperBackdrop's own grain `::after` with
`mix-blend-mode: multiply` (light). Stacking a multiply grain over the warm mesh DARKENS the warm
stops unpredictably; and `bg-background` opaque on the host can occlude the field `background`
layers depending on which wins. This is asserted to "just compose" but is not live-verified — the
real composite (field + opaque bg-background + multiply grain) was never measured on the route.

**Hardening:** live-verify the THREE-layer host composite on `/forms/select` after mount (field
stops + bg-background + multiply grain) and confirm raster meanC ≥ 0.045 survives the grain
multiply — OR move `bg-background` off the host so the `--neutral-0` L0 lives only inside the
`paper-field` stack (as the spike does), and let the grain ride a separate sibling. Don't assert
the compose; measure it post-mount.
