## 1. TOP REFUTATION — Move 4a "aurora ground" is sold as the splice idiom; it is NOT, and the §3 default silently degrades to the CPU data-URI quad

This is the single landing refutation. The BINDING LAW §3 demands **a COLORFUL FIELD behind glass**;
the golden leads §3 ("THE BOLDEST MOVE" is Move 2, but the *material* §3 claim is Move 4a). The golden
asserts Move 4a is "a SPLICE+compose, the SAME idiom the hybrid already uses to splice the goo-blob
field … the Aurora uniforms ride a THIRD binding; the field (binding0) + dot (binding1) structs stay
byte-identical." **This conflates two utterly different operations:**

- **What the hybrid actually does** (verified `goo-dot.wgsl.ts:33-37`, `goo-dot.frag.ts:23-27`): it
  `String.indexOf`-slices the goo-blob field's *helper functions* (sceneDistG/breath/samplePaletteOklch)
  and concatenates them as text into the SAME single program, sharing the SAME binding0 struct. ONE
  pipeline, ONE program, ONE draw (`gooDotSetup.ts:90-116` builds exactly one `createRenderPipeline`;
  `useGooDotMatrix.ts:280-283` issues exactly one `pass.draw(3,1,0,0)`).
- **What Aurora actually is** (verified `aurora.frag.ts`): a heavyweight oil-paint engine —
  `uPalette[8]`, SIX parallel `uNuclei*[6]` arrays (pos/radius/paletteBias/valueBias/driftRadius/
  driftPhase/elong/angle), warp uniforms, FOUR peer mediums (pastel/watercolor/oil/crayon), a curved
  swept-brushstroke SDF, a van-Gogh dab body, ACES tonemap, its OWN hash/fbm loop. Its WGSL is
  assembled from ~10 partials. This is **not a helper-function splice** — composing it is a SECOND
  full render pipeline with a SECOND, large, structurally-different uniform set.

The architectural cost the golden hides:
1. The bind-group layout (`gooDotSetup.ts:75-89`) is **fixed at 2 entries**. A "third binding" needs a
   re-authored BGL, a re-authored pipeline layout, and — because Aurora and the dot-stamp are different
   *programs*, not one shader with three bindings — really a **second pipeline + second draw**, not a
   third binding on the one pipeline. The "byte-identical binding0/binding1" reassurance is true but
   irrelevant: the problem is a whole new pipeline alongside, not a struct extension.
2. The WebGL2 twin needs a **second linked program** (`createGooDotGLResources` builds exactly one
   `linkProgram`); two programs in one context means a program-switch + a state-shuffle every frame, on
   the very tail (`goo-dot.frag.ts` header: "the genuinely-absent ~5-10% tail path") that is **the Safari
   surface** per §7. The golden names Safari as "the LEAD, not an afterthought" yet routes its boldest
   §3 move through the path with the least headroom.
3. The golden's own escape hatch is `auroraFallbackGround` — but that is **NOT a GL pass**: verified
   `auroraFallbackGround.ts:241,288` it bakes a CPU nuclei field to a **`data:` URI and CSS-upscales
   it** (a static `<img>`/background, never a draw call). So the "degrade to the static mesh" branch is
   not a cheaper *pass* — it is a **different rendering mechanism entirely** (DOM background image vs GL
   draw). Under any budget pressure the §3 "living warm aurora" silently collapses to a **static
   bilinear-upscaled JPEG-grade gradient behind the dots**. That is a colorful ground, yes — but it is
   *not living*, and the golden's prose ("a breathing amber→coral aurora", "the dots read as a hot
   halftone over a breathing aurora") oversells what the realistic budget delivers on the majority
   surface. The §3 demand ("a COLORFUL FIELD behind glass + a defined edge") is *met* by the fallback;
   the §3 *gestalt* ("living/breathing") is NOT, and the golden does not own that gap.

**Why it still SURVIVES (not REFUTED):** the §3 bar is "a colorful field behind glass + a defined
edge" — and even the honest fallback (CPU nuclei data-URI) CLEARS that literal bar in both modes. The
move is under-scoped, not impossible. But the golden must stop calling it "the same splice idiom" and
must own the two-pipeline cost + the living-vs-static degrade honestly, or the build agent will discover
mid-wave that "compose Aurora" is a multi-day pipeline graft, not a 3-line concat — and quietly ship the
data-URI as if it were the live aurora.

### Hardening (Move 4a)
- **Re-language**: Move 4a is a **SECOND render pass / pipeline** (WGPU: a second `createRenderPipeline`
  with Aurora's own BGL + module, drawn first with `loadOp:"clear"`, then the dot pipeline with
  `loadOp:"load"`; WebGL2: a second linked program, drawn first, then a program-switch to the dot
  program over `gl.blendFunc(ONE, ONE_MINUS_SRC_ALPHA)`). Drop "third binding / byte-identical structs"
  framing — it is misleading. State the real cost: +1 pipeline, +1 program, +1 draw, +1 BGL.
- **Pick the cheap Aurora variant explicitly**: do NOT compose the full oil/van-Gogh/brush stack for a
  *backdrop*. Splice ONLY the Aurora **nuclei-softmax base color** stage (composition.glsl LUT + the
  Gaussian nuclei) with `uMedium=0` / no brush / no tonemap-heavy path — a genuinely cheap warm field.
  Name this the "aurora-base" reduced shader so the budget claim is real.
- **Own the degrade honestly in §4a + §7**: under the WebGL2 budget tail the ground is the **static
  `auroraFallbackGround` data-URI (NOT a live pass)** — colorful + warm + edged, but *not breathing*.
  The §3 gate (G3) must accept BOTH (live C-variance ≥ 0.05 OR static C-variance ≥ 0.05); the "living"
  claim is a Chrome/WGPU-only enhancement, not a universal promise.

## 2. SECOND REFUTATION — G3's "colorful ground" clause is born-GREEN on the FALLBACK, so the gate does not actually force the bold §3 move

The §3 boldness is the *living* aurora. But G3 reads only "the ground behind the dots has C-variance
≥ 0.05 (a colorful, non-flat field)." The **static data-URI fallback already paints C-variance ≥ 0.05**
(it is a baked nuclei field with real chroma). So an agent can satisfy G3 with the cheap static quad and
NEVER build the live aurora pass — the gate is not born-RED on the boldest §3 mechanism, only on
flat-cream. The golden's self-test bite ("a cream-on-cream ground REDS G3") confirms the gate only
catches the *absence* of color, not the *deadness* of it. A genuine §3 gate must witness **temporal
variance** (the ground's chroma field measurably drifts frame-to-frame on WGPU) as a *separate, additive*
clause from the static C-variance clause — else "living" is unenforced prose.

### Hardening (G3 / §8)
- Split G3 into **G3a (vivid dots: ΔL≥0.18, C_core≥0.13)** + **G3b (colorful ground: static C-variance
  ≥0.05, both modes)** + **G3c (LIVING ground, WGPU-only: the ground's mean chroma centroid drifts ≥ε
  over N frames)**. G3c is the only clause that forces the live aurora; mark it WGPU-conditional so the
  Safari/WebGL2 tail passes on G3b alone (honest about the degrade). Self-test bite: a static-only ground
  REDS G3c on WGPU.

## 3. THIRD REFUTATION — Move 2 (neck-ridge) born-RED gate G2 is mechanically sound BUT the spike's `*4.0` swell magnitude is a magic overfit, and the ridge can read as a hard ON/OFF artifact in a 10px grid

Verified the spike (`golden/spike.html:111`): `dotR = baseR * (1.0 + uWeldSwell*weld*4.0)`. The
production prose (GOLDEN §2 Move 2) writes `(1.0 + uWeldSwell * weld)` with **no `*4.0`**. So the spike
that "de-risks the boldest mechanism" only reads convincingly because of an UNDOCUMENTED 4× multiplier
the production spec drops. With `weldSwell=0.18` the spec gives a 1.18× swell (the prose's stated number);
the spike actually runs 1.72× (0.18*4). The visible neck-ridge in the spike is therefore **not evidence
for the documented production constant** — it is evidence for a different, larger, un-specced one. Either
the prose is wrong (the real swell needs ~1.7×, which then risks dots overflowing the cell pitch and
kissing prematurely → the halftone mushes) or the spike is dishonest about what it proved. This is exactly
the "magic constant smuggled in the de-risk" trap.

Second sub-issue: at `dotPixelSize:10` and `dotMax:0.42` the core dots are already ~4.2px radius; a 1.7×
weld swell pushes the weld dots to ~7px in a 10px cell → they **clip the cell and read as squares /
overlap neighbors**, which in a 10px grid looks like a hard ON/OFF band, not a "ridge of molten dots."
The neck-ridge legibility depends on a pitch/swell ratio the golden never pins to the √φ ladder it
claims governs "all things" (§4).

### Hardening (Move 2 / §2 / §4)
- **Reconcile the constant**: state the ACTUAL `weldSwell` the spike validated (and the `*N` factor) in
  the prose, and pin it so `dotMax*(1+weldSwell*N)*cellHalf < cellHalf` (the weld dot must not exceed the
  cell radius — a √φ-derived ceiling, not a free knob). Add a born-RED self-test: a weld dot radius >
  cellHalf REDS G2 (clipped-square artifact), forcing the ridge to read as *fat round dots*, not squares.
- G2 already witnesses CC-count 2→1→2 + "neck band carries the LARGEST dots" — ADD "and those dots are
  still sub-cell circles (radius < cellHalf)" so the ridge is a swell, not a clip.

## 4. FOURTH REFUTATION — the cartoon shadow (Move 3) is a velocity-coupled offset that the spike admits is a "stub"; on a transparent-ground library default it has NOTHING to cast onto

`spike.html:128`: `vec2 shOff = vec2(1.0,1.6) * (1.0 + uFlowAmt*2.0); // offset (velocity-coupled stub)`
— the comment literally says **stub**. The shadow is a darker disc (`vec3(0.10,0.06,0.03)`) composited
UNDER each dot. Two design-fidelity problems:
1. On the **library default (`background:"transparent"`)**, the dots float over a consumer host. A dark
   premultiplied shadow disc under each dot will paint **dark halos onto a light host** — the 1940s
   cartoon shadow is a *grounding* device that assumes an opaque ground beneath. Over transparent, it is
   muddy fringing, not weight. The golden's cartoon-shadow move is coupled to the aurora-ground move (it
   only reads as weight WITH the ground) but the spec ships them as independent config flags
   (`fieldGround` defaults transparent, but the shadow is unconditional in the read-out). The shadow must
   be **gated on an opaque ground present**, or it degrades the transparent-host default.
2. The "velocity-coupled" offset is `uFlowAmt`-driven, but `uFlowAmt` is a **static config scalar**, not a
   per-frame velocity. The spike couples the shadow length to a CONSTANT, so the "longer shadow as the
   field lunges = the inertia tell" (GOLDEN §3, §5) **does not actually happen** — there is no velocity
   term wired. The cartoon-punch inertia tell is prose, not mechanism, in both the spike and the spec.

### Hardening (Move 3 / §5)
- Gate the cartoon shadow on `fieldGround != "transparent"` (it needs a ground to cast onto); on the
  transparent library default, drop the dark disc and use a lighter specular-only lift (no dark halo on a
  light host).
- Wire the shadow offset to the ACTUAL per-frame pointer velocity / `uBloom` one-shot (the
  `usePointerVelocityField.burst` already in `resolveFrame`, `useGooDotMatrix.ts:191`), NOT to the static
  `uFlowAmt`. Add to G4: the shadow-offset length measurably changes between a still frame and a
  fast-drag frame (else "velocity-coupled" is unenforced).

## 5. FIFTH REFUTATION (minor) — PRM "frozen mid-merge, FILLED + legible" is asserted but the held frame's merge phase is undefined; could freeze on a non-merging beat = no neck-ridge witness in the static frame

§5 + §7 promise PRM paints "ONE static composite (aurora + dots frozen mid-merge, the field FILLED +
legible)". But `tick(0)` freezes at t=0; the satellite-merge phase at t=0 is whatever the field's resting
geometry happens to be. There is no guarantee t=0 is a *mid-merge* beat — it may be the fully-separated or
fully-fused beat, in which case the held PRM frame shows the FILLED field (good, Move 1 delivers that) but
**no visible neck-ridge** (the §3-of-this-viz climax). The golden says "frozen mid-merge" as if the phase
is chosen; nothing chooses it. A PRM user then never sees the boldest mechanism.

### Hardening (PRM / §5)
- The PRM static composite must seed the field at a **deliberate mid-merge phase** (a fixed merge-phase
  constant, not t=0) so the held frame shows the neck-ridge weld — the one frame a reduced-motion user
  gets should showcase the climax, not a random beat. Add to G5/PRM: the held PRM frame's CC-count is 1
  (mid-merge) with the neck band present.
