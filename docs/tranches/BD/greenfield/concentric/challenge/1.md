**Every metric is the EXACT INVERSE of what GOLDEN.md claims.** The image panels DO show vivid warm

`getContext('webgl2')` call inside `probe()` (spike.html:142-144) on canvases whose drawing buffer was
already presented; the readback is black. So:

- The "PIXEL-PROVEN" / "de-risked" / "the boldest mechanism is PIXEL-PROVEN in a live spike" claim

- Worse: §5's binding-π floors are anchored to these phantom numbers — "spike: 0.49/0.42 chroma"
  (line 261), "spike: 1.000 warm" (262), "spike: lumVar 0.10/0.13 > 0.02" (265). Those parentheticals

- This violates the [live-verify-capture] lesson the GOLDEN itself invokes (line 271): a "live-verified"

This does NOT refute the design — the screenshot proves the composite reads vivid in both modes. It
refutes the GOLDEN's *evidence chain*. Default-to-refuted lands on the proof, not the idea.

**Hardening:** Re-run the spike with the probe reading a context created with

## R2 — "NO struct resize / zero new fork" cannot hold 10 tunables in 4 spare float lanes (KISS/DEFT)

GOLDEN §0 (line 36), §2, and §4 (line 196) repeat the spine: *"The GOLDEN tunables ride [u0.w, norm.zw,
line.w] — NO new bind group, NO struct resize... zero new fork. KISS/DRY."* I counted the real spare
lanes in `uniformBridgeWGPU.ts` + `concentric.wgsl.ts`:

- `u0.w` → 1 spare float
- `norm.z`, `norm.w` → 2 spare floats
- `line.w` → 1 spare float
- (`ints` has 3 `_pad` lanes but they are i32; the GOLDEN tunables are floats — not usable without a
  reinterpret the GOLDEN never specifies)

**Total = 4 spare float lanes.** The GOLDEN's §4 table (line 195) and §2 shader demand:
`toneGain`(1) + `shadeAmp`(1) + `lightDir`(**2**) + `indexEvery`(1) + `indexMul`(1) + `inkDarken`(1) +
`castLen`(1) + `velocityHeave`(1) + a `uMode` lane (1, required by §2 line 113 + §4 line 196) = **10
float lanes.** Ten into four does not fit. The GOLDEN MUST add at least one new `vec4` (e.g. a `tune`
+ a `tune2`/`mode` row) — i.e. a **struct resize**, the exact thing it says it does not do. The
"zero new fork / NO struct resize" selling point is therefore false, and it's load-bearing: it's the
headline of the one-line essence (line 12: "zero new fork") and the §4 KISS claim.

Note: a struct resize here is *trivially safe* — `uniformBridgeWGPU.ts` is explicitly the single-source
layout table (its docstring: "a std140-vs-WGSL alignment mismatch is structurally impossible"). So the
fix is cheap. The refutation is that the GOLDEN MISDESCRIBES its own delta as "no resize" when it
provably needs one — an honesty/KISS-accounting defect, not an architectural impossibility.

**Hardening:** Replace the "NO struct resize, NO new bind group" language with the truth: "adds ONE
`tune: vec4<f32>` (toneGain, shadeAmp, indexMul, inkDarken) + folds `lightDir`+`indexEvery`+`mode`
into the surviving `norm.zw`/`line.w`/`u0.w` spare lanes; the bind group is unchanged, the struct grows
by 16 bytes via the single-source layout table — no new bind GROUP, but a +16B struct GROW." Do the
honest byte arithmetic in §4 and bump `CONCENTRIC_UNIFORM_BYTES`. `velocityHeave` need NOT be a uniform
at all (scale `cursorWell` JS-side in `packConcentricUniforms` before the write) — that one IS free, so
claim it correctly: 9 uniform scalars, not 10.

## R3 — the born-RED claim is TRUE, but the gate exits 0 (machinery defect inherited)

I ran `node scripts/proof-concentric.mjs`: it prints **`proof:concentric — RED`** with 30+ failing
clauses (missing `ringField.ts`, `sampleRingField`, `axisRatio`, `ellipsoidalGradMag`, …) — so the
GOLDEN's "FULLY RED against HEAD" claim (line 47) and the §5 rewrite necessity are CORRECT and verified.
The current gate guards the *retired* ring surface; the rewrite is genuinely needed.

BUT: the process **exited 0** despite printing RED. A gate that prints RED but returns success is a
silent-pass hazard — if CI keys on exit code, this gate is effectively a no-op today and the GOLDEN's
§5 rewrite inherits the same harness if it doesn't fix the exit path.

**Hardening:** §5 must add an explicit assertion that the rewritten gate `process.exit(1)` on any RED
clause (and a self-test that the born-RED HEAD run actually returns non-zero). Otherwise "born-RED →
GREEN" is unobservable in CI.

## R4 — the §5 gate has no clause that the new "phantom-number" trap can't recur

§5's binding-π (clauses 1-8) asserts painted-pixel floors — good, it's readback not name-presence. But
it imports the SAME spike-probe pattern that just produced all-zeros. Clause 1 ("avgChroma > 0.06,
grayFrac < 0.15") will FALSE-PASS-or-FALSE-FAIL identically if the Playwright readback races the paint
or samples the letterbox, exactly as the spike did.

**Hardening:** the §5 π must (a) `await` a real painted frame (poll until `nonzeroFrac > 0.9` before
asserting), and (b) sample only the canvas interior (inset by the border-radius). Add an explicit
"non-cleared-buffer" precondition clause: assert `nonzeroFrac > 0.9` FIRST, so a black readback FAILS
loudly instead of silently passing grayFrac (a cleared buffer reads grayFrac→ either 1.0 or 0.0
depending on the bg, an ambiguous signal). This is the concrete fix for the R1 disease at the gate.

## Smaller refutations (hardenings, non-fatal)

- **R6 — KISS overreach on the cel-cast hook.** §1 line 77 ships a `castLen` *lane* (default ~0) "so
  the wave can dial it in." Shipping a dead uniform lane that does nothing is the opposite of KISS — it
  burns one of the 4 scarce spare floats (worsening R2) for a feature explicitly DEFERRED. Cut the
  `castLen` lane entirely; add it WHEN the index hierarchy is proven, not as dead weight. (No-legacy /
  no-dead-hooks discipline.)
- **R7 — Aristotelian-proportion claim is decorative, not load-bearing.** §3.5 reverse-justifies
  existing constants (13 levels, 5-index, 1.06 overshoot, 0.62≈1/φ) as golden-ratio. 5/13 are not
  Fibonacci-*adjacent* in the φ sense that matters (5/8 or 8/13 would be); 5/13 ≈ 0.385, not 1/φ≈0.618.
  The proportion narrative is post-hoc. Non-fatal (it's framing), but don't dress arbitrary constants
  as √φ — either set indexEvery=8 over 13 levels (8/13≈0.615≈1/φ, genuinely golden) or drop the claim.
- **R8 — `levelField.ts` REFINE risks numeric-parity drift.** §4 extends the JS oracle with `tanh` tone
  + ∇H finite-diff "so the JS twin matches." But the hillshade re-samples `sampleHeight` at ±e in the
  shader; if the JS oracle's `e` or finite-diff order differs by one ULP-path from the WGSL/GLSL, L6's
  ΔE≈0 parity reds in ONE backend (the live-π oklab false-FAIL class). Pin `e=0.012` as a SHARED
  constant in `levelField.ts` consumed by all three, not re-typed per shader.
- **R9 — `uMode` per-mode arm duplicates a color seam.** §2 step 5 branches fill/ink by `uMode`, but
  the palette is ALREADY themed per-mode by the consumer (presets-in-consumers). Two per-mode color
  paths (the uniform-fed palette AND the in-shader `uMode` darken/lighten branch) is a DRY violation
  and a second color seam — exactly what L4 forbids ("no second palette/color seam reds"). Resolve the
  per-mode arm entirely in the CONSUMED palette stops + background token, keep ONE color path in the
  shader. The shader should not know "light vs dark"; it should sample the palette it's given.
