## R1 — LANDED (the strongest). The cited spike DISPROVES the §6.2/§1c "settles plump" claim

The golden §7 says the spike "de-risked the boldest move (ratio-free size + orthogonal
squish)". I ran the spike's OWN `__runGate()` live (chrome-devtools-mcp, file://, the
shipped `morph-spike.html`) — it returns, by default (`--motion-weight: 1`, squish on):

```
{ widthMonotonic:false, maxBackstep:9.98, widthBounded:false, maxWidth:320.05,
  cxPinned:true, cxExcursion:0, first:60, last:310.88, expanded:268 }
```

Two facts the golden never states:
1. **`last: 310.88` — the dock SETTLES at 310px, not at the expanded 268px.** I held
   `--dock-t=1` for 1500ms and re-measured: still **310.88px**, with `--dock-squish` pinned
   at **1**. The squish channel is driven by `set(o)` to the SAME 0/1 target as `--dock-t`,
   so at rest-open `--dock-squish` is latched at 1 and the `--s = 1 + 0.16·squish·weight`
   factor leaves the pill **permanently 16% too wide**. Nothing in the spike drives squish
   back to 0 after the overshoot. The golden's prose ("overshoots past full then settles",
   "settles to exactly `expanded`") describes a curve the spike does not produce.
2. The §6.2 gate (`dock-morph-squish-present`) asserts `max(width) > expanded` DURING travel
   THEN "settles to exactly `expanded`". The shipped spike fails the second clause. The
   golden's escape hatch — "measure the SIZE channel with `--motion-weight: 0`" (§6.1) —
   only rescues the BORING claim (the linear blend, which I confirmed GREEN:
   `monotone true · maxBackstep 0 · maxWidth 268 · last 268`). Nobody disputes the blend.
   The CONTESTED claim is the audacious settling punch, and that is exactly the run the
   spike gets wrong.

Why it matters cross-engine: a squish that latches at +16% is a **paint that never returns
to the reserved footprint**. On Safari the residual `scale` keeps the dock on a promoted
compositor layer at the inflated size indefinitely (no settle → no `will-change` teardown),
and the `1/--s` cross-axis pinch latches too — the pill rests visibly thin-and-wide, the
opposite of "plump". This is not a measurement subtlety; it is a real mechanism gap in the
de-risking artefact.

**HARDENING (R1):** the punch curve must be driven on a channel whose REST value is 0 while
the OPEN STATE is 1 on a DIFFERENT scalar. Concretely: `--dock-squish` must be the spring's
*velocity/derivative* (|Δt| per frame), NOT a 0→1 step that co-targets with `--dock-t` — i.e.
the EXACT shipped `useDockOrientationMorph` contract ("the squish is the scalar's DERIVATIVE,
not a wall-clock", `useDockOrientationMorph.ts:131`), which the golden claims to KEEP but the
spike contradicts. The spike must be re-cut so `--dock-squish` returns to 0 at settle and the
§6.2 "settles to exactly expanded" clause actually passes live before any src/ line is
written. Until then, §7 "de-risked" is overstated and §6.2 is unproven.

## R2 — SURVIVES with a fix: the 16% squish OVERFLOWS the shipped `--dock-morph-max-stretch` cap

The golden §1c says the punch "rides the EXISTING `--stretch` machinery in shape.css … which
the dock already imports", and the spike hardcodes `--s = 1 + 0.16·squish` (a 16% swell).
But the shipped dock CAPS `--stretch` at `--dock-morph-max-stretch` = **1.14** (density.css:69,
read live) — and the orientation-morph composable defaults it even lower to **1.08**
(`useDockOrientationMorph.ts:99,104`). A 16% (1.16) squish driven through the existing
`--stretch` path is CLAMPED to 1.14/1.08 by `useLiquidFlex`. So either:
- the punch rides the real `--stretch` and is silently capped to ~8–14% (contradicting the
  spike's 16% "proven" overshoot — the §7 number is unreachable through the KEPT machinery), OR
- the golden introduces a SECOND, uncapped squish multiplier (the spike's raw `--s`),
  which is a NEW forked deformation path — violating its own "ONE squish source, no forked
  deformation math" KEEP claim (`useDockOrientationMorph.ts:111`, `shape.css:127`).

This is a DRY/KISS contradiction the golden does not resolve: it cannot both "reuse the
existing capped `--stretch`" AND ship the spike's uncapped 16% overshoot.

**HARDENING (R2):** pick ONE. Either (a) raise `--dock-morph-max-stretch` for the
collapse/expand morph scope to the cartoon register (e.g. 1.16) and route the punch through
the EXISTING `useLiquidFlex` `--stretch` writer (true reuse, cap honored, one source), and
state the cap value in §1c/§5; or (b) explicitly declare the punch a distinct `--dock-squish`
factor and DELETE the "rides the existing `--stretch`" claim — but then §3's "the punch
channel ALREADY exists" KEEP line is wrong. Resolve before build; the current text reads as
reuse but the spike behaves as a fork.

## R4 — SURVIVES: cross-engine `@property` PRM-zero is sound, but the §L7 url() interaction is unaudited

The golden §4 is strong on the headline WebKit trap: NO `backdrop-filter:url`, the goo is
`filter:url()` on a static sRGB graph — I confirmed src ships exactly that (`fission-bridge.css`,
`DockGooFilter.vue`, `useDockFission.ts` all present; the only `backdrop-filter:url` in src is
`glass-refract.css`, correctly gated behind `@supports (backdrop-filter: url(#…))` and
Chromium-only by design). So far compliant.

BUT: the dock plate is a `.glass-material` and MAY compose `.glass-lens`
(`glass-refract.css:106-111` applies `backdrop-filter: var(--glass-blur-resting)
var(--glass-refract-filter)` when the engine supports url()). The golden's morph animates
`scale` on the SAME element that, in Chromium, carries a `backdrop-filter: url(data:…
feDisplacementMap)`. **Animating `scale` on a backdrop-filtered element forces the backdrop
to re-sample the displacement map every frame** — a Chromium-only per-frame filter cost the
golden's perf section never measures, and a Safari↔Chrome DIVERGENCE (Safari skips the
url() filter entirely via `@supports`, so the two engines paint a materially different morph:
Chrome = refracted-rim pill that re-rasterizes the lens each frame, Safari = plain blur pill).
The golden's "compositor-only throughout, both engines" claim is true for the `scale` channel
but glosses the lens-re-sample asymmetry on the morphing element.

**HARDENING (R4):** during `[data-morphing]`, drop the dock plate to the un-lensed blur base
(remove `.glass-lens` participation or set `--glass-refract-filter: none` under
`[data-morphing]`), so BOTH engines morph the identical plain-blur pill and Chromium does not
re-rasterize the displacement map per frame; restore the lens at settle. Add a perf assertion
(no `Recalculate Style`/filter-rebuild spike during the morph) to §6.
