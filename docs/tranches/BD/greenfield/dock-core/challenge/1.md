## R1 (TOP) — the spike de-risks a CSS-`transition` driver that PRODUCTION WILL NOT USE; the anticipation dip is an artefact of that substitution and cannot exist under `SpringProgress`

The spike's anticipation (the §L4 "dip below origin before bloom") comes from
`dock.style.transition = '--dock-t … var(--ease-cartoon-punch)'` — a CSS transition over a
registered `@property` with a `linear()` easing whose first control points are negative
(`linear(0, -0.012, -0.038 33%, …)`). I live-traced it: `--dock-t` reads `-0.009` at
t≈266ms before overshooting to `1.048`. **That dip is real ONLY because a CSS transition is
interpolating the `linear()` curve.**

But §1(b) + §5 (`dockMorphContext.ts`) mandate production drives `--dock-t` (and §1(b) says
the SAME clock writes `--dock-squish`) via **`SpringProgress`** — imported from
`@mkbabb/keyframes.js`, a damped-spring physics integrator. A damped spring approaches its
target **monotonically from one side** — the GOLDEN itself states this at line 50 ("a damped
spring approaches monotonically from one side"). **A `SpringProgress` output literally cannot
emit the negative pre-dip the `linear()` curve produces.** So in production:

- §6.3 born-RED gate `dock-morph-anticipation` ("assert `--dock-squish` dips BELOW rest")
  **stays RED** — the driver named in §5 cannot produce the dip the gate demands.
- The spike's green is a FALSE de-risk: it proved a CSS-transition path, then §5 specifies a
  spring path. The two are not interchangeable on the one axis (anticipation) that is the
  doc's BOLDEST claim (§2 headline: "the pill **anticipates**").

This is the deepest refutation because it dissolves the headline ("ship the cartoon punch")
into an unresolved integration gap, and the spike was specifically built to retire that risk.

**Hardening:** the squish channel CANNOT ride `SpringProgress`. Either (a) drive
`--dock-squish` via a **separate WAAPI / CSS `transition` on the `--ease-cartoon-punch`
token**, explicitly a SECOND driver (and then retract the "ONE clock / no second clock" KISS
claim in §1(b)/§A13 — name it honestly as a one-shot punch animation layered on the spring),
or (b) keep one clock but pre-bake the anticipation into a **custom sampled curve fed to
`SpringProgress` as a keyframe table** (keyframes.js supports `linear()`-string sampling per
`useSpringMount.ts:38` — verify it accepts a non-monotone table), or (c) drop the
anticipation claim and retune §6.3 to test overshoot-only. Pick one and re-spike with the
ACTUAL production driver, not a CSS transition.

## R2 — the COMBINED bbox overshoots expanded by **45px (17%)**; this collides with live-nav-dock layout and the §6.2/§6.4 gate is self-contradictory

Live-traced combined (`--motion-weight: 1`, the dock's own scope value): per-frame
`maxWidth = 313px` vs `expanded = 268px` — a **+45px (17%) bbox bloom** during travel. The
GOLDEN calls this "intended volume-preserving overshoot" (§7) and §6.2 asserts it must
happen. Two problems:

1. **The spike's own `__runGate()` reported `maxWidth: 268, widthBounded: true` for the
   COMBINED run** — i.e. the shipped gate MISSED the 313px overshoot because its rAF sampling
   is coarse (I caught it only by tightening the loop). A born-RED gate that cannot even
   measure its own §6.2 "audacity bar" is not trustworthy. The §7 spike text claims combined
   `maxWidth 320` — yet `__runGate` says 268. The doc's own numbers disagree with its own
   harness.
2. A 17% width bloom on a real **bottom nav dock** (BottomDock, `justify-content: center`,
   auto-margin) pushes the pill 22px past its settled edges mid-gesture. On a narrow viewport
   or a left/right-anchored SidebarDock this can collide with the viewport edge or sibling
   chrome. §6.4 asserts `cx excursion ≤ 4px` (centroid pinned) — true, the center holds — but
   a centered 17% bloom still EXPANDS both edges outward by ~22px each. The doc never bounds
   the EDGE excursion against the container, only the centroid.

**Hardening:** (a) fix the gate to sample at real rAF AND assert the §6.2 overshoot with a
tight numeric band (e.g. `1.12 ≤ maxW/expanded ≤ 1.20`) so a regression in EITHER direction
fails; reconcile the 268-vs-313-vs-320 numbers. (b) Add an EDGE-excursion gate on the real
nav docks: assert the bloomed bbox stays within the container inline box (no viewport-edge
collision) at the dock's smallest supported viewport, BOTH BottomDock (center) and SidebarDock
(anchored). (c) Consider clamping the squish depth via `--motion-weight` on narrow viewports
(a §L6 proportion guard), since 16% is tuned for a wide centered dock.

(ratio-free bounded center-out size) is real, live-verified bounded, and a genuine union — I
could not break it, and it is a clear improvement over the unbounded-ratio HEAD trap. That core

ANTICIPATES") rests on a spike that de-risks a CSS-transition driver while §5 mandates a spring
driver that provably cannot anticipate (R1) — the single most important refutation, because the
de-risk is for the wrong mechanism. Plus the gate is not actually born-RED (R3, no spec file),
the audacious cast is invisible/unbuilt (R4), `--dock-t` reuse is a disguised rename (R5), and
the combined bbox blooms 45px unbounded-against-container (R2). The size-correctness half is
golden; the cartoon-audacity half is unproven and the integration story is overclaimed.

Top refutation: **R1** — the spike proves anticipation via a CSS `linear()` transition, but
production drives the squish through `SpringProgress` (a damped spring), which by the doc's own
§L2/line-50 statement CANNOT dip below origin; so the §6.3 anticipation gate stays RED and the
headline is undelivered until a real (second) squish driver is chosen and re-spiked.
