# CHALLENGE #1 — CORRECTNESS / DEFT-INTEGRATION / KISS

**Verdict: SURVIVES (with mandatory hardening).** The golden's load-bearing claims are
source-confirmed at HEAD: `tier="quiet"` is what fourier ships (`fourier-field.vue:300`),
`tier="field"` exists (`ShowcaseFrame.vue`), `onFrame` is real (`useFourierField.ts:99`),
the head SDF is a round disc on BOTH twins (`render.wgsl.ts:178`, `glsl.ts:145` —
`dHead = length(p - head)`), both consume `curveSamples`/`uCurve`, `coreR=halfW*1.5`/
`haloR=coreR*3.0` match, `MAX_PHASORS=64` on both, the `setProperty`-per-frame precedent is
real (`useGlassBackdropLuminance.ts:442,448`), and `prefers-reduced-transparency` is a live
3-site idiom. The gestalt is a genuine union, not a fork. But there are real refutations that
land — none fatal, each demands a concrete hardening clause before the build.

## TOP REFUTATION — the §9 prototype is honesty-inflated; it does NOT prove G1/G2

§9 asserts the spike lands "G1/G2 born-GREEN on the spike." **It does not.** The spike's own
`fieldLumaAt()` (phosphor-bloom.html:250-260) confesses in a code comment:

> `// can't read painted pixels without canvas; instead report the seam distance proxy:`
> `// luma proxy = closeness of (ux,uy) to the bloom centre`

So the spike's "near>far" PASS is a **geometric distance to where the JS WROTE the var** — it
proves the *seam writes a var* and *a comet sprite moves*, nothing about the **painted field**.
It cannot touch G1 at all (G1 is an OKLab hue-spread∈[20,70] + chroma≥0.045 readback of the
*painted* warm field — the spike never samples a pixel). It cannot prove G2's real claim ("sample
the field luminance near `--ff-head-xy` vs far: near>far") because that is a *painted-pixel*
luminance assertion and the proxy substitutes geometry for paint. The riskiest mechanism the
spike exists to de-risk — *does the radial-gradient bloom actually READ as a local bright pool
through the screen-blend over the warm mesh, in BOTH modes* — is exactly the thing the proxy
skips. **The de-risk is theater.** Worse: the spike's bloom uses `mix-blend-mode: screen`
(line 110) — screen-blend of a warm-amber over a deep-warm-umber dark base can wash toward a
desaturated highlight (a gray-white risk at the bloom core in dark mode), the precise BA.W-NO-GRAY
trap, and the proxy would never catch it because it never reads the resulting pixel.

**Hardening (mandatory):** the spike must do a REAL readback — render the field+bloom to (or over)
a `<canvas>`/`html2canvas`/`drawImage` and `getImageData`, convert to OKLab, and assert (a) G1
hue-spread∈[20,70] + chroma≥0.045 across ≥3 sampled points, BOTH modes; (b) G2 near-bloom
luminance > far luminance from ACTUAL pixels; (c) the dark-mode bloom CORE chroma stays ≥ the
warm floor (no screen-blend gray-white). Until the spike reads pixels, §9's "born-GREEN" is
struck — restate it as "the spike de-risks the SEAM PLUMBING (one setProperty/frame, the sprite
tracks), NOT the painted readback; the painted G1/G2 are proven first in the src build's π."

## R2 — "flip `tier='quiet'`→`tier='field'`, the field-backed tier ALREADY EXISTS" overstates the lift (KISS/idiom)

§3a says the §3 fold is "ONE class + ONE tier flip, no new component," framing `tier="field"` as
if it supplies the colourful ground. It does NOT. `ShowcaseFrame.vue`'s `field` tier is the
*ABSENCE* of a plate: `border-transparent bg-transparent shadow-none` (verified). It paints
nothing — it only removes the opaque `bg-card` so the glass floats over "whatever live/static
backdrop the page declares." For a fourier stage with no page-level warm backdrop, flipping to
`tier="field"` yields a TRANSPARENT stage over the dead page ground — *more* dead, not less. ALL
the warm colour must come from `.viz-warm-field` painted onto the stage element itself. The flip
is necessary (drop the occluding plate) but is the trivial half; the load-bearing half is the new
primitive. The spec's own §0 admits this ("A NEW warm CSS primitive is owed") — but §3a's "the
field-backed tier ALREADY EXISTS … ONE tier flip" sentence smuggles the impression that the
colour is free. It is not.

**Hardening:** restate §3a as "TWO moves: (a) flip `tier='quiet'`→`tier='field'` to KILL the
opaque plate (BG-2), AND (b) apply `.viz-warm-field` to the stage to PAINT the warm ground — the
tier flip alone yields a transparent (still-dead) stage; the primitive is the load-bearing half."

## R3 — "the comet lights the field" is FALSE at the seam: it's the *model head*, not the *painted comet*, that drives the bloom (idiom/coherence)

§2a's headline claim is "the ground is lit BY the viz … a backdrop can't be lit by its own
foreground in real time; the loom can." But the mechanism (§4 write-seam) computes
`partialSumAt(getSpectrum(), headT)` on the CPU and writes `--ff-head-xy`, then a CSS
`radial-gradient` blooms at that coordinate — a SEPARATE compositor layer BEHIND the canvas. The
bloom is driven by the *same model t* the GPU comet uses, so they're spatially co-located, but the
CSS field is NOT lit by the GPU comet's actual emitted light — it's a parallel CSS sprite reading
the same scalar. Two independent renderers fed one coordinate. If the view-fit mapping
(`computeFourierFit` center/scale) and the canvas's internal device-pixel scaling ever drift
(DPR changes, canvas CSS-size vs drawing-buffer-size mismatch, the stage aspect ≠ the fit aspect),
the bloom and the painted comet DESYNC — the "light" pools where the comet ISN'T, breaking the
entire gestalt. The spec never fences this alignment.

**Hardening:** add a gate clause (fold into G2): assert the CSS `--ff-head-xy` maps to the SAME
screen pixel as the GPU comet head within ≤2% of stage width, in a real readback (sample the
canvas head-pixel brightest point, compare to the `--ff-head-xy`×stage-rect coordinate). And spec
the single source of truth for the model→screen map (the canvas's actual fit uniform, read back —
not a re-derived CPU fit that can drift from the GPU's).

## R4 — §2b squash is "~8 lines" but the volume-preserving anisotropic SDF is the one place twin-parity silently breaks (cross-engine)

The squash math (project `(p-head)` onto `T`/`T⊥`, scale by `(1+k·s)` / `1/(1+k·s)`, take the
length) lands in WGSL, GLSL, AND the GL CPU bead path. The spec claims "parity by construction"
because all derive `T`/`s` from the SAME `partialSumAt`. But the tangent comes from *adjacent curve
samples* — `curveSamples[0]` vs `curveSamples[1]` — and the WGSL compute pass and the GL CPU step
populate that buffer via DIFFERENT code paths (the WGSL compute kernel vs `fourierFieldGLSetup.ts`'s
JS loop, verified at `:159-176`). Floating-point order, sample spacing (`trailArc*frac`), and the
`harmonicN` cap can yield a *slightly* different `curveSamples[1]`, hence a different `T` at a tight
corner where `s→0` and the tangent is ill-conditioned. A normalize of a near-zero tangent
(`s≈0` at a cusp) is a divide-by-near-zero that two engines round differently — the bead aspect
flips one way in Chrome, the other in Safari. "Parity by construction" is asserted, not proven, at
exactly the degenerate point G4 tests ("at a tight corner it inverts").

**Hardening:** spec a guarded tangent — `T = s > EPS ? d/s : lastT` with a SHARED `EPS` constant
(in `constants.ts`, consumed by both shaders + the CPU path) so the cusp degeneracy resolves
identically; and G4's "the webkit project paints the SAME anisotropy" must assert an ABSOLUTE
aspect-ratio ΔE ≤ bar between the two engines at the SAME frozen-T corner frame, not merely
"both > 1 / both invert."

## R5 — the `.viz-warm-field` "≥7 sites, lands ONCE" no-overfit claim is asserted but the 7 sites aren't enumerated, and 6 of them already have grounds (DRY/overfit)

§2c/§3a justify the new `@utility` as systemic ("all 7 flat vizzes adopt it") to dodge the
overfit-audit. But the OTHER flat vizzes already pass `tier="field"` (goo-dot, dot-matrix,
dot-flow-field — verified) and several have their OWN substrate paint. The spec never names the 7
nor confirms they currently render over a DEAD ground (the precondition for "they all need this").
If 5 of the 7 already have an adequate field, the primitive lands at 2-3 real sites and the "≥7,
systemic" framing is overfit-audit cover — a primitive built for fourier, retrofitted onto vizzes
that don't need it (a DRY-violation in reverse: forcing a shared util onto sites for the count).

**Hardening:** §2c must ENUMERATE the 7 sites with a per-site current-ground verdict (dead-cream /
has-own-field) and adopt `.viz-warm-field` ONLY where the ground is genuinely dead; if that yields
<2 sites beyond fourier, the primitive is fourier-local (`fourier-field`-scoped) and the "shared
@utility / systemic" framing is dropped — honesty over the count.

## R6 — gate born-RED integrity: G6's "math byte-identical (a diff REDs)" is a NAME/HASH check, not a runtime call-site (the discipline the spec itself mandates)

§8 opens "Every clause asserts a RUNTIME CALL-SITE or a COMPUTED readback, never a doc keyword /
type-literal / name-presence." G6 then asserts "`math.ts` is byte-identical (a diff REDs)" — that
is a FILE-HASH check, a static-text assertion, exactly the name-presence class the preamble bans.
A byte-diff gate is fine as a SURVIVAL fence but it is NOT a runtime readback and must be labeled
as the static arm, lest it inflate the "all-runtime" claim. (The U3 DFT↔WGSL round-trip arm of G6
IS a real numeric readback — that one is sound.)

**Hardening:** split G6: G6a = the U3 numeric round-trip (runtime ΔE) + the live "curated gallery +
scrub still drive the head" readback (runtime); G6b = the byte-frozen `math.ts`/`WARM_IDENTITY_
PALETTE`/`*0.7` static fence, EXPLICITLY labeled "static survival arm, not a runtime clause." Drop
the blanket "every clause is runtime" to "every BEHAVIORAL clause is runtime; the survival fences
are static byte-diffs."

## R7 — a11y/PRM gap: the draw-loop pointer capture has NO keyboard equivalent (WCAG 2.1.1)

§3c folds `BD.W-FOURIER-INTERACT`'s `useFourierStroke` (pointerdown→move→up). The headline
interaction — "re-thread it by hand" — is POINTER-ONLY. A keyboard/AT user cannot draw a closed
path. The keymap (`FOURIER_KEYMAP`) handles transport (scrub/N/play) but NOT shape authorship. The
curated ℱ/heart/star gallery is the keyboard fallback, but the spec never states that the gallery
IS the 2.1.1 keyboard-equivalent for the draw gesture — and an AT user landing on a "draw your own"
affordance with no keyboard path is a real failure.

**Hardening:** spec the curated gallery (or a "cycle preset shapes" key) as the EXPLICIT WCAG-2.1.1
keyboard equivalent for the pointer-draw, with a `aria-description` on the stage announcing "draw
with pointer, or press [key] to cycle preset shapes." Add a gate clause: the gallery is
keyboard-reachable + selecting a shape drives the SAME `"drawn"`/`activeSpectrum` swap the pointer
draw does.

## R8 (minor) — the `--ff-head-hue` "written once from the palette base" contradicts the lit-field gestalt

§4 writes `--ff-head-hue` "once from the palette base." But §1/§3d describe the source-swap
(elliptic→ℱ→heart→star) cross-fading spectra AND the dark/light arms using different warm anchors.
If the hue is written once at mount, the bloom hue won't track a palette/mode change at runtime
(mode toggle, preset swap) — the bloom goes stale-warm against a shifted field. Minor, but a
coherence seam.

**Hardening:** write `--ff-head-hue` reactively off `getPalette()` (cheap — only on palette change,
not per-frame), so the bloom hue follows the active warm anchor through mode/preset swaps.

## WHAT SURVIVES CLEAN (the fit core, no refutation)

- The KEEP/REFINE/RE-INVENT triage is honest and source-grounded (math byte-frozen, twin engines
  fit, ground genuinely absent).
- The `setProperty`-per-frame seam is a real, cheap, precedented pattern (`useGlassBackdropLuminance`).
- The Safari floor reasoning is correct: plain `radial`/`conic` gradients + `@property` angle, NO
  `backdrop-filter:url` / `filter:url` on the field (the one `backdrop-filter: blur(2px)` in the
  spike is on the glass-hint stand-in, a plain blur — Safari-safe).
- The draw-loop's CPU-minted `"drawn"` spectrum fed to the shared `getSpectrum()` seam IS the KISS
  win — zero new shader code, automatic twin parity (verified: both backends consume `BasisComponent[]`).
- The cap at `MAX_PHASORS=64` is real on both engines (`constants.ts:28`, `GL_MAX_PHASORS=64`).
- No parallel fork: every src touch is a refine of an extant file or one new composable/utility.
