## R2 — [FATAL to §8] The de-risk spike's π readback is FABRICATED ARITHMETIC, not a pixel measurement — it cannot prove the waist on EITHER engine

## R5 — [Safari/compositor] clip-path + filter:url + per-frame transform interaction is UN-TESTED on WebKit; the structural-waist "insurance" is asserted, not measured

The headline claim is that the clip-path hourglass is *"the WebKit insurance — a structural
concavity on BOTH engines BEFORE the filter fuses it... de-risked live in the spike."* But:

1. The spike was *"Verified live in Chrome"* only (§8). **No Safari capture exists.** The single
   load-bearing cross-engine claim has zero WebKit evidence — and the §8 table that stands in for it
   is the fabricated arithmetic of R2, which is engine-blind by construction (it would print identical
   numbers in a text terminal). The "paired-engine π" the GOLDEN demands of the implementation
   (G3, §3) was NOT applied to its own de-risk.
2. **WebKit clip-path + filter compositing is a known divergence surface.** WebKit historically
   rasterizes `clip-path: polygon()` differently when the element is also a `filter: url()` input and
   is animated via `transform`/`scale` per frame — the clip can be applied in *user space pre-transform*
   vs Chrome's *post-transform* in some compositor paths, so a `scaleX`-stretched hourglass polygon can
   read a DIFFERENT throat fraction on Safari than Chrome. The spike `scaleX`-stretches the neck
   (`neckLen` up to ~0.8 of base) AND clip-paths it AND feeds it to the filter — exactly the triple
   that can diverge. "Structural before the filter" does not guarantee "identical after `scaleX` +
   raster" across engines. The clip-path waist is only insurance if the *clip is applied in the same
   coordinate space* on both — unproven.
3. The per-seam `::before` hourglass is `parameterized by --neck-filament/--seam-tension` (§5). If a
   `polygon()` interpolates vertex coords from a CSS var on WebKit, that is the var-driven-filter
   class of bug-adjacency (animated geometry feeding a filter input); the GOLDEN must confirm the
   polygon vertices are STATIC (like the filter literals) and only the `scaleX/scaleY/girth` transform
   animates, or WebKit may re-raster the clip per frame (the §L7 budget fence the GOLDEN itself cites).

**HARDENING:** Add a §8b Safari de-risk: re-shoot the spike on real Safari-26-on-Metal at p=0.55 with
the REAL canvas readback (R2), prove `webkit.waistRatio ≈ chromium.waistRatio (±0.05)` on the SPIKE
(not just promise it for the impl). Pin the hourglass `polygon()` to STATIC vertex literals (animate
only `transform: scaleX scaleY` + `--neck-girth`, never the polygon coords) and document that the
clip is transform-space-stable on both engines, or fall back to a `::before/::after` two-convex-mass
metaball (no clip animation) if WebKit diverges. State explicitly that "structural before filter" is
only insurance once the clip-coordinate-space parity is measured.
