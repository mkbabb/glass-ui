## REFUTATIONS

### R1 (TOP) — The spike de-risks the EASY clauses on the EASY backend; the HARD, Safari-fragile clauses (3 & 4) are UN-de-risked, yet the spec calls "the boldest mechanism de-risked"

`golden/spike.html:182` is `getContext('webgl2')` — **WebGL2-only, Chrome-only.** It proves
clauses 1 (vividness chroma) and 2 (metal fold contrast) — the two clauses that are pure
fragment arithmetic and would never have been in doubt. It NEVER exercises:

- **Clause 3 (catch-light crosses to WGSL):** the spike has `uLightDir`-shaped cursor input on the
  WebGL2 path. The genuinely-hard claim is that the cursor-z-synth light works on the **WGSL struct
  that has no light lane** — the spike does not run WGSL at all.
- **Clause 4 (image texture parity, chromium-WGSL vs webkit-WGSL):** the single named "genuine
  divergence" (premultiply/colorspace/flipY between `copyExternalImageToTexture` and `texImage2D`).
  The spike has NO texture, NO WGSL, NO WebKit. The hardest, most-Safari-fragile surface is wholly
  unproven.

So "the boldest mechanism is de-risked" (§0 verdict, §2) overstates: the WebGL2 spike de-risks the
register that was never the risk. The risk was always the dual-backend cross to WGSL/WebKit, and
that is exactly what is left to faith. **The spike's GREEN gate proves a Chrome-WebGL2 subset of a
spec whose binding law is "perfect in Chrome AND Safari."**

### R2 — The "shared dot-image upload seam" (the load-bearing DRY claim for source:image) DOES NOT EXIST IN HEAD

§3, §6, §9, §10 all rest the blurred-image arm's KISS/DRY on: *"SHARE the texture-upload seam +
the rendered-capture-pair parity gate with `BD.W-DOT-IMAGE` (one upload primitive, two consumers —
DRY)."* But:

- `grep -rn 'texImage2D|copyExternalImageToTexture|createImageBitmap|UNPACK_PREMULTIPLY'` across all
  of `src/` returns **ZERO hits.** There is no image-texture upload anywhere in the engine today.
- `W-DOT-IMAGE` appears **only in `docs/tranches/BD/viz/` planning docs** — it is an UNSHIPPED,
  PLANNED wave, not an extant primitive.

So the "deft union, reuse the extant seam" framing is sharing with a sibling that **doesn't exist
yet**. This is the classic "DRY with a phantom" — either aurora-image must BUILD the first upload
primitive (so it is the *producer*, not a deft *consumer* of an extant one — a net-new subsystem the
union-map hides), or it is co-dependent on an unbuilt wave. The union-map row "Composes: the
dot-image upload seam" is aspirational, not extant. This is the one place the spec's "union not
bolt-on" claim is not yet true against HEAD.

### R3 — §10 self-contradicts §2b on the cursor-light path: "no new cursor path, EXISTING interactivity:light re-pointed" is FALSE on the WGSL primary

§10: *"The catch-light is the EXISTING `interactivity:'light'` axis re-pointed (no new cursor path)."*
But:
- HEAD's `interactivity:'light'` drives `uLightDir` and is **WebGL2-only** (DESIGN.md §214:
  "Cursor-as-light (`light`, **WebGL2**)"; README:206/487 tie it to the WebGL2 impasto `uLightDir`).
- The spec ITSELF (§0.3, §2b) says `uLightDir` is absent from WGSL, so on the primary path the metal
  must `normalize(vec3(uCursor - p, METAL_LIGHT_Z))` — **a brand-new in-shader light synthesis.**

So on the primary path of BOTH browsers there IS a new cursor-light path. The §10 "re-pointed
existing axis, no new path" is true only for the WebGL2 fallback and contradicts §2b's own code.
Minor in mechanism (the synthesis is small) but it is a KISS/idiom MIS-STATEMENT in the union-map
that papers over net-new WGSL shader code as "re-pointing." The wave will under-scope if it believes §10.

### R4 — A visible COLD zone in the live default field; the floor "preserves hue" defense does not protect the warm-floor mandate

The live default render (`aurora-default-live.png`) shows a clear **periwinkle/blue zone upper-right**
over the warm-cream wash. The spec's warm-floor defense (§2a) is: *"the floor LIFTS chroma along the
existing hue, it never injects a cold hue."* That defense is a non-sequitur against this risk: if the
field ALREADY carries a cold-leaning zone (whatever its origin — ACES on near-white, domain-warp, or
page-glass bleed), the vividness floor **preserves and amplifies** that cold hue, making any teal/navy
MORE saturated — the exact BA.W-NO-GRAY violation the spec invokes as its guardrail.

Caveat (intellectual honesty): the default *palette* is genuinely all-warm (hues 45/55/70, shortest-path
interp stays warm), and my 0.543 cold-fraction was measured off a composited SCREENSHOT (text + glass +
page chrome + PNG color-management), not a clean shader readback — so this could be screenshot color-cast,
not field output. But that is precisely the hole: **the spec's gate clause 1 measures only MEAN chroma,
never per-zone HUE.** A field can clear the mean-chroma floor while harboring a saturated cold zone the
floor just intensified. The gate cannot see R4.

### R5 — Gate clause 5 (default byte-identity) is in tension with the "DEFAULT palette ALSO lifts C:0.10→0.16-0.20" identity move

§2a/§10 ship TWO default changes: (a) `vividness` default-high, and (b) the palette chroma lift
C:0.10→0.16-0.20. Clause 5 asserts a `vividness:0` config renders **byte-identical** to the prior
smooth parity capture. But if the DEFAULT palette stops themselves move to C:0.16-0.20, then
`vividness:0` over the NEW palette is **not** byte-identical to the OLD parity capture — it's a
different (more saturated) field with the floor disabled. Clause 5 only holds if it pins the OLD
palette too, which contradicts shipping the palette lift as the default. The byte-identity gate and
the palette-lift identity move cannot both be literally true of the same `DEFAULT_AURORA_CONFIG`.
Needs disambiguation: byte-identity must be asserted against an EXPLICIT legacy-palette+vividness:0
config, not "the default with vividness:0."

### R6 — metal-gradient "twinkle" sparkle is a documented WebKit precision trap the spec half-fences but does not prove

§2c: `hash21(floor(p*DENSITY))` + `sin(t+seed*TAU)^40`. The spec correctly flags `hash21`/`fract` as
mediump-boils-cross-backend and says "highp forced." Good. But two un-de-risked items remain: (a)
`pow(sin(...), 40.0)` is a very high exponent — on some WebKit/Metal compilers `pow` of a near-zero
base at high exponent denormalizes/clamps differently than ANGLE/Chrome, so the flake DENSITY (how
many cells cross the glint threshold per frame) can differ between backends even with highp seeds;
(b) the spike (mode 2) runs this on WebGL2 only — the cross-backend flake-count parity is asserted,
never measured. The fold-contrast number (0.0302) does not capture flake-count drift. No gate clause
covers sparkle cross-backend parity — clauses 1-6 have no twinkle parity assertion.

### R7 (minor) — §0.1 framing imprecision: "oil/vangogh/oil-pastel degrade to the SMOOTH core on WebGPU"

§0.1 says only the oil/vangogh/oil-pastel STROKE cascade "degrades to the smooth core on WebGPU."
HEAD's `applyMedium` (`aurora-mediums.wgsl.ts:308`) degrades them to **`mediumKuwahara`**, not the
smooth core. Doesn't change the dual-port conclusion, but the spec's own ground-truth section
mis-states a HEAD fact while claiming "HEAD wins where lenses disagreed on fact" — a small credibility
ding on the section whose whole purpose is factual precision.

## HARDENINGS (concrete)

- **H1 (answers R1):** Add a WGSL/WebKit arm to the de-risk BEFORE calling the boldest mechanism
  de-risked. The spike must (or `proof:aurora.mjs` must, as a precondition) render the metal on
  **webkit-wgsl** with the cursor-z-synth light and assert a non-zero raked catch-light from a real
  capture — the clause-3 surface the WebGL2 spike cannot touch. Until then, label the spike "Chrome-
  WebGL2 fold/chroma de-risk only; cross-engine UNPROVEN."
- **H2 (answers R2):** Resolve the phantom-seam dependency explicitly: either (a) declare aurora-image
  the PRODUCER of the shared upload primitive (and re-draw the union-map so the row reads "BUILDS the
  upload seam, dot-image consumes" — honest net-new), or (b) hard-sequence `BD.W-DOT-IMAGE` before
  `W-BLURRED-IMAGE-BG` and gate on the seam existing. Do not claim DRY reuse of an unshipped sibling.
- **H3 (answers R3):** Rewrite the §10 union-map cell: metal's light on the WGSL primary is a NET-NEW
  in-shader `uCursor`-synth (not a re-point of the WebGL2-only `uLightDir`). Scope the wave for the new
  WGSL light synthesis on both metal finishes; keep the WebGL2 fallback re-pointing as the *secondary*
  path only.
- **H4 (answers R4):** Add a per-zone HUE clause to gate clause 1: assert the field's chroma-weighted
  mean hue stays within the warm band (e.g. OKLab b ≥ −ε over ≥ X% of weighted area) on the DEFAULT,
  measured from a clean SHADER readback (the gate's `renderAndReadback`, NOT a screenshot). The floor
  preserves hue, so the gate must independently forbid a saturated cold zone. Re-measure the periwinkle
  zone from a backbuffer readback to confirm origin before shipping the palette lift.
- **H5 (answers R5):** Re-author clause 5 to assert byte-identity against an explicit
  `{palette:LEGACY_C010, vividness:0}` config, and document the palette-lift + vividness-high as the
  TWO gated default-identity changes (no-backwards-compat), separate from the byte-identity invariant.
- **H6 (answers R6):** Add gate clause 7 — sparkle cross-backend flake parity: chromium-wgsl vs
  webkit-wgsl metal-gradient frame agree on glint-cell count within tolerance (clamp the `pow`
  exponent + assert highp seed stability across backends, not just within one).
- **H7 (answers R7):** Fix §0.1 to say oil/vangogh/oil-pastel degrade to `mediumKuwahara` (not the
  smooth core) on the WGSL primary.

## VERDICT

**SURVIVES — wounded but standing.** The spec's factual spine is real and verified against HEAD
(MEDIUM 8/9, the discarded gradient in both shader twins, the missing WGSL light lane, the live WGSL
primary, AND the born-RED chroma floor confirmed at 0.0350<0.045 on the *actual* live default). The
core architecture — four orthogonal axes on the one engine, metal-from-the-discard, the opt-out
vividness floor — is genuinely deft, KISS, and a union not a fork. No fatal refutation lands.

But it does NOT survive CLEAN. The single strongest refutation (R1): **the WebGL2-only spike
de-risks the two clauses that were never at risk and leaves the two genuinely-hard, Safari-fragile
clauses (catch-light→WGSL, image texture parity) wholly unproven — so "the boldest mechanism is
de-risked" is true only of a Chrome-WebGL2 subset of a Chrome-AND-Safari mandate.** Secondary: the
DRY-shared upload seam (R2) is shared with an unshipped phantom wave, and the §10 "no new cursor
path" (R3) contradicts §2b's own WGSL light synthesis. These are scope-honesty and de-risk-coverage
gaps, not architectural breaks — they harden cleanly via H1-H3.
