# Aurora GOLDEN — Adversarial Challenge #2 (CROSS-ENGINE / SAFARI / PERF)

Lens: Safari+Chrome parity (backdrop-filter:url / filter / color-interp / compositor),
perf, naive-ellipsoid meatball, a11y/PRM. Default to REFUTED. Every claim re-checked
against HEAD by source-dig; the spike re-read line-by-line.

VERDICT: **SURVIVES, but with one LANDED refutation** (R1) that forces a concrete
hardening of §3 + the gate before this is buildable. The metal finish + vividness floor
arms are sound and genuinely de-risked; the **image source arm is materially under-specified
on exactly the cross-engine axis this golden claims to own**, and the **born-RED gate is a
paper claim for the two backends it never actually exercised**.

---

## R1 (TOP, LANDS) — `source:"image"` is sold as "swap the color stage" but it is the FIRST texture pipeline in a procedural-only engine, and the spike NEVER touched it

Source-verified facts (HEAD):
- `grep -cE "texture2D|textureLod|textureSample|sampler2D|texture_2d"` over `aurora.frag.ts`,
  `aurora.wgsl.ts`, `mediums.glsl.ts` = **0 / 0 / 0**. Aurora is a **100% procedural
  pipeline today** — it has never bound a texture or a sampler.
- `grep "createTexture|texImage2D|sampler|copyExternalImage|createSampler|bindTexture"`
  over all of `src/components/custom/aurora/` = **nothing**. No upload code, no bind-group
  texture entry, no GPUSampler exists anywhere in the aurora tree.

So §3's framing — *"`source:"image"` swaps the color stage: instead of `samplePalette(field)`,
sample an uploaded texture"* — understates the change by an order of magnitude. What it
actually requires, on BOTH backends, NET-NEW:
- a `GPUSampler` + a `texture_2d<f32>` binding + a **new bind-group entry** in the WGSL
  pipeline (which today binds ONLY the uniform buffer);
- a `gl.createTexture` + sampler-param state + a `uImage` sampler uniform + texture-unit
  activation on WebGL2;
- the full `copyExternalImageToTexture` / `texImage2D(ImageBitmap)` decode seam (the §3
  premultiply/colorspace/flipY block) — which the golden DOES name, but treats as the
  ONLY divergence when in fact the whole binding surface is new.

This is not a "value on an existing axis." It is a **second pipeline variant with a
different resource-binding shape**. The golden's own §3 admits a separate shader PROGRAM is
built at construction time (good), but then claims the substrate/lifecycle/parity-net are
"all REUSED" — the parity net has **never round-tripped a textured pipeline**, the bind-group
layout differs, and `useGpuSubstrate`'s frame loop has never owned a sampler resource. The
"deft union, not a fork" claim is the WEAKEST for exactly the arm with the most cross-engine
risk.

And the de-risk does not cover it: **the spike (`golden/spike.html`) renders ONLY the
procedural `sampleBase()` path. It has zero texture sampling, zero `uImage`, zero upload.**
The metal + vividness arms are spiked; the image arm — the one with the genuine
Chromium-vs-WebKit `copyExternalImageToTexture` premultiply trap — is **entirely
un-spiked**. Gate clause 4 ("image source parity, ΔE ≤ threshold, born-RED on premultiply
mismatch") asserts a property the spike never produced a single pixel for.

HARDENING (forces a real build precondition):
1. Reclassify `source:"image"` from "color-stage swap" to **"a textured pipeline variant"**
   in §3 and §9, and add to the union-map row the NET-NEW resources it actually adds
   (sampler, texture binding, bind-group entry on WGSL, texture unit on WebGL2). It is
   still a deft union vs a `<BlurredImage>` fork — but the honest delta is "Aurora's first
   sampler," not "swap a function call."
2. **Spike the image arm before the wave is GREEN-able**: a throwaway dual-backend
   (chromium-WGSL + webkit-WGSL, real WebKit, e.g. Playwright `webkit`) capture-pair of ONE
   uploaded macro-flower decoded both ways, proving the `premultiplyAlpha:"none" +
   colorSpaceConversion:"none"` recipe actually converges ΔE under threshold on a REAL
   WebKit, not an assumed one. Born-RED must be demonstrated on a DEFAULT-premultiply
   build, not asserted.

## R2 (LANDS, narrower) — the born-RED gate claims THREE backends; the spike proved ONE. `webkit-wgsl` parity is asserted, never executed

`grep -in "webkit|safari" spike.html` = **0 matches**. The spike is `getContext('webgl2')`
in Chrome. Yet the gate (§8) loops `for backend of ['chromium-wgsl','chromium-webgl2',
'webkit-wgsl']` and the headline boast is "perfect in Chrome AND Safari, WGSL primary on
both." Every Safari claim in this golden rests on **reasoning about WebKit, not a WebKit
render**. Specifically un-executed:
- the metal `pow(sinTH, 28.0)` + `pow(NdotH, 6.0)` high-exponent crest on **WebKit's WGSL
  compiler** (WebKit historically lowers precision aggressively; a `highp`-on-WebGL2 fence
  is named but WGSL has no `highp` — precision is the adapter's, and the golden gives no
  WGSL-side precision argument);
- the `hash21`/`fract(p.x*p.y)` sparkle seed on WebKit-WGSL (the golden says "highp forced"
  — **WGSL has no precision qualifiers**; the fence as written is a WebGL2-only fence);
- the OKLab `pow(abs(lms), 1/3)` cube-root round-trip ΔE on webkit-wgsl (claimed "ΔE≈0 by
  construction" — never measured on WebKit).

The "WGSL primary on Safari 26, no fallback" architecture claim is correctly read from HEAD
(the WGSL header mandate is real). But "the math ports by construction + round-trips ΔE≈0 in
the parity net" is a **net that runs in headless Chromium**; whether the existing
`shader-eval-harness` even has a `webkit-wgsl` lane is unverified by this golden.

HARDENING:
- The gate's `webkit-wgsl` lane must be a REAL WebKit (Playwright `webkit` / a Safari
  Technology Preview headless), not a chromium stand-in. If the harness has no webkit-wgsl
  lane today, the wave's first task is to ADD it — and that is a born-RED precondition, not
  an assumed capability.
- Replace the WebGL2-only precision fences ("highp forced") with a WGSL-valid argument:
  WGSL has no precision qualifiers, so the cross-backend stability of `hash21` and the
  high-exp `pow` must come from **value conditioning** (e.g. floor'd integer cell seeds —
  which the sparkle already does — and a clamped, range-reduced exponent), not from a
  qualifier that does not exist in the language. State this per-backend.

## R3 (LANDS, perf) — the blur "tap budget" is a FALSE precedent: kuwahara's 32 taps are PROCEDURAL re-evaluations; the image blur's 24 taps are DEPENDENT TEXTURE READS with a per-fragment-VARIABLE radius

§3 and §10 justify the single-pass blur by *"the kuwahara tap-budget precedent that already
clears the perf budget (3 rings × 8 = 24, …)."* Source-verified, this precedent does NOT
transfer:
- `mediumKuwahara` (`mediums.glsl.ts:423+`) samples `sampleBase(p + off, t)` — i.e. it
  **re-evaluates the procedural noise/palette math** at each offset. Those are ALU taps. No
  texture is touched (the engine has no texture).
- The image blur samples `uImage` at `uv + off` — **dependent texture reads**. With a
  zone-driven `radius` that VARIES per fragment, neighbouring fragments read from divergent
  texel addresses. On mobile/tiled GPUs (every iPhone — the literal iOS-27 target) this
  defeats texture-cache locality and disables the hardware's ability to pre-fetch; 24
  variable-stride dependent reads per fragment over a full-viewport background is a
  materially different cost class from 32 ALU re-evals. The golden asserts equivalence with
  zero measurement.
- Worse for WebKit specifically: a **gradient computed inside a varying-radius loop** (if
  any `texture()` auto-LOD is used) yields undefined derivatives; the golden must force
  `textureLod(uImage, …, 0.0)` (explicit LOD) or WebKit may diverge or fall to a slow path.
  Not specified.

HARDENING:
- Drop the "kuwahara precedent" justification for the image blur — it is a category error
  (ALU vs sampler). Re-justify the 24-tap budget with an **actual textured-blur frame-time
  measurement on a real mobile-class GPU / throttled profile** (the iOS-27 target device),
  in the image-arm spike from R1.
- Mandate **explicit-LOD sampling** (`textureSampleLevel` / `textureLod`) for every blur
  tap on BOTH backends (no implicit-derivative texture reads inside the radius loop), and
  state it in §6's WebKit-fences list alongside the existing pow/hash entries.

## R4 (partial) — the vividness floor's `Clift/C` divide-and-rescale can DESATURATE-then-OVERSHOOT hue near gray, and the "warm floor holds, never teal/navy" claim is unproven near C≈0

The floor (`lab.yz *= max(C,Cmin)/C`) is hue-preserving *only when C is meaningfully above
the `1e-4` guard*. In a near-neutral cream zone (the whole point of the §3 complaint — pale
warm-gray), `lab.yz` is a TINY near-zero vector whose DIRECTION (the hue) is dominated by
quantization/precision noise. Scaling that noisy direction UP to `Cmin = 0.115` amplifies
**whatever hue the noise happens to point at** — which on WebKit's lower-precision OKLab
round-trip may NOT be the warm 45–70° band. The "warm floor holds, never teal/navy" promise
is asserted, but the mechanism (scale the existing chroma vector) is exactly the one that
loses hue control where chroma is smallest. The spike's JS-side readback measured *mean
chroma magnitude* (0.031→0.057), NOT *hue stability* — so the spike cannot have proven the
warm-floor claim it is cited for.

HARDENING:
- When `C < epsilon`, do NOT scale the noisy near-zero `lab.yz`; instead **synthesize the
  lift along a fixed warm anchor hue** (the `AURORA_CATCH_LIGHT_ANCHOR` warm direction
  already at `uniformBridge.ts:106`), i.e. `lab.yz = mix(scale-existing, warm-anchor-dir *
  Cmin, smoothstep(eps2,eps1,C))`. This makes "never teal/navy" a STRUCTURAL guarantee, not
  a hope.
- Add a gate clause measuring **hue, not just chroma magnitude**: the lifted default field's
  mean hue stays in the warm band [40°,75°] on BOTH backends, BOTH modes. (Composes the
  BA.W-NO-GRAY warm-floor π on the field side — currently the gate only checks magnitude.)

## R5 (partial, a11y/PRM) — PRM "one static frame" still seats a MOVING cursor-raked catch-light unless the idle-rake path is the ONLY path under PRM, and the gate does not assert the catch-light is FROZEN

§7 says under PRM the metal "seats one lit static frame (rake frozen to idle)." But the
metal's light (§2b) is `L = (uCursorStrength>0 || uCursorBurst>0) ? cursor-dir : idle-rake`.
Under PRM, §7 separately says the cursor write-path early-outs (2.3.3) — so `uCursorStrength`
SHOULD stay 0 and L SHOULD fall to idle. That chains two separate guarantees (the freeze
AND the cursor early-out) to land "frozen rake." If either drifts (e.g. a residual nonzero
`uCursorStrength` from a pre-PRM frame, or a burst decay still in flight), the catch-light
moves under reduced-motion — a 2.3.3 violation. Gate clause 6 only checks "no drift, no
sparkle phase, no rake motion" as prose; it does not pin the catch-light pixel to the idle
value.

HARDENING:
- Make the idle-rake unconditional under PRM **in-shader**: gate the cursor branch on a
  `uReducedMotion` scalar (or reuse the master-tempo==0 signal) so the rake CANNOT read the
  cursor when frozen — one guarantee, not two chained.
- Gate clause 6 must **assert pixel-equality of the catch-light region across two PRM frames
  with a cursor move injected between them** (catch-light must NOT move), not merely assert
  "no rake motion" in prose.

## R6 (minor, KISS/DRY + overfit) — the toy `packGrad` in the spike, and two magic constants, are overfit placeholders presented as the mechanism

- The spike's `packGrad(vec2 g){ floor((g.x*.5+.5)*4095.0)+(g.y*.5+.5) }` is labelled "toy
  pack" and is **never actually unpacked** — the metal reads `grad` directly as an out-param,
  and `structureTensorField` still `return vec4(dir,A,1.0)` with a constant `1.0` in the
  packed slot. So the headline "`vec3(dir,A)` → `vec4(dir,A,packGrad)` return-widening" that
  §2/§9 sells as the deft mechanism is **NOT what the spike validated**; the spike passed
  `grad` via an `out` param, sidestepping the pack entirely. For the real WGSL twin, WGSL
  functions can't take `out` params the same way (no pointer-free out) — so the actual
  mechanism (pack a 2-vector into one float and unpack) is **unspiked and non-trivial**
  (precision of packing two signed components into one f32, on WebKit). This is an overfit
  spike: it proved a convenient variant, not the shippable one.
- `METAL_HEIGHT_SCALE=2.3`, `VIVID_TARGET=0.115`, `METAL_SHININESS_ANISO=28` are presented as
  settled but were tuned against ONE procedural `sampleBase`, not the real `nucleiField`.
  They will need re-tune against the actual field; flag them as spike-provisional in §2b/§10
  so they are not pasted as canon (the analyze-in-full / no-overfit discipline).

HARDENING:
- Resolve the grad-transport mechanism for REAL: either (a) widen the return to `vec4` and
  carry RAW `grad` in `.zw` is impossible (`.z` already = A, only `.w` free → one float) — so
  EITHER widen to a separate `out`/global in GLSL + a returned struct in WGSL, OR pack with a
  precision-proven scheme. Spike whichever on webkit-wgsl. The current "packGrad → never
  unpacked" is a non-answer.
- Mark all metal/vivid constants spike-provisional, re-tuned against `nucleiField` in the
  wave.

## What SURVIVES (kept — fit)

- The **architecture read is correct against HEAD**: WGSL primary on both engines (verified:
  `uniformBridgeWGPU.ts` struct has `cursor` off 64, NO light lane; free pads at scalars3.w
  / cursor.z,.w / ints1.z,.w; `MEDIUM_ID` stops at kuwahara:7 so metal IS 8/9). The
  dual-port mandate and the cursor-synth-light (not phantom `uLightDir`) are RIGHT and are
  this golden's strongest, genuinely cross-engine-correct moves.
- The **metal finish from the re-plumbed structure-tensor gradient** is a real, deft,
  zero-new-tap mechanism, and the spike genuinely separates it (localContrast 0.0011→0.0267,
  25×) — modulo R6's transport caveat.
- The **vividness floor as a shader-resident opt-OUT contract** is the correct literal §3 fix
  and ports as pure OKLab arithmetic — modulo R4's near-gray hue-control hardening.
- **No `backdrop-filter:url`, no naive ellipsoid, no FBO ping-pong, in-shader blur, fixed
  tap count** — the structural WebKit-trap avoidance is sound in PRINCIPLE (the meatball/goo
  lens finds nothing to attack here; aurora is a field, not a metaball system, so the
  naive-ellipsoid precept is N/A and correctly untouched).

The golden's SPINE is fit. It does not survive CLEAN: R1 (image arm is an unspiked new
texture pipeline, not a color-stage swap) is a real landed refutation that must harden §3 +
add an image-arm webkit spike before the wave is buildable; R2/R3 harden the gate and the
perf justification. None of these break the design — they tighten an over-confident spec
back to what was actually proven.
