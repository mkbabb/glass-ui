## TOP REFUTATION — the §2b BASE recipe DOUBLE-SCALES; volume-preservation is BROKEN as published

The GOLDEN §2b **base** keyframe (`gl-liquid-enter`, lines 175-183) sets, in the SAME 0% stop,
BOTH the `scale:` longhand AND a `transform: scale()`:

```css
0% { ... scale: var(--lq-enter-scale, 0.88);
         transform: scale(var(--lq-stretch-x, 1.06), var(--lq-stretch-y, 0.945)); ... }
```

Per CSS Transforms L2, the individual transform property `scale:` composes WITH `transform:`
(they multiply; `translate→rotate→scale→transform` order). Verified live (Chrome):

```
scale: 0.88  ×  transform: scale(1.06, 0.945)
 → effective born  sx = 0.88·1.06 = 0.933 ,  sy = 0.88·0.945 = 0.832
 → effective product = 0.776   (NOT ≈1)
```

So the published base recipe is born at **78% area, isotropically shrunk**, NOT the
"wide+flat ≈1.06·0.945, vol-preserving" the GOLDEN §1 channel-2 promises. The squish reads as
a plain shrink-in, the exact flat-zoom the design says it kills. **The §7b gate point 2
("X·Y product ≈1 mid-flight") would FAIL on the recipe as written.**

Why the spike doesn't catch it: the spike's `gl-cel-slam` uses **only** `transform:`
(no `scale:` longhand), so it IS vol-preserving — but it is the CEL keyframe, not the BASE
keyframe. **The de-risk spike validates a DIFFERENT keyframe than the one §2b ships for the
universal floor.** The "spike-verified" claim does not cover the base recipe.

### Hardening
Express the base squish-grow with a SINGLE transform authority. Either (a) fold the 0.88
bloom INTO the transform leg — `transform: scale(calc(0.88·1.06), calc(0.88·0.945))` is still
wrong (that's an isotropic shrink × a flat squish, still product 0.78); the correct born value
is `transform: scale(1.06, 0.945)` (vol-preserving, product 1.002) with NO separate `scale:
0.88` — the "0.88 grace" must come from the squish itself OR from a separate UNIFORM scale that
the SETTLE also passes through, not a born-only multiplier; or (b) keep `scale:` for the uniform
bloom and DROP the reciprocal from `transform`, driving the reciprocal squish via the live
`--stretch` from `useLiquidFlex` only (the JS-present path) — accept that the pure-CSS floor has
NO squish (it is then just `.glass-reveal`'s scale-grow, which §0 already concedes is the
overlay floor). Pick ONE; re-measure the X·Y product live; make §7b point 2 born-RED on the
base recipe, not only the cel.

## REFUTATION 2 — `vReveal` writes `--d`, the recipe keys `--i`: an un-reconciled stagger fork

GOLDEN §2e/§5: "`vReveal` keeps writing `data-reveal` + `--i`." Source says otherwise —
`vReveal.ts:22` does `el.style.setProperty("--d", …)`. Meanwhile `.scroll-build`
(`scroll-choreography.css:90`) and the §2b `.liquid-enter` recipe both key
`animation-delay: calc(step · var(--i))`. So:

- Either `vReveal` must be changed to write `--i` — a **clean break** that silently re-keys
  every existing `[data-reveal]` consumer CSS (the demo's own `reveal.vue:112` reads `--d`),
  un-flagged by the GOLDEN; OR
- The `.liquid-enter` rows bound by `vReveal` receive **no stagger index at all** (`--i`
  defaults to 0 → every row fires on beat 0, the 1/φ overlap collapses).

This is precisely the bolt-on seam the binding law forbids: two stagger authorities
(`--d` writer, `--i` reader) the GOLDEN asserts are unioned but which use different property
names. The "no fork" claim is contradicted by the live source.

### Hardening
Make the property-name reconciliation EXPLICIT and a clean break: rename `vReveal`'s output to
`--i` (one writer, one reader), update the demo's scoped CSS, and add a census line. State it in
§5 as a breaking change (no `--d` alias — per the no-backwards-compat law). Add a gate assertion
that a `v-reveal="3"` row resolves `getComputedStyle().getPropertyValue('--i') === '3'`.

## REFUTATION 3 — the Safari claims are ASSERTED, not CAPTURED (the §0 binding law is unmet)

§0 binding law + §7d require a **paired-engine π (Chromium + WebKit, both modes)** before GREEN.
The GOLDEN itself admits §7e "OUTSTANDING (not yet captured): the paired WebKit run + both-modes."
So by its own law the gate is NOT green. Three specific WebKit risks the Chrome-only spike cannot
de-risk:

1. **`filter: blur()` co-tenant with `backdrop-filter` (the decongest window).** The surface
   carries `backdrop-filter: blur(13px) saturate(1.6)` (live-confirmed) AND animates
   `filter: blur(4px)→0`. Per CSS Filter Effects, `filter` applies to the element's *composited*
   output — which **includes** its `backdrop-filter` plate. So mid-flight the GOLDEN's claim "the
   resting glass plate is untouched" is **false**: at `blur(4px)` the whole surface (plate
   included) is blurred; it is only "untouched" at the `blur(0)` terminus. In Chrome this reads
   as a benign extra-clarify. In **WebKit** a non-`none` `filter` historically establishes an
   isolated stacking/backdrop context, and `backdrop-filter` sampling can clip to the filter's
   inflated bounds → an **edge halo / re-sampled backdrop** for the duration of the decongest.
   This is the WebKit per-frame-reblur hole the GOLDEN names but routes AROUND only for
   `backdrop-filter:url` — it does not address `filter` + `backdrop-filter` *co-tenancy*.

2. **`linear()` spring curves.** GOLDEN says "Baseline 17.2+." On Safari < 17.2 (still a real
   tail) `animation-timing-function: linear(…)` is unparsed → the entire `animation` shorthand's
   timing falls to its initial `ease`, killing the overshoot interior. The MOUNT register's
   "Safari-15-safe" claim is therefore false for the SPRING — only the channels are 15-safe; the
   *curve* needs a `@supports (animation-timing-function: linear(0,1))` floor to a cubic-bezier.

3. **Cross-engine color-interp of the cast.** `--shadow-cartoon` resolves via
   `color-mix(in srgb, …)` (live-confirmed). Good (sRGB, not oklab) — but the §2c cast child uses
   `z-index:-1` under a glass surface whose `::before`/`::after` already claim layers; verify in
   WebKit the negative-z child paints BEHIND the plate without being clipped by the surface's own
   `overflow`/`border-radius: inherit` rounding (WebKit rounds `inherit` border-radius differently
   when the parent has a backdrop-filter clip).

### Hardening
Add the `@supports (animation-timing-function: linear(0,1))` floor for the spring curves.
Capture the WebKit π for: the decongest window over a real backdrop plate (assert NO edge-halo /
plate re-sample), the cast negative-z paint, both modes. Until that paired capture exists, mark
the gate RED per the GOLDEN's own §0 law — do not let "authored Safari-safe by construction"
substitute for the capture (the [[Live-verify capture]] lesson).

## REFUTATION 4 — perf: the cel-slam mounts TWO animation clocks + a child layer PER surface

`.is-cel` runs `gl-cel-slam` on the host AND `gl-cast-lag` on a `.cartoon-cast` child, each on
the `--spring-snappy-duration` clock, staggered across N rows by `--i`. On a page that opts
EVERY surface into `.liquid-enter.is-cel` (the §3 "non-optional squish on every entrance" framing
invites this), that is 2× compositor layers × N + the backdrop plates. The GOLDEN gates the cast
behind opt-in `.is-cel` (good), but §3's "make the SQUISH non-optional on every entrance" + the
cel framing risk a consumer slamming `.is-cel` globally. No budget/cap is stated.

### Hardening
State an explicit cap: `.is-cel` is for HERO/headline surfaces only (≤ a small N per viewport);
the universal floor is the single-clock base (no child cast). Add a perf note + a gate that the
cast layer count stays bounded. Confirm `will-change`/layer promotion is scoped to the animating
window, not pinned at rest (a pinned `z-index:-1; will-change` cast is a permanent layer cost).

## REFUTATION 5 — naive-ellipsoid / meatball: OUT OF SCOPE but the squish must not read as one

The entrance squish is an axis-scale (`scale(sx,sy)`), which is the *correct* primitive here (no
metaball merge is in this golden's scope). But the binding law's "NO naive ellipsoids" applies to
the VISUAL read: a `scale(1.06,0.945)` on a rounded-rect with `border-radius` produces
**non-uniform corner radii** (the corners stretch into ellipse quadrants) for the duration of the
squish. On a glass card with a defined rim this reads as a momentary squashed-ellipse corner — the
naive-ellipsoid tell. The spike's cards are large-radius so it's subtle; on a pill/chip
(`rounded-pill`) it will read as an egg.

### Hardening
For high-radius/pill surfaces, drive the squish via the wrapper (a non-rounded transform parent)
or cap the reciprocal further on `rounded-pill` (the `1.08` cap is for gel; a pill wants ≤ `1.03`).
Add a visual gate frame on a `rounded-pill` `.liquid-enter` asserting corner-radius read.
