naive-ellipsoid, a11y/PRM, KISS/DRY, born-RED honesty, overfit. Default: REFUTED.

Verdict up front: **SURVIVES — but with two LANDED refutations** that the golden's prose paints

## R1 — THE VELOCITY-BRIDGE COMPOSABLE CLAIM IS A FICTION (the load-bearing refutation)

**The golden says** (§0 table, §3): the smear "composes EXTANT `usePointerVelocityField`"
(+ `useDragMorph` + `useLiquidFlex`) → "a thin `--atom-drag-v` CSS var", "default to the EXTANT
`usePointerVelocityField`", "ONE honestly-named small bridge composable is the ceiling" only "if the
renderer-field cannot drive a CSS var directly".

**The source says otherwise.** `src/composables/motion/usePointerVelocityField.ts` is, by its own
load-bearing header doc, a **NO-OWN-rAF PUSH-API physics model**: "This composable owns NO second
rAF: it is a PUSH-API physics model the renderer FEEDS via `tick(delta)` from inside its existing
frame callback." It is built for the WebGPU/Canvas viz family, which ALREADY owns a frame loop and
calls `field.tick(delta)` once per render frame. It has **no public API that reads pointer velocity
without a host frame loop** and **emits no CSS var** — it returns `PointerVec2` JS values.

A slider has NO renderer, NO canvas, NO frame loop. To get a per-frame `--atom-drag-v` you MUST
spin a fresh `requestAnimationFrame` loop gated to the drag window — which is **exactly what the
golden's own spike does** (`spike.html` lines 166–201: a hand-rolled `loop()` + `requestAnimationFrame`,
zero use of `usePointerVelocityField`). So the spike REFUTES the prose: the bridge is not "compose
extant", it is "stand up a NEW drag-window rAF loop + a NEW composable to own it". The "EXTANT
composable" framing is false; "ONE honestly-named small bridge composable" is not a contingent
ceiling, it is the **mandatory floor**.

This matters because (a) it understates the new surface area (the golden's §4 disposition row says
"NO new core drag composable" under EXCISE — but a drag-window velocity→CSS-var bridge IS a new
composable, even if small), and (b) it risks an implementer literally trying to wire
`usePointerVelocityField` into the slider, discovering it needs a `tick(delta)` it has no loop to
call, and then either (mis)forking the viz composable or quietly violating the no-own-rAF discipline
the viz family depends on.

**HARDENING.** Rename the mechanism honestly: the slider weight-train requires **ONE new small
composable, `useDragVelocity`** (drag-window-gated rAF, `pointerdown` opens / `pointerup` tears down,
writes `--atom-drag-v`, PRM early-returns to 0). State plainly it does NOT consume
`usePointerVelocityField` (wrong shape: that one is a push-API with no own loop and no CSS-var
output; reusing it would force a host frame loop the slider does not have). Keep `useDragMorph` /
`useLiquidFlex` only if they actually contribute to the spring/release math (verify each is wired,
or drop the name — three composable names where the spike used zero is over-claiming). Move the new
composable OUT of §4's EXCISE row and INTO the NEW-wave deliverables with its own born-RED unit
(rAF opens on down, is gone after up — proof:offscreen-pause / no-idle-rAF). Audit it against the
no-idle-cost claim explicitly: assert teardown via a unit that fails if any rAF survives `pointerup`.

## R2 — THE CAST IS A `box-shadow` LAYER THE GOLDEN TRANSLATES PER-FRAME — Safari/Chrome PAINT HOLE

**The golden says** (A5/A8 paint-fence, §3 cross-engine): "NO box-shadow value change per-frame";
the cast "is set per STATE-FLIP, NEVER animated per-frame; its MOVEMENT rides `translate`/`scale`",
"compositor-only", "Safari pays no blur cost on the cast" (0-blur).

**The mechanism it ships contradicts the spirit of the fence.** In the spike (lines 80–86) the cel
cast lives on `.fill::after` as a `box-shadow: 5px 4px 0 0 var(--cartoon-ink)` (set once — good) and
its lag is a `transform: translateX(...)` (animated — the intent). But: **translating an element
whose only visual is a `box-shadow` does NOT cleanly composite a shadow in either engine the way a
painted layer would.** A `box-shadow` is painted relative to the element's border box; moving the box
via `transform` moves the shadow with it as part of that element's composited layer — which is fine —
BUT the golden also has the cast as a SEPARATE z-index:-1 child whose translate must read as the
shadow "lagging behind" the fill. For that lag to be visible the cast child must be a promoted
compositor layer distinct from the fill. The golden never asserts a `will-change`/promotion contract,
and **a 0-blur box-shadow on a non-promoted child is repainted, not composited, when its offset
changes** — the very paint-fence A8 claims to forbid. The fence is asserted but the promotion that
would make it TRUE is unstated. A8's self-test ("a planted animated-box-shadow MUST red") would catch
the WRONG thing — it tests `box-shadow` VALUE churn, not the un-promoted-translate repaint that the
cast-lag mechanism actually risks.

**Cross-engine sharpening.** Safari's compositor is stricter about which `transform`-only changes get
a fast path; a `z-index:-1` child with a `box-shadow` and `backdrop-filter`-bearing siblings can
force Safari to fall back to CPU paint for the shadow region, and Safari has historically mis-clipped
`box-shadow` under `transform` on backdrop-filtered ancestors. The golden's "Safari pays no blur cost"
is true for the BLUR but says nothing about the SHADOW PAINT under translate. This is a real Chrome↔
Safari divergence risk the lens is chartered to catch and the golden does not address.

**HARDENING.** (1) Make the cast a real promoted compositor layer: assert `will-change: transform`
on the `.cartoon-cast` child (or move the cast to a `filter: drop-shadow()` on a promoted layer —
but NO, drop-shadow re-blurs per frame, so keep the 0-blur box-shadow but PROMOTE the child). (2)
Add a paint-fence arm A8b: a Chrome trace + a WebKit trace (Playwright `webkit`) over the drag window
that asserts ZERO "Paint" / "Layerize" events on the cast layer during the smear — value-churn (A8)
AND offset-churn-repaint (A8b) are different failures and the golden only guards the first. (3) State
the WebKit-specific guard: the cast child must NOT inherit the fill's `backdrop-filter` (it would
re-rasterize the backdrop on every translate in Safari); the cast is a pure colored-shadow layer over
transparent, promoted, sibling-not-child of the blurred fill.

## R3 — THE `::after` CAST-SLOT OCCUPANCY CLAIM IS ASSERTED BUT THE SPIKE VIOLATES IT

The golden (§3) says the cast "rides an inert `aria-hidden` `.cartoon-cast` CHILD" because
"`::before`/`::after` are OCCUPIED by the glass catch-light + grain" (the cartoon-shadow H2 lesson),
and §4 EXCISE forbids "any `::before`/`::after` cast". **The spike puts the cast on `.fill::after`**
(line 80) — directly violating the golden's own fence. Minor (the spike is a throwaway de-risk), but
it means the de-risk did NOT actually prove the inert-child path the golden specs; it proved the
`::after` path the golden forbids. The two boldest mechanisms the spike claims to de-risk (weight-train,
arc) were both validated with the WRONG cast carrier. On the live atoms, `.slider-range` and
`.metric-badge` pseudo-element slots must be checked: I confirmed `.slider-thumb.touch-hit-area::before`
is already occupied (the 44px tap-halo, Slider.vue:284). So the inert-child is mandatory, and the
spike's `::after` proof does not transfer.

**HARDENING.** Re-spike the cast on the inert `.cartoon-cast` child (not `::after`) before EXECUTION,
OR explicitly demote the spike to "motion-curve de-risk only; cast-carrier is the inert child per H2,
NOT the spike's `::after`". Add a born-RED unit: the atom must emit a `.cartoon-cast` element and must
NOT set a cel `box-shadow` on `::before`/`::after` (the slots are catch-light + grain).

## R4 — "NAIVE ELLIPSOID" / MEATBALL: N/A but the gate must SAY so, not just assume it

The lens is chartered on naive-ellipsoid/metaball. The golden correctly states the atoms have NO goo
path, NO `backdrop-filter:url`, NO SVG filter — they are flat capsule lenses, so there is no meatball
to get wrong, and A9 asserts no `backdrop-filter:url` appears. **This is the right call** and survives
the meatball lens cleanly: a capsule should NOT be a metaball. BUT two adjacent traps the golden does
not fence:

1. The slider FILL stretching in X (`scaleX`) over a pill `border-radius: 9999px` produces a
   **lozenge whose end-caps go elliptical under non-uniform scale** — a `scaleX(1.06) scaleY(0.95)`
   on a 9999px-radius capsule turns the circular end-caps into NAIVE ELLIPSES (the exact "no naive
   ellipsoid" precept, transposed to 2D). The squash IS a naive-ellipse generator on a stadium shape.
   The golden's "vol-preserving X·Y≈1" does not prevent the end-cap distortion; it only preserves area.
2. The StackedIcon `rotate(--i * 2.4deg)` on a `backdrop-filter`-blurred disc: in Safari, rotating a
   backdrop-filtered element re-samples the backdrop at a rotated basis every frame — a known WebKit
   perf cliff. The golden's "compositor-only" claim is FALSE for a rotated backdrop-filter layer in
   WebKit.

**HARDENING.** (A6/A5) add an end-cap arm: the squash must use a `border-radius` that tracks the
scaled box (or cap the `scaleX` delta so end-caps stay within visual-circle tolerance), and the gate
must assert the end-cap aspect stays ≥ some ratio (no naive ellipse). For the stack: either the
rotating discs drop `backdrop-filter` during the fan (swap to a static tint while in motion, restore
at rest), OR the rotate is removed in WebKit via `@supports`/UA floor — and the cross-engine arm A9
must trace a rotated-backdrop-filter disc on `webkit` and assert no per-frame backdrop re-raster.

## R5 — KISS/DRY: the "reuse `.glass-chip` if it lands first" is a build-order GAMBLE, not a design

§0 + §3 say `.glass-atom` "IS `.glass-chip` re-used (verify at build; prefer reuse over a sibling
class)" IF the chip wave lands first — else a sibling class. Grep confirms **neither `.glass-chip`
NOR `.glass-capsule` NOR `.glass-atom` exists in `src/` today** (0 matches). So the golden's central
recipe is contingent on a sibling wave (`BD.W-TAB-IOS-CAPSULE` EXTRACT) that has not landed, and the
naming/reuse decision is deferred to "build time". This is a DRY risk dressed as DRY: if the chip
wave names its class `.glass-chip` with chip-specific assumptions (chip padding, chip gap), the atom
"reuse" becomes an override-pile (anti-DRY), and if it does NOT land first, you get the sibling fork
the golden swore off. The decision is punted, not made.

**HARDENING.** Make the dependency a HARD ORDER, not a "verify at build": state that
`BD.W-TAB-IOS-CAPSULE` MUST extract a layout-NEUTRAL `.glass-capsule` (body + rim + floor + tint
ONLY, zero padding/gap/size) that BOTH `.glass-chip` and `.glass-atom` compose, and that
`.glass-atom` is NEVER `.glass-chip` (a chip is a SIZED consumer, an atom register is the shared
recipe — they are peers, both consuming `.glass-capsule`). Drop the "reuse `.glass-chip` verbatim"
option entirely; it conflates a consumer with the recipe.

## R6 — PRT (`prefers-reduced-transparency`): the cast-UP escape may CONTRAST-FAIL in light

§3 a11y carve: under PRT "the glass body floors to the opaque escape … the cast goes UP (the only
edge cue without glass)". But the cast is `--cartoon-ink` at a warm chroma; in LIGHT mode over a
light opaque body, a warm-ink 0-blur offset shadow at "UP" alpha may still not clear WCAG 1.4.11
(≥3:1 non-text) as a delineating edge IF the ink lightness is close to the body. The golden asserts
A2's rim clears 3:1 in the glass register but does NOT assert the PRT opaque-escape rim/cast clears
3:1. PRT users are precisely those who lose the blur-edge cue and most need the rim.

**HARDENING.** Add A2b: under PRT (and `prefers-contrast: more`) the rim ΔL vs the OPAQUE body
(not the glass body) clears ≥3:1, measured on the painted composite. The cast-UP is a supplement,
the RIM is the contract.

## SURVIVAL

The golden SURVIVES this lens. Its architecture is a true union (consume-only, depend-honest,
born-RED-accurate against live state), the meatball lens is correctly N/A (capsules, not blobs), and
the no-`backdrop-filter:url` posture is the cross-engine-correct one. The two LANDED refutations
(R1 fictional velocity-bridge / R2 un-promoted cast-translate paint hole) plus the four sharpenings
(R3 cast-slot, R4 end-cap-ellipse + rotated-backdrop-filter WebKit cliff, R5 build-order, R6 PRT
contrast) are all HARDENINGS to a sound design, not a re-invention. Apply R1 and R2 before EXECUTION;
they are correctness, not polish.

**Top refutation:** R1 — the slider weight-train does NOT "compose the EXTANT
`usePointerVelocityField`" (that composable is a no-own-rAF push-API with no CSS-var output and no
host frame loop in a slider); it MANDATES a NEW drag-window `useDragVelocity` composable (which the
golden's own spike hand-rolls, proving the point), and §4 wrongly lists "no new drag composable" under
EXCISE. Honest naming + a no-idle-rAF teardown gate is the required hardening.
