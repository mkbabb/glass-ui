## TOP REFUTATION (the one that lands hardest)

### R1 — The de-risk SPIKE contradicts the §3 shipped mechanism it is supposed to de-risk (cast on `::after`)

§3 states, emphatically: *"The follow-through cast rides an inert `aria-hidden` `.cartoon-cast`
child (the cartoon-shadow H2 lesson — `::before`/`::after` are OCCUPIED by the glass catch-light +
grain)."* This is a HARD architectural constraint and a named prior lesson.

But the golden's OWN de-risk artefact — `golden/spike.html`, the thing that is supposed to prove the
mechanism is compositor-only and cross-engine — implements the cel cast on **`.fill::after`**
(spike.html:80–86) and the stacked puck cast on the element's own `box-shadow` (spike.html:103).
**The spike validates a DIFFERENT mechanism than the one §3 mandates ship.** It proves a pseudo-cast
weight-train; the shipped recipe must use an inert child it never spiked. The lag/follow-through
timing, the z-index stacking with the glass catch-light, and the paint-fence all behave differently
between "`::after` on the fill" and "a real child div behind the glass body" — the child sits in a
different stacking context and cannot `border-radius: inherit` the same way, cannot share
`transform-origin: right center` with the fill without its own transform plumbing.

**Why it matters:** the de-risk is the load-bearing evidence for the boldest move (the weight-train).
A spike that uses the forbidden surface proves nothing about the shippable surface. This is the exact
class of gap that lets a "paint-verified" claim inflate (per the live-verify-capture lesson). The
metric-badge check (src `components.css:80–90`) shows `data-just-resolved` catch-light lives on the
element's own `box-shadow`, NOT a pseudo — so for metric-badge the pseudo MAY be free, but §3
asserts a blanket "`::before`/`::after` are OCCUPIED" that is overstated for some atoms and the
spike just ignores it for the slider. Either the constraint is wrong (then state which atoms have
free pseudos) or the spike is invalid (then re-spike on the inert child). It cannot be both.

**HARDENING:** Re-cut `spike.html` so the cel cast rides an actual `<div class="cartoon-cast"
aria-hidden>` child positioned behind the `.fill` (the SHIPPED surface), and re-capture the
weight-train + arc with the cast as a sibling layer — proving the lag/follow-through still composites
and the catch-light/grain pseudos stay free. Then audit §3's "`::before`/`::after` OCCUPIED" claim
per-atom (metric-badge's own catch-light is on box-shadow, not a pseudo — so be precise about WHICH
pseudo is occupied on WHICH atom; the blanket claim is false for metric-badge).

## SECONDARY REFUTATIONS

### R2 — "ZERO new composable" is asserted in §0/§5 but CONTRADICTED in §3; the headline overstates DRY

§0's boldest-move paragraph: *"it composes ONLY extant engines, zero new core composable."* §5
gestalt: *"costs ZERO new material + ZERO new motion register."* The headline reads as no-new-code.

But I verified `usePointerVelocityField` (src `usePointerVelocityField.ts:273`) returns **JS refs
only** — `velocity`, `speed`, `burst`, `position` — and **emits no CSS variable**. The weight-train
fill reads a CSS var `--atom-drag-v` (spike.html:84, the cast `translateX(calc(var(--atom-drag-v) …))`).
So a bridge that calls `el.style.setProperty('--atom-drag-v', …)` from those refs inside the
drag window is MANDATORY, not conditional. The golden does hedge this in §3 ("IF the renderer-field
cannot drive a CSS var directly, ONE honestly-named small bridge composable is the ceiling") — but
the §0 and §5 HEADLINES drop the hedge and claim zero. The condition is not "if" — it is "always,"
because the extant composable's contract is JS refs. The DRY/KISS proof is softer than advertised:
it IS a new (small) composable.

**HARDENING:** Promote the hedge to a fact in §0 and §5: "the press/hover core is pure CSS (zero
composable); the slider weight-train requires ONE new small bridge — `useDragVelocityVar` (or fold
into the slider's existing setup) — that mirrors `usePointerVelocityField`'s refs onto a single
`--atom-drag-v`, gated to the drag window. This is the ONE honest new composable; everything else
reuses." Name it in the §4 wave row so the build-DAG counts it.

### R3 — The slider "single most legible re-point" is partly a NO-OP: the consumer var is ALREADY wired

§2.B claims the bold re-point is demoting `--primary` to `--slider-range-bg` "(already wired,
`Slider.vue:225`)." I confirmed src `Slider.vue:225`: the fill is ALREADY
`color-mix(in oklab, var(--slider-range-bg, var(--primary)) 88%, transparent)` AND already carries
`backdrop-filter: var(--slider-range-blur, var(--glass-blur-quiet))` AND already carries
`box-shadow: var(--glass-material-rim), …`. So the fill is NOT a flat bar with no glass — it is
ALREADY a backdrop-blurred, rimmed cylinder whose ONLY defect is the **default tint** (`--primary`
dark when the consumer doesn't override). The "re-invent the slider fill material" framing oversells:
the material plumbing (blur, rim, color-mix-toward-transparent) is FIT and EXTANT. The actual fix is
ONE token default flip: make the library default a warm `--glass-fill-tint`-derived value instead of
`--primary`, keeping `--slider-range-bg` as the consumer's loud override (presets-in-consumers).
Calling this "the single most legible RE-POINT … re-invented" violates "REFINE what is weak,
RE-INVENT only what is broken" — the fill is weak (wrong default), not broken.

**HARDENING:** Downgrade §2.B + §4's slider language from "re-invented material" to "REFINED: one
default-tint flip." The wave row should say "the slider fill keeps its extant blur/rim/color-mix;
only the default range tint changes from `--primary` to the warm `--glass-fill-tint` floor." A6/A5
stay (the weight-train motion + squash IS new); but A4 is a one-line default change, not a material
re-invention.

### R4 — Cross-engine A9 has a real WebKit hole: `color-mix(in oklab, … transparent)` premultiply

The golden's A9 cross-engine assertion is *only* "no `backdrop-filter:url` appears." But the spike +
the extant slider both build the glass body with `color-mix(in oklab, <warm> X%, transparent)`
(spike.html:56,66,100; Slider.vue:225). Mixing **toward `transparent` in `oklab`** is a documented
Safari↔Chrome divergence: `transparent` is `rgba(0,0,0,0)`, and oklab interpolation toward it pulls
L and chroma toward black before the alpha is applied — Safari and Chrome have historically differed
on premultiplied handling for `oklab`/`oklch` + transparent, producing a DARKER, GRAYER edge in
WebKit. For a register whose entire identity is "warm-not-gray," a WebKit-only desaturation at the
fill edge is exactly the failure the whole tranche exists to prevent — and A9 does not test for it.
A9 runs "both engines" but only asserts the absence of a url-filter; it never asserts the painted
warm chroma (A1) PASSES on webkit specifically.

**HARDENING:** A9 must run A1 (warm-not-gray painted composite, C ≥ FIELD_FLOOR, H ∈ [45,85]) on
**webkit** as a hard arm, not just chromium. Additionally, spec the warm mixes as
`color-mix(in oklab, <warm> X%, <warm-at-0-alpha>)` (mix toward a transparent-WARM, e.g.
`oklch(0.9 0.05 60 / 0)`) rather than bare `transparent`, so neither engine pulls the edge toward
gray-black. Add a self-test bite: a planted `mix … transparent` (bare) MUST red the webkit warm
arm if the divergence reproduces on the CI WebKit build.

### R5 — The "OPT-IN cast" rule collides with the "every atom casts" gestalt + LIQUID-WEIGHT-UNIVERSAL

§0 resolves the cast-default tension to **OPT-IN** (lens-b): the loud status pill casts only on
`data-cast`/hover; only metric-badge + `+N` light by default. But §5's gestalt bar and the BINDING
LAW (cartoon shadowing universal, "elevate §L4 weak/medium toward UNIVERSAL") want the cel cast as a
family signature on ALL atoms. A `success` badge with NO cast, NO cartoon punch at rest is a flat
sticker — precisely the "missing cartoon-punch" precept violation the challenger lens is told to
hunt. The golden justifies opt-in as "a status pill is information, not a card," which is reasonable
UX — but it is in direct tension with the tranche's universal-cartoon edict, and the golden resolves
it by FIAT (picks lens-b) without reconciling against the BINDING LAW. Under the law, the floor
should be "every atom carries SOME cartoon weight (at minimum the press-squish + a faint rim-cast),"
with opt-in controlling only the LOUD offset magnitude, not its presence.

**HARDENING:** Reframe the register so the cartoon signature is UNIVERSAL-but-graded: every atom gets
the press-squash + a hairline warm rim-cast at rest (the family floor, satisfying the universal law);
`data-cast` escalates the LOUD layered-offset stamp for the flagships. This keeps the "status =
information" restraint (no loud sticker on a `success` badge) WITHOUT a zero-cartoon atom that
violates §L4-universal. State this reconciliation explicitly so the FIAT becomes a derivation.

### R6 — Two un-reconciled names for the core recipe ("`.glass-atom`" vs "IS `.glass-chip`") leaves a fork risk at build

§0 + §1 + §3 repeatedly hedge: "`.glass-atom` … **reuse `.glass-chip` verbatim if the chip wave
lands first**." This is a build-ordering coin-flip baked into the spec. If `.glass-chip` lands first,
the atoms reuse it; if not, a sibling `.glass-atom` is born — and then `.glass-chip` lands later and
you have TWO recipes (the exact parallel-fork the tranche forbids). "Prefer reuse, verify at build"
is not a decision; it is a deferred decision that can resolve into a fork under race. KISS/DRY demands
ONE name decided NOW.

**HARDENING:** Decide the name unconditionally. Either (a) `.glass-atom` is ALWAYS an alias/`@extend`
of `.glass-chip` and the chip wave is a HARD DEPEND of the atom wave (so order is forced, never a
race), or (b) `.glass-chip` and `.glass-atom` are declared the SAME selector list from day one in
one file. Add a gate arm A11: grep asserts exactly ONE shared glass-lozenge recipe selector exists
post-merge (a second sibling recipe = FAIL), killing the race-fork.

### R7 — A5 weight-train "overshoot must cross past target" risks a false-PASS / flaky gate on the real pointer ramp

A5 requires the release `transform` track to "CROSS PAST target (overshoot) … sampled across rAF on
the REAL pointer ramp — not a discrete-class spike; a monotonic settle = FAIL." Sampling a CSS
`linear()` overshoot curve across rAF in a headless engine is timing-fragile: webkit and chromium
tick rAF differently under load, the overshoot window is ~tens of ms, and a slow CI frame can miss
the peak entirely → false FAIL, or a coarse sample reads the settle as monotonic → false PASS. This
is the flakiest arm in the battery and it gates the headline move. It is also engine-dependent (the
`linear()` easing support + sampling cadence differ), making "both engines" doubly fragile.

**HARDENING:** Make A5 deterministic: drive the release via a fixed synthetic value transition (not a
live human ramp), and assert the overshoot by reading the `--ease-cartoon-punch` curve's computed
output at a FIXED progress fraction (e.g. the easing returns >1.0 at t≈0.46 per the spike's
`linear()` knot) OR assert `getComputedStyle` transform exceeds the rest+target envelope at a pinned
`requestAnimationFrame` count after a programmatic `pointerup`. Pair it with a non-rAF static check:
the easing token itself contains a knot >1.0 (overshoot is a property of the curve, provable without
sampling). Keep the rAF sample as a soft corroborator, not the hard gate.

### R8 — `--atom-tint-floor` self-referential `max()` is a CSS no-op (the warm-floor #2 cure may not fire)

§3's recipe writes:
```css
--accent-fill-strength: max(var(--accent-fill-strength), var(--atom-tint-floor));
```
A custom property that references ITSELF in its own declaration is **invalid per CSS variable cycle
rules** — `var(--accent-fill-strength)` inside the `--accent-fill-strength` declaration resolves to
the GUARANTEED-INVALID value (a self-loop), so the whole `max()` becomes invalid and the property
falls back to inherited/initial. The "dormant-tint #2 cure" — the leg the golden says is REQUIRED for
born-RED to flip GREEN — may silently not apply. This is a correctness bug in the load-bearing cure.

**HARDENING:** Resolve the floor without a self-cycle: introduce a separate input var, e.g.
`--accent-fill-strength-in` (the consumer/accent-tone sets it), and the atom computes
`--accent-fill-strength: max(var(--accent-fill-strength-in, 0%), var(--atom-tint-floor));`. Add a
gate arm: the idle (no-field, no-accent) atom's resolved `--accent-fill-strength` ≥
`--atom-tint-floor` (12%/15%) — proving the floor actually fires, not silently dropped to 0.

### R9 — Overfit/≥2-site claim double-counts the slider to reach "5 consumers"

§4 + §1 assert `.glass-atom` clears the ≥2-site bar with "5 consumers (badge-quiet · metric ·
slider track+fill · IconChip-glass · `+N`)." But "slider track+fill" is counted as the load-bearing
multiplicity in two places and the IconChip-glass consumer is a CROSS-LINK to `BD.W-ICONCHIP-GLASS`
(another wave owns it). If the chip wave reuse (R6) makes `.glass-atom` === `.glass-chip`, the
"5 atom consumers" are really consumers of `.glass-chip`, and the atom wave's OWN net-new consumer
count is smaller. The overfit bar is met regardless (metric + badge-glass alone = 2), so this is the
weakest refutation — but the "5 consumers" headline is inflated bookkeeping.

**HARDENING:** State the honest count: ≥2 is cleared by `metric-badge` + `<Badge surface="glass">`
alone (both OWNED by this wave); slider-fill, IconChip-glass (cross-linked), and `+N` are additional.
Don't count "track+fill" as two and don't claim a cross-linked consumer as this wave's proof.

## VERDICT

The golden's FOUNDATION is sound — the born-RED gate is genuinely red (verified live: badge
backdrop/border/shadow none, slider fill `--primary` dark, K5 dark white-flip via
`--shadow-color:--foreground`, uniform-shrink press), the two-register architecture is coherent, and
the no-fork/consume-only discipline is real. The lenses do converge.

But it does NOT survive clean. The load-bearing failures: **(R1)** the de-risk SPIKE validates a
FORBIDDEN surface (`::after` cast) instead of the §3-mandated inert child — the headline move's only
evidence is invalid for the shipped mechanism; **(R8)** the warm-floor #2 cure is a self-referential
`max()` that is a CSS no-op and may never fire; **(R4)** A9 cross-engine never actually asserts the
warm-not-gray paint on webkit and the `color-mix … transparent` mixes have a real WebKit
desaturation hole; **(R2)** the "zero new composable" headline is contradicted by the extant
velocity field returning JS refs (a bridge is mandatory). R3/R5/R6/R7/R9 are refinements that
tighten honesty (slider is REFINED not re-invented; the universal-cartoon law vs opt-in FIAT; the
name-race fork risk; the flaky overshoot arm; inflated consumer count).

None of these are fatal to the DIRECTION — they are fixable with the hardenings above. But as
written, the golden ships a self-no-op cure, a spike that proves the wrong surface, and a
cross-engine gate with a WebKit blind spot. It does not survive this lens intact.
