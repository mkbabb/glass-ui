## R1 (TOP REFUTATION) — §6's "NO `backdrop-filter:url` on any shell path… PERFECT in Safari by construction" is FALSE as stated; the gate arm-4 is mis-scoped and will mis-fire or born-GREEN.

**Evidence (live, on `/substrates` — a page the shell HOSTS):** a stylesheet scan found
`backdropFilterUrlRules: 1` reachable in the cascade — `.glass-lens` with
`--glass-refract-filter: url("data:image/svg+xml,…#glass-refract")`. This is a SVG
displacement filter that **WebKit silently drops** (Safari never honoured
`backdrop-filter: url()`), so any surface wearing `.glass-lens` degrades to a plain blur on
Safari — a real cross-engine delta on a shell-adjacent surface.

The GOLDEN claims its shell paths avoid `url()` — TRUE for the *new* M1/M2/M3 code it adds.
But §8 gate arm-4 is written as **"Born-RED if ANY shell path uses `backdrop-filter:url`
(grep + a webkit paint check)."** A naive grep over "the shell" trips on `.glass-lens`
(used by hero/dock glass surfaces in this very tree) → the gate either (a) mis-fires RED on
shipped, intentionally-Safari-degraded primitives it does not own, or (b) is hand-scoped so
loosely it can never catch a real regression. Either way the "by construction" claim is not
mechanically enforced. The §6 prose overclaims: the shell COMPOSES surfaces that carry
`url()` filters; it does not introduce them, but it cannot assert engine-parity for them.

**HARDENING:** (1) Reword §6 to "the shell introduces NO NEW `backdrop-filter:url`; the
`.glass-lens` refraction it composes is a PRE-EXISTING WebKit-degraded primitive owned by
glass-core, with its own `@supports not (…url…)` blur floor — out of shell scope." (2)
Re-scope gate arm-4 to a DIFF grep: born-RED only if a file UNDER the shell-layout wave set
(`AppShell.vue`, `SidebarDock/BottomDock`, `SectionLanding`, `StorySkeleton`,
`category-hero.ts`) adds a `url(`-bearing filter — NOT a tree-wide grep. (3) Add an explicit
WebKit paint-parity assertion that `.glass-lens` surfaces in the shell still read warm/edged
under the blur-only fallback (the refraction loss must not reveal gray).

## R2 — §0-defect-2 + M2 mis-model the void: it is a PRE-MOUNT void (`<main>` ABSENT), not a "chrome-painted-around-empty-main" void; the `<StorySkeleton>` 3rd-`<Transition>`-branch CANNOT paint frame 0, so "zero void from the first frame" is unprovable as written.

**Evidence (cold cache-busting reload frame-probe, `/display/buttons`):** for t=45→135ms+
the probe records `main:false` (the `<main>` element does **not exist** — AppShell itself
has not mounted), not `main:true / empty`. The GOLDEN says "the chrome (PaperBackdrop + both
docks) paints, but the route region is empty." My probe shows the route region's CONTAINER
isn't in the DOM yet — the whole Vue app is still parsing/hydrating.

This breaks M2's central promise. `<StorySkeleton>` is a 3rd branch INSIDE
`<RouterView>` INSIDE `<AppShell>`. It is downstream of the exact same JS bundle whose parse
is causing the void. It cannot "paint a coherent glass placeholder in the `<main>` rect" at
frame 0 because there is no `<main>` rect at frame 0 — only after the shell mounts. The
skeleton fills the NARROWER window (shell mounted, route chunk pending), which is real and
worth fixing, but the §0 "8 empty frames t=18→128" + the §7 "glass skeleton from frame 0"
language conflates two distinct voids and over-promises the early one.

**Caveat for fairness:** this is partly a DEV artefact (Vite serves unbundled modules; prod
splits the shell chunk from the route chunk, so the shell mounts far sooner). But the gate
arm-2 ("`<main>` non-empty FROM THE FIRST FRAME") must then be measured on a PROD build, or
it is born-RED forever in dev for a reason M2 cannot fix.

**HARDENING:** (1) Split the void into two: V-a (pre-shell-mount, owned by build/chunk
strategy — an inline critical-CSS shell paint or an `index.html` static skeleton stub that
the SPA hydrates over) and V-b (shell-mounted, route-pending — owned by `<StorySkeleton>`).
M2 owns V-b only; say so. (2) For V-a, add a tiny SSR-less static skeleton in `index.html`
(below the app root, removed on mount) so frame 0 is non-void even pre-hydration — THIS is
what makes "zero void from frame 0" true. (3) Gate arm-2 must run against `vite build`
output (prod chunking), not the dev server, and assert V-b non-empty; add a separate
arm asserting the `index.html` static stub covers V-a.

## R4 — M3-b's bento-specimen perf claim guards the WRONG budget: it fences the GL context (1-per-route) but ignores the backdrop-filter COMPOSITING-LAYER multiplication that is the actual Safari cliff. 33 bento cards × real glass primitives = a layer explosion WebKit pays for hardest.

**Evidence (live, `/substrates`):** `bentoCardCount: 33`, `backdropFilterBlurEls: 13`
already on this ONE landing. M3-b proposes replacing each dead glyph with a REAL `<Button>`
(`control`), `<Card>` mini (`surface`), `<Metric>` (`metric`) — and the shipped glass
`<Card>`/`<Button>` carry their own `backdrop-filter: blur(...)`. Per `category-hero.ts`,
most `previewKind`s are `surface`/`control` (display, containers, dock, feedback,
compositions all `surface`; forms, navigation `control`) → a category landing's bento becomes
20-30+ NESTED glass specimens, each a backdrop-filter layer inside an already-glass card,
over a glass landing, over the PaperBackdrop. WebKit re-rasterises backdrop-filter stacks far
more expensively than Chrome (no fast-path layer caching for nested backdrop blur). The
GOLDEN's only stated perf fence — "static DOM/CSS, NOT a 2nd live-GL context, the
one-GL-per-route budget holds" — addresses GL and says NOTHING about the blur-layer count,
which is the binding Safari constraint here. "Budget-safe" is asserted against the wrong
budget.

**HARDENING:** (1) The bento specimen must render the primitive in a FLATTENED, non-blurred
register — a `glass-resting` STILL with the backdrop-filter SUPPRESSED on the specimen
(a `--specimen-flat` variant: keep the edge + warm tint + specular, drop the live blur), so
the card previews the *shape/material read* without a nested backdrop-filter layer. (2) Add a
gate arm: assert a category landing's count of `backdrop-filter: blur` compositing layers
stays ≤ a budget (e.g. the dock + landing chrome, NOT 1-per-bento-card) — born-RED if the
specimen swap multiplies blur layers. (3) Reason it on a Safari Tech Preview paint trace, not
only Chrome.
