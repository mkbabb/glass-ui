## R1 (LANDING) — §2 leg-(a) re-indexes by HUE ANGLE, but the data field is a RAMP INDEX; the spike proves a fiction

**The contradiction, source-verified:**

- `demo/stories/category-hero.ts` `sectionHue` is documented IN THE FILE as *"a `--section-color-N`
  ramp **INDEX**"* — the live values are small integers: `substrates:3, forms:2, containers:9,
  navigation:11` (lines 81/88/102/109). Its mirror `aurora-hero.ts::CATEGORY_PALETTE_HUES` is the
  same integer map (`cat-substrates:3, cat-forms:2, cat-containers:9, cat-navigation:11`).
- The ramp slots resolve to oklch hues: `--section-color-3 = oklch(0.542 0.089 222.8)` (teal),
  `-2 = 265.5` (indigo), `-9 = 239.6` (slate), `-11 = 208.0` (ocean). **These match the GOLDEN's
  cited offenders exactly** — defect-1 is REAL (also LIVE-confirmed, R7).
- BUT the GOLDEN's leg-(a) table (§2) and the de-risk spike (`warm-fence-spike2.mjs`) treat
  `sectionHue` as **raw hue degrees** and "re-point" to **`~20` (rose-coral), `~340`
  (magenta-rose), `~50` (warm gold), `~95` (chartreuse)** — these are *hue angles*, not ramp
  indices. There is **no `--section-color-N` slot whose hue is 20° / 340° / 50° / 95°** (nearest:
  20→sc6 30.4 off 10.4; 340→sc0 359.8 off 19.8; 50→sc5 69.6 off 19.6; 95→sc5 69.6 off 25.4).

**Why this is a landing refutation, not a nit:** the spike's headline de-risk result — *"min
pairwise gap 10.4°, ALL 11 warm, fence identity"* — is **computed on the fictional free angles**
(`const REINDEX = { substrates: 20.0, ... }`), NOT on any realizable integer-index assignment.
The proof therefore **does not bind the implementation.** To actually realize 20° you must EITHER
(b1) mint NEW ramp rows — which §2 *explicitly forbids*: *"never a parallel hue table"* — OR (b2)
snap to the nearest EXISTING warm slot, which §2 *prefers* (*"pick existing warm slots"*) but
which **breaks the 10.4° distinctness math** and **collides** (R2). The spike proves a third thing
that is neither option. The BOLDEST move's de-risk is a category error.

**HARDENING:** Pick ONE realizable mechanism and re-run the de-risk on THAT:
- **Option A (cleanest, KISS):** add 4 *deliberate, named warm ramp rows* to
  `--section-color-N` (e.g. sc13=20, sc14=340, sc15=50, sc16=95) in `tokens/color-radius.css` +
  `dark-arm.css`, re-point the 4 integer indices to them. This is NOT a "parallel hue table" — it
  is extending the ONE identity ramp (the §2-sanctioned "add deliberate warm rows" clause). Re-run
  `warm-fence-spike2.mjs` with the ACTUAL new slot hues (light AND dark arm) and re-bank the gap.
  Then §2's "re-index by angle" prose must be rewritten to "add-rows-then-re-index-the-index."
- Drop the spike's free-float `REINDEX` map entirely; replace with the real `{index → token-hue}`
  the implementation will use, both modes. A de-risk that doesn't model the data type is not a
  de-risk.

## R2 — §2's two rules contradict; the warm-slot reuse path COLLIDES (slot exhaustion)

§2 says, in one breath: *"pick existing warm slots **or** add deliberate warm rows, never a
parallel hue table."* These are not co-satisfiable for 4 NEW distinct warm hues:

- Truly-warm existing slots (h ∉ [180,270], excluding the green-cyan sc4): sc0(359.8) sc1(305.9)
  sc5(69.6) sc6(30.4) sc7(317.5) sc8(8.4) sc10(128.8) sc12(291.9) — **8 slots**.
- The 7 KEEP-warm categories already occupy 7 of them: foundations=7, display=5, dock=6, data=1,
  feedback=8, motion=12, compositions=4(green). Reusing existing warm slots for the 4 cool
  categories forces **collisions**: substrates' nearest warm slot is sc6=30.4 — **already owned by
  dock** (the headline category, "tomato"). navigation's nearest is sc5=69.6 — **already owned by
  display**. Distinct-11 is *unsatisfiable* by reuse.
- So the only realizable path is "add deliberate warm rows" — which the same sentence brands a
  forbidden "parallel hue table" if read strictly. The rule eats itself.

**HARDENING:** Delete the "pick existing warm slots OR" clause. Mandate the additive path
unambiguously: *"mint N deliberate warm rows on the single `--section-color-N` ramp (light+dark
arms), re-point the 4 cool indices to them; the ramp stays the ONE identity source — that is the
union, not a fork."* State the new indices + their exact oklch in BOTH arms in the wave.

**HARDENING:** Either (a) widen the cool band to `COOL_LO≈150` so 171 folds out too (then
compositions must also be re-indexed to a warm slot — it is NOT a KEEP), or (b) explicitly carve
compositions' green as an *intentional* warm-green editorial exception in §7 and the gate (so the
born-RED census doesn't false-PASS it). Right now §2 KEEPs it AND §7 forbids it — pick one. The
born-RED census (§8 arm 1, `!(h∈(180,270))`) would PASS 171° — so the gate is **too loose** to
catch this; tighten the census predicate to the actual warm arc, not just the [180,270] hole.

surface-exists resolution is correct (R4), and M2/M3 are sound unions onto shipped machinery
