# DotMatrix GOLDEN — Adversarial Challenge #2 (cross-engine / Safari / perf)

Lens: Safari↔Chrome parity (backdrop-filter / filter / color-interp / compositor), perf,
naive-ellipsoid meatball, a11y/PRM, KISS/DRY, born-RED integrity, overfit. Default REFUTED.
Live-tested on `/substrates/dot-matrix` (Chrome, localhost:5173) + source-verified at HEAD.

**Verdict: SURVIVES — but with three landing-blocking corrections and several real dents.**
The diagnosis (symmetric-pool / invisible-rest / flat-ground) is true and I confirmed it
with my own eyes + readback. The *mechanism* is engine-honest (instanced billboards, no
backdrop-filter:url, no SVG goo) so the heavy WebKit fence genuinely does not bite. But the
GOLDEN's own §4 cross-engine claim is self-contradictory, two "shipped/already-wired"
reuse claims are FALSE against source, the de-risk spike validated the WRONG configuration,
and three a11y carve-outs are aspirational. None of these break the design's *spine* — they
break specific load-bearing sentences that must be corrected before the wave lands.

## REFUTATIONS (specific, source/live-grounded)

### R1 — [LANDING-BLOCKER] §4's cross-engine color claim is SELF-CONTRADICTORY and the real parity risk is OKLab-on-GPU, not "sRGB throughout"
§4 asserts: *"sRGB color-interp throughout (no oklab-on-GPU mixing surprise … the palette
bakes to linear-sRGB in the bridge, mixed in OKLab in-shader via the shared `procedural-color`
chunk)."* That sentence claims sRGB-only AND OKLab-mixed in the same breath. The actual
shader (`dot-matrix.wgsl.ts` L79–90, `samplePaletteLin`) does `mix(labA, labB, f)` in **OKLab**
and `oklabToLinearSrgb()` **on-GPU**. OKLab↔linear involves `pow`/cube-root nonlinearities —
the *exact* operation whose Metal-vs-ANGLE bit-divergence the GOLDEN's own G8 ΔE clause is
meant to police. So the cross-engine plan misstates its own risk surface: the parity fence is
NOT "light because it's sRGB" — it is **non-trivial precisely because color mixing is OKLab
on-GPU**, and the new `rim`/chromatic-refraction tone path (§2.3) *adds* a second OKLab-driven
read that widens the parity surface. **Hardening:** strike the "sRGB throughout" phrasing;
state the truth — the palette mix is OKLab-on-GPU through the shared `procedural-color` chunk,
the G8 paired-engine ΔE clause is the guard, and the new rim-tone read must be added to the
G8 capture (not just G1–G3). The PARITY-METAL LIVE net must capture the rim-active frame, not
only the rest/sweep frames.

### R2 — [LANDING-BLOCKER] `auroraFallbackGround` is NOT the drop-in warm-mesh ground the GOLDEN claims — it is aurora's headless-contrast software-raster, palette-coupled and static
§2.7/§4 lean the entire §3 "colourful ground" on *"reuse the SHIPPED `auroraFallbackGround.ts`
compositor-only CSS warm-mesh … a slow warm-amber→rose drift."* Source says otherwise. The
module header (`auroraFallbackGround.ts` L1–43): it is the **BB.W-AURORA-SWRASTER** CI/witness
fallback that *"mirrors the shader's STATIC (t=0) composite"* of the **aurora nuclei field**,
bakes a `data:` URI from **aurora's `oklchToLinear` palette + `nucleiField`**, and *"paints
once at mount and PARKS (no rAF)."* That means:
  1. **It is NOT a generic warm ground** — its color comes from aurora's palette/field, which
     is the blue-cyan aurora identity. Dropping it behind dot-matrix paints an aurora-blue
     field → a direct **`proof:teal-navy-purge` (hue∉[180,270]) violation** for G7, the very
     fence the GOLDEN swears it holds "by construction."
  2. **It is STATIC by design** — "a slow warm-amber→rose DRIFT" directly contradicts "paints
     once and parks." The GOLDEN promises animation the primitive deliberately does not do.
  3. Re-parameterizing it to warm + animated is a **re-author, not a reuse** — i.e. the bolt-on
     the GOLDEN claims to avoid.
  **Hardening:** drop the `auroraFallbackGround` reuse claim. Either (a) author a tiny
  *new* warm-mesh CSS ground primitive in the demo chassis (pure `radial`/`conic-gradient`
  stack, sRGB interp, compositor-only — this is what the spike's `#stage` block ACTUALLY does,
  ~6 lines), shared across the six §3 flat-page vizzes; or (b) if reusing aurora's raster,
  prove a WARM palette is injectable and that G7's purge fence passes with the actual painted
  hue. Spec must name the real primitive, not a mismatched one.

### R3 — [LANDING-BLOCKER] the de-risk spike validated the WRONG `gravityRadius` — its headline metrics do not transfer to the shipped config
The spike (`spike.html`) hard-codes `GRAV_RADIUS = 0.30`. The **shipped library default is
`gravityRadius: 0.7`** (`constants.ts` L113) — 2.3× wider. Every spike metric the GOLDEN cites
as proof (ecc ~1.7 / peak 2.17; G2 wake +0.05 / +0.11) was measured at radius 0.30. At 0.7 the
Gaussian falloff is far broader, so: (a) the `STRETCH_GAIN·vmag` term clamped at `1/√φ`
produces a much SUBTLER along-travel eccentricity (the ellipse reads rounder over a wide well);
(b) the comet-tail `exp(-behind²/radius²)` spreads ~2.3× wider → the centroid-behind projection
shrinks toward the symmetric-pool noise floor the spike itself warned about (G2 mis-reads ~0 at
the wrong tuning). **The spike does NOT de-risk the configuration that will actually ship.**
The "lands once, right" promise is unproven for radius 0.7. **Hardening:** either re-run the
spike at `gravityRadius 0.7` and re-report G1/G2 (and re-derive `STRETCH_GAIN`/`WAKE_GAIN` for
that radius), or explicitly drop the default radius toward 0.30 in §2.6's config block and gate
on the shipped value. The √φ ladder must be re-anchored to the radius the gate actually drives.

### R4 — [MEDIUM] the new `u7` lane's byte-layout description is WRONG and "off 112 is free" is false
§2.1 states `u7 : vec4<f32> off 112` and `DOT_RENDER_UNIFORM_BYTES → 208 + 4*16`. Source
(`uniformBridgeWGPU.ts` L52–67): **off 112 is the spin mat3 col0** (the rotation matrix), bg
at off 176, palette array at off 192, and `DOT_RENDER_UNIFORM_BYTES = 192 + MAX_DOT_STOPS*16`
(NOT 208-based). `U_OFF` keys are **vec4-index units** (`u5:20, u6:24`), not the byte offsets
the prose implies. The lane is NOT free at 112 — it must slot before the palette array and
shift spin/ints/bg/pal down, and the JS-side `U_OFF` indices must all increment. The "ONE
table edit, std140≡WGSL by construction" deftness claim survives in spirit (the table IS one
source of truth) but the GOLDEN's *specific offset arithmetic is fiction* and would mislead the
implementer into corrupting the spin matrix. **Hardening:** correct §2.1 to: insert `u7` after
`u6` (vec4-index 28 / byte off 112), shift spin0→128, spin1→144, spin2→160, ints→176, bg→192,
pal→208; `DOT_RENDER_UNIFORM_BYTES = 208 + MAX_DOT_STOPS*16`. Verify the instance-buffer stride
is untouched (it is — separate buffer).

### R5 — [MEDIUM] three a11y/PRM carve-outs are ASPIRATIONAL — "already wired" is false
- §5 / §2 claim `prefers-reduced-transparency` and `prefers-contrast: more` handling. **Neither
  query exists** anywhere in the dot-matrix tree or `usePointerVelocityField` (grep: zero hits).
  These are net-new code, not carves over wired behavior.
- §2.5 / §1 claim the `DockBackgroundToggle` `paused` seam is *"already wired."* `paused` exists
  as a toggle in the demo chassis (live screenshot shows it) but `DockBackgroundToggle` does not
  grep against the dot-matrix source — the wiring asserted is unverified for THIS viz.
  **Hardening:** demote these from "already wired" to explicit work items in §7's file list;
  add `prefers-contrast`/`prefers-reduced-transparency` media-query handling as named deltas
  with their own (currently absent) gate clauses, or cut them from the acceptance bar so the
  gate doesn't claim coverage it lacks. PRM `tick(0)` freeze IS real (verified in
  `usePointerVelocityField` L30–33) — keep that.

### R6 — [MINOR] the "chromatic refraction rim" is partly a re-paint of an EXISTING read — its born-RED for G-rim is weak
§2.3's rim-tone (`out.tone = rim·RIM_CHROMA`) collides with the existing
`out.tone = clamp(1.0 - facing, ...)` (wgsl L199), and in the plane branch `facing = nearness`
(L148) — so the shipped code ALREADY samples the warmer-amber stop at the well rim (tone→1 as
nearness→0). The "chromatic refraction gives the well a defined edge" is therefore *partly
already present*; the genuinely new part is only the magnify-coupled rim BAND (`smoothstep`).
The GOLDEN never acknowledges it must REPLACE the L199 assignment (a clean break per no-legacy),
and risks double-writing `out.tone`. **Hardening:** name the L199 excision explicitly; scope
the rim gate clause to the *added* magnify+band read (measurably warmer hue at the lens rim vs
the symmetric-pool baseline), not "amber rim exists" (which already passes).

### R7 — [MINOR] perf: per-dot `sin(uTime·rate + hash)` twinkle + the wake luminance term add per-instance ALU on a 1400+-dot field every frame; no perf clause in the gate
Every dot now evaluates: anisotropic ellipse (2 dots, dot products), `exp` (well) + `exp`
(wake) + `exp` (nearness) + `sin` (twinkle) + `smoothstep` (rim) per frame, vs the current
single `exp`. On the WebGL2 Safari fallback path (the default Safari render path — WebGPU is
17.4+ only) this roughly triples transcendental load in the vertex stage. The GOLDEN's gate
(G1–G10) has **no frame-budget / no-regression-FPS clause** and no Safari-fallback perf capture.
The PARITY-METAL net checks paint ΔE, not cost. **Hardening:** add a G11 perf-floor clause
(frame time within X% of HEAD on the WebGL2 path, mid-sweep, Safari-fallback emulation) so the
liquid-weight richness can't silently tank the low-end. Consider hoisting the twinkle `sin`
phase to a precomputed per-instance attribute if the spike-at-0.7 shows ALU pressure.

### R8 — [MINOR / watch] sphere-arm re-aim (§2.8) is under-specified and risks the globe TEARING
§2.8 re-aims the sphere well to "the same anisotropic-ellipse measure in screen space" and says
"bound it so the globe doesn't tear." The plane ellipse is volume-preserving in 2D; applied to
a depth-shaded sphere surface, a velocity-stretched screen-space pull can drag near-hemisphere
dots across the silhouette and break the shell read (`proof:viz-dotmatrix` flat-uniform bite).
No concrete bound is given — "bound it" is hand-waving. **Hardening:** specify the clamp (e.g.
gate the sphere warp by `facing` so only camera-facing dots smear, cap displacement to a
fraction of inter-dot spacing) and add a sphere-silhouette-integrity clause to G8/G10.
