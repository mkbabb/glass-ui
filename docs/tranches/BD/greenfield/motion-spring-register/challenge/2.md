# CHALLENGE #2 — CROSS-ENGINE / SAFARI / PERF lens

Adversarial review of `GOLDEN.md` (the MOTION VOCABULARY: spring presets, `--ease-cartoon-punch`,
`--motion-weight` scalar, `linear()` curves, spring-vs-ease + driver-vs-observer rules,
velocity-coupled `useLiquidFlex` squish). Default = REFUTED; keep only what survives the lens.

Live work: ran `golden/spike.html` in Chrome via devtools-MCP (`__SPIKE__.allPass === true`, dock
cap 1.14, observer cap 1.0, punch peak 1.22, neg leg −0.038 — all the spike claims reproduce). Then
source-traced the metaball/drawer/useLiquidFlex plumbing and **measured the velocity→weight write
cost live** on a 400-consumer inheriting subtree. Two refutations LAND; the rest survive.

---

## R1 (LANDS, the headline) — the §2c velocity→weight write is NOT "compositor-only / Safari-perfect"; it is a per-frame style-recalc storm over the driver's whole inheriting subtree

§2c + §8 assert the velocity→weight boost is "compositor-only, Safari-perfect — the painted channels
are `transform`/`--stretch` only." **That conflates the PAINTED channel with the TRIGGER channel.**
The boost is delivered by **writing `--motion-weight` (a registered, `inherits: true` `@property`)
on the driving element every animation frame.** Mutating an inherited custom property invalidates
**style/computed-style on every descendant that consumes it** (directly or transitively) — that is a
main-thread style-recalc pass, NOT a compositor-thread transform update. `transform` being the only
*painted* output does not exempt the *write* from triggering subtree recalc.

**Measured live (Chrome, devtools-MCP, rAF-paced, NO synchronous forced flush — the real animation
condition), 400 transform-only descendants reading `calc(1 + k·var(--motion-weight))`:**

| condition | p50 frame Δ | frames > 20ms |
|---|---|---|
| idle (no var write) | **18.1 ms** | 42 / 85 |
| mutating the inherited var each frame | **41.7 ms** | **85 / 85** |

The inherited-var write **more than doubles** p50 frame time and pushes EVERY frame over the 20ms
budget — a visible jank storm, precisely on the "loud / fast / celebration" moments §2c is meant to
make feel BEST. This is worse in Safari/WebKit, whose style-recalc + `@property` substitution path is
historically slower than Blink's, and which lacks Blink's custom-property-invalidation fast-paths.
The golden's "Safari-perfect by construction" (§8) is unproven and, on this mechanism, false.

The cost scales with the SIZE of the driver's inheriting subtree. `inherits: true` is sold in §2a as
"the whole mechanism… zero prop-drilling" — but it is *also* the whole liability: writing the var on
`.dock` recalcs the ENTIRE dock subtree (every chip, label, icon, tooltip, badge), not just the one
morphing element. A long dock / a sheet with deep content / a reordering list is exactly the
worst-case subtree. The spike NEVER tested this — `spike.html` writes the var ONCE at load and reads
static caps; it has zero per-frame-write, zero subtree, zero frame-budget assertion. **§7's "boldest
mechanism de-risked" is false for the boldest mechanism's actual cost.**

### Hardening (R1)
1. **Do NOT write `--motion-weight` per-frame on a broad inheriting ancestor.** Keep `--motion-weight`
   as the *rest-state, set-once-at-rest* governor it is described as in §1 ("a surface picks
   `--motion-weight` once at rest"). The velocity term is a SEPARATE, NON-inherited, element-local
   channel.
2. Re-home the live velocity term to a **`inherits: false` per-element `@property`** (e.g.
   `--flex-vel`, the specular-cohort idiom in `property-regs.css` — those are explicitly
   `inherits: false`). Write `--flex-vel` only on the **single morphing element** (the one already
   binding `stretchStyle`), so its mutation invalidates ONE element, never a subtree. The cap calc
   becomes `1 + k · (var(--motion-weight) + (1 − var(--motion-weight)) · var(--flex-vel, 0))`,
   evaluated at that one element. Morph-more-on-move survives; the subtree-recalc storm does not.
3. Add a **born-RED frame-budget gate** to `proof:motion-weight-universal`: drive a fast morph on a
   ≥20-descendant driver and assert p50 rAF Δ < 20ms AND no monotonic jank vs idle. The current gate
   (§9) asserts only token VALUES (`weight==0.618`, `cap round-trips`) and the curve SHAPE — it has
   ZERO performance assertion, so it would green a janky build. The boldest move ships ungated.
4. Confirm in **WebKit specifically** (the lens's mandate): run the same rAF probe in Safari/Playwright-WebKit, not Chrome only. "Cross-engine perfect" with a Chrome-only spike is a claim, not a finding.

## R2 (LANDS) — the metaball "reads `--motion-weight` as a uniform" is a hand-waved, dual-engine, JS-bridge change the file-list elides; it is closer to a bolt-on than a one-line union

§5 + §8 + §6 ("the metaball shader (weight uniform)") claim coupling the blob squish to the scalar is
trivial — "the shader reads `--motion-weight` as a uniform, not a filter change… untouched." Source
says otherwise:

- The squash is `sa = 1.0 + tanh(speed·1.6)·uStretch`, where `speed = length(uVelocity)` is an
  **in-shader velocity vector** and `uStretch` is an **amplitude uploaded from JS** (`cInt.stretch`
  via `gl.uniform1f(U.uStretch, …)` in `uploadBlobUniforms.ts`, and packed into `s6.w` in the WGPU
  bridge `uniformBridgeWGPU.ts`). **Nothing reads any CSS custom property into this uniform today.**
- A shader uniform is NOT a CSS var. To "couple `uStretch` to `--motion-weight`" you must add **new
  JS plumbing**: `getComputedStyle(el).getPropertyValue('--motion-weight')` per frame (the same
  forced-recalc read the goo component already pays elsewhere) → multiply into `cInt.stretch` →
  re-upload. That read is itself a style-recalc trigger (R1's cousin) on the goo host each frame.
- There are **TWO shader paths**, both confirmed: WGSL (`metaball.wgsl.ts`, `sa = 1.0 + tanh(speed*1.6)*uStretch`)
  AND GLSL (`metaball.frag.ts`, identical form) — Chrome can take WebGPU; **Safari/WebKit takes the
  WebGL/GLSL path**. So "Safari-perfect, untouched" must land the weight coupling in BOTH upload
  bridges (`uploadBlobUniforms.ts` GL + `uniformBridgeWGPU.ts` WGPU) with byte-identical results, or
  the blob morphs-more-on-move in Chrome and not Safari — a cross-engine DIVERGENCE, the exact precept
  the lens guards (MEATBALLING must be PERFECT in Chrome *and* Safari).

This is not "untouched / a uniform." It is a two-bridge JS change with a per-frame CSS-var read on the
goo host. The golden under-books it as a parenthetical.

### Hardening (R2)
- Either **EXCLUDE the metaball from the weight coupling** for this golden (it already has its own
  volume-preserving `tanh(speed)` velocity register — it is the ONE surface that "morphs more on move"
  WITHOUT the scalar, in-shader, on the GPU, cross-engine, with zero style-recalc cost; it does not
  NEED the scalar). State plainly: blob squish stays in-shader, scalar-independent, and the §5 table
  row changes from "KEEP — shader reads `--motion-weight` uniform" to "KEEP — already velocity-coupled
  in-shader, no scalar wiring."
- OR, if coupling is truly wanted, BOOK it honestly: a `--motion-weight`→`uStretch` multiply landed in
  **both** `uploadBlobUniforms.ts` and `uniformBridgeWGPU.ts`, one CSS-var read per frame on the goo
  host (NOT per blob), and a cross-engine parity assertion (WGSL == GLSL squash at matched weight) in
  the proof. The current file-list ("the metaball shader (weight uniform)") names neither bridge.

## R3 (PARTIAL) — `useLiquidFlex` "writes ONE extra computed-style key, no law change, no primitive change" (§2c/§10) misstates what the primitive is

The module is explicitly "DELIBERATELY framework-light — it owns NO spring, NO rAF, **NO element**…
a PURE projection." It returns `stretchStyle`/`sizeStyle` style OBJECTS; the consumer binds them. It
**writes nothing to the DOM.** §2c's "it writes ONE extra computed-style key on the driving element"
and §6's "useLiquidFlex.ts (the getter rewire + the ONE velocity→weight computed key — no law change)"
therefore DO mutate the primitive's contract: a pure projection becomes an element-writer (it must now
receive/hold `el`, or emit a third style object the consumer is obligated to bind on the *ancestor*).
That is a real API/contract change across the 29 consumers, not "no primitive change." Also: the
M5-determinism doctrine (squish is a pure function of the drive derivative, "NOT a live wall-clock nor
a live pointer speed") is in tension with a velocity term that feeds back into an inherited cascade
var — the reproducibility clause the morph-showcase gate asserts needs re-checking once weight is
live-coupled.

### Hardening (R3)
- Keep `useLiquidFlex` PURE: it returns a THIRD style object `velStyle = { '--flex-vel': … }` (the
  saturating term it already computes). The CONSUMER binds `--flex-vel` on its own morphing element
  (per R1's `inherits:false` home), preserving "owns no element." Reword §2c/§10 to "emits one extra
  style object; the consumer binds it" — not "writes a key on the driving element."
- Re-assert M5: `--flex-vel` is a pure function of the same `travel` derivative, so determinism holds;
  state it, and keep the gate.

## What SURVIVES the lens (refined, not refuted)

- **§2b site-local cap derivation** — the spike's load-bearing correction is CORRECT and reproduced
  live (observer cap = 1.0 at weight 0; dock = 1.14 at rest; the `:root`-calc-token failure mode is
  real). This is the golden's strongest, most honest move. KEEP verbatim.
- **`--ease-cartoon-punch` as a raw `linear()`** — negative leg (−0.038) + 1.22 peak reproduce live;
  `linear()` is WebKit-Baseline-safe, no `-webkit` prefix, transform/opacity only. The closed-union
  argument (not a `SPRING_PRESETS` row, not a `MotionCurveKind`) is sound — `MotionCurveKind` IS a
  closed `spring|bezier` union, a shaped linear() with a negative leg is neither. KEEP. Caveat: verify
  the negative leg doesn't NaN-clamp on an older WebKit `linear()` parser (test on Safari 17.2, the
  claimed floor).
- **Born-RED-ness** — confirmed: `grep` for `motion-weight` across `src/` and `docs/precepts/` returns
  NOTHING; the token genuinely does not exist. Both new gates are legitimately born RED.
- **No-fork discipline** — `--ui-scale` IS a typed `inherits:true` `@property` with the documented
  malformed-override-clamps fail-safe; reusing that idiom is a true union, not a parallel pattern.
  The 29-consumer count verifies. No second spring family, no `MOTION_CURVES` extension. KEEP.
- **PRM carve** — `:root{--motion-weight:0}` collapsing all caps to 1.0 reproduces live (spike obs
  probe). Belt-and-suspenders punch re-alias is fine. KEEP. (But: PRM lands the var on `:root`, which
  is fine BECAUSE it is a one-time write, not per-frame — the very discipline R1 demands everywhere.)

## VERDICT

**SURVIVES with one load-bearing hardening required.** The architecture (triangle + centroid scalar +
site-local caps + raw cartoon-punch) is sound and the §2b correction is genuinely good. But the
**single boldest, headline mechanism — §2c "velocity→weight, universal via one scalar, compositor-only,
Safari-perfect" — is REFUTED as written**: per-frame mutation of an inherited `@property` is a
measured (18→42ms p50, all frames blown) subtree style-recalc storm, not a compositor update, and the
spike never tested it. Move the live velocity term to a NON-inherited element-local `--flex-vel`
(R1/R3) and the golden survives intact; ship it on the inherited `--motion-weight` and the loudest
moments jank hardest in the engine the lens is sworn to protect. The metaball "uniform" claim (R2) is a
dual-bridge bolt-on that must be excluded or honestly booked.

**Top refutation:** §2c/§8's "compositor-only, Safari-perfect" velocity→weight boost — writing the
inherited `--motion-weight` per frame triggers full-subtree style recalc (measured: p50 18→42ms,
85/85 frames > 20ms at 400 consumers), the opposite of compositor-only; the spike never exercised the
per-frame write.

**Hardening (one-liner):** deliver the live velocity term via a NON-inherited, element-local
`@property --flex-vel` written only on the single morphing element (rest `--motion-weight` stays the
inherited governor, set once), and add a born-RED rAF frame-budget gate run in WebKit, not Chrome only.
