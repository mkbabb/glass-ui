## REFUTATION 2 (integration honesty) — §2b mis-describes the live consumption path: the dock/tab caps are read by JS GETTERS off the ROOT, not "inlined as pure-CSS calc on their own element"

§2b's "Two consumption paths" splits the world into (1) "Pure-CSS squish sites inline the calc on
their own element" — naming `#dock` and tabs — and (2) the `useLiquidFlex` getter path. **Path (1) as
described does not exist for dock or tabs.** Source:

- `useDockOrientationMorph.ts:98-105` — the cap is `maxStretchOf()`, a JS getter that reads
  `--dock-morph-max-stretch` off **`rootEl.value`** (the dock root), passed into `useLiquidFlex`.
- `useTabIndicator.ts:237` + `useTabDragMorph.ts:70` — same shape: `getComputedStyle(...)` reads
  `--tab-indicator-max-stretch`, JS.

There is NO element that paints `scale: calc(1 + var(--dock-morph-stretch-k) * var(--motion-weight))`
in pure CSS today — the `#dock` "pure-CSS probe" the golden cites is the SPIKE's synthetic box, not a
shipped surface. So §2b's path-(1) is a description of the throwaway spike, presented as a shipped
consumption category. Every real dock/tab cap is path-(2) (JS getter).

This matters for fidelity because the velocity→weight coupling (§2c) writes `--motion-weight` onto
"the driving element," but the dock getter reads its cap inputs off **`rootEl`** (a possibly-different
ancestor). If `useLiquidFlex` writes the velocity-`--motion-weight` on its own morphing element while
the getter resolves `k` and `w` off `rootEl`, the live weight boost is read from the WRONG node and
the "morph MORE on move" coupling silently no-ops on the dock — the headline mandate, dead on the
most-visible surface. The golden's §2b getter snippet reads off `el.value` (the morphing element), but
the EXISTING dock getter reads off `rootEl.value` — the golden never reconciles which element owns the
weight, and the two disagree.

**Hardening:** Rewrite §2b to state the TRUTH: dock/tab caps are JS-getter-consumed (cite
`useDockOrientationMorph.ts:98`, `useTabIndicator.ts:237`). Delete the fictional "pure-CSS inline
calc" path-(1) (or scope it explicitly to FUTURE pure-CSS surfaces + the spike, clearly labeled
non-shipped). MOST IMPORTANTLY: specify the WEIGHT-OWNERSHIP element unambiguously — the §2c velocity
write and the §2b cap getter MUST read/write the SAME node (resolve both off `rootEl` for the dock, or
move both to the morphing element), and add a gate asserting a fast dock morph reads a transient
weight > 0.7 AT THE GETTER (proving the coupling is wired end-to-end, not just spike-simulated).
