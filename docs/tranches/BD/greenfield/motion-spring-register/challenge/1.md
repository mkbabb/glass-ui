# CHALLENGE 1 — CORRECTNESS / DEFT-INTEGRATION / KISS lens

Adversary #1 verdict on `GOLDEN.md` (the canonical MOTION VOCABULARY). Default REFUTED.
Source-verified against live `src/`. The golden SURVIVES the core idea but its single
boldest mechanism (§2c) is mis-attributed to the wrong layer and is, as written, a
bolt-on the primitive cannot carry — plus three secondary integration gaps.

---

## R1 (TOP REFUTATION) — §2c is a primitive-contract VIOLATION, not "no new engine, the primitive writes it"

The golden's headline move (§2c, "THE BOLDEST MOVE"): *"`useLiquidFlex` already computes
the saturating velocity term `tanh(|ṫ|·k)`. It writes ONE extra computed-style key on the
driving element — `--motion-weight: …`. … Every one of the 29 consumers inherits this the
instant the primitive writes it."* §9 repeats it: *"`useLiquidFlex` … writes the §2c
velocity→weight boost (the one computed key present)."* The acceptance bar (§9 item 3 and
the `proof:motion-weight-universal` assertion) literally asserts *"`useLiquidFlex` … writes
the §2c velocity→weight boost."*

This is FALSE to the primitive's design, and the source proves it:

- `useLiquidFlex.ts` is **DELIBERATELY element-less**. Module header line 18: *"It is a PURE
  projection … no spring, no rAF, no element."* Line 133: *"owns NO spring, NO rAF, NO
  element."* The function takes no `el`/`ref`, holds no DOM node, and **never calls
  `getComputedStyle` or `setProperty`** (grep: zero hits in the file). It returns reactive
  `computed` style OBJECTS (`stretchStyle = { "--stretch": "1.04" }`); the CONSUMER binds them.
- Every actual DOM write lives in the CONSUMER, not the primitive:
  - tab indicator: `el.style.setProperty("--stretch", …)` + `getComputedStyle(el)` at
    `useTabIndicator.ts:237`;
  - dock morph: `r.style.setProperty("--stretch", …)` + `getComputedStyle(r)` at
    `useDockOrientationMorph.ts:144` / `:100`.
- Therefore the §2c "write `--motion-weight` back onto the driving element" CANNOT be a
  one-line addition inside `useLiquidFlex`. It has to be hand-added to **each element-owning
  consumer** (the ones that actually hold a DOM node and already do `setProperty`). By the
  source that is ~3-5 sites (tabs, dock-orientation, dock-fission, drag-morph if it grows an
  element, liquidMorph), NOT "the primitive writes it once and 29 inherit."

Why this is fatal as written: §6's no-fork ledger and §10 claim "no law change, just one
extra computed key in the primitive." But adding a `getComputedStyle(el)` read + a
`setProperty('--motion-weight', …)` write INTO `useLiquidFlex` would **break its load-bearing
invariant** (element-less, M5-deterministic, "no live wall-clock nor live pointer speed").
The golden has either (a) to violate the primitive's purity (a real engine change — exactly
the "no new engine" claim it makes), or (b) to scatter the velocity→weight write across N
consumer call-sites (a bolt-on repeated N times — the opposite of the "one scalar, 29
inherit" universality it sells). Both contradict the golden's own §10 discipline. **The
mechanism is real and good; its HOME is mis-specified, and the universality math collapses
once you place the write where the source forces it.**

### HARDENING R1
Re-spec §2c honestly as a **consumer-side write through a tiny shared helper**, keeping the
primitive pure:
- add `writeVelocityWeight(el, vel)` to `composables/motion/core/` (the DRY home) that does
  the single `el.style.setProperty('--motion-weight', String(0.618 + 0.382 * vel))`;
- each element-owning liquid consumer (tabs, dock-orientation, dock-fission, drawer-squish)
  calls it in the SAME block where it already writes `--stretch` (one added line per
  existing write-site — honest, auditable, no primitive-purity break);
- restate §9 / the proof: assert the write happens **at each liquid write-site** (grep the
  N call-sites), NOT "`useLiquidFlex` writes it"; drop "29 consumers inherit the instant the
  primitive writes it" (false — only DOM-owning descendants of the writing element inherit,
  and the primitive writes nothing).

## R2 — the metaball "reads `--motion-weight` as a uniform" is JS plumbing the golden calls "untouched"

§5 and §8: *"the shader reads `--motion-weight` as a uniform"*, and §8 *"The blob↔meatball
merge is untouched (motion-only golden)."* These contradict each other. A GLSL/WGSL
**uniform is a JS-bound value**, not a CSS-cascade read — the shader physically cannot read a
CSS custom property. Source confirms `metaball-uniforms.glsl.ts` declares `uStretch`,
`uPointer*`, etc., all set from JS. Wiring `--motion-weight` in requires: a new
`uMotionWeight` uniform decl + a JS `getComputedStyle(canvasEl).getPropertyValue('--motion-
weight')` read each frame + a `gl.uniform1f`/WGSL buffer write in the render loop + threading
it into `sa = 1 + tanh(speed·k)·uStretch·uMotionWeight`. That is a real, non-trivial change
to the render pipeline — not "untouched."

### HARDENING R2
Either (a) **scope the metaball OUT of the W-MOTION-WEIGHT wave** (the blob already has its
own `tanh(speed·k)` velocity coupling — leave it, honoring §10 "refine what is weak, reinvent
only what is broken"; it isn't broken), and delete the "shader reads the uniform" line; or
(b) book it as an EXPLICIT sub-wave `W-MOTION-WEIGHT-BLOB` that lands the `uMotionWeight`
uniform + per-frame CSS-var read + the render-loop write, and stop calling the merge
"untouched." Pick one; the current text claims both.

## R3 — the 1.14 / 1.08 cap DRY hazard the k-derivation silently inherits (overfit/hardcoded)

The golden derives `--dock-morph-stretch-k = (1.14−1)/0.618 = 0.2265372` and FREEZES it as a
hardcoded `:root` literal (§2b). But the live cap appears in TWO places with DIFFERENT
values: `density.css:69` `--dock-morph-max-stretch: 1.14` (the real token) and
`useDockOrientationMorph.ts:92,95,100` whose comment + fallback both say **`1.08`** (stale —
"density.css default 1.08" is wrong; it's 1.14). The golden's `k` constant hardcodes 1.14 a
THIRD time, as a magic decimal with the math in a comment. So the shipped cap now lives in:
the token, a stale JS comment+fallback, and a frozen `k` literal — three copies, one already
drifted. This is precisely the DRY/overfit failure MEMORY/overfitting-audit forbids: a
re-tune of the dock cap (a likely future move, the golden itself just lifted 1.08→1.14)
would have to be reverse-solved back through `k` by hand or the byte-identical fence breaks
silently.

### HARDENING R3
- Fix the stale `useDockOrientationMorph.ts` fallback/comment from `1.08` to `1.14` as part
  of this wave (it's a live drift the golden's audit missed).
- Do NOT freeze `k` as a magic literal. Derive it once: keep the cap token as the SoT and
  compute `k` at build/registration time, OR (cleaner) invert §2b so the SITE-LOCAL calc reads
  the EXISTING cap token directly and divides:
  `scale: calc(1 + (var(--dock-morph-max-stretch) - 1) * (var(--motion-weight) / 0.618))`.
  This keeps the cap-at-rest byte-identical AND collapses to 1.0 at weight 0 (the (w/0.618)
  factor → 0), **with ZERO new magic constant** — the cap token stays the single source. The
  golden's separate `--*-stretch-k` cohort is then deletable: pure DRY win, fewer tokens.

## R4 — born-RED is real for the tokens, but two acceptance items are NOT born-RED

Verified: `--motion-weight` and `--ease-cartoon-punch` are absent from all of `src/`
(grep: zero hits) — the token-existence gates (§9 items 1, 5) are genuinely born-RED. GOOD.
But:
- §9 item 6 / `W-MOTION-DOC-SYNC`: `--glass-reveal-enter-scale` re-home. Source shows it
  ALREADY exists at `reveal.css:52` as `--glass-reveal-enter-scale: 0.88` (a real declaration,
  not only a `var(...,0.88)` fallback as §0/§6 claim — the fallback is at `:85`). So "re-home
  from recipe-fallback to `:root`" is half-RED: the token IS declared (just not on `:root`).
  The gate must assert the `:root` HOME specifically, else a grep for the token name passes
  GREEN against the existing `reveal.css:52` decl and the wave looks done before it starts.
- §9 item 2's "every weight-coupled cap evaluates to shipped rest value": today there are
  ZERO weight-coupled caps, so a naive "all weight-coupled caps == shipped" gate is
  **vacuously GREEN** (∀ over empty set). Born-RED requires the gate assert *at least one*
  cap is weight-coupled AND correct — otherwise it passes on the empty pre-state.

### HARDENING R4
- `proof:design-md-current` must assert `--glass-reveal-enter-scale` resolves on
  `getComputedStyle(:root)` (the HOME), not merely that the name exists in the cascade.
- `proof:motion-weight-universal` must assert `count(weight-coupled caps) ≥ 1` (a positive
  existence clause) so the cap-fence is not vacuously true on the empty pre-state.

## R5 — KISS/idiom nits (survivable, but tighten)

- **`--ease-cartoon-punch` PRM redundancy is admitted contrivance.** §3 calls the
  weight=0 + alias-to-`--ease-standard` pair "belt-and-suspenders." Two PRM mechanisms for
  one outcome is anti-KISS. Since the curve's *amplitude* is weight-scaled (§3) and weight→0
  under PRM already kills the visible punch, the alias is redundant UNLESS a consumer uses
  `--ease-cartoon-punch` on a NON-weight-scaled leg. If that case is real, name it; if not,
  drop the alias and keep the one scalar. Don't ship two carves "to be safe."
- **`linear()` cartoon curve is hand-tuned magic with no JS twin and no regen story.** §3
  hand-authors a 13-stop `linear()`. Fine for one token, but the golden's own §6 says the
  generator owns `(response,ζ)`. A future re-tune of the punch shape is a hand-edit of 13
  magic decimals with no gate on monotonic-launch / single-peak shape. ADD a shape-sanity
  clause to `proof:cartoon-punch` beyond "has a neg leg + peak>1.10": assert exactly one
  sign change before the peak and a monotone settle after (so a fat-fingered stop reds).
- **Driver-vs-observer as a scoped var is elegant but UNGUARDED.** §2a pins observers to
  weight 0 via a local override on `<CarouselContent>` / `[data-reorder]`. There is no gate
  that these selectors actually carry the override — a renamed component silently un-pins and
  the observer carousel squishes (the exact bug §2b's spike caught at the cap layer). Add a
  `proof` assert that the known observer roots resolve `--motion-weight: 0`.

## A11Y / PRM — PASSES, with one caveat

§2d's single `@media (prefers-reduced-motion: reduce){ :root{ --motion-weight:0 } }` is
genuinely elegant and the spike proves caps collapse to 1.0. The springs keep their own
`respectReducedMotion` endpoint-snap. CAVEAT: weight=0 zeroes the GOO but the
`--ease-cartoon-punch` curve still has a negative anticipation leg — IF any consumer drives a
NON-amplitude property (e.g. opacity timing) through that ease under PRM, the dip survives
unless the §3 alias fires. This is exactly why R5's "drop the redundant alias" must FIRST
confirm no non-weight-scaled `--ease-cartoon-punch` consumer exists. Keep the alias OR prove
the carve; don't leave it ambiguous.

## CROSS-ENGINE — no live prototype to test (the spike is headless DOM, not a paint)

The golden claims "live-verified in Chrome, both modes." But `golden/spike.html` is a
**headless DOM measurement** (`getComputedStyle` width math + a simulated tanh in JS) — it
proves the CASCADE ARITHMETIC and the `@property` resolution, which is real and valuable. It
does NOT prove a single PAINTED frame, a Safari render, or a "motion feel" in either mode.
The §7 table's "PASS" rows are all numeric assertions, zero of them a screenshot of motion.
Per the live-verify-capture lesson, "live-verified in Chrome both modes" is **inflated** — it
is "cascade-arithmetic-verified, headless, Chrome-only." The cross-engine §8 reasoning
(typed `<number>` Baseline, transform/opacity-only, no `backdrop-filter:url`) is SOUND by
construction, but unproven by paint. No refutation of the cross-engine SAFETY — only of the
"live-verified" CLAIM strength.

### HARDENING (cross-engine)
Downgrade §7's claim to "headless cascade-arithmetic de-risk (Chrome)"; book the actual
both-modes paint verification (dock morph, drawer fling, cartoon-punch one-shot) as a gate
DELIVERABLE of the build waves with a captured screenshot delta, not a pre-claimed PASS.

## SURVIVES?

**YES — the golden's spine survives** (the triangle/centroid framing, `1/φ` rest, the §2b
spike correction that site-local cap derivation is mandatory, the typed-`@property` idiom
reuse, the one-line PRM carve, the cartoon-punch-as-raw-`linear()` no-fork). The core idea is
fit and deftly conceived. But its **single headline mechanism (§2c) is mis-homed** — it
cannot live in the element-less primitive as written, so the "one write, 29 inherit"
universality is false and must be respecified as a consumer-side shared-helper write. With
R1 corrected (the load-bearing one) plus R2-R4's integration honesties, it is buildable and
deft. Without R1, the build will either break `useLiquidFlex`'s purity or scatter a bolt-on
across N sites while the doc claims neither.

**Top refutation:** §2c says `useLiquidFlex` writes the velocity→weight key and "29 consumers
inherit the instant the primitive writes it" — but `useLiquidFlex` is deliberately element-less
(no DOM node, no `getComputedStyle`/`setProperty`; lines 18, 133), so it CANNOT write to an
element; the write must move into each element-owning consumer (a shared helper), and the
"29 inherit from one primitive write" universality is false as stated.
