## What I confirmed live (the parts that DO survive)

Spike `getComputedStyle` (Chrome, file://), rest + pressed, both modes:

- **INK is chromatic, not gray.** `--cartoon-ink-lead` → `oklab(0.216 0.039 0.058 / 0.32)`,
  raw ink `oklch(0.216 0.07 55.98)`. Chroma ≈0.07 > the G1 0.05 floor; lead α 0.32 > 0.28; lead+mid
  blur 0px. G1 mechanism holds. The `max(c,0.07)` floor + `in oklab` mix are correct and
  genuinely cure the landed `color-mix(in srgb … 12%)` gray smudge.
- **PRESS geometry is correct at the endpoints.** Steady press: host `scale 0.96`, `translate -3px
  -3px` (body lifts up-left); `::before` `translate +3.72px +3.72px`, `scale 1.1116` (cast travels
  down-right + spreads). The gap punches open exactly as specified. Confirmed in a dark-mode capture
  (`challenge/pressed-light.png` — toggled dark): a clean warm-dark ink gap, never white, never gray.
- **Cross-engine surface is genuinely the safest in the tranche.** No `backdrop-filter`, no
  `filter:url()`, no metaball, no `color-interpolation-filters`, no SVG goo. Opaque ink +
  `translate`/`scale` longhands + `box-shadow` on a pseudo + `oklch(from)` + `color-mix(in oklab)` +
  `@property <length>` + `linear()` — every primitive is Safari 16.4+/17.2+ Baseline with a stated
  `@supports` floor. The naive-ellipsoid / WebKit-transmissive attack surface is **empty** here —
  this register simply never touches it. That part of the lens finds nothing.
- **`@property inherits:true`** has src precedent (dock.css, glass.css, property-regs.css) — not a
  new risk.

So the *physics* survives. The refutations are about INTEGRATION HONESTY and a couple of overfit
asserts.

## REFUTATION 1 (lands — the headline "ZERO new composable" is false for the drag leg)

**§4d / §10 claim:** "Reuse `usePointerVelocityField` … to write `--cartoon-cast-dx/dy`,
tanh-capped, rAF-coalesced … cleared to 0 on pointerup … ZERO new composable."

**Refuted by the composable's actual contract** (`src/composables/motion/usePointerVelocityField.ts`):
it is a **renderer-driven physics field**, NOT a CSS-var writer. It:
- exposes `velocity`/`acceleration`/`position` as Vue **Refs** — there is NO `setProperty`, NO
  target element, NO `--*-dx/dy` write anywhere in it;
- has **NO own rAF** — the docstring is explicit: *"NO own rAF — the renderer owns the loop"*; the
  consumer must call `tick(deltaMs)` from inside an existing frame callback (it's built for a
  **canvas/WebGPU viz** that already owns a loop);
- does no tanh-cap, no `pointerup`-clear, no `--motion-weight` scale.

A plain `<Card surface="cartoon" data-cartoon-track>` has **no renderer and no rAF loop**. To get a
CSS cast out of this you must stand up your own rAF, call `tick(delta)` per frame, read
`velocity.value`, tanh-cap, scale by `--motion-weight`, `el.style.setProperty('--cartoon-cast-dx',…)`,
and clear on `pointerup`/offscreen. **That glue IS a new composable** (call it `useCartoonCast`) —
it just wears `usePointerVelocityField` as an inner primitive. The "ZERO new composable" for the
drag leg is an overclaim; the GOLDEN smuggled an entire DOM-side rAF→CSS bridge into the word
"reuse."

**Hardening:** Either (a) drop the drag-track leg from the golden core and label it explicitly
"future, requires a thin `useCartoonCast` DOM bridge over `usePointerVelocityField` (a new
composable)"; OR (b) own it honestly: spec `useCartoonCast(el, { weight })` as the bridge, state it
mints one shared rAF, `setProperty`s the tanh-capped `--cartoon-cast-dx/dy`, clears on pointerup,
pauses offscreen via `IntersectionObserver`, PRM-zeroes. Do NOT call this "zero new composable." The
press/hover path (pure CSS + `useLiquidPress`) genuinely IS zero-new — keep that claim, scope it to
the press leg only.

## REFUTATION 2 (lands — the press wiring does not "just pass a pressVar")

**§4c claim:** "a `<Card surface="cartoon" pressable>` passes `pressVar: "--cartoon-press-t"` …
ZERO new composable."

**Refuted by `Card.vue:227`:** the press driver is constructed ONCE, unconditionally, with a
**hardcoded** `pressVar: "--card-press-t"`. It is not surface-conditional. The `.cartoon-surface`
CSS the GOLDEN authors reads `--cartoon-press-t` — **a variable Card never writes** → the entire
`::before` cast-travel scalar (`calc(… * var(--cartoon-press-t))`) sits at 0 forever; the JS press
path is DEAD on arrival. "Just passes a pressVar" is false: `useLiquidPress` writes ONE var per
construction, and Card hardwired it.

**Hardening (the DRY fix, simpler than the GOLDEN's):** Do NOT introduce a second press var. Have
`.cartoon-surface` read the **already-written** `--card-press-t` (the var Card's existing
`useLiquidPress` already drives for every `pressable` card) — one press clock, no Card.vue change,
truly zero-new. If a distinct name is wanted for clarity, alias it in CSS:
`--cartoon-press-t: var(--card-press-t)` on `.cartoon-surface`. The GOLDEN's `--cartoon-press-t`
spelling forces a Card.vue rewrite it claims not to need.

## REFUTATION 3 (partial — the "upper-left key light → down-RIGHT is coherent" is overfit)

**§3 claim:** cast DOWN-RIGHT is "coherent with the upper-left key light the rest of the system
paints from."

**The house light is NOT upper-left.** `--glass-highlight`/`--glass-specular` resolve to
`inset 0 1.5px 0 0 …` — a **top-edge** catch-light (light from straight ABOVE, x-offset 0), and the
moving specular `::before` (material.css) tracks the pointer, it has no fixed corner. There is no
"upper-left key light" in src/ to be coherent with. Worse: the **landed** cartoon tokens cast
DOWN-**LEFT** (`-3/-4/-6px` x). The GOLDEN silently REVERSES the established cast direction and
justifies it with a key-light that doesn't exist. That's a precept-claim built on an overfit
reference, and a direction flip dressed as a "re-point."

**Hardening:** Drop the "upper-left key light" justification (it's fiction). Justify down-right on
its own terms (the dominant 1940s-cel convention is light-from-upper-left → cast lower-right, which
is a defensible *external* canon) OR honor the existing down-LEFT house cast and keep continuity.
Either way, state it as a deliberate directional DECISION with a real basis, not a false appeal to a
nonexistent house key-light. Add a born-RED assert that pins the chosen sign so a future drift is
caught.

## REFUTATION 4 (minor — redundant double-paint at rest; a small perf nit, not fatal)

At rest the **host** `box-shadow` AND the `::before` `box-shadow` are byte-identical
(`oklab(… /0.32) 3px 3px 0, … 5px 5px 0, … 7px 7px 1px`), with `::before` at `inset:0; z-index:-1`
directly behind the host. So the identical three-plane stamp is **painted twice, exactly
overlapping** at rest (and on every non-pressed frame). It doesn't visibly darken (both sit behind
the opaque card), but it is redundant raster + a second composited layer on every cartoon card
whether or not it's ever pressed — against the KISS/"smallest footprint" claim.

**Hardening:** Carry the stamp on ONLY ONE plane at rest. Either the host owns the rest stamp and
the `::before` stamp is transparent until `--cartoon-press-t > 0` (set the `::before` box-shadow via
a press-gated `color-mix`/opacity), OR the `::before` owns the cast and the host carries no
box-shadow. One ink slab, not two stacked identical ones. Add a born-RED assert: at rest exactly ONE
of {host, ::before} carries a non-`none` cartoon box-shadow.

## REFUTATION 5 (minor — born-RED honesty on G3's "follow-through")

G3 asserts the release `translate` track "must cross past target" (overshoot) to pass. But in the
spike, `--cartoon-press-t` is toggled DISCRETELY by a class — only the `translate`/`scale`
longhands transition on the punch curve; `--cartoon-press-t` itself is not `@property`-registered or
transitioned, so the `::before` `--cast-travel` (which multiplies by `--cartoon-press-t`) **jumps**
rather than easing. The follow-through the GOLDEN sells comes from the longhand transition, which is
real, but the spike does NOT exercise the `useLiquidPress`-driven continuous `--cartoon-press-t`
ramp the src/ wave will use — so G3's "spike is the executable seed" is only a seed for the longhand
leg, not the scalar-driven cast spread/travel. The overshoot assert must be checked against the
ACTUAL useLiquidPress drive, not the discrete-class spike.

**Hardening:** Make G3 explicit that the overshoot/anticipation assert runs against the
`useLiquidPress`-driven `--card-press-t` ramp in the real component (Chrome AND WebKit), not the
class-toggle spike. Register `--cartoon-press-t`/`--card-press-t` as `@property <number>` if the
cast-travel must EASE rather than snap with the spring (otherwise the `::before` travel is a step
function while the body eases — a desync the eye catches).

## Net

- Mechanism (ink / stamp / press-punch / cross-engine): **survives** — chromatic, both modes,
  Safari-safe, no transmissive/metaball attack surface, PRM-static stamp persists.
- "Deft union, ZERO new composable, just-pass-a-pressVar": **does not survive intact** — the
  drag-track leg needs a real new DOM bridge composable (R1), and the press leg needs either a
  Card.vue change or a re-point to the already-written `--card-press-t` (R2).
- Two overfit/cleanliness fixes (R3 false key-light, R4 double-paint) and a born-RED scoping fix
  (R5) harden it without re-architecting.

Apply R1+R2 honestly and the register is fit. Leave them as written and the headline claim is a
paper union over a real seam.
