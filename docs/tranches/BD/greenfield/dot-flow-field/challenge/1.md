## REFUTATION 1 (LANDS — top) — the gate is NOT actually carve-able by assertion; the EXTANT `proof:viz-dotflow` fence ACTIVELY REDS the flow kernel

The GOLDEN says (§1.2, §6) "carve the fence: `proof:viz-dotflow` applies ONLY to the `field`
evaluator." But the existing detector is **file-global, mode-blind**:

- `scripts/proof-viz-dotflow.mjs` **F1** greps the WHOLE `flow-field.compute.wgsl.ts` and pushes a
  violation if it finds `/\bpos\s*=\s*pos\s*\+\s*v\s*\*\s*dt\b/` (forward-Euler advection) OR
  `/\breseed\s*\(/` (respawn). The GOLDEN's `flow` branch lives in the SAME `.ts` file and IS
  advection + respawn. As written, F1 fires the instant the flow kernel lands.
- **F4** pushes a violation unless `flow-field.glsl.ts` exports `FLOW_FIELD_FRAG_GLSL` — a
  *fragment* fallback. The GOLDEN explicitly rejects "a fragment-LIC compromise" for a state-texture
  GPGPU ping-pong (§1.2). The two are in direct tension.

The GOLDEN flags the amendment is needed, which is honest — but it presents the carve as a prose
disposition ("AUGMENT + partially SUPERSEDE") when the actual work is a **non-trivial detector
rewrite**: F1 must become branch/mode-scoped (it currently cannot tell which WGSL function a
`pos = pos + v*dt` sits in), and F4 must stop mandating the fragment-fallback gestalt. Until that
lands, the design does not "deftly integrate" — it collides with a frozen gate. The "math fence"
reconcile is the hardest part of the union and it is the LEAST specified.

**HARDENING (1):** Before any flow code, land a concrete `proof:viz-dotflow` amendment that (a)
scopes F1's `reseed(`/`pos=pos+v*dt`/`gridOrigin(`/spring checks to ONLY the `field` branch — by
extracting the `field` evaluator into its own named WGSL function (`fn cs_field(...)`) and having
F1 grep WITHIN that function body's brace-span, not the file; (b) retires F4's
`FLOW_FIELD_FRAG_GLSL`-mandate in favor of a `FLOW_FIELD_STATE_GLSL` (GPGPU ping-pong) export
requirement, with the byte-for-byte one-math-source F3 round-trip extended to cover the advection
integrand. Make THIS amendment a born-RED wave of its own (the current source REDs the new F4
state-texture clause because no GPGPU GLSL exists yet).

## REFUTATION 2 (LANDS) — "PERFECT in Safari" rests on a Chrome-only spike; the WebKit float-RT GPGPU leg is UNTESTED, and it is exactly WebKit's historical weak spot

The binding law's gate is "paired-engine π (Chromium + WebKit)" (§4, §6.1 R6). The de-risking spike
was run **only in Chrome** (the spec itself says "Verified live in Chrome (DevTools MCP)"; I
re-ran it in Chrome, green). But the entire Safari story is:
- `RGBA32F` particle-state texture **as a render target** (the GPGPU ping-pong write target),
- `EXT_color_buffer_float` for the `RGBA16F` trail FBOs,
- float-texture filtering / `gl_PointSize` point-sprite sizing,
- `preserveDrawingBuffer` readback on the WebKit compositor.

WebKit has a long, specific history of gimping exactly this set: `RGBA32F` is frequently
**color-renderable only with `EXT_color_buffer_float`** AND historically non-renderable on some iOS
GPUs even with it; `gl_PointSize` caps and point-sprite rounding differ; `preserveDrawingBuffer`
readback timing differs. The spike proves the *Chromium* WebGL2 path — which is NOT "the Safari-real
path," it is "the fallback path, exercised in Chromium." Calling it "the Safari-real WebGL2 path"
(§0, §8) is a category error: same API surface, different implementation. The single load-bearing
cross-engine risk is the one NOT measured.

**HARDENING (2):** Run the SAME `spike.html` in a real WebKit (Safari Technology Preview or
Playwright `webkit`) and capture the four numbers + a screenshot BEFORE the GOLDEN is ratified. Add
an explicit `@supports`/runtime guard: if `RGBA32F` is not color-renderable in the live context,
fall the state texture to `RGBA16F` (half-float) with a documented precision budget, or to a
`UNSIGNED_BYTE`-packed position encoding (the spike already half-floats the *trail*; the *state*
texture is the untested 32F leg). Gate R6 must be a CAPTURED paired-engine delta artifact (per the
live-verify-capture lesson), not a projected parity.

## REFUTATION 3 (minor — overclaim) — R3 "functionally STATIC" is inflated

The GOLDEN's headline table (§0) claims `litFrac across 6 frames identical → functionally STATIC, no
flow reads.` My live 6-frame readback on the real substrate shows frameSums
`[6915, 6746, 6582, 6561, 7164, 7258]` — deltas up to 603, NOT identical. The `field` twinkle IS
animating; the viz is near-INVISIBLE (the true defect) but not frozen. The "static by construction"
framing oversells. It doesn't change the rebuild need (invisibility is the killer), but R3's born-RED
basis ("identical litFrac across 6 frames") will NOT reproduce as stated, so the gate seed is wrong.

**HARDENING (3):** Re-state R3's born-RED basis as "advection-coherence ≈ 0 / net-displacement ≈ 0"
(the lattice eases to a fixed anchor, so there is twinkle but no *coherent transport*), measured by
the optical-flow / orientation-coherence proxy the gate already proposes — NOT "identical litFrac."

## REFUTATION 4 (minor — gate-seed unreliability) — R4 chroma born-RED does not reproduce

The GOLDEN claims the current viz reads `meanChroma ≈ 0` (R4 born-RED). My live readback returned
`meanChroma 32.1` — because at `litFrac 0.0143` only ~13 of 2304 sampled pixels clear the lit
threshold, and chroma over a near-black-noise handful is statistically meaningless (it can read
anything). The R4 gate seed (`meanChroma > 18` measured over the lit set) is **unstable at low
litFrac** — it can false-PASS or false-RED on noise. The spike's own `meanChroma` sits right at the
floor (20–21), already flagged as needing tuning — so the gate margin is thin on BOTH ends.

**HARDENING (4):** Gate R4 chroma ONLY when `litFrac` exceeds a guard (e.g. measure chroma over the
lit set sized ≥ N pixels, else REPORT-not-gate), and raise the spike's `speedScale`/ramp saturation
+ corner-bloom to clear `meanChroma ≥ 24` with margin (not 18+ε) before ratifying — the spec already
concedes the 18 floor is barely cleared, which is a thin design margin for "audacious technicolor."

## BOTTOM LINE
The AURORA CURRENT design is FIT — the gestalt, the union, the KISS/DRY reuse, and the Chrome-side
de-risk are all real and verified. It SURVIVES. But it does NOT pass clean: the "carve the fence"
(Refutation 1) is the hardest and least-done part of the integration, and "PERFECT in Safari"
(Refutation 2) is asserted on a Chrome-only spike of the exact float-RT GPGPU path WebKit is known to
gimp. Harden both — a concrete mode-scoped F1/F4 amendment as its own born-RED wave, and a captured
real-WebKit spike run — before ratification. R3/R4 gate seeds need restating (3, 4).
