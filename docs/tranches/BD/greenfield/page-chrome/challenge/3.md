## TOP REFUTATION (the one real hit) — the warm-glass register paints GRAY on the default path

The GOLDEN's whole §3-COLORFUL-FIELD / BA.W-NO-GRAY claim rests on the chrome glass resolving a WARM
tint. Every recipe is `color-mix(in oklab, var(--glass-bg-floating), var(--glass-tint-source)
var(--glass-tint-strength))`. **But `--glass-tint-strength` defaults to `0%`** (verified: `glass-fx.css:123`,
`drawer.css:108`, and ladder.css:31 states verbatim "With the default `--glass-tint-strength: 0%` the mix
is a [no-op]"). At 0% strength the mix returns the BARE `--glass-bg-floating` — a neutral/gray plate. The
GOLDEN NEVER shows the wiring that lifts `--glass-tint-strength` > 0% and points `--glass-tint-source` at
the warm `categoryHue` on the StoryHeader / condensed bar / toc.

**The de-risk is a false positive here.** The spike paints warm (measured: bar `[60,47,33]` spread 27,
marker `[66,47,27]` spread 39 — warm) ONLY because `spike.html:33-34` INLINES `--glass-tint-source:
oklch(0.86 0.07 70)` + `--glass-tint-strength: 14%`. The spike fed itself the tint the real chassis does
NOT supply by default. The "de-risked LIVE, the toc marker is warm" claim does not transfer to the
library default — it proves the recipe CAN be warm if tinted, not that the GOLDEN's mechanism delivers
the tint. As specced, the chrome ships **gray** — the exact BA.W-NO-GRAY violation the GOLDEN is built to
kill. Worse, `categoryHue()` is a **JS function returning a number** consumed per-component as an inline
`--hue` binding (`compositions/hero.vue:31`); there is NO CSS path from it to `--glass-tint-source` on the
chrome surfaces, and the GOLDEN supplies none.

**Hardening (REQUIRED before EXECUTION):** the `--chrome-glass` register must EXPLICITLY set both
`--glass-tint-source: oklch(… categoryHue …)` AND `--glass-tint-strength` to a nonzero warm floor (e.g.
`var(--glass-tint-strength-aa)` or a minted `--chrome-tint-strength: 12–18%`) on `.story-hero-shrink`,
`.toc-placard`, and `.story-header-stamp`. Wire `categoryHue` → `--glass-tint-source` via the per-page
inline style the chassis already sets the category hue with (the `--hue`/IconChip path), or compute
`oklch(L C var(--hue))` in CSS. Gate C3/C7 must assert chroma ≥ 0.045 with `--glass-tint-strength` at its
RESOLVED value on the REAL page (not the spike), both modes — currently C3/C7 would PASS the spike and the
real default-path gray would slip if the gate samples a tinted fixture.

## Secondary refutations (each a fidelity hole, none fatal alone)

### R2 — the corner-AA `clip-path` reads a `--radius` the glass tiers do NOT define → may silently no-op
§2e writes `clip-path: inset(0 round var(--radius))` on `.glass-wash/quiet/resting/floating/overlay/card`,
"each tier reads its OWN corner token." But grep of `ladder.css` shows the tiers do NOT set
`border-radius` or `--radius` on themselves — the ONLY radius rule is `border-radius: inherit` (line 442,
on a pseudo). The tiers inherit radius from the consumer box. If `--radius` is UNDEFINED on a tier,
`inset(0 round var(--radius))` is an INVALID clip-path → the whole declaration DROPS → no clip → the
corner-AA src/ paint silently no-ops on every tier that doesn't happen to define `--radius`. This is the
SAME lost-mechanism class as `b538dec7`. **Hardening:** co-declare with a guaranteed fallback —
`clip-path: inset(0 round var(--radius, var(--radius-card)))` — OR derive from the resolved
`border-radius` (a `round` keyword that reads the box's own radius is not available, so an explicit token
with a fallback is mandatory). The gate C6 must assert the clip-path is PRESENT-and-VALID (computed
`clipPath !== 'none'`) on each named tier on a real page, not just count occurrences in source.

### R3 — the de-risked spike's bar OVERHANGS into the toc column (insetL/R = −24px) — the "de-risked" artifact contradicts the specced mechanism
Live-measured spike `::before`: `left: -24px; right: -24px` (the `inset: 0 -1.5rem 0`). The GOLDEN §2b
code block writes `inset: 0` and the §2b "Layout note" ADMITS the spike over-extends and hand-waves it as
"a spike-layout artifact." But the de-risk that allegedly proved the mechanism used the OVERHANGING
version — so the boldest-move claim "the bar the body scrolls FROM" was never live-validated in the
non-overhanging `inset: 0` form the spec actually ships. In a real 2-column route+toc grid, an unverified
`inset: 0` could clip short of the gutter or the bar could mis-anchor. **Hardening:** re-de-risk the
condense in the REAL chassis grid (route column + toc sibling) with `inset: 0`, captured, before claiming
the boldest move is proven. Do not carry the −1.5rem spike forward.

### R4 — `--chrome-rule = --configurator-divider` IS a `light-dark()` token — straight into the MEMORY trap the GOLDEN cites
§2c claims "plain per-mode arms (NEVER a `light-dark()` inset trap — the MEMORY light-dark lesson)" and
sets `--chrome-rule: var(--configurator-divider)`. But `--configurator-divider` is DEFINED via
`light-dark(…)` (`sizing-config.css:89`), with a separate `.dark` override floor in `dark-arm.css:136`.
So the GOLDEN aliases a `light-dark()` token while explicitly claiming it does not. The cited MEMORY
lesson is specifically that `light-dark()` is fatal when an INSET shadow fragment sits inside it (the
whole box-shadow computes to none). `--chrome-rule` is used only as a `border-color` (§2c/2b/2f/2g), so
the inset-shadow trap does NOT trigger here — the alias is SAFE in practice. But the GOLDEN's prose is
FALSE about its own mechanism, and on an engine without `light-dark()` the rule falls to the `.dark` floor
only (the light arm needs its own non-light-dark fallback to stay honest). **Hardening:** either correct
the prose ("`--chrome-rule` reuses the `light-dark()` `--configurator-divider`, SAFE because it is only
ever a `border-color`, never an inset shadow") OR mint `--chrome-rule` with genuine plain per-mode arms as
the prose claims. The current text is a precept-claim the mechanism contradicts.

### R5 — the cartoon-punch is borrowed but the ENTRANCE register is `text-display`-soft, not cel-SLAM, on the calm rung
The GOLDEN halves the chrome title to `--chrome-title-rung` (`text-display-1`, ~26–42px) AND keeps the
cel-slam entrance. But the binding law demands the 1940s-technicolor register: bold LAYERED-OFFSET shadows
+ squash-stretch with real WEIGHT. The spike's `header-slam` is a 12px translate + a 6% squash + a 3px
overshoot — a tasteful settle, NOT a cartoon SLAM, and there is NO `--shadow-cartoon` layered-offset
shadow on the title (it is a DEPENDS, ABSENT in the spike, never visually proven). On a ~32px calm label
the "cartoon punch" is sub-perceptual — a calm title cannot carry a technicolor cel. The GOLDEN's own
§1-reconciliation ("punch on entrance, calm on scroll") is sound in THEORY, but the calm rung + the
absent layered shadow means the cartoon-punch precept is asserted, not delivered. **Hardening:** prove the
cel-slam + layered `--shadow-cartoon` on the REAL halved rung is still perceptible (a captured frame-series
showing the overshoot + the offset shadow), or accept that the chrome title wears WEIGHT (anticipation +
follow-through) but is NOT a full technicolor cel — and stop claiming "cel-SLAM masthead" if the rung is a
calm label. C9 asserts a mid-frame scale ≠ 1 but does NOT assert the layered shadow exists — a gap.

## A11Y / PRM / cross-engine (no new refutation; minor)

- PRM path is sound (the large static hero holds, no occluding fragment) — design-correct.
- One nit: §4 claims the halved `<h1>` "IMPROVES the heading-scan." True, but the stamp `<code>` carrying

  has no semantic twin. **Hardening:** add a visually-hidden label or `aria-label` carrying the kind
  ("importable path" vs "demo route") so the path-standard is conveyed non-visually too.

## Bottom line

The GOLDEN IDEA — one warm-glass marquee, one `--chrome-t` scalar, one `--chrome-rule`, one clip, six
asks falling out by construction — is **fit and survives**. The born-RED is honest, the mechanism
de-risks, the union is real, KISS/DRY hold. But the **default-path gray-glass wiring gap (R1) is a direct
BA.W-NO-GRAY hit** that the spike's inlined tint masked, and the **corner-clip `--radius` resolution (R2)**
could silently no-op the one src/ paint. Both are CONCRETE and must be hardened (explicit tint wiring +
`--radius` fallback + real-page gate sampling) before EXECUTION. R3-R5 are fidelity refinements. Keep the
golden; refine the weak; the gray-glass wiring is the one thing that, left unhardened, ships the exact
defect the GOLDEN exists to kill.
