## REFUTATIONS

### R1 (TOP, LOAD-BEARING) — the condense bar is GLASS-SAMPLES-GLASS in the scroll case; §L1 only defends the RESTING field

The GOLDEN's §L1 defense: *"never glass-samples-glass (the field is a `-z` sibling)."* That is true
**at rest**. But the condense placard's whole job is to be the surface **the body scrolls UNDER**
(C3: *"the body in the bar's y-band is OCCLUDED by the bar"*). I measured the spike: the condense
`::before` carries `backdrop-filter: blur(20px) saturate(1.7)` AND the body `.demo-card` it occludes
**also** carries `backdrop-filter: blur(20px) saturate(1.7)`. So when a glassy body card scrolls into
the bar's y-band, the bar's `backdrop-filter` is sampling a region that contains **another
backdrop-filter element** — the exact nested-backdrop condition.

- **Chrome:** mostly resolves (composites the under-layer's painted output).
- **WebKit:** nested `backdrop-filter` sampling is the canonical Safari failure — the inner glass
  frequently resolves **flat gray / un-blurred / clipped to the wrong rect** because WebKit's
  backdrop root for the inner filter is not the outer filter's output. This is the **BA.W-NO-GRAY**
  violation the binding law forbids, surfacing exactly where the spike never looked (Safari, scrolled).
- The real demo bodies are NOT the inert `.paper-field` — `/display/buttons`, `/navigation/*`,
  `/motion/*` are **glassy cards, dock chips, glass controls**. The GOLDEN's "the field is a `-z`
  sibling" is a sleight: the FIELD is `-z`, but the BODY CARDS that scroll under the bar are not.

**HARDENING:** the condense placard must NOT stack a `backdrop-filter` blur **over** a region of
other `backdrop-filter` glass. Two fixes, pick per the §L1 doctrine: (a) the bar's backing reads a
**raised-opacity solid-leaning tier** (push `--glass-level` toward the opaque escape in the bar's
condensed pose — the same W54 `.glass-opaque` endpoint the drawer-detent GOLDEN uses — so the bar
OCCLUDES rather than re-samples; transmission is the resting-pose enhancement, opacity is the
condensed-pose correctness); OR (b) keep the blur but gate it `@supports`-off on WebKit to the solid
tier. Either way the C11 "static blur" assertion must be **paired-engine WebKit-captured**, and a NEW
bite C13 must FAIL on a bar that nests backdrop-filter over body glass (measure: a glass card pixel
in the bar's y-band, both engines, must read warm not gray).

### R2 (LOAD-BEARING) — `animation-timeline: scroll()` Baseline-Safari-26 is a 2025-NEW floor; the `@supports`-off fallback is a SILENT SECOND DESIGN that was never measured

§4 says: *"Baseline Safari 26+; `@supports` → static large header."* Safari shipped scroll-driven
animations only in **26 (2025)** — the installed base on Safari ≤18 (the overwhelming majority for
~12+ months) takes the `@supports`-OFF arm. That arm is described in one phrase ("static large
header") and **never spiked**. Consequences the GOLDEN glosses:

1. On non-supporting WebKit the page gets the **109px-equivalent large title FOREVER, never
   condensing** — but the GOLDEN RETIRED the protagonist floor for the chrome (`--chrome-title-rung`
   ~46px is the static value), so the fallback is a ~46px static label, **not** the audacious hero.
   Fine — but then the iOS-27 "title condenses into a bar you scroll from" headline behaviour, the
   entire reason-for-being, **silently does not exist on the majority Safari install base.** The
   GOLDEN never states this honestly; §5's gestalt bar ("a content page reads as ONE warm chrome
   shell … condensing into a slim warm-glass placard bar") is FALSE on Safari ≤25.
2. The sticky bug the GOLDEN claims to fix ("the page scrolls under bare text") — under the
   `@supports`-off arm there is **no placard `::before` materialization** (it's keyed inside
   `@supports (animation-timeline: scroll())`), so the static sticky header on Safari ≤25 is back to
   **bare sticky text** — the EXACT defect (lens-b's `top:-563` occlusion) re-appears on the fallback
   engine. The fix is keyed to the one engine that least needs it.

**HARDENING:** (a) the `::before` placard backing must paint a **static warm-glass bar at rest**
(opacity ≥ floating floor without the scroll() ramp) so the sticky header has a backing on EVERY
engine — the scroll() timeline only ANIMATES the opacity 0→1; it must not be the only thing that
PAINTS it. (b) C3/C11 must add a WebKit-no-scroll()-timeline project arm asserting the static bar
still occludes. (c) §5's gestalt prose must be honest: "condenses on scroll()-supporting engines;
static warm bar elsewhere." NO LEGACY ≠ no-fallback-honesty.

### R3 — `backdrop-filter` on a `z-index:-1` pseudo-element is WebKit-fragile

The placard backing is `.chrome::before { z-index:-1; backdrop-filter:… }`. WebKit has a long tail of
bugs where `backdrop-filter` on a **negative-z pseudo-element** (which pulls it behind its own
originating box's content) fails to establish the correct backdrop root — the filter samples nothing
or the wrong layer, rendering the bar **clear** in Safari while opaque in Chrome. The spike de-risked
this in Chrome where it works. It is precisely the kind of `::before`-with-backdrop-and-negative-z
that the GOLDEN's own MEMORY warns about for OTHER properties (the light-dark inset-shadow trap, the
scoped `:global` drop — the pattern is "Chrome-passes-Safari-drops").

**HARDENING:** spike the `::before` backing **in WebKit** before committing the `z-index:-1` approach.
If it drops, the backing moves to a **real sibling element behind the cluster** (a `.chrome-placard`
div, z-ordered under the text, no negative-z pseudo) — still zero new SFC (it's a div in StoryHeader),
still DRY. The gate must capture the bar's resolved `background`/`backdrop` α **in the webkit project**,
not infer it from Chrome.

### R4 — the toc "goo-morph" marker is a `transform`+`height` transition; **`height` is NOT a compositor property** (C8 perf-floor self-contradiction)

The marker (2g + spike `:153`) transitions `transform 360ms, height 360ms`. C8 asserts *"no … marker
keyframe animates … `height` … (transform/opacity/clip-path/`block-size`/static-backdrop only — the
CLS floor)"* — yet the spike animates **`height`** and the GOLDEN CSS animates **`block-size`**
(`:2g` uses `block-size`, the spike uses `height` — they are the same property; both are
**layout-triggering, NON-compositor** properties). Animating `block-size`/`height` per frame on the
marker forces **layout on every frame of the morph**. The GOLDEN tries to launder this by calling it
`block-size` and listing it as allowed in C8 — but listing a layout property as "compositor-safe"
does not make it so. This is a self-inflicted KISS violation: the marker should morph on the
**compositor** like every other liquid-weight element in the library.

**HARDENING:** the marker morphs on **`transform` only** — `scaleY` (height delta) + `translateY`
(position delta) off a fixed base rect, the standard liquid-indicator technique already shipped in
`useTabIndicator` (the GOLDEN even cites it for the dock-tab work). REUSE `useTabIndicator`'s
transform-only glide+squish instead of minting a `height`-transition fork. C8 must then FAIL on a
`height`/`block-size`-animating marker (it currently PASSES it — the bite is mis-set). This also
delivers the **squish** (scaleY overshoot) the liquid-weight law demands, which a `height` lerp cannot.

### R5 — sRGB-vs-oklab interp claim is INVERTED for the warm tint; the spike uses `oklab` everywhere

§4: *"`color-mix(in oklab, …)` is WebKit-native … sRGB interp pinned on the warm tint stops (the
Safari oklab-default mud avoided)."* But the spike's warm stops are **all `in oklab`** — the marker
`color-mix(in oklab, var(--glass-tint-source) 40%, transparent)`, the bar
`color-mix(in oklab, var(--glass-bg-floating), var(--glass-tint-source) …)`. Mixing a warm color
**toward `transparent` in oklab** is the well-known premultiplied-vs-not / hue-toward-gray pitfall:
`color-mix(in oklab, <warm> 40%, transparent)` can desaturate through gray at the midpoint in some
engines. The GOLDEN's PROSE says "sRGB pinned on the warm tint stops" but its CODE pins `oklab`. The
ledger contradicts the implementation — a born-AMBER honesty gap, and a potential **gray-glass
violation** at the toc marker (the very thing C7 forbids).

**HARDENING:** mix warm-toward-warm, never warm-toward-`transparent` for the tint: use a defined warm
low-α stop (`color-mix(in oklab, var(--glass-tint-source) 40%, var(--glass-tint-source-fade))` where
the fade stop is a warm low-α color, NOT bare `transparent`), OR pin the mix in `srgb` as the PROSE
claims and update the CODE to match. Add a born-RED bite: the marker's resolved color at 40% must hold
C ≥ 0.045 warm (no gray midpoint), **measured in webkit**.

### R6 — perf: TWO independent `scroll()` timelines + a JS scroll listener on the SAME scroller

The chrome runs the shrink + the bar-in + the subsume on `animation-timeline: scroll()` (3 keyed
animations), AND the toc marker runs a JS `scroller.addEventListener('scroll', …)` that calls
`getBoundingClientRect` in the handler (spike `:205-211`). Even passive, the rAF-less rect-read on
every scroll tick is a forced-reflow risk, and it duplicates work the shipped `useScrollTracker`/
`useSidebarFollow` already coalesce. The GOLDEN claims "ONE morphing warm pill … no new tracker" —
good — but the spike ships a NEW hand-rolled tracker (the `scroller.addEventListener` block) that is
exactly the second scroll reader the §3 union table forbids ("NOT a … 2nd … scroll engine").

**HARDENING:** the production marker MUST drive off the shipped `useScrollTracker` active-id (as §2g
states) — the spike's `addEventListener('scroll')` is throwaway and must not leak into the wave. The
gate/census should assert **zero new `addEventListener("scroll")`** in the chrome diff (the
single-reader law, already a MEMORY/precept).

### R7 — `prefers-reduced-transparency` PRT fall-back is asserted, never demonstrated; the OPAQUE tier must still be WARM, not gray

§4 PRT: *"the bar + the toc + the stamp fall to the library's opaque tier."* If the library's opaque
tier is a neutral `--card` gray (the common case), then under PRT the warm-glass identity **becomes
the gray slab C7 forbids** — PRT users get the exact defect the GOLDEN was born to kill. The binding
law's NO-GRAY floor has no a11y exemption.

**HARDENING:** the PRT opaque tier for the chrome surfaces must resolve a **warm-tinted opaque**
(`color-mix(in oklab, var(--card), var(--glass-tint-source) <small>)`), not bare `--card`. Add a PRT
arm to C7 (toc warm under PRT) — born-RED on a gray opaque fallback.

### R8 — overfit / hardcoded: the spike's stand-in tokens leak magic numbers the GOLDEN must source

The spike hardcodes `--chrome-title-rung: clamp(2rem,1.4rem+2.2vw,2.9rem)`, `--chrome-condense-range:
170px`, `--motion-weight: 0.618`, the marker `40%`, the tint `14%/22%`. The GOLDEN says these "depend"
on shipped families, but the §6 census must prove each resolves to a **named library token**, not a
re-minted px. `170px` condense-range vs the shipped `.story-hero-shrink` `--hero-condense-range:160px`
is already a DRIFT (170 ≠ 160) — a fork-by-magic-number. The GOLDEN reuses `.story-hero-shrink` but
the spike picks a DIFFERENT range.

**HARDENING:** the chrome condense MUST reuse `--hero-condense-range` (160px), not mint 170. The
overfitting-audit (the MEMORY canon) runs at close: every `--chrome-*` token has ≥2 readers or is the
shared `--chrome-glass` register; the range/scale/weight are the SHIPPED `.story-hero-shrink` values,
not spike re-picks.
