## TOP REFUTATION (the one that lands hardest) — the §1-defect-2 source trace is WRONG; the Tier-1 "fix" may be a no-op

The GOLDEN's load-bearing reconciliation (§0 table row 2, §1 defect 2, §4.2) credits
lens-c with "the exact source trace … the precise truth":

> `mode:"capture"` forces `initStrategy:"eager"` → a SYNCHRONOUS arm in the constructor →
> on the WebGPU backend the async device-acquire THROWS `device not acquired` … at the
> `createAurora` CALL, one statement BEFORE `armAsync()` is ever reached.

**This describes a code path that does not exist in HEAD.** In
`src/components/custom/aurora/composables/runtime.ts`:

- L116 `shouldInitEagerly` returns `true` for capture — BUT
- **L462: `if (options.mode !== "capture" && shouldInitEagerly(options)) { armRuntime(); }`** —
  the synchronous constructor arm is **explicitly GATED OFF for capture mode**. `createAurora`
  under `{mode:"capture"}` does NOT sync-arm and does NOT reach `buildContext()` in the
  constructor.

And `usePresetThumbnails.ts` (live on disk) **already** awaits `armAsync()` at L90 —
exactly the "RIGHT" fix the GOLDEN §4.2 proposes as the correction. The BC.W-VIZ-AURORA
(T2) await is ALREADY THERE (L84-90, with the matching comment in runtime.ts L450-455).

So the GOLDEN's "the await is never reached, one statement too late" story is false: the
await IS reached, IS run, and the bake STILL dies. I confirmed live:

```
console: [Aurora] thumbnail bake aborted: Error: [useWebGPUCanvas] device not acquired

```

The throw `device not acquired` fires from `useWebGPUCanvas.ts:312` (`buildContext`,
`if (!device) throw`). With the sync-arm gated off, this fires INSIDE the `armAsync()`
chain (the device-acquire genuinely failing in this host), NOT before it. **The defect is
NOT init-ORDER — it is that the device cannot be acquired at all** in this environment
(the validation-probe / SwiftShader / lying-adapter class the runtime.ts L138-148 comment
itself describes).

**Why this is load-bearing, not pedantic:** §4.2's Tier-1 fix is "swap `mode:"capture"`
for `initStrategy:"deferred"` + `await armAsync()`." But the code ALREADY awaits
`armAsync()`, and `initStrategy:"deferred"` changes the CONSTRUCTOR arm timing — which is
ALREADY gated off for capture (L462). **The proposed Tier-1 reorder fixes a bug that is
already fixed and does not touch the bug that actually fires.** If the device can't be
acquired, deferring the arm doesn't make a device appear. Tier-1 as written would ship
GREEN-on-paper and STILL-DEAD-live (the exact AW "headless-green / visually-broken" trap
in MEMORY).

**HARDENING (required):**
1. Re-trace the throw against HEAD and CORRECT the §0/§1/§4.2 narrative: the sync-arm is

## R4 — Safari is ASSERTED, never EXERCISED (the whole cross-engine leg is Chrome-only evidence)

§6 claims "byte-identical Chrome ⇄ Safari, the WHOLE Safari story is Tier-0." The spike's
determinism test (a===b on two same-process calls) proves DETERMINISM, NOT cross-ENGINE
parity. `auroraFallbackGround` runs `rasterizeField` → `canvas.toDataURL("image/png")`
(L361). **`toDataURL` is exactly where engines diverge:** Safari's PNG encoder, color
profile tagging, and `getContext("2d")` `putImageData` round-trip can differ from
Chrome's. The spike emits `image/png` from a 2D canvas — a known cross-engine seam — yet
the GOLDEN claims "byte-identical" without ever opening the proof in Safari. The SSR path
(layered radial-gradients) WOULD be byte-identical, but the browser path takes the RASTER
(L292), not the SSR fallback.

Worse: the `.well` in the spike uses `aspect-ratio:16/10` + `background-size:cover` on a
`grid×grid` (8×8) data URI with `image-rendering` default. Safari and Chrome bilinear-
upscale an 8px raster DIFFERENTLY at the sub-pixel level — visually fine, but "byte-
identical" is flatly false for the raster path.

**HARDENING:** (a) Soften the claim from "byte-identical" to "perceptually-identical,
device-free" for the raster path — OR force the SSR layered-gradient path in the gallery
(genuinely byte-identical, zero canvas, zero `toDataURL`) and reserve the raster for a
faithfulness-certify only. (b) The gate MUST actually run in WebKit (Playwright webkit or
a real Safari capture), not assert Safari from a Chrome+jsdom run. "Live-verified" needs a
captured WebKit DELTA artefact (MEMORY: live-verify-capture), which this GOLDEN lacks.
