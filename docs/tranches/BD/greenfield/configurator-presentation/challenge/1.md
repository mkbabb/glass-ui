# CHALLENGE 1 — CORRECTNESS / DEFT-INTEGRATION / KISS lens

Adversarial pass over `GOLDEN.md` (the configurator + preset GALLERY). Default verdict:
REFUTED until the golden proves it survives. Live-tested on `/substrates/aurora`
(1440×900, dark mode), source-verified on disk, ran the Tier-0 spike.

**Net: the golden SURVIVES the lens (the gestalt + the born-RED + the Tier-0 win are
real), but with FOUR material refutations that demand hardening — one of them lands on
the single boldest move.** None are fatal; all are cheap to fix; the design after the
hardening is honest.

## REFUTATION 1 (the STRONGEST — lands on §3, the boldest move): the deal's tile→stage
## flight is mis-attributed to `useLiquidReveal`, which EXPLICITLY cannot do it.

§3 beat-2: *"the tile does a `useLiquidReveal`-style FLIP from its tile rect → the STAGE
rect."* §7's union table credits the whole deal to `useLiquidReveal` + `fission-bridge` +
`useLiquidFlex` + merge-splash, and §3 boasts *"composed 100% from"* those + *"zero new
physics core."*

**This is false.** `useLiquidReveal`'s own module header (read on disk) states:

> "We construct `ElementMorph(settledRect, triggerRect)` … blooms FORWARD onto its own
> rect. … **We do NOT use `flipShared`'s forward play here (that morphs a→b's rect in
> place, the wrong direction for a reveal)**."

`useLiquidReveal` reveals a surface onto **its OWN settled rect FROM a trigger** — a
reveal-from-source. The deal needs the OPPOSITE: take a tile element and fly it to a
DIFFERENT element's rect (the stage) and merge — the a→b forward FLIP that
`useLiquidReveal` deliberately omits. The correct primitive is **`flipShared`** (it DOES
ship — `keyframes.js`, surfaced via `src/composables/motion/suite.ts`) — but the golden
never cites it. So §3 is built on the wrong engine, and either:
(a) it silently needs `flipShared` → the "every primitive verified, complete union table"
claim is incomplete; or
(b) it needs new orchestration glue → "zero new physics core" is overstated.

Worse, the **ARC** principle (beat-2's "non-straight path") is a curved translate that
NEITHER `useLiquidReveal` (linear settled→trigger translate delta) NOR `useLiquidFlex`
(scale/`--stretch` only, NO translate) produces. A non-linear flight path is genuinely
new motion code masquerading as "recomposed shipped engines."

**HARDENING:** rewrite §3 + §7 to cite `flipShared` (the real forward-FLIP) as the tile→
stage flight engine; demote `useLiquidReveal` to the re-erupt-from-core role only (where
it IS correct). Explicitly name the ONE genuinely-new piece — the arced-translate
phase-map keyer on `--gallery-deal-t` — and de-risk it with a spike (a `flipShared`
forward play + a Bézier/parabolic path sample), the same way §3's Tier-0 thesis was
spiked. Drop "zero new physics core / composed 100% from"; say "composes shipped engines
+ ONE new arc-path keyer (spiked)."

## REFUTATION 2 (a11y precept gap): `role="tablist"`/`role="tab"` + `aria-pressed` is an
## ARIA contradiction, and `GlassDock` provides NO tablist semantics.

§6: *"the gallery dock is a real `<GlassDock>` `role="tablist"` of preset
`role="tab"`/`aria-pressed` tiles (roving tabindex inherited)."*

Two faults:
1. **`GlassDock` does not expose `role="tablist"`** (grep: zero `tablist`/`role="tab"` in
   `GlassDock.vue`). It is a generic dock container with a roving model for *dock
   buttons*, not a tab strip. The "roving tabindex inherited" is asserted as free; it is
   not — the tablist semantics would be NEW wiring.
2. **`role="tab"` + `aria-pressed` is invalid ARIA.** `role="tab"` uses `aria-selected`;
   `aria-pressed` is the toggle-button pattern. Today's `PresetPickerRow` correctly uses
   `aria-pressed` on plain buttons. The golden mixes the two patterns — a screen reader
   gets a "tab" that announces a "pressed" state, which is contradictory. The §8.1 gate
   even asserts on `aria-pressed`, cementing the wrong pattern.

**HARDENING:** pick ONE pattern and state it. Either (a) keep the toggle-button idiom
(plain buttons, `aria-pressed`, a `role="group"`/`aria-label="Presets"` container, roving
optional) — simplest, matches HEAD, KISS; or (b) commit to `role="tablist"`/`role="tab"`/
`aria-selected` + `aria-controls` pointing at the live stage, and spec the NEW GlassDock
`role` axis it requires. Do NOT claim both. Given the preset gallery is a single-select
applied-state picker, (a) is the fitter survivor.

## REFUTATION 3 (cross-engine claim narrower than stated): "byte-identical Chrome ⇄
## Safari" is proven for the WRONG (node/SSR) path; the BROWSER path is a 2D-canvas
## `toDataURL` raster that is NOT guaranteed byte-identical across engines.

§3/§4.1/§6 + the spike sell Tier-0 as *"byte-identical Chrome ⇄ Safari."* But
`auroraFallbackGround` has TWO branches (read on disk): in a real browser it takes the
**2D-canvas raster** path (`rasterizeField` → `canvas.getContext("2d")` →
`toDataURL`), and ONLY falls back to the layered-radial-gradient string when
`document === "undefined"` (SSR/node). The spike runs in `environment: "node"` — so the
5/5 GREEN proves the GRADIENT-FALLBACK is deterministic in node; it does **NOT** exercise
the browser raster path that actually ships. And `canvas.toDataURL` PNG/WebP encoding +
anti-aliasing + color-management is the classic Chromium⇄WebKit divergence (canvas
fingerprinting exists precisely because they differ). "Byte-identical" is unproven for the
shipping path; the spike's own emitted `tier0-proof.html` uses gradient strings (node
path), so even the HTML proof doesn't open the real browser path in Safari.

**HARDENING:** downgrade the claim from "byte-identical" to "**device-free + visually
equivalent + never-blank**" (which IS true and sufficient — pixel-equality is not
required for a thumbnail). Re-run the spike with the raster path forced (jsdom/happy-dom
canvas or a real-browser harness) OR have the gate's R1 capture the tile well in BOTH
engines and assert chroma>floor + ≥2 hues (perceptual, not byte) live. Keep the gradient
fallback as the explicit Safari floor if a WebKit `toDataURL` ever drifts. The win
survives; the adjective was too strong.

## REFUTATION 4 (the born-RED gate cannot run RED on HEAD — it THROWS): every selector
## the §8.1 gate keys on is absent on HEAD, so it errors rather than failing clean.

§8.1 keys on `[data-preset-tile]`, `[data-gallery-dock]`, `[data-preset-core]`, and
`rect('#stage')`. Live DOM check: NONE exist on HEAD — `#stage` is a Vue SLOT named
`"stage"`, not an `id`; the configurator stage element is `.configurator-stage`; the tiles
are `aria-pressed` buttons with no `data-preset-tile`. So `rect('#stage').top` and
`rect('[data-gallery-dock]').top` throw `Cannot read properties of null` on HEAD — the
gate ERRORS, it does not cleanly assert-RED. A born-RED gate must FAIL (a false assert),
not throw on a missing selector; otherwise "born-RED on HEAD" is unverifiable as written
(you can't tell a real RED from a typo'd selector).

This is the BC.W-CONFIG-RIGHT lesson's cousin: the gate's selectors are aspirational
(they appear only after the golden adds them), which is fine — but the gate must DEGRADE
to a clean RED on their absence, and must be runnable against HEAD to earn the
"born-RED" stamp.

**HARDENING:** make each R-assert null-safe → a clean fail: e.g.
`const gal = q('[data-gallery-dock]'); assert(gal && rect(gal).top < ...)` so a missing
node is a RED, not a throw. Add the HEAD-equivalent selectors as the RED baseline
(`.configurator-aside` for the cramped gallery, `[class*=skeleton]` for the dead tiles,
`.configurator-stage` for the stage) so the gate provably runs RED on HEAD TODAY, then
GREEN on the golden's new `data-*` hooks. Capture the RED artefact (the 13-skeleton + 360px
screenshot I took confirms it's there to capture).

## Lesser dings (note + move on; not survival-threatening)

- **§0 table path slip:** `DOCK_SPRING {response:0.32, ζ:0.7} (useLiquidMorph.ts)` — it
  actually lives in `src/components/custom/dock/constants.ts` (and its values come from
  `springPreset("dock")`, not literal 0.32/0.7 inline). Fix the citation path in the
  "honesty table"; the engine is real, the path is wrong.
- **"Gray" overstated in R5:** the dark tile measured `rgb(53,42,34)` (warm-brown, chroma
  0.074) — it is an OPAQUE `bg-card` plate, NOT neutral gray. The real defect is
  "opaque plate, no §3 read-through," which is correct; the word "gray" is imprecise and
  the R5 `isGrey(bg)` assert would arguably PASS on the warm-brown (chroma > 0 already).
  Re-state R5 as "opaque, non-transmissive, no §3 field behind" + assert on
  background-alpha < 1 / no read-through, not on `!isGrey`.
- **`<VizStudioGallery>` naming vs reality:** §2.4 names a `<VizStudioGallery>` component
  (implies a NEW wrapper = a bolt-on); §7/§9 say it's a `#gallery` slot +
  `galleryCollapsible` axis ADDED to the existing `VizStudio` (a union). It cannot be
  both. Pick the union framing (extend `VizStudio`) and drop the new-component name, or
  the DRY/no-fork claim is muddied.
- **`useLiquidReveal` header says "ship UNCONSUMED at HEAD"** — stale; it IS now consumed
  (bloomUp, cta-receive, celebration, the reveal demo). Doesn't hurt the golden, but the
  golden leans on a comment that contradicts the disk; trust the disk.

## VERDICT

**SURVIVES — conditionally.** The gestalt (studio-IS-a-dock, gallery-to-top, collapse-to-
core, ONE chassis), the born-RED (live-confirmed), the R1 root-cause (source-accurate),
and the Tier-0 device-free win (spike-GREEN) are all REAL and fit. The four refutations
are corrections of OVERSTATEMENT, not collapses of the design:
1. the boldest move (§3) is built on the wrong primitive (`useLiquidReveal` cannot do the
   tile→stage forward flight; `flipShared` can) + hides one genuinely-new arc keyer →
   re-cite + spike;
2. the a11y model self-contradicts (`role="tab"` + `aria-pressed`; GlassDock has no
   tablist) → pick ONE pattern;
3. "byte-identical" is proven for the node path, not the shipping browser raster →
   downgrade to "device-free + visually-equivalent + never-blank" + live perceptual gate;
4. the born-RED gate throws (not fails) on HEAD's absent selectors → null-safe asserts +
   HEAD-baseline selectors.

After those four hardenings the golden is honest and the strongest of the configurator
designs. Without them, §3 over-claims "zero new physics" and the gate can't earn its
"born-RED" stamp.
