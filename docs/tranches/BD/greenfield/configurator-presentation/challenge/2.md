## TOP REFUTATION (the one that lands hardest)

### R-A · The "byte-identical Chrome ⇄ Safari, compositor-only" Tier-0 claim is FALSE for the path the browser actually runs — and the spike PROVES the wrong path.

The GOLDEN §4.1/§6/§3 repeatedly asserts the Tier-0 preview is *"compositor-only, one
paint, **byte-identical Chrome ⇄ Safari**, needs no device"* and that this *"deletes the
entire Safari failure surface."* That is the load-bearing cross-engine WIN. It does not
survive a read of the shipped `auroraFallbackGround.ts`:

1. **The default browser path is a 2D-CANVAS RASTER, not compositor-only CSS.**
   `auroraFallbackGround()` calls `rasterizeField()` FIRST (line 291-298): it creates an
   8×8 `<canvas>`, `putImageData`, and **`canvas.toDataURL("image/png")`** (line 361). When
   `document` exists (i.e. every real browser), it returns `url("data:image/png;…")` — a
   rasterized PNG. The pure-CSS layered-`radial-gradient` stack (line 300-319) is the **SSR
   fallback ONLY** (`if (typeof document === "undefined")` → line 333). So in Chrome AND
   Safari the tile well is a `toDataURL` PNG bitmap, not "compositor-only one paint."

2. **A 2D-canvas `toDataURL` PNG is NOT guaranteed byte-identical across engines.** Canvas
   `putImageData` of explicit RGBA is fairly portable, BUT the well is then **CSS-upscaled
   with `image-rendering` bilinear** over the tile (the module's own comment, line 326-327)
   — the upscale filter is engine-defined, and PNG encoders differ. "Byte-identical" is an
   over-claim; "visually-close" is the honest bar.

3. **The spike "proves" Safari parity by testing the WRONG path in the WRONG environment.**
   `tier0-render.spike.test.ts:89-96` ("DETERMINISTIC — byte-for-byte Chrome⇄Safari
   parity") compares `a.backgroundImage === b.backgroundImage` for **two same-process,
   same-engine (Node/vitest) calls**. That proves *determinism within one engine*, NOT
   *cross-engine parity*. Worse: in Node `document` is undefined → it exercises the SSR
   **CSS-gradient** branch, which the browser NEVER runs. The test certifies a code path
   that does not ship to users and calls it "Chrome⇄Safari parity." This is the exact
   `feedback_live_pi_oklab_paint_arm` / `feedback_live_verify_capture` failure mode: a
   device-free gate passing while the real surface is unproven.

4. **The provenance is also misrepresented.** `auroraFallbackGround` was built for
   **BB.W-AURORA-SWRASTER** — a HEADLESS software-raster *contrast-certification* ground
   (its docblock: "speedtest's CI/witness harness must still certify text-on-aurora AA
   contrast floors HEADLESS"). It is consumed ONLY on the `"css"` substrate
   (`Aurora.vue:155: isCssSubstrate`). The GOLDEN repurposes a headless-certify fixture as
   the universal preview field — plausible, but it inherits an 8×8 grid (64 softmax-Gaussian
   samples over ALL nuclei per preset) whose **per-preset cost was never budgeted for 13
   live tiles on mount**, and the upscaled-8×8 fidelity was tuned for a luminance mean, not
   a 320×200 thumbnail a human stares at. Calling it "the §3 COLOURFUL FIELD" is aspirational.

**Hardening for R-A:** (a) Stop claiming "byte-identical" — claim "device-free + visually
equivalent within ΔE band, no WebGL/WebGPU/Safari-context surface" (which IS a real win).
(b) Make the cross-engine gate REAL: render the actual `rasterizeField` path in **both
Chrome and Safari/WebKit via the live π** and assert a perceptual-ΔE bound on the well
bitmap (not a Node string-equality). (c) Decide ONE shipping path: if "compositor-only" is
the promise, ship the **CSS-gradient stack in the browser too** (force the SSR branch) and
drop the canvas raster for the gallery — then it genuinely IS compositor-only and the
byte-claim becomes defensible for the gradient string. (d) Budget the 64-sample×13 mount
cost (defer/idle-chunk) and prove it under WebKit, not just assert "one paint."

## SECONDARY REFUTATIONS (each lands)

### R-B · The headline SCROLL-COLLAPSE (R4) does NOT match the studio's layout — `useScrollChrome` will not fire.
Live-verified: on `/substrates/aurora` the **document does not scroll** (`docSH==winH==806`,
`docScrolls:false`). The studio is a fixed-viewport flex layout (stage flex-1 + right
aside); the ONLY scroll container is the OUTER `.demo-main-scroller` (sh 1753 > ch 806),
which scrolls the WHOLE studio out of view, not "content rising past a pinned gallery while
you tune." `useScrollChrome` ramps `collapseT` off a scroll **delta** in a container
(useScrollChrome.ts:182-221). A `position:absolute` top-pinned island over a NON-scrolling
stage has no scroll to read. So R4's π — *"a scroll-down past collapseRangePx collapses the
rail"* — cannot pass on the real page without re-architecting the studio to scroll, OR the
collapse is driven by the explicit core-toggle only (which the spec lists as an alternative
but the GATE asserts the scroll path). The interaction is built on a scroll that isn't there.
**Hardening:** drive the collapse from an explicit toggle / focus-mode button + (optionally)
the stage's own intersection, and REWRITE R4's π to assert the toggle path, not a scroll the
page doesn't have. If scroll-collapse is wanted, the studio must become a scroll container
first — name that as a precondition, don't assume it.

### R-C · The "merge into the live field" (Beat 3, the boldest move) collides with the WebGL/WebGPU stage — goo cannot weld a DOM tile to a canvas.
The deal's climax is the thumbnail tile *"goo-MERGES into the live field… the tile's metaball
neck snaps into the stage canvas… the preview literally BECOMES the stage."* But the stage is
a **WebGL/WebGPU `<canvas>`** (live-verified: 1728×2447 canvas). `DockGooFilter`'s SVG
`filter:url()` metaball graph operates on the **alpha of sibling DOM/SVG shapes in the same
filter region** — it CANNOT form a metaball waist between a CSS tile and the opaque pixels of
a GL canvas (the canvas is not part of the filter's alpha field; a `filter` on a parent does
not let two independent stacking contexts fuse). The "neck reading at the seam between tile
and stage canvas" is not physically achievable with the cited primitive. What's actually
deliverable is a tile FLIP onto the stage rect + a cross-fade of the GL config (which is
fine and shipped) — but that is NOT a metaball merge, and selling it as one over-promises the
cartoon-punch precept. **Hardening:** scope the goo neck to DOM↔DOM seams only (gallery
collapse/erupt, tile↔core) where the filter region genuinely contains both alphas; for the
tile→stage climax, ship the FLIP + GL cross-fade + a merge-SPLASH overlay (a DOM element over
the stage that DOES share the filter region), and stop describing it as "the tile becomes the
stage via a metaball neck into the canvas."

### R-D · Several "defects" are already fixed → overfit / inflated born-RED.
- Defect-3 guard ("the card needs `type=button` + `@click.stop`"): tiles **already** carry
  `type="button"` (live-verified). The stray-nav fix is partly a non-defect; asserting it as
  born-RED risks a gate that's GREEN on HEAD.
- Defect-4 "gray, not glass": in LIGHT mode the tile bg is `rgb(253,245,236)` — already
  **warm-cream**, not gray. The real miss is it's OPAQUE (`backdrop-filter:none`, no §3
  read-through) and the DARK tile is `rgb(53,42,34)` (warm brown, opaque). The "gray" framing
  is inaccurate; the honest defect is "opaque, no transmission, no field-behind." Keep R5 but
  re-word: the floor is TRANSMISSION + §3, not de-graying (it's already warm).
**Hardening:** re-base the born-RED on what is actually red (no transmission / no §3 / no
collapse / dead thumbnails / cramped), drop the already-true `type=button` and the "gray"
mischaracterization so the gate is honestly born-RED and not partially pre-green.

### R-E · DRY chassis (R6) is asserted against a slot that doesn't exist; the generalization is bigger than "additive."
VizStudio today exposes a `#presets` slot + a `presets` prop (VizStudio.vue:62-65,122,147),
NOT a `#gallery` slot or `galleryCollapsible` axis, and the gallery renders INSIDE
`<Configurator>`'s aside. The GOLDEN's "ONE additive axis, default unchanged" understates the
work: portaling `#presets` OUT to a `position:absolute` top island, adding `galleryPlacement`
to BOTH `Configurator.vue` (src) AND `VizStudio.vue` (demo), re-hosting 6 divergent idioms,
and a precompiled CSS arm — that touches the SHIPPED `src/components/custom/configurator/
Configurator.vue` (a library component, not just demo). The "demo-chassis only, zero src
physics" framing (§9) is wrong: `galleryPlacement` lands in `src/`. **Hardening:** state
plainly that `Configurator.vue` (src) gains the prop + portal branch + CSS arm (a real
library change, gated/tested as such), and that R6's "≥2 studios" requires the `#presets`→
gallery-dock re-host in each — not a free slot.

### R-F · PRM + a11y gaps under live test (not yet proven, asserted).
The GOLDEN asserts `useScrollChrome`/`useLiquidReveal` honor PRM — TRUE in source
(useScrollChrome.ts:128-139 discrete snap; useLiquidReveal PRM step). BUT the **deal's
canvas cross-fade + accent-flood + the `auroraFallbackGround` repaint on pick** are NOT
motion-gated and the spec hand-waves "a color change is not vestibular." The 64-sample
re-raster of a tile on every pick under PRM is still a main-thread cost, and the merge-splash
is motion. Also untested live: focus-move-on-erupt + restore, Escape-collapse, roving tabindex
on a `position:absolute` portaled dock (portaling can break the GlassDock roving model's
DOM-order assumptions). **Hardening:** add a live PRM π that captures ZERO transform/blur/cast
frames on pick AND bounds the per-pick main-thread cost; live-test the portaled dock's roving
tabindex + focus restore + Escape, since the portal moves the dock out of its natural
tab-order parent.

### R-G · Tier-1 perf: the "ONE shared context" bake still blows the budget premise it cites.
§4.2's Tier-1 keeps the `mode:"capture"` … no — it switches to `initStrategy:"deferred"` +
`await armAsync()`. Fine. But it still creates a `left:-99999px` offscreen canvas + a real
`createAurora` + 13 sequential `update`+`renderAt`+`toDataURL("image/webp")`. On Safari/WebKit
where WebGPU may be absent and WebGL2 software-rasters, `armAsync` resolves to the SwiftShader
path and the 13 webp bakes run on a software rasterizer — the GOLDEN says "Tier-0 stays" if
`armAsync` rejects, but SwiftShader does NOT reject, it succeeds slowly, producing 13 slow
webp encodes on the main thread. The "offscreen-park" guard (only when on-screen+idle)
doesn't bound a single mount-time burst. **Hardening:** gate Tier-1 on a real
hardware-accelerated-GPU probe (not just "armAsync resolved"), keep it strictly OFF under
software-raster, and chunk the 13 bakes across idle frames with an abort-on-navigate.

## VERDICT

**SURVIVES — but the cross-engine WIN as written is unproven and partly false, the headline
scroll-collapse doesn't fit the page, and the metaball-merge climax is physically
overstated.** The gestalt (up-top large scrollable collapse-to-dock gallery, render-the-
presets, warm transmissive glass, cartoon deal, DRY chassis) is right and the born-RED is
real. The fittest-survives reconciliation (no phantom engines) is genuinely better than the
lenses it synthesizes. But the GOLDEN's signature claim — "device-free, byte-identical
Chrome⇄Safari, Safari-failure-surface DELETED" — rests on `auroraFallbackGround`'s
**canvas-raster** path while the proof tests its **SSR-gradient** path in **Node**. Harden
R-A (real cross-engine π on the shipping raster path, or ship the CSS-gradient path in-browser
and claim only what's true), fix R-B (collapse off a toggle, not a scroll the studio lacks),
and de-overstate R-C (FLIP+cross-fade+splash, not a tile↔canvas metaball neck), and it holds.

### Top single refutation
The "byte-identical Chrome⇄Safari, compositor-only, Safari-surface-deleted" Tier-0 win is
asserted on the canvas-`toDataURL` path the browser actually runs, but the spike proves only
same-engine Node determinism on the SSR CSS-gradient branch that never ships — the
cross-engine claim is unproven and the "compositor-only" claim is false for the shipping path.
