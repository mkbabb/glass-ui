## R1 (TOP REFUTATION) — the POUR is Safari-18+, not "Safari 16.4+"; on 16.4–17.x it is a DEAD SLAB

§7 asserts: *"`@property --menu-pour-t` / `--menu-row-index` — Safari 16.4+"*. This conflates
two distinct WebKit features:
- `@property` **registration** — yes, Safari 16.4+.
- **transitioning** a registered custom property (the pour's entire mechanism: `transition:
  --menu-pour-t var(--pour-dur) linear` driving each row's `--rp` window) — WebKit only shipped
  custom-property / `@property` **animation** in **Safari 18.0 (Sept 2024)**. On Safari
  16.4–17.6 `transition-property: --menu-pour-t` is a no-op: `--menu-pour-t` JUMPS 0→1, every
  row's `--rp` jumps 0→1 simultaneously → **the pour collapses to the very slab the born-RED
  indicts** (§0 "rows materialize as one rigid slab"). The `nth-child --i` "zero-JS floor" does
  NOT save it — that floor only sets `--menu-row-index`; the cascade still needs `--menu-pour-t`
  to *sweep* for the windowed `--rp` to fan out in time. No sweep → no stagger.

This directly violates acceptance #7 ("Identical Chrome↔Safari … same pour, compositor-only")
and G8's paired-engine arm. Verified in Chrome 149: `CSS.supports('transition-property',
'--menu-pour-t')` → true, and the spike interpolates `--menu-pour-t` 0→0.066→0.737→1 (real).
Chrome is fine; the GOLDEN's own Safari-version label is wrong by a major version.

**HARDENING:** (a) Correct §7 to **Safari 18+** for the pour, and add a real Safari-<18 arm:
gate the pour mechanism on `@supports (transition-property: --menu-pour-t)` — absent it, drive
the cascade with a **`transition-delay` ladder** keyed off `--menu-row-index` on a plain
`opacity`/`translate` transition (the classic staggered-delay pattern — works back to Safari
9, compositor-only). The registered-scalar form is the Chrome/Safari-18 refinement; the delay
ladder is the everywhere floor. (b) Add `webkit` to the G8 paired-engine matrix and assert the
delay-ladder stagger on the <18 arm, NOT just the scalar.

## R3 — the ANTICIPATION (G5) is sub-perceptual; the headline "welling recoil" is a fiction

§1/§3b sell "a hair of recoil (anticipation), the menu recoils back into the trigger." Measured
(Chrome 149, fresh closed→open, tight rAF): closed scale **0.9135**, observed min **0.9131** — a
**0.04% dip** (theoretical max with the punch curve's −0.032 trough = 0.9135 + (−0.032)(1−0.9135)
= 0.9107, a **0.3% recoil**). Human scale-change perception floors around ~1%. **The anticipation
is invisible** — at 0.3% theoretical and 0.04% observed it is below threshold, and G5's "scale
DIPS BELOW CLOSED (recoil)" is technically true only by sub-pixel.

Root cause: the punch `linear()` trough is applied to the *normalized* 0.9135→1.0 interp, so the
sub-zero portion only scales the 0.0865 travel — it cannot recoil the menu meaningfully smaller
than its already-near-1 enter-scale. The "welling FROM the trigger" the iOS-27 reference shows
needs a much deeper squish origin OR an explicit pre-frame at a smaller scale, not a curve trough
on a shallow interp.

ALSO: G5/G6/G8 are spec'd as main-thread **"frame-series"** gates, but `scale`/registered-prop
transitions run **off the main thread on the compositor** — `getComputedStyle` cannot observe the
intermediate frames (my sample gap: 9ms → 355ms, nothing in between; the spike's own pre-dip is
unobservable). **The gate as written cannot measure what it asserts in Chromium.**

**HARDENING:** (a) Deepen the enter squish so the recoil is real: `--glass-reveal-enter-scale:
calc(1 - 0.20 * var(--motion-weight))` (≈0.876→0.83 effective trough) OR add a tiny explicit
`@starting-style`/closed-frame recoil so the dip clears ≥1% and is felt. (b) G5/G6/G8 must
measure via `performance_start_trace` compositor frames OR a `requestAnimationFrame` driven
**Web Animations getComputedTiming / element screenshot diff per frame**, NOT main-thread
`getComputedStyle` sampling — state this in §9 or the gate is unfalsifiable.

## R5 — the POUR translate is CLIPPED by the scroll container (overflow-y:auto)

`[data-slot=select-content]` ships `overflow-y: auto` + a `max-height` clamp (verified
`select.css:42`). The pour's `translate: 0 -0.4rem` drops each row in *from above its slot*. The
top row pouring from −0.4rem above its position sits **inside the scroll clip** — its
"drop-in-from-above" arc is sheared at the menu's top inner edge. Visually the top-of-list arc is
amputated; only rows below the fold pour cleanly.

**HARDENING:** either pour with a `translate` that arrives from *below* (positive → settle, so
the motion is always inside the box), or add a small top inset / `scroll-padding` so the −0.4rem
travel lives in unclipped space, or clamp the arc to 0 for row 0. Note this in §4 + add a G8
sub-assert that row-0's arc is not clipped.
