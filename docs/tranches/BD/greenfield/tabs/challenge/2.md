# CHALLENGE #2 — Cross-engine / Safari / Perf / a11y adversarial lens on the TABS GOLDEN

**Verdict: SURVIVES (the spine is fit), but with REAL refutations that must be hardened.**
The structural backbone (extract `.glass-capsule`, widen the W55 seam, mint the cartoon
substrate, add the 2nd `useLiquidFlex` channel, born-RED recess/blob/hover) is sound and
disk-verified. But the GOLDEN ships at least **one false cross-engine safety claim**, a
**flaky non-deterministic gate** whose own committed artefact captured a FAILURE, an
**overshoot that violates its own anti-taffy fence**, and **several under-counted
edit-sites**. None sink the design; all must be fixed before the gate can be trusted.

---

## R0 (TOP REFUTATION) — the §6 "capsule sits OVER the track, not nested inside its blur" claim is FALSE; it IS nested → real Safari double-blur

GOLDEN §6: *"Capsule fill — `backdrop-filter` on the surface's OWN layer (the capsule
sits OVER the track, not nested inside its blur → the §L1 'glass cannot sample glass'
trap avoided)."*

**Live-measured on `/navigation/tabs` (Chrome, this session):**
```
indicatorIsChildOfTrack: true
trackBackdropFilter:      blur(8px) saturate(1.4) brightness(1.02)
→ GLASS-IN-GLASS: the .segmented-indicator IS a DOM child of the
  .segmented-tabs track, and the track HAS its own backdrop-filter.
```
The spike reproduces the same nesting (`spike.html:167` — the `#ind` is a child of
`.segmented-tabs`, which sets `backdrop-filter: blur(8px)` at `:87`).

A `backdrop-filter` element nested inside another `backdrop-filter` element samples the
**parent's already-filtered output**, not the page backdrop. Blink and WebKit resolve
this nesting differently (WebKit's backdrop-root handling for nested filters has shipped
divergences for years), so the capsule's `blur(13px)` over the track's `blur(8px)` will
NOT read identically Chrome vs Safari — exactly the cross-engine parity the GOLDEN
claims to have eliminated "by construction." The §6 floor is built on a DOM-structure
assertion that contradicts the actual component.

**Hardening:** drop the §6 nesting claim and EITHER (a) lift the indicator out of the
track's backdrop-filter subtree (a sibling, not a child — but `anchor()` + the
`inset`-glide assume the current parentage, so this is a real structural change, not a
hand-wave), OR (b) accept the nested-glass and add a paired-engine π arm that
*measures* the capsule-over-track luminance/blur delta in BOTH webkit and chromium and
asserts it within tolerance — never assert "identical by construction." The honest line
is: the blur is nested, so parity must be **proven**, not declared.

## R1 — the §8 "born-RED gate" is born-FLAKY; the committed spike artefact froze a FAIL

The spike's own `window.__gate()` is the prototype of the §8 acceptance bar. Run live
this session, 6 consecutive runs over the unchanged spike:

```
run1 fit 0.056 frames 7 PASS
run2 fit 0.062 frames 6 FAIL
run3 fit 0.050 frames 6 PASS
run4 fit 0.086 frames 7 FAIL
run5 fit 0.047 frames 5 FAIL   (overshoot 1.223)
run6 fit 0.056 frames 7 PASS
```
**3 PASS / 3 FAIL.** `shrink_PASS` is `fitDelta < 0.06`; the measured fitDelta
oscillates **0.047–0.086** straddling the threshold, and the frame count is only **5–7
rAF samples** across the whole 700 ms envelope — so whether a sample lands near the
release is luck. This is precisely the "computed-not-measured / flaky" failure §8 swears
to forbid, reintroduced one layer down.

**Hard proof of the inflation:** `golden/spike-light.png` and `golden/spike-dark.png`
(the committed "GREEN both modes" §9 artefacts) show the on-page readout frozen at
`"ALL_PASS": false`, `"shrink_PASS": false`, `"fitDelta": 0.074`, `"frames": 0`. GOLDEN
§9 reports `peak 1.163×, end fitDelta 0.000, ALL_PASS GREEN`. **The committed evidence
contradicts the table it is cited to support.** Either the table was hand-edited or a
different run was screenshotted; either way "live-verified GREEN" is not what the
artefacts show. This is the cardinal-lesson inflation (the captured DELTA must MATCH the
claim).

**Hardening:** (a) the gate must sample the bbox at a fixed, dense cadence (e.g. a
`MutationObserver`/timestamped capture every animation frame for the FULL clock, not a
700 ms race that yields 5 samples) and assert on the **monotone shrink-to-fit tail**
(the last N frames strictly decreasing toward target ±2%), not a single end-frame
delta near a knife-edge; (b) re-shoot the spike PNGs from an actual GREEN run and
correct the §9 numbers to the real measured values (overshoot ≈1.21, not 1.163); (c) the
real π must run the morph N times and require N/N green, never 1 lucky frame.

## R2 — the area overshoot (~1.21) BLOWS PAST the GOLDEN's own ≤1.12 anti-taffy fence

GOLDEN repeatedly fences area at **≤1.12** ("the area blob caps ≤1.12 (anti-taffy)",
§1; "cap ≤1.12", §0/§3b; "blob cap >1.2 RED", §8). But the **measured** peak overshoot
in the spike is **1.21–1.223** every run — because the visible bbox AREA is
`--tab-blob × --stretch` on the long axis composed against the short axis, and at peak
`blob≈1.10 × stretch≈1.12 ≈ 1.23` on the elongated axis, which the area metric reads as
~1.21. The "≤1.12" claim conflates the *per-channel* blob scalar with the *composed*
visible area. So the design's own §8 detector bite ("a blob cap >1.2 RED") would fire on
the GOLDEN's own default tuning. Either the fence is wrong or the tuning is taffy.

**Hardening:** define the fence on the **composed visible area** (blob×stretch), not the
bare `--tab-blob` scalar, and re-derive the caps so the *product* stays ≤ the intended
taffy bar (drop `--tab-indicator-max-stretch` further, or cap blob lower, so
blob×stretch ≤ ~1.14). State the metric the gate measures (composed area) and tune to
THAT number. Today the prose says 1.12 and the pixels say 1.21.

## R3 — "compose `--tab-blob` into THE ONE existing scale write" undercounts the edit sites (KISS/DRY claim is overstated)

§3b: *"The CSS composes it into the **ONE** existing `scale` write
(`segmented-tabs.css:121`)."* Disk truth — there are **four** `--stretch`-bearing scale
writes:
```
:121  .segmented-indicator                     scale: var(--stretch) calc(1/--stretch)   (horizontal)
:129  .segmented-tabs--vertical .…-indicator    scale: calc(1/--stretch) var(--stretch)   (vertical)
:311  .…--underline …mark                       scale: var(--stretch) 1                    (paper-mark H)
:324  .…--underline--vertical …mark             scale: 1 var(--stretch)                    (paper-mark V)
```
GOLDEN §8 also demands `variant="underline"` reads a crisp SLIDE with **zero area
inflation** — which means the underline mark's two arms must explicitly NOT receive
`--tab-blob`. So the change is at minimum the two indicator orientation arms PLUS a
deliberate exclusion on the two underline arms — not "ONE write." The byte-minimal DRY
framing is marketing; the real diff touches 2 inflate-sites + 2 must-not-inflate sites.

**Hardening:** enumerate all four sites; apply `--tab-blob` to `:121` and `:129` only;
leave `:311`/`:324` on bare `--stretch` (no blob), and let the §8 underline arm guard
the exclusion. Drop "the ONE write" language — it is false and hides a real edit surface.

## R4 — the `plus-lighter` flood has NO isolation group → Blink/WebKit blend divergence

The flood `::after` uses `mix-blend-mode: plus-lighter` (§4, spike `:131`). Measured
live: the indicator host is `isolation: auto`, `mix-blend-mode: normal`, no isolated
stacking context. `plus-lighter` without an explicit `isolation: isolate` on the host
blends against whatever sits behind the element in the same stacking context — and
WebKit vs Blink have documented divergence for `plus-lighter`/`plus-darker` compositing
when no group is established (WebKit historically treats `plus-lighter` as a -webkit
group-only blend). GOLDEN asserts "plus-lighter blend + opacity: Safari-safe, sRGB" with
no isolation and no @supports floor. Also the flood gradient uses `color-mix(in oklab,
…)` — an oklab interpolation feeding a `plus-lighter` layer mixes a wide-gamut
interpolation with an additive sRGB-ish blend; the "sRGB-safe" label is asserted, not
shown, and the interaction is exactly the color-interp gap this lens exists to catch.

**Hardening:** put `isolation: isolate` on the `.segmented-indicator` (the flood host) so
`plus-lighter` composites inside a defined group identically on both engines; add an
`@supports (mix-blend-mode: plus-lighter)` floor with a plain `opacity`/`screen`
fallback; and decide the flood gradient's interpolation space deliberately (`in srgb`
for the additive layer, since the blend is additive-sRGB) rather than `in oklab`. Add a
webkit π arm that samples the flood's peak accent luminance, not just chromium.

## R5 — `@property --tab-blob` interpolation on the SAME `transition` as `scale`: a registered scalar inside a `calc()` does not animate the way the prose implies

§3b/§9 lean on "registration lets the CSS glide INTERPOLATE it; a bare custom snaps."
True for a property that is *itself* the transition target. But here `--tab-blob` is
consumed INSIDE `scale: calc(var(--tab-blob) * var(--stretch)) …`, and the element
transitions `scale` (the composed value), not `--tab-blob`. In the spike the smoothness
comes from transitioning `scale` directly on the cartoon-punch curve while JS snaps
`--tab-blob` to a peak then to 1 — the registration of `--tab-blob` is doing far less
than the §9 table implies (the visible glide is the `scale` transition, not a
`--tab-blob` interpolation). The real driver is the §3c `useLiquidFlex` writing
`--tab-blob` frame-by-frame OR the `scale` transition — but the GOLDEN runs BOTH a JS
release timer AND a CSS `scale` transition on the punch curve, which can double-animate
(JS sets blob=1 at releaseAt WHILE the scale transition is mid-flight on a 620ms curve →
the curve restarts from the current composed value). The spike's flakiness (R1) is partly
this JS-timer-vs-CSS-transition race.

**Hardening:** pick ONE animation authority for the area channel — either CSS transitions
`--tab-blob` itself (registered, on the punch curve) with NO JS release timer, OR JS
drives `--tab-blob` every frame via `useLiquidFlex` with NO CSS `scale` transition on the
blob axis. Running a JS snap-timer AND a CSS transition on the composed `scale` is the
"second timer" the §8 bite forbids, wearing a disguise.

## R6 — PRM/transparency carve is asserted but the spike does not exercise it; `prefers-reduced-transparency` path is unproven

§7 claims `prefers-reduced-transparency` → opaque-tier escape, recess+lift survive. The
spike has NO reduced-transparency arm and the live `.glass-capsule` opaque fallback is
not demonstrated. The recess `inset 0 1px 2px --tab-track-recess-ink` is `--foreground`
at 7%/11% — under `prefers-contrast: more` GOLDEN says it floors UP, but with no token
defined for the contrast arm, this is a phantom like the ones §0 correctly flags. Also
`reduced-motion` keeps the static recess+lift — fine — but the glyph `aria-selected`
scale base is overwritten to `calc(1 + 0.06*--motion-weight)`; under PRM `--motion-weight:0`
gives `scale:1` (correct), but this COLLIDES with any extant `aria-selected` transform
(live shows the selected tab currently at `scale:1` with only `transition: color 0.2s` —
so adding a `scale` transition is additive, but the GOLDEN must confirm no existing
`:246` rule sets translate/scale that the new value clobbers).

**Hardening:** add explicit reduced-transparency + contrast-more arms to BOTH the spike
and the π; define the `prefers-contrast: more` recess-ink token as a real per-mode pair
(not prose); and diff the existing `:246 .segmented-tab[aria-selected="true"]` block to
prove the new `scale` is purely additive.

## R7 — overfit / hardcoded refs in the cited spike-as-evidence

The spike hardcodes `--glass-bg-quiet`, rims, recess ink as literal `hsl()` values
(`spike.html:33-52`) that do NOT match the live tokens (live track bg is
`color(srgb 0.994 0.96 0.926 / 0.5)`, live indicator is `oklab(0.793 0.005 0.012 /
0.84)`). So the spike proves a *look-alike*, not the shipping material. The §9 claim "it
mirrors the EXACT shipping CSS write" is true ONLY for the `scale` composition line — the
material (the warm-floor, the W55 adaptive seam, the saturate-over-field gray catch) is
faked with static hsl, so the spike CANNOT prove the §8 `meanChroma ≥ 0.02`
no-gray-over-aurora arm. That arm — the one lens-b says is the binding bar — is the LEAST
de-risked, yet is presented as covered.

**Hardening:** the §8 `meanChroma ≥ 0.02` over a LIVE aurora field must be proven on the
real component (real `--glass-bg-floating-tinted` under `saturate()` over the aurora),
not the hsl spike. State plainly that the spike de-risks the MOTION composition only; the
MATERIAL no-gray arm is unproven until the real-component π runs.
