# CHALLENGE #1 — CORRECTNESS / DEFT-INTEGRATION / KISS

Adversarial lens on `tabs/GOLDEN.md`. Default REFUTED. Every claim re-grepped on disk;
the boldest mechanism re-run LIVE in Chrome against the golden's own `spike.html`.

**Verdict: SURVIVES with a LANDING DEFECT.** The spine (extract `.glass-capsule`, union
with the shipped engine, no re-fork, compositor-only, recess + warm floor) is sound and
deftly integrable. But the headline motion claim is **self-refuted by the golden's own
spike**, and three secondary refutations land. None is fatal to the design; all need a
concrete hardening before build.

---

## R1 (TOP, LANDS) — the anti-taffy cap is arithmetically impossible; the spike DISPROVES the claim it was built to prove

GOLDEN §1 promises "the area blob caps **≤1.12** (anti-taffy)"; §3b "cap ≤1.12"; §8
expects "**~1.08–1.12× at peak**"; §9 reports the spike at **1.163×** and frames it as
GREEN proof of restraint.

Re-running the golden's OWN `window.__gate()` live in Chrome (4 consecutive runs):

```
overshootRuns: [1.211, 1.237, 1.223, 1.210]   (never 1.163; never < 1.21)
fitDelta on the headline run: 0.058            (doc claims 0.000; lands at the 0.06 edge)
```

The 1.163 in §9 is a cherry-picked low sample of a **non-deterministic, frame-timing
dependent** measurement. The true steady-state peak is **1.21–1.24×** — it ALWAYS
breaches the golden's own ≤1.12 anti-taffy fence.

This is **structural, not a tuning miss.** The cap (`--tab-indicator-blob-max` 1.10) is
on the *target value*, but `--tab-blob` is driven onto a `scale` transition timed by
`--ease-cartoon-punch`, which (live-measured) overshoots its target delta by ~1.19×
(probe: a 0→100px left interp on the curve peaks at **118.65px**, and dips to **−1.08px**
— the anticipation is real). So:

- blob axis peak = 1 + (1.10−1)·1.19 = **1.119 per axis**
- both axes carry blob → **area peak ≈ 1.119² = 1.25×**
- the WIDTH axis also carries the squish → blob·stretch peak = **1.28×**

The golden caps the *input* and never accounts for the curve multiplying the *output*.
"Caps ≤1.12" and "rides the punch curve" are mutually exclusive as written. The §8 gate
that asserts `overshoot > 1.04` is **born-RED on HEAD** correctly, but its UPPER bound
(implied "~1.08–1.12") is silently absent from the gate code — so the gate would GREEN a
1.4× taffy blob. The detector self-test bite "a blob cap >1.2 RED" is described in prose
but **not implemented** in the spike, and the live mechanism is already > 1.2.

**HARDENING:** Either (a) drive `--tab-blob` with a NON-overshooting ease (the punch
curve's anticipation/overshoot belongs to the GLIDE leg only, not the area leg — split
the `transition` so `scale` rides a monotone ease while `left`/`width` ride the punch),
**or** (b) lower the blob target to ~1.045 so the curve-amplified peak lands at ~1.10×,
**or** (c) clamp the composed scale with an explicit upper-bound gate arm
(`peakArea/targetArea < 1.12 → else RED`) and re-tune until live-measured peak obeys it.
Pick (a): it preserves the cartoon punch on travel (where it reads) and kills the taffy
on area (where it doesn't). Re-run the gate until 4/4 runs land ≤1.12, and ADD the upper
bound to §8 step 2.

## R2 (LANDS) — the spike proves far LESS than §9 claims; "live-verified" is inflated

§9's table asserts the spike GREEN-proves: anticipation, "warm NOT gray both modes", the
flood ordering, the glyph-pop. Inspecting the actual `__gate` source live:

```
gateAssertsAnticipation: false
gateAssertsCenterPinDuringFlight: false   (only END cx is checked, not the flight path)
gateChecksColorOrChroma: false             (no meanL / meanChroma / rgb anywhere)
gateChecksFloodOrdering: false
```

The gate measures exactly three things: end-overshoot, end-fit, end-cx. "Warm not gray,"
"anticipation," "flood trails spatial," and "center-pin across the WHOLE envelope" are
**eyeballed from two static PNGs**, not gated. This is the cardinal "live-verified needs a
captured DELTA / paired-π, not a claim" lesson (MEMORY) recurring at the spike roll-up:
the §9 table presents screenshot-eyeball verdicts in the same GREEN column as the three
real readback assertions, conflating them.

Worse: the center-pin claim is "0px" but the gate only samples the **final** frame. A
capsule can drift wildly mid-flight (the punch curve's overshoot moves the box) and still
land at cx-delta 0 — the gate cannot see it. The §8 step-4 "stays pinned across the whole
envelope" is therefore NOT what the spike proves.

**HARDENING:** Demote §9 to "proves overshoot-then-shrink + end-centerpin ONLY." Move
anticipation (min-cx-during-flight < launch-cx), the chroma floor, and flood-ordering into
the REAL paired-engine π (§8) where painted pixels are read — do not let the spike carry
their weight. Add a mid-flight cx-extremum capture to the gate so center-pin is asserted
across the envelope, not just at rest.

## R3 (LANDS, KISS/DRY) — `.glass-capsule-hover` is a NEW fork of an EXISTING specular-lift register

GOLDEN §0/§2c assert the glassy hover is "**ABSENT** — color-only" and mints
`.glass-capsule-hover` as net-new. Disk says otherwise: `segmented-tabs.css:399`
`.glass-drag-lift` ALREADY ships the exact two-channel idiom the golden re-invents — a
sub-perceptual `--glass-specular: 0.1` catch-light lift + a `will-change: transform`
compositor hint ("the W-GLASS-CAL specular register, disco-FREE"). The golden's
`--glass-specular: 0.14` + `scale: 1.015` is the SAME register at a different magnitude.

Minting a parallel `.glass-capsule-hover` beside the live `.glass-drag-lift` is the
bolt-on/parallel-fork the golden elsewhere forbids. The two specular-lift classes will
drift. This is a DRY violation hiding inside a doc that claims "no parallel button-glass
fork."

**HARDENING:** Don't claim the register is ABSENT — it's PARTIAL (exists for drag, not for
hover). Factor the SHARED specular-lift primitive (`--glass-specular` step + optional
scale + `will-change`) once; `.glass-capsule-hover` and `.glass-drag-lift` both compose it
with their own magnitude/cursor. One register, two consumers — the golden's own KISS law.
Correct the §0 census row from "ABSENT" to "PARTIAL (drag only)".

## R4 (LANDS, overfit/source-accuracy) — a cited lever is internally contradictory on disk; the build will inherit the ambiguity

GOLDEN §0 + §3e cite the live max-stretch as **1.18** (`constants.ts:18`
`DEFAULT_INDICATOR_MAX_STRETCH = 1.18`, `scale-paper.css:57`
`--tab-indicator-max-stretch: 1.18`) — VERIFIED correct. But the SAME consumed file,
`useTabIndicator.ts:231`, comments "default **1.08** if unset," and `useDragMorph.ts:91`
asserts the cap is "**≤1.08**." The source the golden builds on disagrees with itself
1.18-vs-1.08. The golden's §3e plan ("bring 1.18 DOWN to ~1.10–1.12") will land in a file
whose own comments say 1.08 — the build agent inherits an un-flagged contradiction and may
mis-calibrate.

**HARDENING:** §3e must call out the source contradiction explicitly and pick the actual
runtime value (1.18, since `Number(capRaw) || DEFAULT` resolves to the 1.18 token/const,
NOT the 1.08 comment). Fix the stale 1.08 comments in the same wave (no-legacy law: a
comment that lies about the value IS legacy cruft). Otherwise the calibration target is
built on a misread.

  phantom. Minting `--ease-cartoon-punch` + `--motion-weight` (PRM→0) is correct and the

## Net

The design is FIT and integrates deftly. The single load-bearing crack is **R1**: the
headline 5-beat motion, as composed, produces a **1.21–1.24× taffy peak** that breaches
the golden's own anti-taffy fence, and the spike's cherry-picked 1.163 hides it. Split the
area leg off the overshooting punch ease and add the missing upper-bound gate arm. R2–R4
are honesty/DRY/source-accuracy corrections that harden the doc without re-architecting it.
