## TOP REFUTATION (the one that lands hardest)

### R1 — The "BROKEN consumer" verdict + the "stuck/born-skipped-forever" gate clauses are
### a STATIC-READ inference that DOES NOT REPRODUCE LIVE. Clause A's "frozen forever" framing is FALSE.

The golden's table (lines 38-46) brands goo-blob and concentric **BROKEN** and asserts a
**"born-skipped 2nd-canvas-forever"** trap + an aurora **"frozen 300×150"**. I tested all three
routes live. None of those permanent-failure claims reproduce in Chrome:

| Route | Live result (chrome-devtools, dpr 2) | vs golden claim |
|---|---|---|
| `/substrates/aurora` #1 | 300×150 at T0 → **self-heals to 1012×576 by 2.5s** | "frozen 300×150 at T0" — *transient, NOT frozen*. The rAF-double-resize (runtime.ts:352) heals it. |
| `/substrates/blob` (2 canvases, one `offFold:true`) | **BOTH 1116×640 = round(558×2) at T0**, incl. off-fold | "BROKEN, freezes at canvasSize constant" / "2nd-canvas-forever" — *neither reproduces* |
| `/substrates/concentric` | **1012×576 = round(506×2)**, never 640 | "BROKEN, freezes at 320-const" — *does not reproduce* |

Root cause of the gap: the "BROKEN" verdict assumes `clientWidth===0` under a `content-visibility`
skip. **The golden's OWN spike README (lines 33-36) admits this is false** — "`clientWidth` is NOT
reliably 0 under a content-visibility skip (Chromium reported 952 here)." So the broken branch
(`|| constant`) is **never taken** on the real routes in Chrome. The only place the trap bites is
the spike's *artificial* C2 case (a `display:contents` canvas with `gBCR(self)=0`) — a construction
**no real consumer uses**. The live blob 2nd-canvas under a CV ancestor still reported `clientWidth=558`.

**Why this matters (not pedantry):**
1. **Gate clause A is partly born-GREEN, not born-RED, as written.** "aurora #2 (below-fold)
   300×150 forever" and "frozen 300×150 at T0" are the RED justifications. Live, the below-fold
   blob is 1116×640 and aurora heals. The clause that is *genuinely* RED is narrower: *aurora's
   T0 first-paint window* + *any route that actually parks a canvas under a CV-skip on a WebKit
   engine where clientWidth truly zeroes*. A born-RED gate that asserts a condition the live page
   does not exhibit will either be re-written to pass trivially or will FALSE-FAIL honest code.
   The cardinal-lesson inflation (live-verify DELTA, not a claim) applies to the golden's OWN
   diagnosis table.
2. **The "DELETE the N broken copies" prune is sold on a false-urgency.** The DRY win is real and
   worth doing, but the copies are *drifted*, not *live-broken*; the wave note must say "unify for
   DRY + WebKit-clientWidth-zero safety," not "fix the live stuck canvas in blob/concentric"
   (which is not stuck).

**HARDENING:** Re-state the diagnosis table with the LIVE column: aurora = *transient* T0 blur
(heals via the double-rAF), blob/concentric = *latent* drift that only bites where `clientWidth`
zeroes (WebKit CV-skip / `display:contents`), NOT live-stuck in Chrome. Re-scope clause A: assert
`canvas.width === round(box×dpr)` **at T0, frame 0, before any rAF** (this is where aurora is
genuinely RED and where G2's sync-at-mount is the cure) — drop "forever/frozen." Add an explicit
WebKit arm to clause A (run the same probe under webkit where the `clientWidth`-zero actually
manifests) so the RED is engine-honest, not a Chromium artifact that the spike itself disclaims.

## R3 — G1's body is a RE-INVENTION of aurora's sizer, not "aurora's verbatim logic promoted."

The golden (line 88-89) sells `sizeBacking` as aurora's body "promoted, not re-invented." They
differ in the ONE dimension that matters for the spike's own keystone proof:

- **aurora (runtime.ts:305-307):** `parentRect = canvas.parentElement?.getBoundingClientRect()` —
  a **single** parent level. `cw = rect.width || parentRect?.width || 1`.
- **`sizeBacking` (GOLDEN line 107-110):** a **`while` loop walking the FULL ancestor chain**.

These are not the same function. The spike's decisive C2 (`display:contents` canvas → real
ancestor 600×300) **only passes because of the while-loop**; on aurora's actual one-level sizer,
a box-0 element two levels below a laid-out ancestor would still floor to `1`. So the golden
*improved* aurora's sizer (good!) but mislabels it "verbatim," which (a) undercuts the
"survival-of-the-fittest, keep-the-fit-code" claim — this is REFINE, not KEEP — and (b) hides that
the new while-loop is an **unbounded ancestor walk** with no depth cap: on a deeply-nested skipped
tree it walks to `<body>` every RO tick. KISS violation: aurora's one-level fallback was a
deliberate bound; the unbounded walk trades a known floor for an O(depth) gBCR storm on every
resize of every viz (gBCR forces layout).

**HARDENING:** Call G1 a REFINE of aurora (not "verbatim promote"). Cap the ancestor walk (e.g. 3
levels, or stop at the first `content-visibility` ancestor — which G2 already locates) so it is not
an unbounded layout-thrash. Add a clause to the gate: `sizeBacking` causes ≤1 forced reflow per
resize tick (assert via a PerformanceObserver layout count), so the DRY win doesn't import a perf
regression onto the N viz that previously did one gBCR.

## SECONDARY REFUTATIONS (do not sink the golden, but must be folded)

### R4 — G2's "frame 0 has a sharp buffer before the device exists" overstates what is wireable.
useWebGPUCanvas.ts:14-17 + :420 (`acquireDevice`) show `lifecycle.arm()` (→ `build()` → `resize()`)
is reached **only after** the async device acquire resolves (or times out). So sizing "synchronously
at mount before the acquire" is NOT just "move the RO up" — it requires a NEW pre-arm code path in
the leaf that runs `sizeBacking` + a transparent surface BEFORE `arm()` is ever called. That is a
genuinely new mechanism (a "pre-arm size" phase), not the "thin union, no new path" the golden
claims (line 83). It is achievable and worth it, but the golden under-scopes it. **HARDENING:** name
the new leaf phase explicitly (`presize()` called from the substrate factory before `armAsync()`),
and acknowledge it is a new public seam on the leaf, not a zero-surface move.

### R5 — G1's "consumer resize collapses to one line" is an N-consumer BREAKING signature change.
Today every consumer `resize` is a zero-arg closure over `gl`/`prog` (useWebGLCanvas.ts:216
`resize: () => frameHooks?.resize()`). The golden's new contract passes `BackingSize` INTO
`resize(s)`. That changes the hook signature for **every** backend + **every** consumer
simultaneously — a coordinated breaking change, not "a one-line shrink per viz." It is the right
design, but the golden's "no churn at the leaf's call-sites" (line 121) is false: the call-sites
keep their NAME but change their ARITY and their semantics (measure→upload), which is exactly the
kind of silent prop/signature drift MEMORY's `glass_ui_binding_verification` lesson warns goes
uncaught by vue-tsc. **HARDENING:** flag the signature change as the wave's primary churn surface;
require a typecheck + an e2e paint pass per consumer (not just unit), and enumerate ALL consumers
touched (the golden lists 7 in the prune but the resize-arity change hits every GL+WGPU setup pair
— ~16 files).

### R6 — G3 "compose IO into the leaf, retire per-consumer `useIntersectionPause`" risks a
double-write / double-park. aurora/goo-blob/goo-dot CALL `useIntersectionPause` today; if
`createGpuSubstrate` ALSO composes it, the retirement must be atomic per-consumer or two IO
observers write the same `off-screen-io` reason (the one-writer-per-reason invariant the leaf
relies on — createCanvasLifecycle suspend-Set). The golden asserts the invariant "holds" but does
not show the retirement is same-commit as the composition. **HARDENING:** gate G3 with a clause that
asserts exactly ONE IO observer per canvas after the change (count `IntersectionObserver`
instances, or assert the reason-Set never receives a duplicate add), and require the per-consumer
`useIntersectionPause` deletion in the SAME diff as the leaf composition.

### R7 — born-RED gate naming collides with an existing fleet. There are already
`proof:substrate-cohesion`, `proof:substrate-staging`, `proof:substrate-paints-color` (package.json
:899-943). The golden's `proof:substrate-golden` is net-new (good for born-RED) but the doc never
says how it relates to the extant substrate gates — risk of a parallel-gate fork (the very
anti-pattern the lens hunts). **HARDENING:** state whether `proof:substrate-golden` SUBSUMES or sits
beside the existing trio, and ensure clause C/E reuse `proof:substrate-paints-color`'s probe harness
rather than re-rolling a fourth screenshot pipeline (DRY at the gate layer too).

## BOTTOM LINE

The golden's SPINE (G1 sizer unify + G2 sync-at-mount decouple) is a correct, deft, real-wound-
closing union and SURVIVES. But it survives DENTED: the diagnosis table inflates a transient/latent
drift into a live-permanent-stuck claim that the routes refute (R1); the signature move G6 cites two
non-existent tokens as shipped (R2); G1 is a relabeled refine with an unbounded-walk perf foot-gun
(R3); and three scope claims ("no new path," "one-line shrink," "invariant holds") understate the
real churn (R4-R6). Land the seven hardenings and it converges. Ship it as-written and the born-RED
gate will either false-pass (clause A asserts a non-live condition) or block on a token that doesn't
exist (clause F), and an implementer will trust "verbatim/shipped/zero-new" labels that aren't true.
