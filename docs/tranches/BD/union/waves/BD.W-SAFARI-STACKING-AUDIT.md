## The defect / the ask

The SEED roster (`SEED-DRAFT.md` line 30, Band 8) names this verbatim: "**W-SAFARI-STACKING-AUDIT [NEW]** (the backdrop-filter-dead-inside-transformed-descendant DOM-hierarchy gate)." The charter §8 (Safari-first ABSOLUTE) lists "the backdrop-stacking-context trap audited" as a binding fence. The orchestrator notes (ORCHESTRATOR-NOTES §"SAFARI/WEBKIT IS ABSOLUTE") demand every glass AND goo move ship Safari-first with no Chromium-only path.

**The trap (a real cross-engine paint fact):** a `backdrop-filter` samples the content painted BEHIND the element in its STACKING CONTEXT, walking up to the nearest backdrop root. When an ANCESTOR establishes a NEW stacking context that ISOLATES the subtree (a `transform`, `filter`, `opacity < 1`, `will-change: transform`, `isolation: isolate`, `contain: paint`), the backdrop-filter element can no longer reach the page behind it — it samples a BLANK/own-subtree surface and the glass plate paints over NOTHING (a transparent or flat plate, the glass-dies-silently class). Safari/WebKit is STRICTER about this than Chromium — a layout that "looks fine" on Chrome can paint a blank dock plate on Safari. The morphing dock is the load-bearing case because the morph wave (BB.W-DOCK-MORPH-FAMILY) introduces `transform: scale` + `will-change: transform` onto morph elements — exactly the stacking-context establishers that can orphan a descendant's backdrop-filter.

The audit must PROVE the current dock DOM keeps the backdrop-filter PLATE and the morph TRANSFORM on SEPARATE elements (the plate is NOT a transformed descendant of the morph wrapper) — and gate it so a future refactor cannot invert the hierarchy unaudited. The HEAD facts:

1. **The plate's `backdrop-filter` lives on `.glass-dock` (the root).** Read `src/styles/dock/shell.css:149` — `.glass-dock { backdrop-filter: var(--dock-surface-blur); }` (the dock glass plate), and `shell.css:115` — `.glass-dock { contain: layout style paint; }` (a stacking-context establisher on the SAME element). The plate IS the dock root.

2. **The morph `transform: scale` lives on `.dock-layers` (a DESCENDANT of `.glass-dock`).** Read `src/styles/dock/layers.css:59-90` — `.glass-dock[data-morphing] .dock-layers { transform: scaleX(var(--dock-morph-scale)); will-change: transform; }` (BB.W-DOCK-MORPH-FAMILY). The morph transform + its `will-change` (both stacking-context establishers) sit on `.dock-layers`, BELOW the plate, not ON the plate.

3. **So the CURRENT arrangement is SAFE — but un-asserted.** The backdrop-filter plate (`.glass-dock`) is the ANCESTOR; the morph transform (`.dock-layers`) is its DESCENDANT. The plate's backdrop sampling walks UP past the dock to the page — it never crosses the descendant's transform. The dock glass paints correctly on Safari. BUT: there is no gate proving this DOM invariant. A future wave (the BD now-playing pill `<DockNowPlaying>`, the goo-split sub-dock, the fission morph) that wraps the plate INSIDE a transformed morph container — OR re-points `transform: scale` onto `.glass-dock` itself alongside its backdrop-filter — would orphan the plate's backdrop on Safari with no test catching it (the chromium-headless projects are more forgiving). The `.glass-dock[data-morphing]:not(.vertical)` ROOT box rides an `inline-size` CALC (layers.css:105-118), NOT a transform — so the ROOT keeps NO transform on the backdrop element (the morph-axis size is a `calc()`, not `scale`); this is the load-bearing distinction the gate must preserve.
