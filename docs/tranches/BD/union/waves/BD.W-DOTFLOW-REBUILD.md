## The defect / the ask (live-confirmed — `page-audit/substrates.md §5`)

The dot-flow-field canvas (`data-testid="dot-flow-field-canvas"`, 2066×920 real pixels, WebGPU context, `navigator.gpu` present, NOT paused) paints ZERO lit pixels: a `drawImage` → `getImageData` sample returns **`meanLum: 0, maxLum: 0, litFrac: 0`** — no console error. The README/blurb describe "a calm anchored dot-matrix a LARGE wave sweeps slowly through" (and the wider W-DOT-IMAGE "wave washes over / arbitrary image tessellation" register), but the page renders NOTHING. Two compounding causes:

### (a) The render is DEAD under WebGPU (a real `src/` bug)

The field self-stages WebGPU-first (`useDotFlowField.ts:175` `setupWGPU: createFlowWGPUSetup`): a compute pass advects the lattice + a render pass draws instanced billboard quads against `context.getCurrentTexture()`. The live canvas is a `webgpu` ctx but draws nothing. The candidates (the build's §"Confirm the render path" arm pins which):

- **The compute→render two-pass produces no output** — the compute pass writes a storage buffer the render pass reads; a bind-group / storage-buffer-usage mismatch (a `STORAGE` vs `VERTEX` usage flag, a stale bind group across the swap-chain texture re-acquire) yields a clean-but-empty draw (no validation error, no pixels).
- **OR the WebGPU swap-chain output is not landing on the VISIBLE canvas** (the same WebGPU-output suspect as W-PRESET-RENDER, but here the read target is the on-SCREEN present, not a `toDataURL` readback) — e.g. the render pass `loadOp:"clear"` clears to the background but the instanced draw never reaches the attachment (a `colorAttachment` / pipeline-target-format mismatch).
- **The WebGL2 fragment fallback (`setupGL`) NEVER runs here** — it is only reached when WebGPU is ABSENT (the picker arms WebGPU because `navigator.gpu` is present), so the dead WebGPU path is the live one. The fallback's health is NOT the cover (the WebGPU primary must paint).

### (b) Invisible-by-DESIGN even if it painted (the D0 contrast-dead default)

`DEFAULT_FLOW_CONFIG` (`constants.ts:101`) is warm-cream dots (`WARM_IDENTITY_PALETTE`, L:0.92 C:0.03 h:78) over `background: "transparent"`, `globeMask: false`, `dotSize: 2.0`, `contrast: 0.6`. The demo page (`dot-flow-field.vue`) mounts it in a `<ShowcaseFrame tier="field">` over the manifest `background: "grid"` (a LIGHT-GREY page wash). **Warm-cream dots over a light-grey page = near-zero contrast** — even a WORKING field reads as near-nothing. The MONO-on-near-black REFERENCE preset (the look the spec wants — `FLOW_PRESET_MONO_REFERENCE`, `presets.ts:44`: a warm near-black ground L:0.1 + mono-warm-white dots L:0.95) is OFF by default (the demo Switch defaults `useReference: false`, `dot-flow-field.vue:22`). So the page LEADS with the contrast-dead warm-cream variant on a contrast-dead light stage.

The ask (folds W-DOT-IMAGE + W-VIZ-PRESENCE): (1) fix the WebGPU render so the canvas paints; (2) put it on a CONTRASTING stage so the dots READ (the field functions to the "wave washes over / anchored dot-matrix" spec); born-RED on `litFrac:0`.

## The mechanism — confirm + repair the render, then stage it to READ

### 1. Confirm the render path (the §(a) diagnosis — pin the dead WebGPU output)

The build's FIRST arm is a faithful WebGPU-output trace (the same diagnosis discipline as W-PRESET-RENDER, but on the ON-SCREEN present, not a readback):

- **Drive a single deterministic frame** (`renderAt(1.0)` on the capture handle, OR the live loop) and read the VISIBLE canvas pixels (`getImageData` over the canvas backing store — the on-screen present, NOT a `toDataURL`). `litFrac:0` confirms the dead render.
- **Bisect the two-pass output:** (i) read the compute storage buffer back (a `copyBufferToBuffer` → `mapAsync` of the particle buffer) to confirm the compute pass advected real positions (non-zero displacement off the lattice); (ii) confirm the render pass's `colorAttachment` targets `context.getCurrentTexture().createView()` with a matching `format` (`navigator.gpu.getPreferredCanvasFormat()`) + `loadOp:"clear"` to the background + `storeOp:"store"`; (iii) confirm the instanced draw count + the bind group are bound BEFORE `draw`. The dead pixel set means EITHER the compute buffer is empty (a usage/binding bug) OR the draw never reaches the attachment (a pipeline-target-format / vertex-buffer mismatch).
- **The fix is the named buffer/binding/format mismatch** the bisect surfaces — NO shader-math edit (the `flow-field.compute.wgsl`/`flow-field.render.wgsl` math is the BC.W-VIZ-DOTFLOW retopology, gate-fenced; the bug is in the PLUMBING — the buffer usage flags, the bind-group layout, the attachment format — not the Gerstner evaluator). IF the bisect finds the WebGPU output genuinely cannot land on this host (a lying-adapter / headless-Metal class), the picker's WebGL2 fallback is the correct degrade (`useGpuSubstrate`'s `armAsync` validation-probe fall) — but the WebGPU primary must paint on a real GPU, and the gate's live arm runs on a real GPU.

The PAGE background promotes off the dead light-grey `grid` to the field's OWN near-black ground (the viz IS its own background, full-bleed — W-PAGE-BACKGROUND), so the dots read against the dark ground the field paints. This is presets-in-consumers (the near-black ground stays a DEMO preset; the library `DEFAULT_FLOW_CONFIG` warm-cream identity is byte-UNTOUCHED — `proof:viz-dotflow` F5 holds).
- **Stage B — a contrasting STAGE under the warm-cream default.** Keep the warm-cream library default but mount it over a CONTRASTING dark stage (a `ShowcaseFrame tier="field"` over a dark page background, OR the field's own dark ground via `background` set to near-black in the demo config) — so the warm-cream dots read against a dark backdrop. The "wave washes over" spec (W-DOT-IMAGE's stateless `f(uv,t)` reveal front) is the field's existing `waveBand`-driven sweep (`flowField.ts` `sampleHeight` — the LARGE iso-band crossing the lattice); this wave confirms it PAINTS + READS, and books the full `target` coverage axis (generative/texture/sdf) to W-DOT-IMAGE (the sibling — this wave is the render+presence floor it builds on).

## Shared root, divergent FIX (the W-PRESET-RENDER relationship)

W-DOTFLOW-REBUILD and W-PRESET-RENDER SHARE the **WebGPU-output root family** — both surfaced because a WebGPU canvas's drawn output does not land where a consumer reads it. But the FIX DIVERGES, because the READ target differs:

- **W-DOTFLOW-REBUILD is a VISIBLE-RENDER bug.** The dot-flow canvas IS the on-screen present (the user looks at the swap-chain DIRECTLY — there is NO `toDataURL` readback for the live view), yet it paints `litFrac:0`. So the fix is the render path (a compute/render buffer/binding/format mismatch — the PLUMBING, not the math) + a CONTRASTING stage. There is NO readback to repair for the on-screen view.
- **W-PRESET-RENDER is a READBACK bug.** The thumbnail bake reads the swap-chain via `toDataURL` AFTER present → empty. The drawn frame is FINE; the OFF-SCREEN READ is broken (a same-tick read / a readback-capable backend / an owned target).

So the two waves are SIBLINGS, not duplicates: the shared diagnosis is "trace the WebGPU output path," but W-DOTFLOW-REBUILD fixes the ON-SCREEN render + stage and W-PRESET-RENDER fixes the OFF-SCREEN readback. Each carries its OWN born-RED gate (`proof:dotflow-rebuild` on `litFrac`; `proof:preset-render` on thumbnail variance). They do NOT block each other (no dependency edge). The ONE place they re-converge: IF this wave's §1 bisect finds dotflow's dead render is the SAME swap-chain-present class (the WebGPU output genuinely not landing), and IF dotflow owns a capture/parity READBACK (the `flow-field-wgpu-parity-capture` arm), that readback inherits W-PRESET-RENDER's same-tick discipline — but the live ON-SCREEN view is fixed here, independently.
