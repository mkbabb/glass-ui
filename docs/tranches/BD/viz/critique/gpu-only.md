## H1 (LOAD-BEARING HOLE) — the reorder does NOT eliminate the canvas-clone; it only shrinks WHEN it fires. The pipeline-validation poison survives.

The doc's keystone (§3) — "`requestAdapter()` doesn't poison, only `getContext("webgpu")` does, so probe the adapter first and the clone evaporates" — is TRUE for **two** of the THREE WebGPU init-failure classes, and the third is the one that ACTUALLY poisons the canvas mid-flight:

- `acquireDevice()` (`useWebGPUCanvas.ts:291`) runs `requestAdapter` → `isSoftwareWebGPUAdapter` → `requestDevice` — ALL before any getContext. The selector CAN hoist these. ✓ (adapter-null + software-adapter)
- BUT the **`pipeline-validation` reject** (`armAsync` line ~378, kind `"pipeline-validation"`) fires AFTER `lifecycle.arm()` has already run `buildContext()` → **`canvas.getContext("webgpu")` (line 197)** → `setup()` → the one-shot probe draw inside `pushErrorScope("validation")`. This is the **"lying adapter"** — a Metal adapter reporting `apple/metal-3` that passes `requestAdapter`/`requestDevice` cleanly yet cannot validate the consumer's metaball/aurora pipeline (the documented headless-software-Metal class, the exact reason the validation probe exists at all).

The selector CANNOT move this check earlier — you cannot validate a render pipeline without a configured `webgpu` context, and configuring the context IS the poison. So on a lying-adapter host the canvas is ALREADY poisoned when the reject fires, and the WebGL2 net STILL needs `freshCanvasForFallback`. **The clone + `fallToWebGL2` chain do NOT evaporate — they survive for the pipeline-validation class.** The "~120 LOC evaporate" / "the chain is GONE" claim is overstated; what's actually true is "the chain fires for one rarer class instead of all three." The doc must either (a) keep a residual single-class fall-chain (contradicting "the chain evaporates / armAsync-only seam") or (b) DROP the pipeline-validation probe and accept the `[Invalid RenderPipeline]` per-frame flood on lying adapters (a hard regression the probe was built to kill, BC.W-WEBGPU-EVERYWHERE). Neither is acknowledged. This is the single biggest gap and it directly undercuts the wave's headline elegance claim. **FIX: re-scope the doc to "the selector handles adapter-null + software-adapter pre-getContext (the common 99% of falls); the pipeline-validation class either keeps a one-canvas-clone residual OR is demoted to onInitError." Quantify honestly — it's not 120 LOC, it's the clone + a narrowed chain.**

§9-G + §10 assert the spine changes ZERO live pixels "every viz already paints WebGPU/WebGL2." That's true for a real-GPU END USER. But it is FALSE for the tranche's CI: the headless π runner + the `:5199` SwiftShader capture path is EXACTLY a software-adapter host that, under HEAD, falls to WebGL2 and PAINTS. Under the new policy a `"none"` verdict (software-WebGL + no real WebGPU) arms NO loop → **the inert placeholder, not the field.** The doc's §5a says the circuit-breaker "survives as `"none"`" — but the siblings explicitly flagged that the headless contrast cert + every headless π capture rides the swraster/WebGL2-software path. If `"none"` means "don't arm," then **CI captures black/placeholder boxes and the BD charter's paint-first / live-verify discipline loses its headless floor on the same host it certifies on.** The "no ba-gestalt, zero pixels" framing hides this. The honest statement: there IS a pixel delta on the no-GPU/headless host (field-ground → inert placeholder), and that host is load-bearing for the tranche process. Must be confronted, not waved off as "no real GPU = no gestalt anyway."
