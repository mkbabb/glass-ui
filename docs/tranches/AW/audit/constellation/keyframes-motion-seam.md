# keyframes-motion-seam — the --spring-* seam is genuinely single-source; AW.W2's planned APIs all EXIST; the live drift is a PIN gap (^2.2.0||^3.0.0 vs npm 4.0.0), not an API break

## Findings

### A. The `--spring-*` token regen IS derived from keyframes spring math (single source — NOT hand-tuned)

1. `scripts/regen-spring-tokens.mjs:18,83-89` imports `springLinearStops` from `@mkbabb/keyframes.js` and emits each `--spring-{smooth,snappy,bouncy,gentle,dock}` `linear()` string by sampling the SpringProgress ODE — the `(response, dampingFraction)` PRESETS table (`regen-spring-tokens.mjs:30-61`) is the source of truth; the `linear()` stop-sets are DERIVED, never hand-precomputed. The header comment (`:5-9`) records that hand-precomputation was the pre-AL.W9-γ state and is retired. So the token block carries ZERO drift-by-hand-tuning risk **between the table and the CSS**.

2. The drift that DOES matter is dual-write between the JS runtime driver and the CSS token. `useLayerTransition.ts:19` declares `const DOCK_SPRING = { response: 0.5, dampingFraction: 0.5 }` and its own doc-comment (`:6-11`) names the contract: "MIRRORS the `--spring-dock` PRESETS row… A retune MUST touch BOTH this const AND the PRESETS row." This is a TWO-place literal that a regen does not synchronize — the regen only owns the CSS side. `proof:spring-tokens-synced` (`scripts/proof-spring-tokens-synced.mjs:37-61`) only diffs the committed CSS block against `generateBlock()` — it does NOT assert `DOCK_SPRING === PRESETS.dock`. So today the runtime/CSS dock-spring lockstep is a CONVENTION enforced by a doc-comment, not a gate. (AW.W2 closes this — see Wave-forming input.)

3. `proof:spring-tokens-synced` is fail-closed and correct for its scope: bite-check at `:13-14` (hand-edit a `--spring-*` value → RED; re-run generator + commit → green). It composes with `proof:animation-coherence` (AW.W31, planned, born-RED) which adds the no-fork-OUTSIDE-the-generator assertion. The two-gate split (generator-equality + no-external-fork) is sound.

### B. AW.W2's planned keyframes APIs ALL EXIST at the published version — the plan is idiomatic

4. AW.W2's core mechanism is "allocate a SECOND `SpringProgress` for opacity, critically-damped (ζ≈1.0), co-`play()`d from the same gesture origin; on a retarget re-seat BOTH solvers from `(value, velocity)`" (`AW.W2-dock-motion-unify.md:33-47, 117-133`). Every API this needs is present in the published `SpringProgress`:
   - `set target(value)` re-seats the closed-form solution from current `(value, velocity)` continuously (`keyframes.js/src/animation/spring.ts:237-264`, the `reseatTarget` private; the class doc `:132-147` states "Mid-frame target changes re-seat the closed-form solution from the current `(x, v)` state… API mirrors SwiftUI's `.spring(response:dampingFraction:)`"). This IS the velocity-carry primitive W2 §2 requires.
   - `get value` / `get velocity` / `get target` (`spring.ts:218-235`), `.play(onFrame)` / `.stop()` (`:458,476`), `.dispose()` (`:443`) — all present. `useLayerTransition.ts:308,317-318` already drives the SIZE spring through exactly this surface (`new SpringProgress(...); activeSpring.target = toSize; activeSpring.play(w => …)`), so the OPACITY companion is a literal duplication of an already-working pattern. No new keyframes capability is needed.
   - The phrase "SpringProgress clock SLAVED to the size morph's progress" (`AW.W2:19`) is glass-ui's own composition over two independent `SpringProgress` instances co-`play()`d — NOT a keyframes API. There is no `SpringProgress.slave()` or master-clock coupling primitive; the lockstep is "shared gesture origin + same `--spring-dock` response" (`AW.W2:39-40`). VERIFIED: no phantom keyframes API is assumed by the plan.

5. AW.W2 names "`SpringProgress` clock" (`:19`) and "two solvers" (`:36`) — both real. The plan does NOT cite a "SpringProgress.css()" or "velocity re-seat()" method that does not exist. The one place the plan reaches outside the SpringProgress surface is `springLinearStops` in the regen — also present and stable (signature `springLinearStops(opts: SpringLinearStopsOptions): string`, `keyframes.js/src/animation/springLinearStops.ts:46`, defaults `sampleCount=24`).

### C. THE LIVE SEAM DEFECT: glass-ui pins `^2.2.0 || ^3.0.0` but keyframes npm latest is 4.0.0 (the pin EXCLUDES the current line)

6. `glass-ui/package.json` peerDependencies pin: `"@mkbabb/keyframes.js": "^2.2.0 || ^3.0.0"` (verified at HEAD). npm `latest` = `4.0.0` (`npm view @mkbabb/keyframes.js version` → 4.0.0; dist-tags `{latest: 4.0.0}`). The `^2.2.0 || ^3.0.0` range does NOT satisfy 4.0.0 — a consumer that installs glass-ui 3.3.0 AND wants keyframes 4.0.0 gets a peer-range violation warning. glass-ui's own node_modules currently resolves the file-linked **2.2.0** (`glass-ui/node_modules/@mkbabb/keyframes.js/package.json` → version 2.2.0).

7. The good news: the API glass-ui consumes is NOT touched by the 4.0.0 breaking changes. keyframes 4.0.0 CHANGELOG (`keyframes.js/CHANGELOG.md` §4.0.0) breaks `tickDt(dt: ms)` (the no-arg `SmoothProgress.tick()` removed; `SpringProgress.tick(seconds)` demoted to private `@internal`). glass-ui calls NONE of these — it only uses `.play()`, `.stop()`, `.target=`, `.value`, `.velocity`, `.dispose()`, `.snap()`, `.reset()`, `.subscribe()`, `.settled` (verified across `useLayerTransition.ts` + `useSpring.ts:106-172`), all of which survive 2.2.0→4.0.0 unchanged (cross-checked `spring.ts:218-478` 4.0.0 vs the installed 2.2.0 `dist/keyframes.d.ts`). `springLinearStops` is a black-box helper, signature-stable. So glass-ui can WIDEN the pin to `^2.2.0 || ^3.0.0 || ^4.0.0` with no source change.

8. `proof:package` (`scripts/proof-package.mjs:95-110`) is a peer-MATRIX witness, but its matrix is hardcoded `["2.2.0", "3.0.0"]` (`:101`) — it proves the range ACCEPTS 2.2.0 and 3.0.0, it does NOT prove the range tracks npm latest. So the pin-vs-latest drift (Finding 6) ships green today: the gate cannot see that 4.0.0 exists and is excluded. This is a stale-matrix class defect, not a false pass on what it checks.
