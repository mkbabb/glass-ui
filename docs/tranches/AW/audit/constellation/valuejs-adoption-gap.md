## Findings

1. **The AW.W5 aurora derive-color front door is a near-perfect fit, and the demo already has an EXPLICIT deferred-work marker waiting for it.** `demo/color-picker/App.vue:209-214` mounts the aurora on a static config: `const auroraConfig = reactive<AuroraConfig>(structuredClone(DEFAULT_AURORA_CONFIG)); useAurora(atmosphereCanvas, () => auroraConfig, {...})`. The comment at `App.vue:210-211` reads: *"W0 landed a static AuroraConfig; a glass-ui-derived picker-tracking palette is the conditional A.W6 work (re-scoped — docs/tranches/A/audit/W6-deferred.md)."* The picker already holds a live brand color (`cssColorOpaque`, provided as `CSS_COLOR_KEY` at `App.vue:140`). W5's "hand it ONE brand color → derive the gamut-mapped `OklchStop[]` palette" is exactly the missing seam: `useAurora` consumes `AuroraConfig.palette: OklchStop[]` (verified `node_modules/@mkbabb/glass-ui/dist/components/custom/aurora/constants/presets.d.ts` — `AuroraConfig.palette: OklchStop[]`, no derive entry today), and the demo wants the atmosphere to track the active picker color. A W5 `deriveAuroraConfig(brandColor)` front door lets `App.vue` replace the static clone with `() => deriveAuroraConfig(cssColorOpaque.value)`. NOTE: value.js IS glass-ui's upstream color peer (`@mkbabb/value.js`), so any in-shader OKLCh / gamut-map derive logic glass-ui ships in W5 must NOT duplicate logic value.js already owns (`src/units/color/gamut.ts gamutMapSRGB`, used by `useColorGeneration.ts:31`); the union-coordination contract has value.js owning color/parsing.

2. **`AuroraPane.vue` is a SHIPPED, live "under rework" STUB — a standing adoption debt the AW aurora waves resolve.** `AuroraPane.vue:1-9` documents it bound the *retired* `useAuroraBlobs`/`AuroraBlobsConfig` schema; rather than rebind the live 30-field `AuroraConfig`, it renders an honest empty-state message ("Atmosphere controls are temporarily unavailable while the tuning panel is rebuilt"). So W4-8 not only adds aurora capability, it directly unblocks a demo pane that is currently a stub.

(Today it resolves `file:../glass-ui` symlink so it tracks HEAD, but a registry bump would regress.)

4. **The local `goo-blob` is a self-contained fork that is RICHER than glass-ui's shipped `/goo-blob` — adoption is NOT a simple swap.** `demo/@/components/custom/goo-blob/` is fully local (no `@mkbabb/glass-ui` import inside the dir; verified by grep — zero hits). It ships a mood state machine (`BlobMood = idle|happy|curious|sleepy|excited`, `types.ts:3`), a satellite phase system (`SatellitePhase`, merge/emerge timings), and pointer attraction. `HeroBlob.vue` drives it as a color-showcase surface: `<GooBlob :color="cssColorOpaque" @click="onBlobClick">` with `gooBlobRef.value?.setMood("happy")`/`nudge()` (`HeroBlob.vue` lines 5-9, mood timers). `demo/CLAUDE.md:78` flags it: *"consumes glass-ui pending — extirpation routes to a successor tranche post-glass-ui-ship."* The AW.W9-11 blob-perfection waves (lit droplet material, soft-body pointer, mood/iridescence) are the natural convergence target — but glass-ui's `/goo-blob` would need to reach feature parity (mood machine + satellites + `:color` showcase binding) before the demo can extirpate its fork. This is a >=2-consumer convergence story (speedtest is the other goo-blob heritage consumer), legitimately load-bearing, NOT speculative.

5. **`ConfigSliderPane.vue` is a hand-rolled configurator shell that only partially adopts glass-ui's `/configurator`.** `ConfigSliderPane.vue:21` imports `ConfiguratorRow` and uses it per labeled slider row, but the section-group wrapper, the empty-state, and the floating copy/reset `GlassDock` (`ConfigSliderPane.vue:147-159`) are demo-local.
