That is the whole wave: the reactive aurora is a **composition of the shipped reactive config**, presets-in-consumers.

## The mechanism

The reactive aurora is a **CONSUMER-side DockStage seam** — the album palette enters via a consumer prop/CSS var, NEVER a library token. No library shader edit, no new aurora medium, no `--motion-accent`-style library hue: the field reads the playing palette the consumer hands it.

1. **The library seam is ALREADY shipped — `<Aurora :config>` is reactive.** `Aurora.vue` (read it — `useAurora(canvasRef, () => props.config, mergedRuntimeOptions.value, …)`) re-derives the nuclei field + palette LUT whenever `config` changes (the `getter`-wrapped reactive source). `AuroraConfig.palette` is `OklchStop[]` (2..MAX_STOPS) — a first-class public field on `/api`. A consumer that swaps `config.palette` for a new stop set re-paints the field smoothly on the existing rAF loop. **This wave writes NO `src/` aurora code** — the reactive substrate exists; the wave proves + demonstrates the consumer wiring and locks the fence that keeps the album hue OUT of the library.

2. **The V2 reactive-aurora signature — `reactiveAuroraConfig(base, paletteSource)` (a thin DEMO-side composable, `demo/stories/dock/useReactiveAurora.ts`).** A pure derivation helper the demo Now-Playing surface composes: it takes a `base: AuroraConfig` (the library default field — its nuclei/warp/medium identity) and a `paletteSource: MaybeRefOrGetter<OklchStop[]>` (the consumer's live album palette, e.g. extracted by the consumer's own art-sampler) and returns a `ComputedRef<AuroraConfig>` that splices ONLY the `palette` stops onto the base — `{ ...base, palette: toValue(paletteSource) }`. The field's STRUCTURE (nuclei positions, drift, warp, the satin/prism medium) is the library identity; only the HUE STOPS come from the consumer. This is the V2 signature: a base-config + a reactive palette source, palette-only, no nuclei/medium injection. It lives in `demo/` (presets-in-consumers — it is the reference adoption, never a library export).

3. **The DockStage seam — `<DockStage :palette-source>` (an additive demo-private prop).** `DockStage.vue` gains an OPTIONAL `paletteSource?: MaybeRefOrGetter<OklchStop[] | null>` prop (demo-private — `DockStage` is already a `demo/stories/` chassis, off the library barrel). When present, the staged `<Aurora :config>` reads `reactiveAuroraConfig(DEFAULT_AURORA_CONFIG, paletteSource)` instead of the frozen default; when absent (every existing caller), it falls to `DEFAULT_AURORA_CONFIG` byte-identical (the no-op floor — every current DockStage story renders unchanged). The album palette enters HERE, in the demo, through the consumer-shaped prop — never a library token, never a `:root` CSS var the library reads.

4. **The CSS-var alternative (the second consumer-entry form, documented).** A consumer that drives the field from CSS (not a JS palette array) sets `--album-stop-0`/`--album-stop-1`/… on a DockStage ancestor; the demo composable reads them via `getComputedStyle` and maps to `OklchStop[]`. This is the CSS-var entry the SEED §1 names ("the album palette enters via a consumer prop/CSS var"). Both forms terminate in `config.palette` — ONE reactive seam, two consumer-entry shapes, neither a library token.

5. **Compositor + substrate discipline (free-ridden).** The field is the shipped `<Aurora>` — offscreen-paused by construction, PRM one-static-frame, consumer-owned DPR, the `useIntersectionPause` + `content-visibility` seam. A palette swap re-derives the LUT (a uniform/texture update on the existing loop), never a layout property — `proof:no-layout-animation` holds by construction (the wave adds no animated CSS; the field paints on the GL canvas).

## Fences

- **No-legacy / clean break.** No `--motion-accent`-style library hue, no dual default/reactive config path: `DockStage` resolves the reactive config WHEN `paletteSource` is present, the byte-identical default otherwise (one branch, no alias). NO new medium, NO `uMedium` edit (the satin/prism mediums are W-AUR-SATIN/PRISM's; this is palette-reactivity, not a new finish).
- **Presets-in-consumers (the load-bearing fence).** The album palette / now-playing hue lives ENTIRELY in the consumer — the demo composable + the demo prop are the reference adoption, never a library token, never a `:root` var the library reads. The library's own default field is `DEFAULT_AURORA_CONFIG` (its identity). A consumer's art-sampler (the palette EXTRACTOR) is the consumer's own code; the library/demo seam only CONSUMES the `OklchStop[]` it produces.
- **The GL color-seam fence (D26) held from the field side.** The album hue tints the FIELD (a public reactive config the consumer owns), never a per-piece GL SHADE inside the shader (the deferred D26 primitive). This wave does NOT touch `aurora.frag`/`aurora.wgsl`/the color path — it swaps the public `config.palette`. The two are disjoint: D26 is a per-piece shader shade (deferred); this is a config-palette swap (shipped substrate).
- **The specific anti-pattern this must NOT become:** an `--album-hue` / `--now-playing-color` token minted in `src/styles` that the library reads (the album hue entering the library identity — the presets-in-consumers violation the gate's C2 anti-evasion scan kills), OR a `useReactiveAurora` LIBRARY export that re-derives the field outside `<Aurora>` (a second aurora substrate — the re-fork class), OR a non-palette config injection (nuclei/medium from the album source — the structure-is-consumer's drift the C4 fence kills).
