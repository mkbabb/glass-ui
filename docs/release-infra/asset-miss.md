# asset-miss: a chunk that is not there answers 404, uncached

Branch `infra/deploy-asset-miss`. Not merged, not deployed. The deploy itself is
`deploy-demo.md`.

## The fault

Run 44033814964 of `deploy-demo` (2026-11-17, 06:48 to 06:54 UTC, two attempts)
built and shipped 422 hashed files. Attempt 1 waited three tries for the new
index. After that, its last nine tries of `scripts/check-served.mjs` and all 12
of attempt 2's failed on the same three files:

```
try 1/12: the index matches; 3 of 422 assets not served as built (checks-B6psvwuG.js (200 text/html; charset=utf-8), chip-Ccgx14rN.js (200 text/html; charset=utf-8), nav-Baf9xD9D.js (200 text/html; charset=utf-8));
...
try 12/12: the index matches; 3 of 422 assets not served as built (checks-B6psvwuG.js ..., chip-Ccgx14rN.js ..., nav-Baf9xD9D.js ...)
```

From another network the same URLs answered `200 application/javascript`.

A miss under `/assets/` today is the SPA index with a 200, and the `/assets/*`
rule in `demo/_headers` reaches it by path:

```
$ curl -sI https://glass.babb.dev/assets/nonexistent-XXXX.js
HTTP/2 200
content-type: text/html; charset=utf-8
cache-control: public, max-age=31536000, immutable, no-transform
```

Cloudflare's edge keeps that answer. The same junk URL, asked for twice
(2026-11-17, from this Mac):

```
200 text/html; charset=utf-8   public, max-age=31536000, immutable, no-transform   cf-cache-status: MISS
200 text/html; charset=utf-8   public, max-age=31536000, immutable, no-transform   cf-cache-status: HIT
```

Cloudflare "only caches based on file extension and not by MIME type", and
caches when "`Cache-Control` is set to `public` and `max-age` is greater than 0"
([default cache behavior][cache]). A `.js` URL answered with HTML in the
propagation window is cached as that HTML for a year at that edge, and so is
any browser's copy. The routes that load the chunk (`/forms/checks`,
`/forms/chip`, `/dock/nav`) break for every visitor behind that edge. All three
file names are still in the current build, because their content did not
change.

## What the docs say

- **SPA fallback and 404s** ([Serving Pages][serving]). "If your project does
  not include a top-level `404.html` file, Pages assumes that you are deploying
  a single-page application" and "serves the root (`/`) for any incoming path
  that does not correspond to a static asset". Otherwise "Pages will then
  attempt to find the closest 404 page. If one is not found in the same
  directory as the route you are currently requesting, it will continue to look
  up the directory tree".
- **`_headers`** ([Headers][headers]). Rules match by URL pattern only. "An
  incoming request which matches multiple rules' URL patterns will inherit all
  rules' headers", applied in file order. There is no match on status. Headers
  "are not applied to responses generated by Pages Functions".
- **`_redirects`** ([Redirects][redirects]). "Redirects are always followed,
  regardless of whether or not an asset matches the incoming request", so no
  rule can pick out a miss. A 404 status is unsupported: `/blog/* /blog/404.html
  404` is the docs' example of an unsupported rewrite.
- **Functions** ([routing][routing], [pricing][pricing], [advanced mode][advanced]).
  `_routes.json` in the build directory limits which paths invoke a Function.
  "Requests to your Functions are billed as Cloudflare Workers requests". On the
  Free plan they share the daily quota, and "Fail open" means "static assets
  will continue to be served" once it runs out. "Requests to static assets are
  free and unlimited". The advanced-mode page does not say whether
  `env.ASSETS.fetch()` applies `_headers`.

The docs give a 404 for misses under `/assets/` with static config: a nested
`assets/404.html` is the closest 404 page for those paths, and there is still no
top-level one, so every other path keeps the SPA fallback. They do not say what
Cache-Control a 404 carries. Read alone, the `/assets/*` rule would reach it by
path.

The asset handler does say. `packages/pages-shared/asset-server/handler.ts` in
cloudflare/workers-sdk is "used internally to power Wrangler and Cloudflare
Pages" (the package README). After it applies `_headers`, it runs this:

```ts
if (responseWithHeaders.status === 404) {
    // Remove any user-controlled cache-control headers
    // This is to prevent the footgun of potentionally caching this 404 for a long time
    if (responseWithHeaders.headers.has("cache-control")) {
        responseWithHeaders.headers.delete("cache-control");
    }
    // Add cache-control: no-store to prevent this from being cached on the responding zones.
    responseWithHeaders.headers.append("cache-control", "no-store");
}
```

That landed in workers-sdk #5875, "Don't cache 404s from the asset-server"
(2024-05-21). The same file's `notFound()` walks from the request's directory up
to `/404.html`, and serves `/index.html` with a 200 only when it finds none.
That matches the docs' wording.

## The mechanism

`demo/vite.demo-dist.config.ts` gets one more plugin, `pagesAssetMiss()`, which
emits `dist-demo/assets/404.html`:

```html
<!doctype html>
<meta charset="utf-8">
<title>Not found</title>
<p>No such file.</p>
```

- A request under `/assets/` that matches no file answers that page with a 404.
  The handler swaps the `/assets/*` `immutable` for `no-store`, and no cache
  keeps `no-store` ([default cache behavior][cache]: not cached when
  "`Cache-Control` is set to `private`, `no-store`, `no-cache`, or `max-age=0`").
  The other `_headers` (the CSP, `nosniff`, `Referrer-Policy`) still apply.
- Every real hashed file is served as before, with `public, max-age=31536000,
  immutable, no-transform`.
- Every other path has no closer `404.html` and no top-level one, so it gets the
  SPA index with a 200, as today.
- `demo/_headers` is unchanged, so `dist-demo/_headers` is too, CSP included.
  There is no `_redirects`, `_routes.json` or `_worker.js`.

The page is HTML because Pages serves its own type for it. A module import fails
on the 404 before it looks at the type.

`deploy-demo.yml` fails the build step if `dist-demo/assets/404.html` is not
written, as it does for `_headers`. A rollback to a tag from before this change
fails red there.

### Why not a Function

A Function was the fallback if static config could not do it: `_worker.js` plus
`_routes.json` with `"include": ["/assets/*"]`, turning a `text/html` answer from
`env.ASSETS.fetch()` into a 404 with `no-store`. It is not needed, and it costs
more:

- Every asset request becomes a billed Functions request. The index alone loads
  59 files, so the Free plan's 100,000 a day, shared with the account's Workers,
  covers well under 2,000 visits.
- Past the quota, "Fail open" serves static assets, which brings back today's
  fault. "Fail closed" returns an error page for every asset.
- Every asset gains a Worker hop.
- Whether `env.ASSETS.fetch()` responses keep `_headers` is undocumented, so the
  hits' `immutable` and CSP would depend on that too.

If a real deploy shows a 404 that keeps `immutable` (the check below names it),
this is the design to build.

## check-served

`scripts/check-served.mjs` now names each asset that is not served as built by
its mode:

- `html-for-js`: a script answered 200 `text/html`. That is the SPA index, and
  an edge may be holding it. The line carries `cf-cache-status` and `age`.
  `html-for-css` and `html-for-woff2` are the same for other types.
- `HTTP 404` (or another status).
- `size got/built`.

If `html-for-js` is still there on the last try, the run ends with its own
`::error title=html-for-js::` line naming the URLs to purge. The run also asks for
a deep link (`/served-check/<ts>`), which must answer the built index with a
200. Under `--headers`, which only Pages satisfies, a hashed `.js` must carry
`immutable`, and `/assets/served-check-miss-<ts>.js` must answer 404 with
`no-store` and no `immutable`. `assets/404.html` is left out of the asset
census. It is the miss page, not a hashed file, and Pages answers it at
`/assets/404`.

**The retry budget stays at 12 tries, 10 s apart.** The fault's 21 tries over
six minutes saw the same three files every time, while another network got the
JavaScript. That was one edge's cache, not slow propagation, so a longer budget
would not have passed. The index itself propagated within three tries. With the fix, a chunk
that has not reached an edge answers 404 `no-store`, which nothing caches, so
each try sees the deployment as it is. Nothing measured says Pages needs more
than two minutes to propagate. A cached `html-for-js` clears in no budget, and
the named failure says what to do instead.

## Only a real deploy shows

- That production Pages runs the 404 `no-store` swap, which developers.cloudflare.com
  does not document. The next deploy's `check-served --headers` asserts it, and
  goes red with `a miss under /assets/ is cacheable (…)` if not.
- That the edge really skips a 404 `no-store` for a `.js` URL (a MISS that stays
  a MISS). This depends on babb.dev having no Cache Rule that overrides origin
  Cache-Control, which can't be read from here.
- The first deploy that carries this. Its old deployment has no
  `assets/404.html`, so an edge still on it can hand out a new chunk as cached
  HTML one last time. If that deploy's check names `html-for-js`, purge those
  URLs and re-run. Deploys after it inherit the fix on both sides.
- The edge that answered the runner on 2026-11-17 may still hold HTML for
  `checks-B6psvwuG.js`, `chip-Ccgx14rN.js` and `nav-Baf9xD9D.js`, all three still
  in the build. A deploy does not clear the zone cache. If the next check names
  them, purge those three URLs (dashboard: babb.dev, Caching, Purge Cache, Custom
  Purge), or purge them now.
- That deep links still answer the index on Pages for real routes. The emulation
  shows all 79, and the check's deep-link probe asserts one per run.
